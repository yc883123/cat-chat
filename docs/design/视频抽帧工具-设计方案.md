## 1. 背景与目标

### 1.1 需求

当前 Naiba Chat 能"看图片"（`vision_analyze`），但**看不到视频内容**。用户上传一个 mp4，
模型既读不出它的时长/帧率，也拿不到任何画面——视频对模型而言是个黑盒文件。

### 1.2 目标

让模型具备「**看清视频里发生了什么**」的能力，且能力形态与现有 PDF 体验完全一致：

- 产物是**图片**，自动落托管缓存、自动挂进消息媒体区（可点开灯箱）；
- 产出的帧图能被 `vision_analyze` 直接读，无需用户手动指定；
- 全过程**不污染会话工作区**，重复调用直接复用。

### 1.3 非目标（v1 明确不做）

- 视频**转码 / 剪辑 / 压缩**（那是 `pwsh` + ffmpeg 的事）；
- 视频**音频**理解（转录、语音识别）——独立课题，且涉及额外模型；
- 视频**内容检索 / 语义索引**（按内容找片段）。

## 3. 结论：做内置工具，且照抄 PDF 三件套的形态

### 3.1 为什么必须是内置工具，不能是 Skill

| 能力 | 内置工具 | Skill（`run_skill_script`） |
|---|---|---|
| 走 `MEDIA_DECLARATIONS` 自动采集产物 | ✅ | ❌ |
| 产物自动挂回消息媒体区 | ✅ | ❌ |
| 帧图能被 `vision_analyze` 直接读 | ✅ | 需手工传路径 |
| 受 `/api/imaging/clean` 与缓存统计覆盖 | ✅ | ❌ |
| 参与上下文圆环计数 | ✅ | ❌ |
| 权限档位（只读/确认）可配 | ✅ | 恒为高风险组 |

抽帧产物天然是图片，必须享受与 `pdf_render_pages` 完全相同的待遇 → **只能是内置工具**。

### 3.2 形态：与 PDF 逐条对应

| PDF（已有） | 视频（本方案） | 职责 |
|---|---|---|
| `read_pdf` | **`probe_video`** | 读元信息：时长/帧率/分辨率/编码/有无音轨 |
| `pdf_render_pages` | **`extract_frames`** | 抽帧 → PNG（含联系表） |
| `pdf_zoom_region` | ~~`zoom_frame`~~ → **v1 不做，见 §3.3** | 局部放大 |

### 3.3 关于第三件：为什么 v1 不做 `zoom_frame`（重要设计取舍）

初看应与 PDF 对称地配三件。但细读现有能力后，结论是**第三件对视频的边际价值很低**，理由有两条：

1. **局部裁剪能力已存在**：`vision_image_ops` 已提供 crop 族操作，对"已经抽出来的帧图"做裁剪，
   功能上与 `pdf_zoom_region` 重叠。
2. **PDF 与视频的信息论差异**：`pdf_zoom_region` 之所以真高清，是因为它**从矢量页重新按高倍渲染**，
   是"重新取样"；而视频帧一旦以长边 1600 落盘，再裁剪**不可能恢复更多细节**——只会得到一张更小的图。

**唯一有真实价值的场景**：源视频分辨率远超 1600（如 4K 源被降采样落盘后想看小字界面）。
此时的正确做法不是"裁剪"，而是**按时间点以原生分辨率重新抽该帧**。

因此 v1 建议：
- **新增两件**：`probe_video` + `extract_frames`；
- 局部细看的路径 = `extract_frames` 抽帧 → `vision_image_ops` 裁剪（复用，不新增工具）；
- **v2 可选**：给 `extract_frames` 加 `native=true` 参数（按时间点以原生分辨率抽单帧，绕过 1600 降采样），
  这才是视频语境下真正需要的能力。是否提前进首发，取决于**实际素材里 4K 源的占比**（见 §12 第 4 条）。

## 4. 详细设计

### 4.1 工具 1：`probe_video`（只读）

**职责**：让模型先知道"这个视频有多长、多少帧"，才能决定抽哪些秒。描述只答职责，编排规则进系统提示常驻区。

```python
ToolSpec(
    name="probe_video",
    description=(
        "读取视频文件的元信息：时长、帧率、分辨率、总帧数、视频编码、是否含音轨。"
        "用于在抽帧前了解视频基本信息，决定抽帧的时间点或间隔。"
    ),
    parameters={
        "type": "object",
        "properties": {"path": _string("视频文件绝对路径")},
        "required": ["path"],
    },
    side_effect=False,
    retryable=True,
    timeout=60,
    permission="confirm",   # 与 read_pdf 同构：读外部路径需确认
)
```

**返回**（JSON 字符串）：

```json
{
  "duration": 134.78, "fps": 24.0, "width": 2560, "height": 1472,
  "frame_count": 3234, "frame_count_estimated": true,
  "video_codec": "h264", "has_audio": true, "audio_codec": "aac"
}
```

**实现要点**：`PyAV` 打开容器 → `stream.duration * stream.time_base` 求时长；`stream.average_rate` 求帧率；
`stream.codec_context.name` 求编码；音频流存在性判 `has_audio`。
**不要**用"总帧数"字段（很多容器没有 `nb_frames`）——用 `duration × fps` 估算，并在返回值里**如实标注** `frame_count_estimated`（静默给估算值 = 误导源，维护说明 §九.24 同口径）。

### 4.2 工具 2：`extract_frames`（核心）

```python
ToolSpec(
    name="extract_frames",
    description=(
        "从视频里抽取画面帧并保存为 PNG 图片。支持三种抽取模式："
        "按指定时间点（times）、按固定间隔（interval）、按画面切换自动挑关键帧（keyframes）。"
        "可同时生成一张联系表（contact_sheet，把多帧拼成网格图，适合先概览全片）。"
        "单次最多 8 帧。返回帧图路径列表，重复调用直接复用。"
    ),
    parameters={
        "type": "object",
        "properties": {
            "path": _string("视频文件绝对路径"),
            "mode": _string("抽取模式：times / interval / keyframes", "interval"),
            "times": _string('时间点列表（mode=times 时使用），如 "3,15,42.5"（秒）', ""),
            "interval": {"type": "number", "description": "每隔多少秒抽一帧（mode=interval 时使用）", "default": 2},
            "threshold": {"type": "number", "description": "画面切换灵敏度 0-1（mode=keyframes，越小越敏感；建议 0.2-0.5，默认 0.3）", "default": 0.3},
            "start": {"type": "number", "description": "起始时间（秒），缺省从头"},
            "end": {"type": "number", "description": "结束时间（秒），缺省到结尾"},
            "max": {"type": "integer", "description": "最多抽几帧（上限 12，默认 8，超过按间隔均匀裁剪）", "default": 8},
            "max_edge": {"type": "integer", "description": "单帧长边像素上限", "default": 1600},
            "contact_sheet": {"type": "boolean", "description": "是否额外生成一张拼图联系表", "default": True},
        },
        "required": ["path"],
    },
    side_effect=True,
    retryable=True,
    timeout=180,
    permission="auto",   # 与 pdf_render_pages 同构：只写宿主管控缓存
)
```

> **`max` 默认 8 的理由**：一次返回 8 帧 + 1 张联系表 = 9 个媒体源，与 `MEDIA_BUCKET_LIMITS.video = 8`
> 同口径；硬上限仍留 12（模型显式要求时才给），避免逼近 `image` 桶 20 的上限而在消息里被截断。

**返回**：

```json
{
  "duration": 134.78, "mode": "interval", "count": 8, "truncated": false,
  "frames": [
    {"t": 0.0,  "path": "%LOCALAPPDATA%\\NaibaChat\\uploads\\video_frames\\<sha16>\\frame_000_t0.0.png", "width": 1280, "height": 736},
    {"t": 12.0, "path": "…/frame_001_t12.0.png", "width": 1280, "height": 736}
  ],
  "sheet": "…/sheet_4x3.png",
  "next_step": "把帧图路径（或联系表）交给 vision_analyze 识别内容；联系表用于先概览全片，可疑片段再抽单帧细看。"
}
```

**三种模式的实现**：

| 模式 | 用途 | 实现 |
|---|---|---|
| `times` | 模型已知"第 35 秒那个界面" | 逐点 `container.seek(int(t / time_base), stream=video_stream)` |
| `interval` | 快速扫全片（默认） | 从 `start` 到 `end` 步进 `interval` 秒，逐个 seek |
| `keyframes` | **真正意义上的"抽关键帧"** | 顺序解码，逐帧与上一保留帧降采样比对，差异超 `threshold` 即保留 |

`keyframes` 的实现建议（不依赖 ffmpeg 滤镜）：
1. 按 `VIDEO_KEYFRAME_PROBE_FPS` 抽成候选 → 缩到 64×64 灰度；
2. 与上一保留帧算**平均绝对差**（归一化到 0-1）；
3. 超过 `threshold` 则保留该时间点（受 `VIDEO_KEYFRAME_MIN_GAP` 约束防连发）；
4. 结果超过 `max` 时，退化为按差异值**从大到小取前 N 个**并按时间排序。

> 这样做的意义：对"界面切换 / 翻页 / 切镜"这类真正的"关键信息节点"，比按秒均匀抽准得多——
> 短片里按秒均匀抽可能全落在静态画面，而 keyframes 能精确落在切点。
>
> ⚠️ `threshold` 用的是**平均绝对差**，与 ffmpeg 的 `scene score` **不是一个量纲**：
> 模型若按 ffmpeg 经验传值会过敏感。描述里必须写清"建议 0.2-0.5"，并在 §8 用夹具标定默认值。

**联系表（contact sheet）——省 token 的关键**：

用 **PIL 自己拼**（PIL 已在依赖里，不必引入 ffmpeg 滤镜）：

- 每帧缩到约 320px 宽 → 按 `cols = ceil(sqrt(n))` 或固定 4 列排布 → 每帧下方标注 `t=12.0s` 小字；
- 整张图长边 ≤ 1600；
- 返回它作为 `sheet` 路径。

**为什么这是关键**：一次 `vision_analyze` 看 1 张联系表 ≈ 看 8 张单帧的信息量，但只占 1 张图的 token。
对照现有约束（视觉单批 4 张、消息级图分桶上限 20），联系表能把"概览全片"压缩到 1 次视觉调用。

### 4.4 缓存与幂等（与 PDF 的关键差异）

| | PDF | 视频（本方案） |
|---|---|---|
| 缓存位置 | `uploads/pdf_pages/<sha16>/` | `uploads/video_frames/<sha16>/<params_key>/` |
| 键的算法 | **sha256(文件内容)** | **sha256(绝对路径 + size + mtime_ns)** + **sha256(抽取参数)** |

**为什么不同**：PDF 几十 MB，全文哈希可接受；视频动辄几 GB，**读全文算哈希会让每次调用多花几十秒**。
用 `路径 + 大小 + 修改时间` 做键，既避免全量读取，又能在文件真正被替换时失效（mtime/size 变化）。
文件名冲突（同路径同大小同 mtime 但内容不同）概率可忽略，且最坏后果只是"复用了旧帧"，不产生错误行为。

**落盘命名**：`frame_<序号>_t<时间>.png`（时间保留 1 位小数，便于人工核对与模型引用）。
**幂等**：同键目录已存在且帧数一致 → 直接返回既有路径，不重新解码。

**两级上限（口径必须写死，见评审 B4）**：

```
uploads/video_frames/<video_sha16>/          ← 一个视频一个根
    ├── <params_key_1>/                      ← 一组抽取参数一个目录，上限 VIDEO_CACHE_MAX_IMAGES=200
    ├── <params_key_2>/
    └── …
```

- **目录级** `VIDEO_CACHE_MAX_IMAGES = 200`：抄 `PDF_CACHE_MAX_IMAGES` 的口型，在**单目录内**判（渲染前 `len(existing) + n > 200` 即报错），与 `pdf.py:205` 同构；
- **视频级** `VIDEO_CACHE_MAX_PER_VIDEO = 600`：因为**参数一变就是新目录**，只按目录计数拦不住总膨胀
  （同一视频用不同 `times` 试十次就是十个目录）。超限时报明确错误，引导"指定 `start`/`end` 区间或先清缓存"。

> 这是本方案**第二容易抄错的地方**（第一是缓存键）。只写 `MAX_IMAGES=200` 一个常量会让它变成没人用的死常量。

**清理归属**：`storage/media.py::_image_cache_dirs` 已覆盖整棵 `uploads` 树，
故 `uploads/video_frames` **无需登记**即被 `/api/imaging/stats` 与 `/api/imaging/clean` 统计与回收（按字节阈值）。
两级上限是**字节清理之外的业务护栏**，二者不冲突。

### 4.5 媒体声明（`MEDIA_DECLARATIONS`）

```python
"probe_video":    {"policy": "never",      "extract": "none"},        # 只出文本元信息
"extract_frames": {"policy": "inline",     "extract": "structured"},  # 结构化帧记录 + 联系表
```

与 PDF 三件套逐条对齐（`read_pdf`=never/none；`pdf_render_pages`=inline/structured）。

> 采集器 `_visit` 会递归扫描结果，从 `frames[].path` 与 `sheet` 里取到全部图片源（`_SOURCE_KEYS` 含 `path`）。
> 默认 8 帧 + 1 联系表 = 9 个源，落在 `image` 桶 20 以内，不会触发截断提示。

### 4.6 权限策略

| 工具 | 策略 | 理由 |
|---|---|---|
| `probe_video` | `_make_read_policy`（工作区/Skill 根内免确认，越界必确认） | 与 `read_file` / `read_pdf` 同构 |
| `extract_frames` | `_no_confirm_policy`（恒返回 `""`） | 只写宿主管控缓存目录，`path_within` 已校验；与 `pdf_render_pages` 同构 |

### 4.7 系统提示编排（两个注入点）

与 PDF 的两处**同口径、同位置**，条件为「会话工具集含 `extract_frames`」：

**(1) 系统提示常驻段**（`naiba/run/chat.py`，PDF 策略段旁）：

> 视频理解策略：先用 `probe_video` 读时长与帧率；再按目标用 `extract_frames` 抽帧
> （指定时间点用 `mode=times`，全面扫一遍用 `mode=interval`，找画面切换点用 `mode=keyframes`）；
> 先把返回的**联系表**交给 `vision_analyze` 概览全片，再对可疑片段抽单帧细看。
> 帧图的局部细节可用 `vision_image_ops` 裁剪放大。

**(2) 附件引用行**（`naiba/core/attachments.py`）：

`upload_reference_lines(uploads, *, pdf_tools=True)` 增加 `video_tools: bool = True` 参数，
对视频扩展名（取自 `core/media_types.py`，不硬编码）追加同类指引。`compose_user_content` 同步透传。
`_run_chat` 与历史重放**必须传同一个值**，否则破坏"逐字节一致"契约与前缀缓存。

> 注意：`upload_reference_lines` 现在用 `path.lower().endswith(".pdf")` 判断类型。
> 视频分支应改为**读 `core/media_types.py` 的类型判定函数**（`media_kind_of`），避免扩展名名单二次维护。

## 5. 解码后端选型

| 方案 | 体积 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| **PyAV**（`pip install av`） | wheel ≈35MB | 内嵌 FFmpeg（LGPL）；精确 seek；元信息完整；H.264/265/AV1/VP9 全覆盖；纯 pip 安装 | 打包需收 dll | **推荐** |
| OpenCV headless | ≈45MB | API 最简（`cap.set(CAP_PROP_POS_MSEC)`） | seek 精度差、编码支持窄（AV1/H.265 常缺） | 备选 |
| 外部 `ffmpeg.exe` | ≈80MB | 滤镜能力最强（`select='gt(scene,0.3)'` 一行做场景检测） | 冻结版须打包 exe 并处理路径探测；用户机器环境不可控 | 不推荐 |

**选定 PyAV**，理由：① 与项目"用 pip 依赖、随 PyInstaller 打包"的既有做法一致（PyMuPDF 同理）；
② `keyframes` 模式需要的"逐帧顺序解码 + 降采样比对"，PyAV 原生支持，无需外部进程；
③ 不引入"用户机器上 ffmpeg 在哪"这类环境不确定性问题。

**联系表用 PIL 拼**——PIL 已在依赖里，无需为拼图引入任何新库。

### 5.4 解码依赖的导入纪律（评审 B2）

维护说明 §九已记过一次同构事故：`naiba/pdf.py` 顶层 `import pymupdf`，
**依赖一缺就不是 video 测试红，而是 `test_pdf_tools` 整组 error**（导入期即炸，测试收集阶段全崩）。
新建的 `naiba/video.py` 如果顶层 `import av`，会原样重演——而 `av` 是本项目第一个"打包后才需要、
CI 少装一行就全炸"的重依赖。

**要求**：

1. `naiba/video.py` **顶层不 import `av`**，改为在函数内惰性导入；
2. 导入失败时抛**明确的业务错误**（不是裸 `ImportError`）：
   `"视频解码依赖未安装（av）；冻结版请重装最新版，源码模式执行 .venv\\Scripts\\python.exe -m pip install av"`
   ——与 `read_file` 对二进制文件"明确报错 + 给工具引导"同一口径；
3. `tests/test_video.py` 里**必须有一条缺依赖降级用例**（monkeypatch 掉 `av` → 断言拿到上述文案而不是 `ImportError`）。

## 10. 风险与边界

| 风险 | 说明 | 对策 |
|---|---|---|
| **CI 依赖漏装** | 冻结版抽帧报 `ImportError` / `DLL load failed`，且**测试不红** | §6.1 改 workflow 名单；§6.3 冻结版实跑 |

## 11. 验收标准

1. 上传一个 mp4，模型能**自行**（无需用户提示工具名）说出视频时长、分辨率、大致内容；
2. 提问"第 X 秒画面里写了什么"，模型能抽该帧并读出画面文字；
3. 提问"这个视频整体讲了什么"，模型能**先用联系表概览、再对关键片段抽单帧**；
4. 帧图自动出现在消息媒体区，可点开灯箱、可左右切换；
5. 重复调用同一视频同一参数，**不重新解码**（日志可见缓存命中）；
6. 冻结版（打包后）实跑通过；
7. `项目维护说明` 与代码严格一致，无"已过时"表述；
8. **新增**：`.github/workflows/release.yml` 的一次真实流水线全绿（依赖 + 测试 + 编译）。
