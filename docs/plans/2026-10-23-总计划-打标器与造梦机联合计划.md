## 1. 目的与范围

本计划回答两项工作台计划能否一起实施、会触碰哪些相同边界，以及建议的实施顺序。两份单项计划提供需求和设计依据；本文件负责跨模块依赖与冲突，不把单项计划里的历史阶段重新列成待实施功能。

实施采用**分阶段串行**：先核实并完成打标器 LoRA 训练包剩余缺口，再实施造梦机。只有两边各自通过阶段验收，才进入下一阶段。当前只是文档规划，本文件不代表开工授权。

### 1.1 已有基线

- 打标器页面、批量任务、provider 调用、逐图状态、取消/重试/恢复、标注库、常规导出已经存在，不得重做。
- 当前工作区已有未提交改动，至少涉及 `naiba/http.py`、`naiba/labeler/export.py`、`naiba/labeler/service.py`、`public/index.html`、`public/js/23-labeler.js`、`public/styles.css`、`tests/test_labeler.py`。这些变更需按当前源码核对，不得覆盖或回滚。
- 当前 `captions` 导出代码生成的 ZIP 只含 `.txt`；新增的导出目录按钮用于打开受管目录。这不等于完整 LoRA 训练包，也不能据此认为配对图片和原图留存已经完成。
- 造梦机尚无工作台模块。聊天域已有 ComfyUI Job/工具链，单项计划规定新工作台域应保持独立，不能把聊天 Job 全盘迁移或重做。
- 用户确认：打标文件和图片使用相同短文件名主干；训练包保留上传原文件；内容相同但来源文件名或目录不同的图片仍保留为两组训练样本。

### 1.2 总体交付目标

1. 打标器可导出可直接用于 LoRA 训练的成对训练包：每张图片与一个同主干 `.txt` 一一配对，例如 `000001.png` 和 `000001.txt`；图片字节与用户上传原文件一致；manifest 可追溯原始名称、相对路径、短名和校验值。
2. 造梦机可导入用户已在 ComfyUI 跑通的 API 格式工作流，自动扫描参数，执行任务、取消/恢复并查看本地保存的产物。
3. 两模块共享工作台框架时，页面偏好、上传缓存保护、请求体限制、路由顺序和前端加载关系均有单一、可验证的契约。

| Studio 横向样式与状态 | 两个页面共用导航、窄屏区域和分页记忆 | 新模块 CSS/状态污染打标器或模块库 | 新样式使用独立前缀，移动端逐页检查；页切换和返回时状态不互相覆盖 |
| 交付版本 | 当前版本 3.6.5-beta | 把模块完成误当成已发布或擅自 bump 版本 | 本计划不安排版本升级；若之后决定发版，另按维护说明执行完整发布流程 |

## 3. 分阶段计划

### 阶段 0：冻结共同边界与源码基线

- 逐项读取当前工作区和两份计划，记录未提交文件的实际行为；不依赖计划中先前的行号或“已完成”文字替代现状核查。
- 确认共同工作台契约：有效 page key、偏好恢复、前端模块加载顺序、API 鉴权、请求体上限分流、应用启动/关闭生命周期、前端轮询暂停规则。
- 确认数据边界：Labeler 原图保留区、Labeler 标注/任务库、ComfyUI 工作流/任务/产物目录互不混放；ComfyUI 不消费或修改 Labeler 训练数据。
- 建立阶段开始时的 `git status` 清单，之后只修改本阶段明确列出的文件；已有未提交改动按原所有权保留。

**阶段门槛：** 共同契约与当前工作树清单可供评审；没有以“全部重做 Labeler”作为实施前提。

### 阶段 1：收口打标器训练包

本阶段仅实施打标器单项计划列明的训练包缺口和明确列出的浏览器验证，不重做已存在功能。

- 先确定原图留存方式和生命周期：输入源为用户上传的原始字节；训练包导出必须可校验原图 SHA-256，不能回退使用缩放/压缩后的缓存图。
- 按源样本身份建导出映射。短名在确定顺序后分配，图片与 caption 共用短名主干，并在 manifest 中保存源名称、源相对路径、导出短名和哈希。
- 内容相同但来源路径/名称不同的文件是两条样本，各自导出图片和 `.txt`；不能按内容哈希合并。重复任务记录引用、源样本身份映射歧义、缺少原图、配对不完整或包内目标冲突时整包失败，不生成半包。
- 明确上传去重、`validate_image_refs()` 路径校验与标注记录之间的身份映射；不得假定“ZIP 生成器里改名”足以保留多份来源样本。
- 核查已有 `captions` ZIP 和“打开导出文件夹”变更，复用可用 UI/目录能力，但将训练 ZIP 的 API、导出名和错误提示与常规 captions 汇总格式区分清楚。
- 补配对、原字节、哈希、同内容不同源、路径同名、缺失原图、拒绝原子性和 manifest 的守门测试；验证已有 Labeler 功能未回归。

**阶段验收：** 两个不同来源但内容相同的输入形成两组独立的短名图片/caption；每个图片与 `.txt` 主干一致；包内图片 SHA-256 等于各自上传原文件；manifest 可追溯；任何不完整输入均拒绝整包。按维护说明完成相关测试、编码检查及 Playwright 桌面/375px 手机视口。

### 阶段 2：造梦机 P0-P1（领域骨架与工作流库）

- 新增独立 `naiba/comfyui/` 服务；不改写现有聊天域 `jobs.py` ComfyUI worker。
- 加入造梦机页、`comfyui` page key、HTTP 端点和工作流存储；逐一落实 §2 的共同边界。
- 仅导入 API 格式工作流；UI 格式明确拒绝并显示导出步骤；常驻显示先在用户自己的 ComfyUI 完整跑通的提醒。
- 后端从工作流节点扫描可编辑参数并按原值类型保存/应用；不要求为每份工作流手写参数模板。
- 工作流 JSON 有体积上限、结构校验和受管存储；导入、详情、删除对历史任务引用的行为符合单项计划契约。

**阶段验收：** 工作流库增删查；API 工作流成功导入并显示槽位；UI 工作流被拒并显示完整指引；网络不可达时连接状态明确；Labeler/模块库页签和刷新偏好正常。

### 阶段 3：造梦机 P2-P3（执行、取消与产物）

- 工作台独立串行 runner、任务快照和事件游标；工作流参数覆盖、seed 限制、ComfyUI 队列/历史状态处理。
- 取消同时请求中断当前执行和移除排队任务；提交失败带服务端原因；任务删除保护正在执行任务。
- 完成后将 `/view` 返回的产物字节写入 Cat Chat 受管目录，任务只保存相对路径；本地服务产物，不依赖 ComfyUI 历史长期存在。
- P5 图片输入上传仍单独评审；若纳入，必须复用有边界的上传路径、做图片引用保护并定义与 ComfyUI `LoadImage.filename` 的绑定，不读取任意客户端磁盘路径。

**阶段验收：** 两段任务进度正确；执行中取消能影响 ComfyUI 当前段与队列；产物在 ComfyUI 清历史后仍可查看；任务/产物命名与工作流删除行为经测试。

### 阶段 4：造梦机 P4 与端到端验收

- 启动后恢复遗留任务为可解释状态；按 checkpoint 查询已完成段，已完成工作不重复提交；重试从未完成段继续。
- 失败诊断显示阶段、ComfyUI 拒绝原因和可确定的节点错误，不伪造状态。
- 用用户自己的 ComfyUI 中已跑通的 API 工作流，从导入、填参、提交直到查看本地结果做一次真实端到端验证；与不联网单元测试分开记录。
- 对实际触及的公共路由、状态、文件服务和停止流程运行相应回归测试；完成 Playwright 桌面与 375px 手机视口验证。

**阶段验收：** ComfyUI 重启或应用重启后任务与产物状态一致；已完成段不重复提交；真实工作流端到端通过；前端无 JS 错误、布局无重叠。
