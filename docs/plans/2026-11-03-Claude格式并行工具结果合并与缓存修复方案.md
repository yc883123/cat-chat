# Claude 格式并行工具结果合并与缓存修复方案

- 日期：2026-11-03。
- 性质：**方案文档，未实施**。本轮只做源码核查与本地只读复现，未改动任何生产代码、未提交、未推送、未发版。
- 触发：用户反馈在线模型「Zooywoo」（`api.zoowyoo.dpdns.org`）走 claude 格式（`/v1/messages`）返回

  ```text
  HTTP 400: messages.8: tool_use ids were found without tool_result blocks immediately after:
  call_3_1_26f51af6, call_3_2_af075f26. Each tool_use block must have a corresponding
  tool_result block in the next message.
  ```

- 关联问题：同一中转站「chat 格式调 Claude 缓存不命中，只有 claude 格式才命中」，见第 7 节。

## 0. 结论

**这是 Cat Chat 自己的 wire 序列化 bug，不是中转站不兼容。** 只要模型在某一步发起**多个并行工具调用**，`_claude_message` 会把每条工具结果分别序列化成一条独立的 `user` 消息，产出「一条 assistant 带 N 个 tool_use，后面跟 N 条 user」的形状。Anthropic 官方在校验前会把连续同角色消息合并，所以官方端点不报错；自研兼容网关按「紧接的下一条消息必须含全部 tool_result」逐条校验，直接 400。

同一根因还牵出三个连带问题（缓存断点位置、流式 usage 解析、空 content 序列化），本方案一并处理，但按优先级分批落地。

### 分级

| 级别 | 问题 | 影响面 | 是否本次必修 |
|---|---|---|---|
| **P0** | 并行 tool_use 结果被拆成多条 user 消息 | 所有走 claude 格式 + 并行工具调用的用户，必 400 | 是 |
| **P1** | 空 `tool_calls: []` / 空 content 产出 `content: []` | 严格网关 400（潜在） | 是（同一函数内顺手） |
| **P2** | 缓存断点永远停在首条提问，Agent 多步往返零收益 | 走 claude 格式的全部 Agent 任务 | 是（需真机验证后启用） |
| **P3** | claude 流式 usage 丢掉 input / cached 字段 | 用量与命中率显示恒为 0 | 是（否则 P2 无法验证） |
| **P4** | chat 格式可选注入 `cache_control` | 依赖中转是否透传 | 否，需产品决策 |
| **P5** | assistant 同时有正文与 tool_calls 时正文被丢弃 | 当前路径不触发，潜在 | 否，观察 |

## 1. 证据（本地只读复现）

### 1.1 复现 400

内部消息序列（还原用户那次第 3 步并行 3 个工具调用）：

```python
msgs = [
    {"role": "user", "content": "继续"},
    {"role": "assistant", "content": "", "tool_calls": [
        {"id": "call_3_0_9b1c0d1e", "name": "read_file", "arguments": {"path": "a.txt"}},
        {"id": "call_3_1_26f51af6", "name": "read_file", "arguments": {"path": "b.txt"}},
        {"id": "call_3_2_af075f26", "name": "read_file", "arguments": {"path": "c.txt"}},
    ]},
    {"role": "tool", "tool_call_id": "call_3_0_9b1c0d1e", "content": "..."},
    {"role": "tool", "tool_call_id": "call_3_1_26f51af6", "content": "..."},
    {"role": "tool", "tool_call_id": "call_3_2_af075f26", "content": "..."},
]
```

经 `ProtocolMixins._claude_message` 转换后的 wire：

```text
0 user       [text]
1 assistant  [tool_use:call_3_0_9b1c0d1e, tool_use:call_3_1_26f51af6, tool_use:call_3_2_af075f26]
2 user       [tool_result:call_3_0_9b1c0d1e]
3 user       [tool_result:call_3_1_26f51af6]
4 user       [tool_result:call_3_2_af075f26]
```

按「只检查紧接的下一条消息」的严格校验，输出与用户报错一字不差：

```text
messages.1: tool_use ids were found without tool_result blocks immediately after:
call_3_1_26f51af6, call_3_2_af075f26.
```

报错里的两个 id 正好是「不在紧随那条 tool_result 里」的第 2、3 个，与实测完全对应。

### 1.2 代码定位

| 位置 | 事实 |
|---|---|
| `naiba/llm/protocols.py:366-386` `_claude_message` | `role == "tool"` → 固定返回**一条**独立 `{"role":"user","content":[单个 tool_result]}`；`assistant` 分支把全部 tool_calls 塞进**一条** assistant 的 content |
| `naiba/llm/runtime.py:1362-1367` | claude 分支用列表推导逐条转换、**不做合并**，直接赋给 `payload["messages"]` |
| `naiba/skills/agent.py:1655-1664` | 内部消息序列本来就是「一条 assistant(tool_calls) + N 条 role=tool」，这是 OpenAI 系的正确形状，不该动 |
| `naiba/skills/agent.py:1648` | id 生成 `call_{step}_{index}_{uuid8}`，与报错 id 形状一致，可反推 step=3、index=1/2 |
| `naiba/skills/agent.py:1413` 注释 | 代码自己写着「直接追加会让 messages 变成连续两条 user（模型侧非法）」——Agent 层知道，wire 层却在批量制造 |

### 1.3 官方口径（对外部文档的引用）

- 连续同角色合并：Messages API 文档 —— "Consecutive `user` or `assistant` turns in your request will be combined into a single turn."
- 紧邻性：工具调用文档 —— "Tool result blocks must immediately follow their corresponding tool use blocks in the message history." / "You cannot include any messages between the assistant's tool use message and the user's tool result message."，并直接给出 `tool_use ids were found without tool_result blocks immediately after` 这一错误码。
- 块顺序：同一页 —— "In the user message containing tool results, the `tool_result` blocks must come FIRST in the content array." / "Any text must come AFTER all tool results."

即：官方靠「先合并再校验」宽容通过了我们的形状；中转站只是**严格执行了同一条规则**。

### 1.4 附带确认的三处同源风险

1. **工具结果 + 图片批**：`naiba/skills/agent.py:1688` 在 tool_result 之后追加 `_image_batch_message`（`role: user`），同样制造连续 user。
2. **工具结果 + 插话**：下一轮开头 `consume_interjections()` 往末尾追加 `role: user`。
3. **空 content**：`_claude_message({"role":"assistant","content":"","tool_calls":[]})` → `{"role":"assistant","content":[]}`，空数组对严格网关是 400。

一个真实的多步 trace 里连续同角色对数为 3（user→assistant→user→user→user→user），全部由上述路径产生。

## 2. 修复方案

### 2.1 落点选择

**只在协议层（wire 序列化）合并，不动 Agent 循环。**

理由：

- OpenAI 系（`openai_chat`）要求的就是「assistant.tool_calls + N 条 role=tool」，改内部形状会破坏现有 OpenAI/DeepSeek 行为与既有前缀缓存基线。
- 内部消息序列会被 `run_context["trace_messages"]` 原样落库并跨轮重放，其字节稳定性是既有缓存契约（`naiba/core/history.py:520-547` 明确要求逐字节不变）。合并必须发生在**读取内部序列之后、序列化之时**，不能回写 trace。
- 合并是确定性纯函数：同一份内部历史永远产出同一份 wire 字节，跨请求仍可命中前缀缓存。

### 2.2 P0：新增 `_claude_merge_adjacent`

位置：`naiba/llm/protocols.py`，紧跟 `_claude_message` 之后、`_claude_apply_cache_control` 之前。

```python
@staticmethod
def _claude_merge_adjacent(messages: list[dict[str, Any]]) -> list[dict[str, Any]]:
    """把相邻同角色消息合并成一条（Anthropic 要求的 wire 形状）。

    为什么必须显式做：官方 Messages API 会把连续同角色 turn 合并后再校验，
    所以「assistant(N 个 tool_use) + N 条 user(tool_result)」在官方端点能通过；
    但严格的兼容网关按「紧接的下一条消息必须含全部 tool_result」逐条校验，
    直接 400（2026-11-03 用户实测 Zooywoo 中转）。我们不能依赖上游帮忙合并。

    合并规则（与官方语义一致）：
    - content 统一成 block 数组；
    - 同角色相邻则 content 拼接；
    - 合并后把 tool_result 块前置（官方：tool_result 必须排在 content 数组最前，
      文本必须在其后）；
    - 空 content 的消息整条丢弃（含 `tool_calls: []` 产出的 `content: []`），
      空数组对严格网关同样是 400。
    """
```

规则细节：

1. 逐条把 `str` 内容转成 `[{"type":"text",...}]`；非 list/str 一律按空处理。
2. 空 block 列表的消息**跳过**。
3. 与上一条同 role → `extend`；否则新起一条。
4. 收尾统一做一次稳定排序：`tool_result` 权重 0，其余权重 1，**同一权重内保持原相对顺序**（Python `sort` 稳定）。这一步同时覆盖「tool_result + 插话文本」「tool_result + 图片批」两种混合。

返回新列表，不修改入参（避免影响 `_debug_payload_dump` 之外的任何引用）。

### 2.3 P0 接线

`naiba/llm/runtime.py:1362-1386`：

```python
claude_messages = ModelRuntime._claude_merge_adjacent([
    ModelRuntime._claude_message(item)
    for item in messages if item.get("role") != "system"
])
payload = {
    "model": model,
    "messages": claude_messages,
    "max_tokens": claude_max_tokens,
    "stream": stream_enabled,
}
...
ModelRuntime._claude_apply_cache_control(payload["messages"])
```

顺序不能反：必须先合并，缓存断点才能看到「合并后的最后一条消息」。

对既有自愈链无影响：`_slim_payload_images`（`runtime.py:503`）按 `message["content"]` 列表遍历图片槽位，合并后仍是列表；`_image_slot_kind("claude")` 认 `type == "image"`，不变。

### 2.4 P1：空 content 防线

在上述合并函数内以「丢弃空 block 消息」一次性解决，**不改** `_claude_message` 的返回形状（保持它与 `_gemini_message` 的对称性，也避免牵连 `tests/test_local_image_history_flags.py:650` 那类逐条调用转换函数的守门）。

### 2.5 P2：缓存断点前移

现状：`_claude_apply_cache_control`（`protocols.py:930-957`）倒序找「最后一条**非 tool_result** 的 user 消息」。Agent 循环里工具往返之后新增的消息全是 tool_result / assistant tool_use，倒序会一路跳过 —— 断点永远停在用户最初那句提问上，第 2…N 步的请求只能命中 `[tools + system + 首条提问]`，每个工具结果都在重复付费。

目标：断点落在**最后一条消息的最后一个 block**，让每一步把「到这一步为止的全部内容」写进缓存，下一步整段读回。

配套三项（按收益排序，前两项风险为零）：

1. **工具定义打缓存点** —— `_tool_schemas(rows, "claude")` 产出后，在最后一个 tool 上追加 `"cache_control": {"type": "ephemeral"}`。Anthropic 的缓存前缀顺序是 tools → system → messages，当前 tools 完全没被缓存。官方明确支持在 tools 数组元素上打点。
2. **system 已有断点**（现状保留，`runtime.py:1374-1381`）。
3. **消息尾块断点** —— 把「跳过含 tool_result 的 user 消息」改为「取最后一条消息的最后一个 block 打点」。

断点总数：tools 1 + system 1 + 消息 1 = 3，未超过官方上限 4。

**必须先验证再启用第 3 项**：现有注释断言「绝不能标记在含 tool_result 的 user 消息上（否则 API 400）」，而官方文档现在明确写「Tool use and tool results: Content blocks in the `messages.content` array, in both user and assistant turns」可以承载 `cache_control`。两者冲突，只能靠真机判定（见第 5.2 节探针）。若验证失败，保留跳过逻辑，只做第 1 项 + 保持第 2 项。

**自愈兜底**：仿照现有 `max_tokens` 回退（`runtime.py:1837-1860`），在 400 且 `detail` 命中 `cache_control` 时，剥掉消息断点重试一次，并 `status` 提示「当前接口不接受消息级缓存断点，已自动关闭」。只重试一次，禁循环；`payload` 要回写（同既有约定：剥掉的字段必须累积）。

**禁用开关**：给 profile 增加可选键 `claude_cache_breakpoints`（`"auto" | "off"`，默认 `auto`），落 `naiba/config.py` 的 provider schema；`off` 时不发任何 `cache_control`，供对缓存语义敏感的中转使用。

### 2.6 P3：claude 流式 usage 聚合

现状 `_online_usage`（`protocols.py:717-765`）取「最后一个带 `usage` 的 chunk」：

- `message_start` 的用量嵌在 `message["usage"]` 里（顶层没有 `usage` 键），因此**取不到**；
- `message_delta` 顶层只有 `{"output_tokens": N}`，**最后一条命中它**；
- 结果：`input_tokens` / `cached_tokens` / `cache_creation_input_tokens` 全丢。

实测：

```text
流式  -> {'input_tokens': 0, 'output_tokens': 50, 'total_tokens': 50, 'cached_tokens': 0}
非流式 -> {'input_tokens': 12325, 'output_tokens': 15, 'total_tokens': 12340, 'cached_tokens': 12000}
```

修法：`request_format == "claude"` 时单独走一条聚合 —— 从 `message_start.message.usage` 取 `input_tokens` / `cache_read_input_tokens` / `cache_creation_input_tokens`，从 `message_delta.usage` 取 `output_tokens`（两者字段合并而非整体覆盖），再进入现有的「claude 输入补齐」分支（`input_tokens += cached + cache_creation`）。

这一项是 P2 的**前置条件**：不修它，界面上的命中率在 claude 格式下恒为 0，任何缓存改动都无法验证，也会误导用户得出错误结论（见第 7 节）。

### 2.7 P4（可选，需产品决策）：chat 格式注入缓存断点

部分中转（如 OpenRouter）在 **OpenAI 兼容的 `/chat/completions`** 上接受 Anthropic 风格的 per-block `cache_control`。若用户的供应商属于这一类，可以在 `openai_chat` 分支按供应商开关注入。

不建议默认开启：严格的 OpenAI 端点会因未知字段 400。落地形态应是模型卡片上的显式开关（例如 `openai_prompt_cache: off | anthropic_blocks`），默认 `off`。

### 2.8 P5（观察项）

`_claude_message` 在 `assistant` 带 `tool_calls` 时**丢弃 content 正文**。当前原生工具轮的 assistant 消息 content 恒为空串（`agent.py:1656` `assistant_message("", tool_calls=...)`），所以线上不触发。若将来允许正文+工具同轮，需按官方顺序输出 `[text..., tool_use...]`。改动会变更已有 wire 字节，需重新基线，故不列入本次。

## 3. 不做什么

- 不改 `naiba/skills/agent.py` 的并行执行与消息追加逻辑（OpenAI 系正确形状，且牵动 trace 字节契约）。
- 不改 `parallel_tool_calls` 发送与否（那是 `openai_chat`/`lm_studio` 的字段；claude 分支压根不发）。
- 不改 `tests/test_comfyui_module.py` 的既有本地修改、不碰 `NUL` 等无关工作树文件。
- 不调整版本号、不提交、不推送、不发版（发版与 4.0.1 的后续处置按用户既有暂停口径另行确认）。
- 不为 `gemini` 做同类合并（它同样是一条 functionResponse 一条 user；Gemini 侧无此报错证据，不做无由改动）。

## 4. 实施顺序

1. **P3**（usage 聚合）—— 独立、零副作用，先让指标可信。
2. **P0 + P1**（合并函数 + 接线）—— 修 400，是本轮用户问题的主修。
3. 本地回归（第 5.1 节）。
4. **P2 探针**（第 5.2 节）→ 依据结果决定是否启用消息尾断点并加自愈兜底。
5. **P2 落地**（tools 断点 + 可选消息尾断点 + profile 开关）。
6. 真机复测用户的 Zooywoo 供应商（并行工具调用场景必测）。
7. P4 单独排期，需产品确认。

### 5.2 真机探针（需用户授权、需计费）

新增 `verify/_probe_claude_wire.py`（离线自检，可直接跑）：

- 构造 3 工具并行 + 插话 + 图片批的混合场景；
- 打印 wire 摘要（角色序列、每条的 block 类型序列）；
- 内置严格相邻校验与「tool_result 前置」校验，失败退出码 1。

新增 `verify/_probe_claude_cache.py`（联网、付费，**先跑最小样本**）：

1. 固定一段超过最低可缓存长度的长前缀（Sonnet 4.5 / Opus 4.8 是 1024 token，Opus 4.5 / Haiku 4.5 是 4096，取 8k 稳过阈值）；
2. 同一供应商、同一模型，连发两次，只改 `request_format`：`claude` vs `openai_chat`；
3. 原始打印两次响应的 `usage`（不做字段归一），对比：
   - claude 格式第二次是否出现 `cache_read_input_tokens > 0`；
   - chat 格式的 usage 里**是否存在** `cached_tokens` / `cache_read_input_tokens` 键。
4. 判定：
   - chat 侧连键都没有 → 中转没透传，不可证伪，只能按「中转未实现」处理；
   - chat 侧有键且恒为 0 → 中转确实没做缓存；
   - claude 侧第二次仍为 0 → 检查是否为最低长度不足 / 中转未透传断点 / 我们的断点未生效。

第 3 步同时用于验证 P2 的「消息尾断点」是否被接受（若 400 且提到 `cache_control`，即证伪，回退到只做 tools 断点）。

## 6. 风险与回滚

| 风险 | 表现 | 处置 |
|---|---|---|
| 合并改变 wire 字节 | claude 格式前缀缓存首次失效一轮 | 属预期一次性代价；合并是确定性的，后续稳定 |

## 7. 关于「chat 格式缓存不命中，claude 格式才命中」

**有可能，而且机制上必然如此——但需要先排除我们自己的观测误差。**

### 7.1 为什么 chat 格式大概率不命中

Anthropic 的前缀缓存只有两种开法，都定义在 `/v1/messages` 的请求体里：

- 在具体 content block 上打 `cache_control: {"type":"ephemeral"}` 断点（最多 4 个）；
- 或在请求顶层放一个 `cache_control` 开自动缓存。

OpenAI 的 `/chat/completions` 请求体**没有任何字段能表达这两种语义**（`prompt_cache_key` 是 OpenAI 自己那套缓存的键，不是给 Anthropic 的）。我们的 `openai_chat` 分支（`runtime.py:1256-1290`）发出的就是纯 OpenAI 字段，一个缓存提示都没有。

所以走 chat 格式时，**只能指望中转自己替用户补一个 `cache_control`**。多数中转只做字段翻译，不补这个 —— 于是上游 Anthropic 从未被要求写缓存，`cache_read_input_tokens` 恒为 0。这是"正常且可预期"的，不是 bug。

### 7.2 但必须先排除我们自己的观测误差

**P3 那个 usage 解析缺陷意味着：在 claude 格式下，我们的流式请求根本读不到 input / cached。** 实测 `input_tokens` 与 `cached_tokens` 都是 0。

也就是说，「claude 格式能命中」这个观察，要么发生在非流式路径，要么来自该中转把 usage 放在了别的位置。**在 P3 修好之前，界面上的命中率不能作为判断依据** —— 完全可能两边都是 0，只是 claude 那边看起来"应该有"。

因此顺序必须是：先修 P3，再对比两种格式的原始 usage，才谈得上结论。

### 7.3 最低可缓存长度这个坑

Anthropic 对短前缀根本不缓存，各模型阈值不同：

- 512 token：Fable 5.1 / Mythos 5.1 / Opus 5.5 / Opus 5 / Sonnet 5.5
- 1024 token：Opus 4.8 / Sonnet 5 / Sonnet 4.6 / Sonnet 4.5
- 2048 token：Mythos Preview / Opus 4.7
- 4096 token：Opus 4.6 / Opus 4.5 / Haiku 4.5

用几句短对话测试「缓存有没有命中」，无论哪种格式都必然是 0。探针必须用 8k 以上的固定前缀。

### 7.4 给用户的答复口径

> 同一个 Claude 模型，claude 格式能命中、chat 格式不命中，是**正常且可预期**的：缓存断点只存在于 Anthropic 原生协议里，chat 格式下要不要缓存完全取决于中转站是否替你补断点。多数中转不补。
>
> 想要缓存收益，这个供应商就得选 claude 格式 —— 而那正好是当前会 400 的那条路，两件事撞在一起了。本次修复 P0 之后，claude 格式的并行工具调用会恢复正常，届时可以整体切到 claude 格式，既解决 400 也拿到缓存。
