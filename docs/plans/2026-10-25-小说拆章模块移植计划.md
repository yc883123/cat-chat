日期：2026-10-25

## 1. 目标与边界

把竞品《启元提示词助手》的「TXT 小说按章拆分」能力移植到 Cat Chat，让用户能把一整本本地小说 TXT 拆成可用章节，供后续的生成链路（改写、分镜、配音、封面配图）消费。

**分两阶段，本次先评 P1：**

| 阶段 | 交付形态 | 谁来用 |
|---|---|---|
| **P1 工具层** | 拆章算法成 `naiba/tools/` 的一个工具，AI 在会话里直接调用 | 用户一句话 + AI 干活 |
| **P2 工作台页** | Studio 新增「小说」功能页：导入 → 勾选 → 章节列表 → 落盘作品 | 人手工操作 |

**本次不顺带做**：人物/场景/道具表、大纲编辑器、知识图谱、章节正文的大文本在线编辑区、一键成片。

**相对竞品的差异化**：启元只能「人手动导 TXT」。Cat Chat 应当做到「AI 生成长文本 → 自动拆章 → 回填」，这才是它做不到的。

## 2. 竞品算法还原结论

取证对象 `D:\qiyuan_re\启元提示词助手.exe_extracted`（v1.91.62，PyInstaller + Python 3.13 + pywebview）。

### 2.1 代码落在哪

| 文件 | 职责 |
|---|---|
| `PYZ.pyz_extracted/backend/txt_import.pyc` | 算法本体，纯 `re` 正则，无第三方依赖，约 180 行 |
| `PYZ.pyz_extracted/backend/archive.pyc` | `file_outline` / `file_chunks` 两接口实现 |
| `PYZ.pyz_extracted/backend/bridge.pyc` | 路由分发 |
| `novel-editor.html`（1.4MB，抽出 `dumps/nv_main.js` 17483 行） | 前端勾选 UI |
| `dumps/txt_import_consts.txt` | 本次导出的保序常量清单（移植时照此写） |

### 2.2 最关键的一招：两段式 API

这是它能扛几十 MB 小说的全部秘密，必须照抄：

```text
POST /api/file/outline   {path}
    → 只回索引：{ok, name, encoding, total, chapters:[{i, title, len}]}     不带正文
POST /api/file/chunks    {path, idx:[0,3,7]}
    → 才回这几章的正文：{ok, chapters:[{title, content}]}
```

前端先弹勾选框（只需索引，秒开），用户勾完再取正文。**不要一次性把整本回传前端**。

### 2.3 四级降级

`split_chapters(text, max_len=6000)` 依次尝试，命中即停：

| 级 | 策略 | 触发条件 | 细节 |
|---|---|---|---|
| ① | 按标题切分 | 识别到 **≥2 个**章节标题 | 主流路径 |
| ② | 符号分节 | 某类符号分隔行出现 **≥5 次** | 古籍/论坛贴用 `◎` `***` `===` 分节，取其**后一行**当标题（限 24 字，超出叫「第 N 节」） |
| ③ | 单标题兜底 | 只识别到 1 个标题 | 仍按它切，好过乱切 |
| ④ | 等分兜底 | 一个标题都没有 | 纯按字数硬切，尽量在换行处收尾（在目标点前后 60% 窗口内找最近换行） |

### 2.4 正则清单（已还原，可直接用）

| 常量 | 作用 | 表达式要点 |
|---|---|---|
| `CHAPTER_RE` | 认章标题 | `(第 N 章`（带前括号的变体）、`第 N 章`、`卷 N`、`楔子\|序章\|序言\|引子\|尾声\|后记\|後記\|终章\|終章\|番外`、`[Cc]hapter\s[0-9IVXLC]{1,8}`、`N. 标题`；字符集 `[0-9０-９零一二三四五六七八九十百千万两]{1,12}`；题名后允许 60 字以内副标题 |
| `VOL_RE` | 认卷/篇/部/集/季 | `^\s*(第 N [卷篇部集季]\|卷 N)` |
| `SYMBOL_RE` | 认符号分隔行 | `^[\W_]{1,10}$`，带 `re.UNICODE` |
| `BODY_MARK_RE` | 认「正文」标记 | `^[=＝\-—*＊~～]{2,}\s*(正文\|全文\|内容\|开始\|序章)?\s*[=＝\-—*＊~～]{2,}$` |

字符集**同时含汉字数字与全角数字**（还特意收了 `两`，用于「第二十三章」「第１００章」这类写法），这是实战细节，移植时别漏。

### 2.5 三个容易忽略的处理

1. **剥头部**（`_strip_head`）：网文 TXT 开头是版权声明/简介。用 `BODY_MARK_RE` 找分隔标记，**且只在全文前 20% 范围内找**，避免把正文中间的某条分隔线误认成正文起点。
2. **卷不单独成章**（`_by_heads`）：`VOL_RE` 命中的大标题拼进所属章，变成`第一卷 平庸少年 · 第一章 离乡`。**根因是**否则会冒出一堆只有几个字的空章。同时标题行前 ≤30 字的铺垫行归给上一章。
3. **超长章再切**（`_cap_chunks`）：单章 >6000 字再切小块，标题加 ` (1/2)` 后缀。**这是为喂模型服务，不是给人看的**，所以 UI 层可以考虑不暴露。

### 2.6 阈值与辅助

| 项 | 值 |
|---|---|
| 单块上限 | 6000 字 |
| 单文件上限 | 60 MB（超了直接拒） |
| 编码嗅探 | `utf-8-sig → utf-8 → gb18030 → big5`（gb18030 是中文盗版 TXT 标配） |
| 缓存 | `TXT_CACHE`，按 `(path, mtime, size)` 签名复用，反复勾选不重读盘 |
| 前端去重 | 导入时 `stripDupTitle` 去掉正文里与 title 重复的那行标题，避免标题显示两遍 |

## 3. Cat Chat 现状核查

### 3.1 Studio 当前是「两层模型」，装不下「作品」

`naiba/studio/`（catalog / custom / store / runner / jobs / service / handoff，约 1850 行）本质是：

- **catalog**：只读预设目录（`public/studio/` 的 JSON）
- **tasks**：单次生成任务记录，落 `data_dir/studio/tasks/`

**没有任何「作品 / 书稿 / 章节列表」这种长期存在的用户数据域。**这是移植的真实成本所在——不是算法难，是没有容器。

竞品把整本书丢浏览器 `localStorage`（键 `novel_screenplay_v1`，它自己在界面上警告 5MB 上限）。**Cat Chat 不能这么干**，必须落 `data_dir`。

### 3.2 可直接复用的现成范式

| 要什么 | 抄哪里 |
|---|---|
| 每条目一个 JSON 的持久化 | `naiba/studio/custom.py:63-64`（`data_dir/studio/custom`）、`:109-120`（同目录 tmp + `os.replace` 原子写，失败不覆盖） |
| 防路径穿越 | `naiba/studio/custom.py:69-73` `_safe_path` |
| 新增业务接口 | `naiba/studio/service.py` 加 `api_*` 方法（现有 20 个，`api_catalog_*` / `api_custom_*` / `api_task_*` 都是这个形状） |
| HTTP 转发 | `naiba/http.py:558`（GET 链起）/ `:728`（POST 链起）——**手写 elif 链，无自动注册**，加一个路由要加一处 |
| AI 可调工具 | `naiba/tools/providers/*.py` + `naiba/tools/registry.py` 的 `build_xxx_tool_specs()`，`:1312` `build_tool_registry()` 汇总。**`documents.py` provider + `:1168 build_document_tool_specs()` 是最贴近的落点** |
| Studio 新功能页 | 照 `23-labeler.js` 的范式：独立 js + 独立后端域 + 一个 page entry |

### 3.3 一处需要更正的认知

项目里流传的「storage 写路径全包 `@_retry_transient_write`（AST 守门）」——**核了，范围没那么大**：

`tests/test_sqlite_write_retry.py:109-135` 的 `_scan_write_paths()` 只 `ast.parse` **一个文件**（`STORE_PATH` = `naiba/storage/store.py`）且只扫 **`ChatStorage` 这一个类**。`naiba/studio/` 下的写路径**不在守门范围内**。

所以 P1/P2 的新写路径**不会被这个测试抓住**。但建议仍沿用 `custom.py:109-120` 的 tmp+原子写范式（一致性 + 真的更安全），而不用去满足那个装饰器。

### 3.4 绕不开的项目铁律

- 改了 `public/`（含新增 js / html）**必须重编 exe**（约 40s），然后跑 `dist\naiba-chat.exe --run-skill-script verify\_probe_packed_markers.py`

## 4. 推荐路线：P1 优先

| | 路线 A（工具层） | 路线 B（工作台页） |
|---|---|---|
| 改动量 | 小 | 中～大 |
| 新增 UI | 无 | 一个完整功能页 + index.html view |
| 价值 | AI 可在会话里直接拆书干活，还能「生成→拆章→回填」闭环 | 人能可视勾选 |
| 打包影响 | 无（不动 `public/`，无需重编 exe） | 要重编 exe、要走 UI 冒烟 |
| 依赖 | 无 | 需要先有 P1 的后端能力 |

**推荐先做 P1。**理由：①Cat Chat 的主战场是会话，工具层立刻可用；②P2 的后端部分就是 P1，先做不浪费；③差异化（AI 生成后自动拆章）靠工具层就能实现，不依赖 UI。

给启元做不到的一击：**AI 写完长篇 → 调 `novel_split` → 拿到章节数组继续干活**，全程不用人导文件。

## 5. P1 实施步骤

### 5.1 新增 `naiba/studio/novel.py`（纯算法层）

纯函数模块，**不 import 任何 Cat Chat 业务、不做 IO**：

- `read_text_auto(path) -> (text, enc)`：四连编码嗅探（含 BOM）
- `split_chapters(text, max_len=6000) -> [(title, body)]`：四级降级（§2.3）
- `CHAPTER_RE` / `VOL_RE` / `SYMBOL_RE` / `BODY_MARK_RE` 四条正则（§2.4）
- `_strip_head` / `_by_heads` / `_split_by_sep` / `_split_by_len` / `_cap_chunks`

**配套单测 `tests/test_novel_split.py`**（新文件）：各种常见/畸形输入的回归——

| 用例 | 断言 |
|---|---|
| `第1章` / `第一章` / `Chapter 3` / `12. 标题` | 都能认 |
| 全角数字 `第１２章`、`第两章` | 能认（字符集别漏 `两`） |
| 有卷标题 | 卷并进章标题（`A · B` 形态），不产生空章 |
| 前面有版权声明 + `====正文====` | 头部被剥掉 |
| 无任何标题 | 走等分兜底，且**在换行处收尾** |
| 超长单章 | 切成 `(1/2)` |
| 空文件 / 只有一行 / 纯乱码 | 不崩，返回兜底结果 |
| 编码：gb18030 样本、带 BOM 的 UTF-8 | 都能读，且 `encoding` 字段报对 |

### 5.2 注册成 AI 工具

`naiba/tools/providers/documents.py` 加实现，`naiba/tools/registry.py` 的 `build_document_tool_specs()`（`:1168`）加两个 spec：

- `novel_outline({path})` → `{name, encoding, total, chapters:[{i,title,len}]}`
- `novel_chunks({path, idx})` → `{chapters:[{title, content}]}`

照抄竞品**两段式**：**`outline` 绝对不能带正文回传**，否则长会话里上下文会被整本书撑爆。这一点比算法本身更关键。

`max_len` 默认 6000，参数可覆盖。

### 5.3 后续叶子（P1 做完后自然长出）

- 「AI 生成长文本 → 自动拆章」：`novel_split_text({text})` 变体，直接吃字符串不吃文件
- 章节 → Torako 生图 / H3 视频的一条龙

## 9. 风险与坑

| 风险 | 说明 | 对策 |
|---|---|---|
| 中文 TXT 编码五花八门 | gb18030 是盗版站标配，UTF-8 直接 decode 会炸 | 严格走四连嗅探 + `errors="replace"`，出错不崩 |
| 一次性回传整本书 | 会把会话上下文撑爆 | **硬性：outline 不带正文**（照抄竞品两段式） |
| 算法换到别的书会误判 | 部分出版物用「壹、贰」或纯「一、」当章节标题 | 先拿几十个真实样本实测，确认不够再扩字符集；不要一上来就把正则放宽到会把正文当标题 |
| 以为 AST 守门会兜住新写路径 | **核实：守门只扫 `ChatStorage`**，新代码不被覆盖 | 自觉采用 tmp+原子写；不要指望测试报错 |
| 改了 `public/` 忘记重编 | 打包产物与源码不一致 | 严格按 §3.4 走编译 + 探针流程 |
