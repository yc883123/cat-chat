## 一、这个功能解决什么问题

长对话逼近模型上下文窗口时，用户会遇到两种中断：撞上限后只能新建对话，或者提前手动写交接总结。前者打断当前任务，后者把上下文维护的活转嫁给用户。

自动整理让用户留在当前对话继续工作：把**较早的历史换成一份交接总结**，最近的若干个完整轮次原样保留。完整聊天记录一条不删，模型只是每轮不再收到被总结替换掉的那部分旧消息。

## 二、方案：阈值触发、同一模型隐藏总结、摘要定稿后稳定复用

### 不引入摘要模型

总结请求用**当前对话这一轮实际选中的 profile**（同一个 provider、同一个 model、同一份配置），只多发一次请求。不需要任何「摘要模型」设置项，不需要额外 Key，不请求另一个模型。

### 隐藏请求

- 不走 agent 循环，`options` 里**没有 `tools` 键**（模型看不到任何工具）
- 不流式（`stream: False`）
- 只喂两样东西：**将被压缩的历史**（模型视图，含旧摘要）+ 固定的结构化指令
- 图片降级成 `[图片]` 文字标记（总结只需事实与路径，不必重看历史图）

### 摘要定稿即冻结

摘要在触发时生成一次并写进标记，之后每轮从标记里**原样重放**，不在每轮重写。系统提示、工具定义、摘要消息模板都保持稳定——这是缓存能持续命中的前提。

### 保留完整轮次，不按消息行数切

一轮 = 一条 user 消息及其后的全部内容（assistant 回复、工具调用、插话），到下一条 user 消息为止。保留最近 N 轮（默认 3）。按轮次切避免把一轮里的提问和答复劈成两半（那会让摘要丢结论、或让保留区缺前提）。

### 旧摘要不丢

再次整理时，被整理区间的模型视图**天然以旧摘要开场**——旧标记就在区间内，`build_model_history` 会把它还原成摘要消息放在最前面。所以交给模型的是「旧摘要 + 新进入区间的历史」，不是只总结原始消息。指令里也明确要求模型合并旧摘要、输出完整合并版。

### 触发点提前

默认阈值 **70%**（不是 80%）：整理要额外发一次总结请求、之后本轮还要正常回复，两者都必须有空间。触发点公式：

```
触发点 = min(窗口 × 阈值%, 窗口 − (总结输出上限 + 回复预留 + 1024))
```

## 三、与现有机制的关系

| 现有机制 | 关系 |
| --- | --- |
| `profile["context_window"]` / `usage["context_limit"]` | 触发判断沿用同一窗口值 |
| `SkillAgent._context_fits` 轮首闸门 | 估算器同源；闸门语义不变（超限仍拦截，不静默截断） |
| `session_start`（新会话分割线） | 同构：标记写在消息 metadata 上，不插行；重放端遇标记改历史 |
| `reset_context`（模型写总结重置上下文） | **完全保留，未被替换** |

### 与 `reset_context` 的分工

| | `reset_context`（原有） | 自动整理（本次新增） |
| --- | --- | --- |
| 谁触发 | 模型自己决定调用 | 系统在发请求前自动判断 |
| 做什么 | 要求模型写交接文档，然后**彻底截断** | 系统发隐藏请求做交接总结，**保留摘要继续** |
| 是否调模型 | 是（模型写文档，同一轮内） | 是（额外一次隐藏请求，同一模型） |
| 落点 | `session_start` → 线以上彻底不进上下文 | `compaction` → 线以上换成摘要仍进上下文 |
| 用户可见 | 分割线 + 「填入种子消息」 | 整理卡，可展开、可撤销 |
| 工具集要求 | 会话需勾选 `reset_context` | 无需任何工具，设置三档即可 |

`naiba/tools/` 与 `naiba/skills/` 两个目录 `git status` 零改动。

## 四、行为设计

### 三种模式

设置位置：设置 → 运行设置 → 基础参数。

| 模式 | 行为 |
| --- | --- |
| `auto` 自动整理（**默认**） | 每轮发请求前估算用量，达阈值 → 整理后继续本轮 |
| `remind` 整理前先提醒 | 达阈值只推一条提示，本轮照常发送 |
| `off` 关闭 | 与没有这个功能时完全一致（估算也不做，零字节差异） |

### 三个参数

| 设置项 | 默认 | 含义 |
| --- | --- | --- |
| 自动整理触发阈值 | 70% | 上下文估算用量达到模型窗口的该百分比时开始整理 |
| 整理时保留最近几轮 | 3 轮 | 最近这几轮完整保留，只整理更早的部分 |
| `summary_max_tokens`（无界面入口） | 2048 | 总结请求的输出上限 |

### 摘要的九个分区

指令要求模型严格按下面结构输出（缺分区写「(无)」，不能省略）：

1. 当前目标
2. 用户约束
3. 已确认事实
4. 已作决定
5. 完成进度
6. 待办事项
7. 关键工具结果与文件路径
8. 尚不确定的事项
9. 下一步

规则里明确要求：路径/标识符/数值/报错原文原样保留；不提及「总结」「压缩」这些动作；若已有旧摘要则合并成完整版而非只写新增部分。

### 校验（不合格就不整理）

| 判据 | 阈值 | 不通过时 |
| --- | --- | --- |
| 长度下限 | 120 字符 | `summary_too_short` |
| 长度上限 | 20000 字符 | `summary_too_long` |
| 分区关键词 | 至少命中 4 个 | `summary_missing_sections(N)` |
| Markdown 标题数 | 至少 2 个 | `summary_not_structured` |
| 是否真的变短 | freed_est > 0 | `freed_too_small` |

任何一项不过、或请求抛异常、或写库失败 → **不写标记**，本轮按原历史继续（fail-open）。

### 标记落在哪

写在**被整理区间最后一条消息**的 metadata 上（`compaction` 键），不新增消息行。

原因：`messages` 表的排序键是 `(created_at, rowid)`，想在中间插一行必须构造或回移时间戳，同毫秒相邻时会插错位。写在被标记的那条消息的 metadata 上位置天然精确，与 `session_start` 做法一致。

撤销会二次确认：`撤销这次整理？被整理的旧消息会重新进入模型上下文；下一轮对话会重建一次缓存。`

## 七、API 契约

### 手动整理

```
POST /api/conversations/<conversation_id>/compact
```

无请求体。用**该会话自己记录的模型**（`conversation.model_key` / `model_name`）发一次总结，`force=True` 跳过「释放量是否值得」检查（但仍要求区间够大）。

响应：

```json
// 成功（201）
{"ok": true, "compacted": true, "region_messages": 12, "freed_est": 8342,
 "summary": "...", "marker_message_id": "..."}

// 不合格（409），带用户可读原因
{"ok": false, "compacted": false, "reason": "region_too_small",
 "message": "更早的消息太少，还没有可整理的内容"}
```

原因文案映射：

| reason | 用户看到的 |
| --- | --- |
| `region_too_small` | 更早的消息太少，还没有可整理的内容 |
| `region_empty` | 更早的消息里没有可整理的内容 |
| `freed_too_small` | 摘要没有比原文更短，整理没有意义 |
| `summary_too_short` | 模型返回的交接总结太短，没有采用 |
| `summary_too_long` | 模型返回的交接总结过长，没有采用 |
| `summary_not_structured` | 模型返回的内容不是结构化交接格式，没有采用 |
| `summary_failed:*` | 总结请求失败，本轮没有整理 |
| `summary_missing_sections(N)` | 模型返回的交接总结缺少关键分区，没有采用 |
| `marker_write_failed` | 保存整理结果失败 |

### 撤销整理

```
DELETE /api/compaction/<message_id>
```

只摘掉 `compaction` 键，消息与其余 metadata 保留。响应 `{"ok": true}`（200）/ `{"ok": false}`（404）。

## 九、缓存影响（已实测）

### 设计上如何保证

| 场景 | 对缓存的影响 |
| --- | --- |
| `off` 模式 | **零影响**。估算都不做 |
| `auto` / `remind` 但未达阈值 | **零影响**。只读估算，不写不改 |
| 触发整理的那一轮 | 历史前缀被摘要替换 → 新前缀，缓存重新预热（一次性成本） |
| 整理之后的每一轮 | 摘要逐字节稳定，前缀从摘要位置往后正常复用 |

摘要只在触发时生成一次并保存，之后原样复用；系统提示、工具定义、摘要模板都不每轮重写。

### wire 探针（零成本，前缀字节对比）

A/B 用 `git archive HEAD` 导出基线树。**普通会话（无任何整理标记）在两棵树上的历史 sha256 完全一致**：

| 树 | 普通会话消息数 | 字符数 | history_sha |
| --- | --- | --- | --- |
| baseline（HEAD） | 18 | 2232 | `b91f18cdef65a9fb` |
| candidate（本次） | 18 | 2232 | `b91f18cdef65a9fb` |

**逐字节相同**——这是「未触发整理时会话零影响」的核心证据。

candidate 树 5 项检查全部通过：

- `no_marker_repeat_determinism`：重复组装结果一致
- `no_marker_no_summary_leak`：无标记时历史里没有摘要痕迹
- `marker_replaces_prefix_with_summary`：带标记时以摘要开场、消息数变少
- `marker_repeat_determinism`：同一标记重复组装逐字节一致
- `tail_after_marker_unchanged`：标记之后的轮次原样保留

baseline 树上「标记替换」失败是预期的（旧代码不认识这个键），恰好证明探针真的在区分两棵树。

### live 探针（真实供应商，tedschat / deepseek-v4.1-flash）

| 阶段 | 树 | input | cached | miss | 命中率 |
| --- | --- | --- | --- | --- | --- |
| 冷启动 | baseline | 747 | 0 | 747 | 0% |
| 冷启动 | candidate | 746 | 0 | 746 | 0% |
| **稳定态合计** | **baseline** | **1490** | **1280** | **210** | **85.91%** |
| **稳定态合计** | **candidate** | **1488** | **1280** | **208** | **86.02%** |
| 整理后合计 | baseline | 1345 | 640 | 705 | 47.58% |
| 整理后合计 | candidate | 1169 | 384 | 785 | 32.85% |

**结论：稳态命中率 86.02% vs 85.91%，差 0.11 个百分点，cached token 完全相同（都是 1280）** —— 满足「近乎不变」的要求。

整理后那一轮两棵树都是低命中（新前缀冷启动），这是设计预期；差别来自基线树的 `sample_with_marker` 不含摘要消息（旧代码不认标记，历史更长），所以两者不是同一负载，这一行只作参考、不作门槛。

**注意**：具体命中率仍取决于供应商缓存策略，无法作硬保证。上面的数字是本次实测。

| 1 | 新增 `compaction` 事件未登记契约 | 两个事件契约守门测试失败 | 补 `EventType.COMPACTION`、`EVENT_PAYLOAD_KEYS`、`EventPayload` 字段 |
| 2 | `retain_boundary` 边界算错一位 | 保留区会把一轮的 user 与 assistant 劈开 | 改为停在「倒数第 N 条 user 消息的前一行」 |
| 3 | `reserve` 用 `budget - used` | **任何会话都会被判成需要整理**（短会话也发总结请求） | 改成 `limit - budget`（窗口里不属于历史预算的部分） |
| 4 | `SYSTEM_ESTIMATE_SLACK` 重复计入 `used` | 短会话被误判接近上限 | 从 `used` 里去掉，固定成本只体现在 `budget` 上 |
| 5 | `cancelCompaction` 的 `confirm` 字符串跨行未闭合 | **整个 04-messages.js 语法错误，页面全白**（`node --check` 查不出，浏览器才报） | 改为 `\n\n` 转义 |

第 5 条特别值得记：`node --check` 对「字符串里跨了真实换行」这种错误是**通过**的（因为它把换行当字符串内容），只有浏览器解析才报 `Invalid or unexpected token`。浏览器手验不可替代。

## 十三、设计取舍说明

**1. 摘要以 `role: user` 进入上下文，不是 system。**
system 每轮重发且位置敏感；放在 user 消息里更接近「历史里的一条记录」，也不影响 system 字节稳定。

**2. 默认 `auto` + 阈值 70%。**
70% 而非 80%：整理要额外发一次总结请求、之后本轮还要正常回复，两者都要空间。默认 auto 依据产品讨论稿的建议；若希望默认不打扰，改成 `remind` 是一个默认值改动。

**3. 保留轮次而非消息行数。**
按行数切会把一轮的提问与答复劈开，摘要会丢结论或保留区缺前提。

**4. 总结请求把图片降级成 `[图片]`。**
总结只需要事实与路径，不必让模型重看历史图（省视觉编码，也避免要求模型具备视觉能力）。

**5. 失败一律 fail-open。**
请求失败/输出不合格/写库失败都不留痕迹，本轮按原历史继续。宁可这轮不整理，也不写一个坏摘要污染后续所有轮次。
