## 1. 做了什么（对应交接 §3）

### ① 工具可执行（原卡点）

- `naiba/tools/providers/video.py`：新增 `_make_exact_execute()` 执行体并登记，`system=True`
  （与 `run_in_background` 同类：自己创建 Job，不经确认引擎）。临时「缺实现就跳过注册」的兜底分支已删除。
- 执行体的四道门（缺一不可）：
  1. `run_context["video_frames_intent"]` 为假 → 返回稳定拒绝码 `video_frames_intent_required`，**不建 Job、不写盘**；
  2. `depth > 0`（子 Agent）或 `interaction_mode == "plan"` → `video_frames_context_required`；
  3. 缺 `job_registry` / `run_id` / 会话 id → `video_frames_job_unavailable`（辅助对话与后台 Job 走这条）；
  4. `resolve_exact_range()` + `check_exact_capacity()` 失败 → 原文返回失败文本，创建前整项拒绝。
- 通过后创建 `JobSpec(kind="video_frames", detached=True, origin_run_id=ctx["run_id"], parent_job_id=None)`；
  幂等：同 owner + 同视频指纹 + 同范围的活动 Job 直接复用（参数从 run snapshot 读，不进 `/api/jobs` 列表）。
- 返回给模型的只有紧凑 JSON：`{ok, job_id, status, range, estimated_frames, manifest_api[, reused]}`，
  **不返回帧路径清单**。

## 2. 实施期发现并修掉的缺陷（交接文档未覆盖）

1. **终态 manifest 丢失帧数组**：`extract_frames_exact` 结尾用只含摘要的 `result` 覆盖 manifest，
   导致「抽取完成」后分页读出 **0 帧**。已改为终态清单单独写入 `frames/failed_frames/range_complete`；
   由 `test_manifest_pagination_has_no_duplicates_or_gaps` 守门。
2. **worker 失败文本带 `ValueError:` 前缀**：文件不存在 / 缺 av 这类本来就是给人看的文本，
   现在 `_run_video_frames` 单独捕获 `ValueError` 原样落库。
3. **时间区间 `range_complete` 过于宽松**：改为与 fps 估计值比对（容差 = 5% + 2 帧），
   超差判 `partial`，不再「有帧就算完整」。帧区间仍是精确比对。
4. **ComfyUI 脚本指引点名了本会话没有的 `write_file`**：改为按可用工具条件生成。
5. 删除 `extract_frames_exact` 里的死变量（`in_range_count`、`cache_root`）。
6. **提交路径把 Agent 收窄成四个字段，丢掉了 `tool_opt_ins`**：授权在设置页存下了，但新会话
   固化时拿不到，工具永远不出现在 `allowed_tools` 里。已在 `naiba/run/chat.py` 的提交路径与
   计划路径两处补上，并由 `test_submit_path_keeps_opt_ins_when_narrowing_agent` 守门。

## 3A. 缓存命中率验证（2026-10-23 补做）

### 3A.1 应用侧确定性（无网络，已纳入 CI）

新增 `tests/test_cache_prefix_stability.py`（4 条），走真实 `SkillAgent.run` 组装、假模型捕获
「模型实际收到的 messages + tools」：

- 同一授权快照下，「普通概览」与「明确逐帧」两条用户消息的 **system / tools / 历史前缀逐字节一致**，
  只有本轮新增用户消息不同；
- 未授权快照的 tools 不含 `extract_video_frames_exact`；授权快照只**追加**它，既有工具顺序不变；
- 同一输入重复组装两次，system/tools 哈希完全一致（无随机顺序、无时间戳）；
- Job 紧凑结果只作为新增尾部出现，不回写前缀、不携带帧路径清单。

### 3A.2 真实供应商（TE，按用户既有口径）

- 探针：`verify/_probe_cache_optin.py`（`wire` 零成本 / `live` 实测；`verify/` 已在 `.gitignore`）。
- 供应商：`tedschat`（`https://teynex.com`）+ `deepseek-v4.1-flash`（冻结版正式配置，未用免费默认链）。
- 基线：`git archive HEAD`（`c71b994`）导出的只读代码树，同脚本、同供应商、同语料。
- 语料：合成纯文本，无媒体、无用户数据；每条序列 cold → append → resend，另有意图措辞变体与 Job 后续追问。
- 采样：基线 3 组、候选 5–6 组（每组一次冷启动），取中位数。

### 3A.3 绝对门槛（§7.3-5，长历史前缀）

短前缀下绝对命中率天然上不去（固定尾部就占 180–250 token），因此单独补了长历史实测：
`verify/_probe_cache_optin.py long`——真实 `build_model_history` 构造 16 轮历史（约 4.9 万 input token），
每组先冷启动再复放，尾部覆盖「明确逐帧」「普通概览（拒绝）」「Job 结果」三种。

| 指标（候选，49,474 input） | 实测 | 门槛 | 判定 |
|---|---|---|---|
| 排除冷启动后的整体命中率 | **99.63%** | ≥99.5% | 通过 |
| 预热轮逐请求命中率 | 99.61%（cached 49,280） | — | — |
| 逐请求相对预热轮最大下降 | 0（Job 尾部 +0.05pp） | ≤0.5pp | 通过 |
| 前缀字节一致性 | 4 组复放 cached 完全相同（49,280）；prefix_sha 固定 | 完全一致 | 通过 |
| 未命中 token 波动 | 167–194（Job 尾部首次 167） | 采样范围内 | 通过 |
| 授权/拒绝双尾部 | 概览尾部 99.63%，与逐帧尾部共用同一前缀 | 只改尾部 | 通过 |

基线未超过 99.9%，因此适用 99.5% 门槛，不触发 99.8% 条款；候选比基线高 0.11pp。

**阈值敏感性（如实披露）**：同一序列在 33,052 input 时整体为 **99.49%**，比 99.5% 差 0.01pp——
短前缀下尾部占比变大就会擦线。这不是代码回归（前缀字节一致、复放 cached 恒定），而是该绝对门槛
依赖长上下文的固有性质；验收口径以长历史场景（§7.3-5 的「长历史」前提）为准。

**采样与停止**：候选 4 组完整采样（4 组指标完全一致）、基线 2 组（第 3 组按用户要求中途停止，
未计入）；短前缀候选 1 组。合成确定性文本，无媒体、无用户数据；单一供应商/模型/OpenAI Chat 协议。

抖动记录（短序列）：同一序列在不同组之间出现 1 次 400（手写 tool_calls 桩）、1 次空正文（推理吃满输出预算）、
1 次 0 命中（路由到另一通道）。均为中转侧抖动，已按多次采样报告，未挑选高命中样本。

## 5. 设计取舍与已知限制（沿用交接 §5，另有补充）

- detached 用显式列表达，不复用「空父 ID」；`origin_run_id` 只做审计，不建立取消级联。
- 精确模式独立目录树 `uploads/video_frames_exact/`，仍受「同一视频跨参数目录 ≤ 600 张」约束；
  因此 `EXACT_MAX_FRAMES=3000`（单 Job 预检）在长视频上通常先被 600 张容量检查拦住——
  这是有意的双重护栏，不是漏检。单参数目录 200 张的严格口径仍未单独实现（精确模式按 Job 口径，见交接 §6）。
- 时间区间续跑仍是「从头解码 + 跳过已提交帧」（无损但慢）；要优化需在 checkpoint 存 seek 锚点，改之前先写测试。
- `video_frames` 仍不在 `JOB_SUPPORTED_KINDS` 内：只能走专用工具，避免绕过意图与范围校验。
- 重启恢复走 `interrupted`，不自动续跑；checkpoint 保留供显式 retry。
- manifest 已有 HTTP 接口，但**尚未做浏览器内的帧清单浏览/预览 UI**（本次范围只到接口与任务面板可见）。
