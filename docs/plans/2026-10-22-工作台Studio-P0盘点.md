## 2. 模块边界与生成链路核验（P0 修订版计划）

按修订版计划 §「代码归属与依赖边界」：

- `naiba/studio/` 新域：`catalog.py`（只读目录）、`custom.py`（每条一个 JSON 的自定义库）、
  `store.py`（Studio 数据持久化）、`runner.py`（模型执行）、`jobs.py`（异步任务管理）、
  `service.py`（业务编排与 API 业务方法）、`handoff.py`（聊天交接 adapter）。
- `naiba/app.py` 装配 Studio 服务并注入 `config`、`ModelRuntime` 与交接回调；`naiba/http.py`
  只做 `/api/studio/*` 路由转发。Studio 业务规则不进 app.py/http.py。
- Studio 生成禁止 import `naiba/run/chat.py`、`ConversationRunManager`，不读写会话消息与
  `run_events`；不产生 chat Run。

### `ModelRuntime.complete()` 公共入口核验结论

public 入口（已逐项核对源码）：

- **profile 解析**：`config.profile(model_key)`（`naiba/config.py::profile`）返回完整 provider
  配置（kind/model/base_url/api_key/context_window…），支持 `online:<id>` / `local:<id>` 与默认
  回退；`app._resolve_model_profile(body)` 是现成的非会话解析入口。会话里的 `model_name` 覆盖
  （`profile["model"] = 名称`）与本地模型窗口探测（`naiba/llm/local_probe`）逻辑需要 Studio
  自行编排，不 import run/chat.py 的 `_profile_with_model_override`。
- **options 键**（已核对生产点）：`stream`（默认 False，True 走流式）、`reasoning_enabled`、
  `cancel_event`（threading.Event）、`lock_label`（本地锁占用标签）、`temperature`、`max_tokens`、
  `connection_test`、`request_timeout_seconds` / `first_byte_timeout_seconds` /
  `stream_total_timeout_seconds` / `reasoning_stream_break_chars` / `request_attempts`、
  `tools`（Studio 不传 → 无工具）、`online_payload_budget_bytes`。兜底护栏用
  `config.runtime_guard_options()`（first_byte/max_steps 两道保险，config 域可直用）。
- **status 回调 payload**：`{"type":"status","message"}`、`reasoning_start/reasoning_delta/reasoning_end`、
  `{"type":"delta","content"}`。**没有 usage/finish_reason 增量事件**——用量与终止原因只能
  在 complete() 返回后从实例属性 `last_usage` / `last_reasoning` / `last_finish_reason` /
  `last_diagnostics` 读取（与子 Agent 现状同一套）。
- **取消能力（P3.2 重点核验）**：cancel_event 在 HTTP 打开（`_urlopen_cancelable`）、响应读取
  （`_read_response_cancelable`、本地/在线流式循环）与重试等待（`cancel_event.wait(delay)`）
  全程被消费。**取消能中断底层请求**，任务终态不会假报成功。
- **并发边界（重要）**：`last_usage/last_reasoning/last_finish_reason` 是 ModelRuntime 实例属性，
  两个并发 complete() 会互相覆盖读数。本期处置：**Studio 生成任务串行执行**（单 worker 队列，
  同一时刻最多一个生成任务在跑）：单用户桌面场景收益大于损失，本地模型本来就要排队，
  换来用量/思考/终止原因取数正确。该边界如实写入 P4/P5 汇报（如后续需要并行，先给
  complete() 增加按调用收Usage 的捕获钩子，再解除串行）。
- 既有先例：`app._test_provider` 就是"非会话直调 complete()"的同款用法
  （system+user 消息、`{"stream": False, "connection_test": True, "lock_label": 连接测试}`），
  Studio 复用同一形态不违反"不另造 provider 客户端"。

## 3. 任务/事件/持久化（Studio 自有生命周期）

- 任务记录：`data_dir/studio/tasks/<task_id>.json`（状态、输入摘要、result、error、usage、
  handoff 指针）+ `<task_id>.events.jsonl`（增量事件流，cursor 读取；字体全部 UTF-8）。
- 任务状态机：`queued → running → done | cancelled | failed`；服务启动时把遗留 `running` 收敛为
  `interrupted`，并从 events 重建已产出的部分结果（可重试）。
- 事件 type（登记进 `naiba/core/contracts.py` 的 `STUDIO_TASK_EVENT_TYPES`）：
  `status / reasoning_delta / delta / usage / done / cancelled / error`。前端 22-studio.js 仅
  通过 `/api/studio/*` 消费，不接触 `/api/runs`。
- 写入：同目录临时文件 + `os.replace` 原子替换；events.jsonl 追加行，不整文件重写。

## 5. P4 增量决策（用户反馈）

- 「用户输入」是一级输入位：生成表单为 条目（可选：自由输入 / 预设 / 自定义）→ 变量填空 →
  **用户输入框（主输入，加紫色边框突出）** → 模型选择 → 生成。未选条目即"自由输入"模式。
- 变量只是模板作者的填空位（{{key}} 字面替换），不是"参数微调"；模型参数（温度/长度）
  一律跟随用户自己的模型设置，模板不携带参数、条目的 `model` 字段仅作为建议展示。
- 自定义库（我的 tab）提供 导入（.txt/.md/.json）/ 编辑 / 导出 / 删除（导入入口统一走
  `POST /api/studio/custom/import`，同一前后端动作）。
