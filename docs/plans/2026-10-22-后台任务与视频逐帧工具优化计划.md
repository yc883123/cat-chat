# 后台任务与视频逐帧工具优化计划

- 日期：2026-10-22
- 状态：**研究与实施方案，尚未修改实现代码**。
- 核查基线：`master` @ `25cf2e0d`（3.6.2-beta），并参考本次已读取的工作区代码。其他模块仍在并行修改；实施前必须重新记录提交号及相关文件差异，不能把其他模块改动算成本计划效果。
- 范围：后台任务工具的选用、shell 参数与查询语义；视频信息探测、抽样与精确逐帧分批；两条链路共同的前缀缓存保护与实测验收。
- 前置计划：[长任务后台工具默认开放](2026-10-20-长任务后台工具默认开放计划.md)、[媒体工具提示与缓存稳定](2026-10-21-媒体工具提示与缓存稳定计划.md)。本计划承接已经实现的能力，不重复恢复预设工具、不改工作台模块。

## 1. 总体决定

1. **长命令在启动前创建 Job。** 清除提示词里将 `pwsh` 与后台执行并列的含糊表述，为 `run_in_background` 提供明确的 shell 参数契约和一个固定示例。
2. **保留同步与后台的区分。** 直接调用 `pwsh` 仍是对话内工具执行，不伪装成后台任务；只有实际创建的 Job 才进入任务列表。不实施运行一段时间后接管进程，也不超时后重新执行一遍原命令。
3. **保留视频抽样工具并新增正式工具 `extract_video_frames_exact`。** `probe_video` 读取元信息；`extract_frames` 继续做时间点/时间间隔/画面变化抽样；唯一逐帧工具名为 `extract_video_frames_exact`，只在当前用户明确要求逐帧时创建独立 `video_frames` Job。该 Job 默认只抽取并交付逐帧 manifest，不等同于逐帧反推。
4. **新逐帧工具执行时硬门控。** schema 在工具集启用后静态暴露以保护缓存；后端用当前用户原文校验意图，未明确要求、明确否定或仅要求概览/播放时不得创建 Job 或写帧。精确抽取不得均匀裁减帧，也不得把抽样或部分失败的结果说成完整逐帧。
5. **缓存“几乎不变”是发布条件，不是设计口号。** 固定提示、schema 和既有历史字节稳定是必须条件；同供应商、模型与可比负载下的预热命中率和未命中 token 还要通过第 7 节量化门槛。任一核心场景不达标，不得将本优化标为验收完成。
6. 本次只写计划，不启动真实供应商调用、不重启正式/开发实例、不提交或推送代码。


## 2. 研究结论与证据

### 2.1 后台工具已经开放，剩余问题是选用与契约

- `naiba/config.py` 的标准、长会话和 ComfyUI 预设已包含后台五件套；旧会话的工具集仍按 `naiba/run/session.py::bake_session_tool_ids` 固化。不能继续套用旧诊断中“默认预设都没有后台工具”的结论。
- `public/js/08-conversations.js::renderRunTasks` 与 `/api/tasks?jobs_only=1` 排除 `chat` / `plan_execute`。直接 `pwsh` 只产生对话的工具事件，不创建独立 Job，因此不会单独进入后台任务列表。
- `naiba/skills/agent.py` 同时存在“批处理、轮询写脚本”“耗时任务用后台”的指引；`comfyui_script_guide_text` 仍写“pwsh 或 run_in_background”，没有明确区分长短任务。
- `naiba/tools/registry.py::build_job_tool_specs` 对 `spec` 只有泛化对象说明，没有声明 shell 的 `command`、`cwd`、`timeout` 层次。schema 列出 `agent`，但 `JobRegistry._workers` 没有 `agent` worker；创建器把 `kind` 原样传给注册表，没有别名转换。推荐在创建入口把旧 schema 中的 `agent` 显式归一为 `subagent`，验证必需的 `instruction` 并持久化统一 kind；未知类型创建前拒绝，避免 Job 已登记后才以未知 worker 失败。
- 后台 shell 的缺省墙钟是 120 秒、最高 7200 秒；同步 `pwsh` 最高是 900 秒，`run_skill_script` 最高是 7200 秒。以实际代码为准，不沿用注释中“三者都一样”的说法。
- `job_wait` 缺省等待 600 秒。`JobRegistry.wait` 到期可返回仍在运行的快照，但 handler 目前把非 completed 状态统一返回失败并称“Job 结束”，可能误导模型重复提交或认定任务失败。
- shell worker 的缺省目录来自应用全局配置，而创建器没有自动将当前对话工作区写入 `params.cwd`；示例和实现都必须避免漏填后落入错误工作区。
- `SkillAgent` 还有 `_pending_background_jobs` 收尾检查：普通子任务 Job 未结束时，本轮会要求模型继续收集终态。因此“创建工具立即返回 ID”不等于普通后台任务会让这轮聊天立即结束、释放输入互斥位。新增 detached `video_frames` Job 必须从该收尾集合中排除，才能与主聊天并行；本计划不改变普通 Job 的收尾语义。

### 2.2 视频存在真实精度缺口，不只是调用次数问题

- `probe_video` 读取容器/流元数据。`frame_count` 可能为声明值，也可能由时长与帧率估算，已有 `frame_count_estimated` 标记。不能承诺一定只读固定大小文件头，也不能把估算帧数当成精确逐帧范围或 EOF 依据。
- `extract_frames` 目前只有 `times`、`interval`、`keyframes`。默认 8 帧、硬上限 12 帧；时间点候选过多时执行 `_trim_evenly`，这是抽样，不是连续分页。
- 新增工具不复用 `extract_frames` 的抽样上限语义：`extract_video_frames_exact` 由明确逐帧意图触发，创建 `video_frames` Job，按用户指定的时间区间或帧范围顺序解码，结果写入带帧号的 manifest；Job 只交付抽取事实，不默认调用视觉模型。
- **本次对已有 24 fps 夹具做了实际解码核查：** `interval=1/24` 生成的时间网格被舍入为三位小数。请求 `0.042s` 实际取到 `0.083333s` 的帧，后续请求 `0.083s` 又取到同一帧；请求 `0.167s` 取到 `0.208333s`。这会漏帧、重复取帧，不能宣称只要分段并设 `interval=1/fps` 就能严格逐帧。
- 当前返回帧记录的 `t` 是请求时间，不是解码帧的真实时间。精确逐帧必须返回实际帧序号和时间戳；旧模式不能无说明地更换 `t` 含义。
- 同一视频跨参数目录最多 600 个 PNG，单参数目录最多 200 个 PNG；联系表也计数。它不是无限视频导出能力，且张数护栏不等于磁盘字节预算。
- 视觉装载形态每次只把结果中的前 4 张编码为图像部件；同一工具调用的剩余图片不会自动在后续请求中全部看完。分析形态也只分析本次允许数量，并提示传剩余路径继续调用。截图中的“自动分批”不能作为无限自动续读的承诺。
- 在线多模态历史通常保留已有图片；本地历史滑动图片限制当前默认关闭。不能为了新逐帧功能重新启用滑窗、折叠或改写早期图像消息，那会破坏缓存共享前缀。
- 工具抽取数量、模型实际看过的图片数量和消息媒体卡片数量是三件事。消息汇总图像卡片上限为 20，部分相同图片/同名产物还会在展示链路去重；不能由卡片数推断是否抽全或分析完毕。

## 3. 后台任务优化方案

### 3.1 统一固定选用规则

规则只依赖会话冻结的 `allowed_tools`，相同工具集输出相同文本。建议固定规则：

> 可用时，预计超过 30 秒、需要持续轮询/等待外部生成、或耗时不确定的长脚本，必须在执行前创建后台 Job；不得先用 pwsh 启动再等待，也不得用加大 pwsh 超时来代替 Job。已有 ComfyUI 工作流使用 comfyui_batch，自定义长命令使用 run_in_background 的 shell 类型。短的一次性检查或单次状态查询才用 pwsh。创建成功后使用真实 Job ID 查询，已提交不等于已完成。

- 30 秒是建议的模型选用阈值，不是同步执行器硬超时，也不要求先执行命令测时。
- “批量”不一律等于长任务：生成工作流文件等短时准备可同步；批量生成、持续等待、长时间转码等执行段必须走 Job。
- 去掉“脚本可用 pwsh 或 run_in_background 执行”的等价表述；统一说明脚本的编写与执行入口是两个决策。
- 当前会话没有通用后台创建器时，不提不存在的工具，不声称任意子 Agent 创建器等价于 shell Job；只有专用 ComfyUI 创建器时只指导其支持的任务。
- 对已确认仍在运行的任务不能重新启动；查询失败或等待到期不能变成再次提交付费生成/有副作用脚本的理由。

### 3.2 shell 参数与固定样例

在现有 `run_in_background` 中完善 `spec.kind`、`spec.label`、`spec.params` 的结构说明，不新建另一套后台工具。shell 参数如下：

| 字段 | 含义 |
|---|---|
- `spec.kind` | `shell`；其他类型照各自已有/未来契约验证，不把 schema 展示名当作 worker 支持保证 |
| `spec.params.command` | 要执行的 Windows PowerShell 命令，不能为空 |
| `spec.params.cwd` | 当前任务的工作目录；省略时由创建器冻结当前 Run 工作区，不在 worker 启动时读取变化后的全局设置 |
| `spec.params.timeout` | 整个命令墙钟秒数；长任务显式填写，范围 1–7200 |
| `spec.label` | 面向用户的简短任务名 |

固定样例使用语义根占位符，实际调用时替换为当前已知绝对路径，不把任务名/路径/ID 动态填进 system：

```json
{
  "spec": {
    "kind": "shell",
    "label": "运行批量处理脚本",
    "params": {
      "command": "python -u '<工作区绝对路径>/scripts/batch.py'",
      "cwd": "<工作区绝对路径>",
      "timeout": 3600
    }
  }
}
```

实施约束：

- 样例只出现一处固定指引，不在多个工具描述里重复；工具顶层描述继续遵守不超过 100 字、3 句的守门规则。
- `params` 兼容其他实际支持类型的字段，不能为了 shell 描述清楚而禁掉 ComfyUI/HTTP/子 Agent 参数。优先用基础对象 schema 加类型相关运行时校验，避免未经验证地引入供应商不支持的复杂条件 schema。
- 错误 kind、非对象 params、缺 command 等在创建 Job 之前失败，不能先报“已提交”再由未知 worker 立即失败。
- shell 缺省超时本阶段仍为 120 秒、上限仍为 7200；规则与样例明确长任务必须填超时。提高缺省生命周期不是本次既定方案，不能悄悄把所有漏填任务改成两小时。
- 沿用现有审批、会话工作区、取消和所有者边界；不能因改用 Job 而绕过相同命令原本需要的批准。冻结版 Python/Skill 脚本调用方式必须按当前支持入口验证，不能假定所有安装环境都有 `python` 命令。

### 3.3 查询语义与任务列表

- `job_wait` 等待到期但 Job 为 queued/running/waiting 等活动态时，返回“本次等待到期，任务仍在运行”的正常快照；不返回“Job 结束（running）”的失败文本，也不取消任务。
- completed、failed、cancelled、interrupted 分开表述；中断不能伪装成完成或自动续跑。兼容当前文本返回通道，不为该修复重写全部 Job API。
- shell 运行超时与 `job_wait` 等待到期是两种不同事件，测试分别覆盖。
- 保留任务列表只显示真实 Job 的设计，直接 `pwsh` 仍只显示对话工具卡片。用列表接口与浏览器验证真实 shell Job 的日志、状态、停止及完成记录。
- 本次不改变普通后台 Job 的 `_pending_background_jobs` 收尾规则；detached `video_frames` Job 必须排除在该集合之外，不等待其终态。若后续要求普通 Job 也采用“用户选择只提交后本轮立刻结束”，需另外设计显式交接与父子取消语义，不能靠提示词假称本次已经支持。

### 3.4 能保证什么

- 可以硬保证参数校验、真实 Job 登记、状态解释和工作区快照，保证不将查询当成创建。
- “长任务先创建 Job”在本阶段是清晰的模型行为约束，必须做目标模型遵循率验证；仅靠提示词不能声称任何模型都不会误选同步命令。
- 不用关键词拦截任意 PowerShell 来冒充可靠时长预测；不超时后自动重跑；不改变 `pwsh` 已运行进程的归属。若明确需要执行层绝对兜底，再设计同步硬时限/进程接管，另行评审。

## 4. 视频探测与精确逐帧方案

### 4.1 保留原有能力，修正说明

- `probe_video` 仅用于元信息；用户只问时长/分辨率/帧率时不抽帧、不做视觉分析。
- 原有 `times`（指定时间点）、`interval`（固定时间抽样）、`keyframes`（画面变化抽样）不改用途和默认输出数量；工具说明改为“默认 8、单次最多 12”，不再写“单次最多 8”又在 max 中写 12。
- 原模式的 `t` 保持请求时间兼容；可加 `actual_t` 明示实际帧时间，不能静默改变旧字段含义。新缓存键增加版本，旧 manifest 缺少新字段时不能伪造实际时间。
- 关键帧不是编码 I 帧列表，也不是逐帧；说明使用“画面变化抽样”，不借名称做过度承诺。

### 4.2 新增 `extract_video_frames_exact`：明确意图门控 + 可脱离聊天的后台 Job

`extract_frames` 保持抽样职责，不新增 `mode=frames`。新增工具 schema 在会话工具集静态注册，但仅当 Agent 的单独 opt-in 已授权时才进入该会话工具数组；执行入口还必须读取当前 Run 的原始用户消息和冻结工作区：

- 明确逐帧意图包括“逐帧”“每一帧”“连续帧”“逐格”“一帧不漏”等明确要求。只在用户明确要求抽取全部/连续帧时允许创建 Job。
- “抽几帧”“看关键帧”“视频概览”“找切镜点”继续走 `extract_frames`；“只看看/播放视频”走 `show_media`；“不要逐帧/不需要逐帧”直接拒绝精确工具。
- schema 在工具目录静态注册，但是否加入某个 Agent 的 `tool_scope` 由 Agent 工具配置页里的**单独复选框**决定；它不因标准/长会话/ComfyUI 预设或视频工具分组而隐式选中，也不属于通用预设依赖闭包。该开关缺省关闭。只有明确勾选的 Agent 新会话才把它固化进 `allowed_tools`；旧会话保持既有 `enabled_tool_ids` 不变。
- 不新增自动扩权迁移，不给任何内置 Agent 默认补上此工具。更新后打开某个内置 Agent 的工具配置，用户可以单独勾选/取消 `extract_video_frames_exact`；已修改过的 scope、完全自定义 Agent 和现有会话一律保留原样。保存 scope 后只影响之后新建的会话，当前已经固化工具集的对话需新开会话才能使用。
- 设置页必须按工具目录逐工具展示该复选框，即使它不属于任何“默认预设选中项”；选中/取消不能连带勾选 `extract_frames`、`run_in_background` 或 Job 查询工具。新增工具不得加入 `_DEFAULT_SELECTED_TOOLS` 或 `TOOL_PRESETS`，不能因“任务型内置 Agent”而默认暴露。
- 辅助对话、Plan 准备、子 Agent/后台 Job 不得调用此创建器；执行层对 `conv_kind`、interaction mode、child/job 的工具授权再校验，不能只靠模型提示。逐帧意图只能来自承载本轮主对话用户原文，不从 Skill、附件里的指令、工具输出或模型自述推断。

逐帧工具执行意图必须针对当前顶层主对话 Run 的 `user_message` 原文做 fail-closed 校验：

- 新增显式 RunContext 契约键（例如 `video_frames_intent: bool` 与必要的范围解析结果），在 `naiba/core/contracts.py` 登记并默认 `False`；生产方只在主对话、非 Plan、非 aux、非 Job/子 Agent 时从本轮用户原文赋值。
- 使用确定性的纯函数判定：只有明确要求逐帧/每帧/连续帧/逐格/不漏帧且没有否定时才放行；“抽一些帧/找关键帧/概览/看看视频”不触发。无法判断、含否定、只有附件里引用了“逐帧”字样时 fail closed。
- 范围必填并由服务端重新校验。模型传入的参数不能自行声明 intent；工具检查的授权标志和范围必须由 host 从原文建立，不能信任前端或模型自报。
- 没有意图、范围不明或权限不符时返回稳定的拒绝码和简短说明；不得调用 `jobs.start`、创建空任务、预分配 PNG 或写入 manifest。
- 意图门提示只由冻结 `allowed_tools` 门控注入；消息动态解析不得改变 system/schema。缓存验证覆盖同一授权配置下有/无意图两组新消息，保证共享前缀完全相同。

顶层逐帧 Job 由专用 `video_frames` worker 执行，不经过通用 shell，避免模型绕过权限与结构化范围，或把长视频解码命令重新走 `pwsh`。

建议参数：

```json
{
  "path": "<视频文件绝对路径>",
  "start": 0.0,
  "end": 5.0,
  "max_edge": 1600
}
```

或者按解码帧号指定半开区间：

```json
{
  "path": "<视频文件绝对路径>",
  "start_frame": 0,
  "end_frame": 120,
  "max_edge": 1600
}
```

内部按实际解码顺序保留范围内每一帧，不能使用 `1/fps` 时间网格、`_trim_evenly` 或画面差异筛选。时间范围与帧范围同时传入时创建前拒绝。

每帧 manifest 记录至少包含：

```json
{
  "frame_index": 0,
  "pts": 0,
  "timestamp": 0.0,
  "path": "<托管帧路径>",
  "status": "extracted"
}
```

结果总览至少包含 `status`、`frame_count`、`first_frame`、`last_frame`、`manifest`、`failed_frames`、`range_complete`。抽取成功只代表帧文件和清单完整，不表示视觉模型已逐帧分析或已生成提示词。

### 4.3 新工具的逐帧 Job 与反推边界

- `video_frames` worker 按可中断的小块顺序解码；每块最多暂存/转换 12 帧，但须处理指定范围内的全部帧。小块只是 worker 内部资源控制，不是要求模型多次调用的“逐帧分页模式”。
- 每次 `extract_video_frames_exact` 调用创建一个 detached Job，使用 `detached=true` 和独立 `origin_run_id`；不能只用 `parent_job_id=""` 表达 detached，因为现有 active-run 检查把无父 ID 的活动行视为顶层 Run。
- 新增数据库字段/查询条件，使 detached `video_frames` Job：进入 `/api/tasks?jobs_only=1` 列表，但不占 `active_run` 互斥位、不出现在“当前正在回答”的 `list_primary` 结果、不被 `_pending_background_jobs` 等待；普通 `chat` / `plan_execute`、父子 Job、取消级联和 run 恢复语义保持不变。`origin_run_id` 只用于审计/来源显示，不作为父子取消关系。
- 创建工具向 Job snapshot 写入视频指纹、半开区间、输出设置、origin run、owner 和格式版本；检查重复的同一 owner + 同一视频指纹 + 同一区间活动任务，幂等复用同一 Job。不同会话/不同范围不跨 owner 复用。
- Job checkpoint 持久化最后已提交帧号、manifest 版本/位置和失败帧。每块结果原子提交；取消时完成当前安全解码边界后停止，保留已成功帧并把其余部分标为 pending/failed，不能把半成品标成 `range_complete=true`。
- 服务重启时选择并测试：恢复机制能校验视频指纹且从已提交帧无损续跑才标记 resumable；否则启动时转为 interrupted，由用户显式重试。不能因为 checkpoint 存在就宣称系统已能恢复。
- 顶层 detached Job 不因聊天 Run 正常完成或用户取消聊天而被级联取消；聊天取消接口只取消该 Run 和普通父子子任务。任务面板停止按钮单独校验 owner 并向 Job 发取消信号；manifest 仍归属原发起会话。
- 任务列表与 `job_status` 返回范围、预计/完成帧数、状态、错误和受权限保护的 manifest 引用等紧凑摘要，不包含所有帧路径。新增独立 manifest 分页/下载接口，服务端用 Job ID + owner 校验定位托管文件，不接受客户端任意文件路径；Job 结果不回写旧聊天消息、tool_runs、trace 或全部帧媒体卡。
- 提交前按实际范围与当前视频缓存占用检查 200/600 PNG 护栏。容量不足就整项拒绝，不自动截断、不删除历史引用帧、不抽取一部分后谎称完整。逐帧模式默认不生成联系表。
- 逐帧抽取不会自动反推提示词。若用户后续明确要求逐帧反推，另创建分析任务读取 manifest，按 vision 模型每批最多 4 帧处理；每条记录包含 frame_index、timestamp、独立结果或失败原因，写入 JSONL/CSV。只有范围内每帧均有结果或明确失败记录，才能报告逐帧反推结束；抽取成功不等于分析成功。

### 4.4 工具注册与 Agent 单独开关

- `extract_video_frames_exact` 是唯一正式逐帧工具 ID；在 `naiba/tools/registry.py`、`naiba/tools/providers/video.py` 独立注册，不给 `extract_frames` 增加 `mode=frames`。工具说明在现有 100 字/3 句预算内强调“只在用户明确要求逐帧时使用”。
- **Agent 工具配置页为它提供独立复选框，缺省关闭。** 不把它混入现有 `tool_scope`；在 Agent 配置记录新增专用 `tool_opt_ins: ["extract_video_frames_exact"]`（或等价、白名单化的可选能力字段）。用户可在每个 Agent 的“工具配置”中单独勾选/取消；该字段不跟 `extract_frames`、标准/长会话/ComfyUI 预设、全选、分类全选或任务型 Agent 批量联动。选中时只是授权此静态 schema 纳入该 Agent 新建会话的 `allowed_tools`，不是按某一轮消息动态改变工具数组。
- 保持旧 `tool_scope` 语义完全不变：`[]` 仍为“不限制”，全能预设仍代表当时的全部普通工具；`tool_opt_ins` 是一个严格 opt-in 扩展，默认空，不因空 scope、旧会话兼容回退、`group:*`、应用预设或 Agent 新建默认工具而获得逐帧工具。不要将该工具加入 `EXPLICIT_OPT_IN_TOOLS` 后又无意在全能 `group:*` 中放行；应将其从普通工具展开/旧会话 `all_tool_names` 里排除，再仅按配置显式并入。
- 新建会话的工具固化 = 普通 `tool_scope` 解析结果 + 已登记且当前 Agent 明确勾选的 `tool_opt_ins`。已固化会话只按自己的 `enabled_tool_ids`；配置页取消 opt-in 不追溯改变它，未固化的旧会话回退到“全工具”时也必须排除新增 opt-in 工具。
- 设置页在全开/不设限状态下仍将该复选框单独显示为未勾选，并标注需单独授权。用户显式勾选/取消后保存 `tool_opt_ins`；不能把普通 scope 里的 `extract_frames`、`run_in_background`、Job 查询器或其它工具增删当成副作用。全选/预设操作不得改变该字段。
- 同步 Agent 配置 API 的读写/校验、`ConfigStore` 默认数据与导入导出，以及工具目录/排序和 Agent 编辑页测试；已保存配置缺字段按空列表处理，不做自动授权迁移，不改旧 Agent scope 和所有旧会话工具快照。
- `tool_opt_ins` 只允许登记过的 opt-in 工具 ID，服务端对非法值拒绝或剔除并给出确定行为；scope 展示计数需区分普通工具与单独授权项，不能让预设匹配或 `toolScopeLabel` 把逐帧 opt-in 误判成纯标准预设。


## 5. 两条链路共用的缓存设计


### 5.1 固定前缀

- 逐帧工具 schema 在工具集固化时静态存在；本轮的授权值只放 RunContext/工具调用参数并经后端重验，不能改变 system、工具声明或排序。
- 固定意图规则使用泛化稳定文字，例如“仅在用户本轮明确要求逐帧时执行”，不把当前用户原文、命中的关键词、帧范围或媒体路径嵌入规则/schema。
- 不根据本轮是否长任务、视频是否存在、逐帧授权结果、当前帧号、Job 数量、是否命中文件缓存来切换 system 片段。
- 工具 schema 固定，不临时删掉 `pwsh` 强迫模型选 Job，也不每次换一种 schema 推荐某个视频模式。
- 完整样例只出现一处；删除已有重复/冲突规则后再加必要说明，控制净新增前缀 token。通过实际请求分词测量，不用字符数代替 token 数。

### 5.2 动态内容只追加

- Job ID、状态、日志、帧号、页游标、路径、实际 PTS、附卡事实只出现在对应调用的新结果或当前新消息中。
- 已发送的结果作为 trace 原样持久化、原样重放；Job 后来完成、视频文件后来变化，都不能回填旧工具消息而改变它的历史字节。
- 动态提示若确实必要，追加在当前消息尾部并进入 trace，不能反复插入会话最前面。
- 不重写旧视频附件引用行以添加新模式说明。优先在固定 system 中更新流程；如必须修改新附件行，需要版本化/保存首次形成的模型可见文本，防止旧消息每轮用新函数重建出不同字节。
- 不改变图片编码质量、内容字节、历史保留策略、模型切换策略或 Anthropic 缓存断点。本次不是全量缓存系统重构。

### 5.3 允许与不允许的缓存成本

- 修改 system/schema 后，旧版本前缀可能需要一次冷启动。允许单独报告这次成本；重新预热后的连续请求必须满足“几乎不变”门槛。
- 新的图片和工具结果本身是新增输入，会有必要的未命中 token；必须与旧历史前缀失效区分。新增内容不能解释无关纯文本场景持续退化。
- 不以不断加长固定提示来“刷高命中率”。同时检查未命中 token 与任务完成总输入/请求数；比率通过但总成本明显变高也不能放行。

## 7. “缓存命中几乎不变”的强制验收

### 7.1 应用侧 opt-in 与前缀确定性：必须全部通过

- `extract_video_frames_exact` 只经 Agent `tool_opt_ins` 并入新会话的 `allowed_tools`；同一 Agent/会话下，用户消息从普通概览变为明确逐帧要求时不会动态增删 `tools`。
- 测试两种静态授权快照：显式勾选时 schema/tools 固定包含该 ID；未勾选时 schema/tools 不含该 ID。授权差异只发生在 Agent 配置变更并创建新会话时，不由本轮句子触发动态 schema。
- 意图门结果（授权/拒绝）只改变本次工具调用是否产生副作用和新增结果；system、schema、旧历史与工具排序逐字节不变。
- 空普通 `tool_scope`、全能模式、工具分组全选、预设、配置导入及旧会话未固化回退都必须排除 opt-in 工具，各自有确定性权限测试。
- Job 从 queued/running 变为 completed/interrupted、manifest 从摘要变完整文件时，只允许独立任务快照/manifest 接口内容变化；不回写/改写旧聊天消息、trace 或历史图片。
- 实时发送、存储、下一轮 `build_model_history`、协议转换后重新发送，保留相同共享前缀；测试 OpenAI Chat/Responses 与 Claude 路径。
- `NAIBA_DEBUG_CACHE=1` 的摘要用于定位分叉；必须比较原始序列化文本/图像部件，不以 hash 相等代替内容审查。

### 7.2 真实供应商对照：不是单测替代品

固定同一供应商、模型 ID、端点、思考选项、工具集、Agent、图像参数、上下文长度档位和测试素材。至少覆盖：

| 场景 | 检验重点 |
|---|---|
| 纯文本短历史与长历史 | 无功能使用时不能产生缓存退化 |
| 一次短 pwsh 后追问 | 同步工具与旧历史回放仍稳定 |
| 未勾选/已勾选两个 Agent 工具快照 | 未勾选时会话 `tools` 不包含 `extract_video_frames_exact`；勾选后新会话静态包含。相同快照内普通概览/逐帧语句不改变 schema |
| 同一 Job 的 queued/running/completed/interrupted 与 manifest 读取 | 变化只出现在任务列表/owner 授权的 manifest API；不改对话消息或历史前缀 |
| 明确要求逐帧、普通概览、用户否定、引用素材含“逐帧”、缺少范围 | 仅已 opt-in 的主对话可以通过明确意图门创建 Job；其它情况零副作用 |
| manifest 摘要与完整结果追问 | model-visible Job 结果只含 Job ID/范围/状态/结果接口引用，不含全路径清单；历史重放字节稳定 |
| 只查询视频元信息 | 不额外抽帧/载图，后续缓存稳定 |
| 普通视频抽样、视觉读取、追问 | 旧视频使用路径无回归 |

使用三个互补实验，并明确区分“跨版本等价对照”“固定 opt-in 快照内的前缀测试”和“模型工具选择实验”：

1. **跨版本等价缓存实验。** 只对 baseline/candidate 都能执行的功能场景做严格 A/B（纯文本、短 pwsh、普通视频元信息/既有抽样）。固定动作序列与实际工具结果/图像输入内容，分别通过两版本的真实协议发出请求；固定提示/schema 有意变更的冷启动成本单列报告。该实验只判断旧路径是否退化。
2. **固定 opt-in 快照内的新增工具缓存实验。** 对“未勾选 Agent”固定运行工具集并验证新工具完全不进入 `tools`；对“已勾选 Agent”用全新会话固定包含的工具 schema。每种快照内部用普通概览、逐帧明确指令、意图拒绝三个后续请求比对 system/tools/共享消息前缀；Job 状态、manifest 生成与读取经独立接口，不能改写聊天历史。Job 创建结果只返回紧凑的 Job ID/状态/manifest 地址引用，对相同历史重放时字节应稳定。
3. **自然工具选择与拒绝实验。** 让目标模型按固定语料分别处理明确逐帧、普通概览、用户否定、附件引用内含逐帧措辞、未勾选 opt-in、无范围等请求。记录是否调用唯一工具、是否在 host 侧拒绝、是否零 Job/零写盘，以及长任务是否先选 Job；不同模型决策造成的不同工具序列只用于衡量遵循率与成本，不混入固定序列缓存命中 A/B。

旧功能场景两版本各做至少 1 个预热会话、3 个测量会话；新增工具的每种固定 opt-in 快照至少 1 个预热会话、3 个测量会话；每个测量会话至少含 3 次可比后续请求。固定语料和序列，交错执行，记录全部成功/失败样本，不挑高命中样本。

Job ID/随机任务标识不能进入固定 system/schema；固定序列缓存测试可在独立测试实例里重复同一 mock/已保存的 Job 工具结果字节，但不能替换真实会话里已经发给模型的 ID。manifest 使用同一固定结果引用或在独立 API 之外读取，不把整个帧路径清单塞回消息。候选配置的运行时输入采用与该配置一致的真实工具集，不能用 baseline 不存在的工具执行 A/B。

优先使用用户确认的 TE/摆烂测试供应商，不静默改走免费默认链。真实调用使用隔离数据和本地合成素材，凭据不落报告；测试预算与外发素材范围单独明确。不存在返回缓存字段的供应商时，不能用另一个供应商的结果冒充该供应商已通过。

### 7.3 通过标准

**以下全部是阻断条件，按场景分别计算，不能用纯文本好结果平均掉视频退化。旧功能使用版本间 A/B；新增 `extract_video_frames_exact` 功能使用 candidate 内部固定载荷的预热重复测试，不伪造旧版本对照。**

1. 第 7.1 节共享前缀测试全部通过。
2. 旧功能可比场景排除预热后，命中率使用 `cached_tokens / input_tokens`，同时报告逐请求中位数与加权总体值。两者相对基线均不得下降超过 **0.5 个百分点**；基线已达到 99% 以上的长历史场景，下降不得超过 **0.1 个百分点**。
3. 可比输入下 `cached_tokens` 中位数不得低于基线的 **98%**，同时检查长度和比率，不能靠缩短历史让命中 token 变少后还称已保住前缀。
4. 旧功能等负载实验中，未命中 token 中位数的增量不超过基线的 **5% 或 64 token（二者取较大值）**。对每场景报告规则净增 token、实际未命中增量和请求数，不能用加长固定前缀掩盖成本。
5. 新 `extract_video_frames_exact` 在 candidate 内对相同视频、相同用户原始授权消息、相同范围、相同解码结果和相同 Job 结果载荷做预热后的请求复放；排除首次冷请求后，共享请求前缀字节必须完全一致。固定语料必须包含明确授权与明确拒绝两种序列，证明是否创建 Job 只改变新增的本轮结果尾部，不改变 system/schema/既有历史。该场景的整条用户请求序列仍须达到通用目标：整体命中率至少 99.5%，若同模型同负载基线已高于 99.9% 则不得低于 99.8%；同时稳定预热后逐请求命中率相对 candidate 预热轮下降不超过 0.5 个百分点。未命中 token 中位数波动在重复采样范围内，新增视频 Job 结果的冷 token 单列报告。若新增请求使整条任务链达不到目标，必须调整结果/manifest 传递与历史设计并重测，不能用“这是新功能”豁免。
6. 同类任务自然执行的请求数/总输入若明显上升（超过重复采样波动或约 10%），必须给出必要新增处理量的独立说明；无功能收益的重复轮询、重复载图、长规则堆叠属于回归，不能放行。自然模型跨轮可能选择不同工具序列，该场景用于验收遵循率和成本，不用于声称请求字节必须相同。
7. 样本波动超过上述界限时，结论是“未证实通过”，检查供应商路由、有效期和请求前缀并重测；不能扩大阈值或换模型凑通过。

本计划比既有媒体缓存计划的“下降不超过 2 个百分点”更严格：用户当前要求是“几乎不变”，高命中长会话不能从 99.9% 下降到 97.9% 后仍被宣布正常。新功能整条任务链还要满足接近基线的绝对命中率；如果图片输入本身令供应商无法缓存并使指标不达标，功能仍可保留为未验收研究分支，但不得绕过门槛放入面向用户的默认路径。

供应商未提供缓存 usage 时，只能报告“应用侧字节稳定已通过，真实命中率未验证”，不得给缓存验收打勾。应用不能控制第三方 TTL、路由、配额或每次缓存调度；这里的保证是**代码不破坏前缀，且受测配置实测不达标就不发布**，不是对任意供应商、任意时刻许诺相同百分比。

## 8. 功能测试清单

### 8.1 Job

- [ ] 后台创建器与查询工具分别门控，缺工具不引导调用；只读/辅助会话不扩权，旧会话快照不改。
- [ ] ComfyUI 工作流仍走专用创建器，短准备可同步；批量执行/等待不再被并列引导到 pwsh。
- [ ] 固定 shell 样例经实际 handler 和 worker 桩验证，不只是 JSON 能解析；不支持的 kind/缺 command 在创建前失败。
- [ ] 显式 cwd 与 Run 工作区缺省快照正确，应用全局工作区后来变动不影响已提交任务；审批边界不放宽。
- [ ] 缺省 120、显式长超时、7200 上限、非零退出码、无输出时取消和超时均正确。
- [ ] `job_wait` 等待到期返回仍运行，不创建重复任务；真正失败/取消/中断与等待到期可区分。
- [ ] 真 Job 出现在任务列表，同步 pwsh 不出现；日志增量、完成状态和停止可用。
- [ ] 创建工具立即返回与主聊天等待终态的区别有测试，未授权改变收尾行为。
- [ ] 固定长任务语料至少 10 次有效目标模型运行中，先选 Job 且 shell 参数正确率至少 90%；任何重复副作用提交、虚构 Job ID 或未创建却宣称已后台的样本都单独阻断。该指标不替代运行时硬保证。

### 8.2 视频

- [ ] probe 元数据、估算标记与旧三个抽样模式回归通过。
- [ ] 24 fps 间隔网格的实测漏帧/重复现象有反例测试；`extract_video_frames_exact` 以解码帧序号和 PTS 对指定范围通过严格无漏/无重复断言，不依赖 `1/fps` 时间网格。
- [ ] 单次工具调用只创建一个 detached `video_frames` Job；Job 在 worker 内部分块处理完整范围，不需要模型传 `next_frame` 或再次调用抽帧工具续页。对半开时间/帧范围、空范围、负数、越界/EOF 都有确定的创建前校验和结果语义。
- [ ] worker 分块大小及边界正确；取消只在安全解码边界生效，已提交块可核对，剩余帧不会被报告为完整。manifest 分页游标稳定、无重复/遗漏，错误游标和跨 owner 读取被拒绝。
- [ ] CFR、VFR、非整数帧率、非零起始 PTS、B 帧或相应解码桩验证显示顺序与真实时间；不依赖平均 fps 推导索引。
- [ ] 相同画面的不同帧依然在 manifest 中保留；帧文件名在单 Job 的完整范围内唯一，不因 worker 分块或 manifest 分页而覆盖、去重。
- [ ] Job 预算、缓存幂等、旧 manifest 缺字段、源文件改变、200/600 张护栏正确；超限在创建前拒绝整个范围，不截断后谎称完整。
