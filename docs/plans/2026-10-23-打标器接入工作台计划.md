## 1. 目标与依据

**目标**：在工作台（Studio）里加第二个功能页「打标器」——批量给图片打标签/描述，存本地库，导出 JSON / CSV / .txt。

**依据**：

1. 本人发来的 tutu v1.3.0 拆解报告（`图图超级智能标注工具` 静态拆解），其 §四「打标器是怎么实现的」与 §七「最小可行架构」是本计划的功能蓝本。
2. 本人定调：**不做应用内本地模型打标**。模型一律来自设置里的 provider：云端 API 与
   Ollama / LM Studio / llama.cpp 这类本地后端都算 provider（2026-10-23 明确：
   「有 provider 就行，不要用小模型打标」）。
3. 既有代码核查（下文 §2 全部为实测行号，非推测）。

**核心判断**：不另起 Electron 壳。工作台已有「pywebview + WebView2 壳 / `naiba/http.py` 单进程 HTTP / 域模块 / Studio 任务持久化」结构，可复用界面、模型配置和任务基础设施；但打标器有批量逐图状态、幂等恢复和导出授权等新增契约，不能把 Studio 单任务生成器原样照抄。

### 2.3 一个更正：并发恐惧来自过时注释

`naiba/studio/runner.py:1-12` 顶部注释称「`ModelRuntime` 实例属性并发会互踩，同一时刻只跑一个生成任务」。
实测：`naiba/llm/runtime.py:632` 已是 `self._local = threading.local()`，`last_usage` / `last_reasoning` / `last_reasoning_id`（`:644-666`）与 `_FINISH_REASON`（`:107`）全部 thread-local。

⇒ `last_*` 读数是线程局部变量，但这只解决调用线程之间的诊断字段隔离，不证明多线程端到端安全、供应商限流可承受或结果与用量关联正确。`kind=local` 在 `complete()` 内有全局执行锁，实际串行。施工前必须按 §5 P0-a 实测，并在生产调用线程内立即捕获该调用结果及诊断信息；不得由管理线程读取 `last_*` 推断某一图片的用量。

## 3. 范围边界

### 3.1 本期做

- 侧栏「打标器」功能页 + 页签切换骨架
- Provider 打标：带图调 `app.models.complete()`，走现有 provider profile（云端或本地后端）
- 批量任务：提交 / 进度 / 取消 / 重试 / 断点续跑 / 恢复找回
- 标注落库（`labeler.db`）+ 导出 JSON / CSV / `.txt` 标签文件（归入受管导出包，不覆盖原图目录）。
- 打标侧重预设（LoRA 六档）+ 高级配置字段
- 句子库（规则分句，可检索）

### 3.2 本期不做

| 不做 | 原因 |
|---|---|
| WD14 / JoyCaption 本地模型打标 | 需 torch，包体积爆炸 |
| BiRefNet / SAM3 抠图 | 需 torch；SAM 受 License 商用限制 |
| 模型下载器 + sha256 校验、显存策略（懒加载/闲置卸载） | 无本地模型即无需求 |
| spaCy `zh_core_web_sm` 分句 | 规则分句兜底，后续可选 |
| 素材爬虫、视频处理、AI 生图、激活码、遥测上报 | 不在定位内 |

**留后路**：引擎按明确的 `engine` 标识扩展，本期只实现 `provider`（经 provider 调模型）。
模型 ID / tag 不承担安全或引擎路由职责；后续若要接应用内本地标注引擎，由独立适配层接入，
不改动前端页面结构。

**范围澄清**：允许所有已配置的 provider（`kind=online` 与 `kind=local`）。本地后端共用 runtime 的
全局执行锁，因此批次固定一次处理一张，并在每张开始前礼让进行中的对话 Run（聊天不被批量任务卡住）。
仍然**不接受**客户端提供的 `base_url` / `provider_info` / API Key：只认设置里已存在的 `model_key`。

## 4. 关键决策

| # | 决策 | 理由 |
|---|---|---|
| D1 | 打标器 = 工作台**功能页**，不是与「对话/工作台」平级的第三种模式 | 与模板同属生成域，共享任务/结果/交接基础设施；侧栏注释已预留此口子 |
| D2 | 唯一引擎 `provider`（云端与本地 provider 都走 `complete()`），不内置本地小模型 | 零新增依赖，exe 维持 81MB |
| D3 | 标注库用**独立 `data/labeler/labeler.db`**，不进 `chat.db` | 事务隔离，不污染消息库；清理策略独立 |
| D4 | 复用 Studio 的文件记录/事件流约定，但新增逐图事务化 checkpoint 存储；事件流仅用于通知和展示 | 现有 Studio 事件流与任务 JSON 不构成跨文件原子事务，不能单独保证计费安全恢复 |
| D5 | 并发数先由**探针**决定；初始默认 1，探针通过后才开放经验证的档位 | 供应商限流与逐图结果关联优先于吞吐；本地后端全局串行 |
| D6 | 图片编码复用现有视觉编码管线，经验证后再决定尺寸配置 | 避免重复实现；编码后的格式/MIME、尺寸和体积需有明确限制 |

## 5. 分期实施

### P0-a：并发探针（前置，不写业务代码）

- 在隔离实例对在线 provider 用 N=1/2/4/6/10 调用 `app.models.complete()`；每次响应使用可区分的假模型用量/内容，验证调用线程内返回正文、usage、reasoning、finish reason 的归属，并覆盖超时、取消和异常。
- P0-a 只验证 `app.models.complete()` 在线调用线程中返回值/诊断数据的归属、取消/超时行为与运行时并发边界；Labeler worker 调度、事件顺序和 SQLite 并发写属于 P1/P2 实现后的自动化测试，不作为未实现代码的前置探针。
- 判据：每个结果都关联到提交项；无错配/丢结果/重复计数；探针不代表所有供应商限流安全。业务初始并发固定为 1，用户调高的档位仅开放已验证值。
- 产出：一个 `verify/_probe_labeler_concurrency.py` 只读探针 + 结论写回本节。探针不得默认联网或触发真实付费调用。
- 不通过则保持串行；UI 只显示当前并发上限和用户操作说明，不暴露内部探针术语。

**P0-a 结论（2026-10-23 实测，离线模式）**

- 探针：`verify/_probe_labeler_concurrency.py`，产物 `verify/_probe_labeler_concurrency_out.json`。
- 离线模式（默认，不联网不计费）重建了 `ModelRuntime` 的线程局部契约，按 N=1/2/4/6/10
  并发 + 串行基线 + 取消/异常两路跑完整套：正文标记、`usage`、`reasoning`、`finish reason`
  逐项归属正确，无错配/丢结果/重复计数，`passed=true`。
- 反向确认（§2.3）：`naiba/llm/runtime.py:632` 确为 `threading.local()`；异常路径下
  诊断读数会保留**本线程上一次的残留值**，因此打标器 runner 必须在 worker 线程内
  「调用+读诊断」一次完成，失败项不得读 `last_usage` 记用量。
- 在线小样本（`--live`，需 `--model-key/--model-name/--confirm-paid`）尚未执行：
  按 §12.1 第 5 条，首个真实批次限定 1 张图、1 个任务，届时再跑。
- **业务落地口径**：初始并发固定 1；P1 runner 按「worker 线程内捕获」实现，
  UI 只暴露已验证档位（首期仅 1）。本地 provider 因全局执行锁实际串行；runner 在每张
  开始前礼让进行中的对话 Run（`runs.list_primary(active_only=True)`），并在每张结束后
  短暂让出锁，保证打标期间聊天与其它功能仍可正常使用（2026-10-23 用户追加要求）。

### P0-b：输入、安全与数据契约（开工前冻结）

- **必须支持拖入文件夹批量打标**：在打标页设置明确的文件夹拖放区；用户拖入目录后，前端通过浏览器/WebView2 的目录条目 API 递归枚举目录内文件，只筛选允许的图片格式，再逐批通过现有 `/api/uploads` 上传到 `data_dir/uploads`，后端只接收上传成功后返回的受管引用。保留相对路径用于结果分组/导出命名，不向服务端传原目录绝对路径。需处理目录深度/文件数/总字节上限、重复文件、同名文件、空目录、坏图、上传失败部分重试、上传进度、取消和拖入非图片文件；文件上传需限并发并避免一次性把整个目录读入内存。
- 拖放实现要验证当前 WebView2 对目录条目的支持；优先使用 `DataTransferItem.webkitGetAsEntry()` 递归读取并以 `File` 对象上传。提供 `webkitdirectory` 文件选择作为拖放不可用时的备用入口。拖放事件须在打标器 drop zone 阻止默认行为并阻止冒泡，不能被聊天区或应用级 drop handler 抢走；禁止用 pywebview 回传的任意目录路径直接读文件。
- **首期默认批量上限**：每批最多 500 张图片，单图沿用受管图片校验上限（当前 Studio 单图 20 MiB），每批待上传总量最多 1 GiB；超过上限时拒绝启动批次并提示用户拆分，不静默截断。上传并发默认 3，可在 P0-b WebView2 实测后下调；分批请求且进度按文件统计。上限作为服务端常量校验，前端只做提前提示。
- 单文件上传沿用现有校验；批量上传设有界的单图、总数量、总字节和请求体上限。任务只持久化服务端校验后的受管引用及用户拖入目录内的相对路径，不持久化原目录绝对路径。使用 `normalized_path_key()` 作为路径身份，另定义内容版本（至少记录大小与 mtime；若需识别原位替换再加内容摘要）。明确缓存引用保护覆盖活动及可重试任务，任务删除/过期后按保留策略释放。
- API 请求只传服务端已配置的 `model_key`、模型选择和经白名单验证的参数。服务端通过既有 profile resolver 解析凭证；不接受客户端 `provider_info`、API Key、任意 `base_url`，任务 JSON/事件/日志不得出现密钥。提交时冻结非秘密配置快照；重试继续使用该快照，若 profile 已删除或凭证无效则明确失败，不静默改用新模型。
- 为每个输入图片生成稳定 `item_id`。SQLite 是逐图完成/失败状态的恢复权威；逐图状态、标注结果、用量和任务计数在一个事务里提交。事件 JSONL 是可重建的通知日志，不作为唯一 checkpoint。明确崩溃发生在模型已计费但结果未落库时只能标为“结果不确定”，不得承诺绝对不重复计费。
- 明确重新打标唯一性：首期保留历史版本；查询默认按同一 `path_key + content_version + config_fingerprint` 返回最新成功结果，也可按任务查看历史。`config_fingerprint` 纳入 engine、model、output_mode、preset、prompt 版本及影响结果的筛选参数，不含密钥。`revise_existing_data` 从首期请求契约删除，后续若支持覆盖再单独设计迁移与确认交互。
- 导出只基于选定数据库记录，不接受写入路径。定义受管导出产物与下载/保存对话框；若当前壳无安全保存桥接，首期导出到应用导出目录并提供受控下载。明确 UTF-8、同名/部分失败、CSV 公式注入防护；原图同目录 `.txt` 写入首期默认不做，不覆盖素材。
- 请求/任务上限、每图超时、重试次数上限、全局并发任务数、队列取消、关机收敛、HTTP 鉴权复用和错误分类均需落到服务端校验与测试；所有本地文件操作受现有 API 授权与受管目录约束。

### P2：批量执行与断点续跑

- 提交接收受管 `image_refs[]` + 白名单 `config`；禁止 `image_paths[]` 和客户端 `provider_info`。
- checkpoint 粒度 = **每个 item_id**：记录 queued/running/succeeded/failed/cancelled/uncertain；SQLite 事务原子提交该项状态、标注结果、usage 及任务计数，再追加事件。恢复时从 DB 状态恢复，不以事件文件推导完成集合。
- 仅对明确可重试的限流/服务端错误做有上限的指数退避；认证、参数、图片解码等永久错误不重试。取消需区分尚未开始、请求中和已完成项；请求中取消可能无法撤销供应商计费。
- “继续未完成”创建新任务并记录 `source_task_id`，只复制未完成/失败/结果不确定项（不确定项需用户确认可能再次计费）；成功项不重复调用。明确区分 `mode=failed_only|unfinished`。
- 恢复列表按 `interrupted` / 部分失败 / 近期活动等明确定义筛选；`recent` 是 Labeler 新接口，不是现有 Studio `_recoveryMode`。响应需提供状态、进度、失败数、是否可继续、来源任务关系和更新时间。

### P3：前端打标页 `public/js/23-labeler.js`

- 先核实入口模块的真实 ESM 装配链，只在一个入口 import，避免双重初始化；切换功能页时暂停非当前页高频轮询，回来后由服务端状态校准。
- 文件夹拖放：拖放区递归读取目录文件，筛选支持的图像格式并逐批上传；目录选择控件使用 `webkitdirectory` 兜底。显示待上传/已上传/跳过/失败数及相对路径，支持取消上传和仅重试失败文件。
- 打标页：左（批次/队列/断点状态）、中（打标侧重 + 后端 + 参数 + 开始/取消/继续）、右（结果三档：按图 / 按标签 / 句子库）。
- 轮询复用 studio 的任务轮询模式；`reconcileActiveTask` 同款校准逻辑。
- 样式：优先复用 `.studio-*` 类，新增 `.tagger-*` 控制在最小集。

### P4：标注库、导出、句子库

- 标注入库：包含 `item_id / source_task_id / path_key / content_version / relative_path / engine / model / output_mode / preset / prompt_version / config_fingerprint / tags[] / confidences[] / description / created_at`；同图同内容同配置重复导入复用既有成功结果，不重复调用；配置不同保留独立历史记录。`relative_path` 只来自前端枚举的相对名称，服务端禁止把它拼接为任意落盘路径。
- 导出：JSON（含置信度）、CSV（扁平并防公式注入）、受管目录中的 `.txt` 包。原图同目录写入首期默认不做，不覆盖原始素材。
- 句子库：规则分句（中英标点 + 换行）→ 频次统计 → 可检索；结果标记 `degraded`（未启用 spaCy）。

### 6.2 checkpoint

- 逐项状态与标注结果在 SQLite 同一事务提交；之后追加带 `item_id`、seq 的 `image_done` / `image_failed` 事件。事件日志损坏时可从数据库重建展示，不反向覆盖数据库事实。
