# 拆章非法 JSON 内容抢救修复计划

> 状态：已实施并随 4.7.1-beta 发布（2026-11-21）；全量测试与静态检查见第 6 节验证记录。
>
> 日期：2026-11-21

## 1. 问题

用户实测（deepseek-flash，拆章目标 10 章）：模型输出不是合法 JSON 时，流水线报
「拆章不是合法 JSON」，待处理编辑器为空，只能反复重试、从零手打 10 章、或跳过
（跳过=这批章号永远缺失）。

根因：`naiba/writer/prompts.py::extract_json_payload` 只认「纯 JSON 或单个完整
代码围栏」。拆章是全流水线单次输出最大的 JSON（一批最多 20 章、每章带 ≤2000 字
梗概与 ≤500 字钩子），最容易因四种坏法翻车，而这四种以前全部整批作废：

1. 输出撞上长度上限被截断（截断的 JSON 必然不合法）；
2. 字符串值里夹裸换行/控制符、没转义的引号；
3. 闭括号前多逗号等小语法错误；
4. 表格外带解释文字（deepseek 类模型的常见习惯）。

「给了但不完整」（合法 JSON 只拆出 7 章）的人工接管链路已在
`docs/plans/2026-11-20-织书台结构化输出兼容与新建诊断修复计划.md` §11 落地；
缺的就是「JSON 语法坏了」这一档——内容在原文里却因为解析不了而全丢。

## 2. 修复原则

**只修语法，不猜内容。** 抢救出的内容要么走原有全量校验（与干净 JSON 同等信任），
要么进待处理编辑器由用户检查后「补充继续」；坏 JSON 里捞出的行**不给「接受」按钮**
（`accepted` 不设置），必须经用户确认。

## 3. 实施内容

### 3.1 `naiba/writer/prompts.py` — 有界抢救层

新增（均在 `extract_json_payload` 之后、同一段注释块内）：

- `_load_strict_json`：与 `extract_json_payload` 同一套钩子（`_unique_json_object`、
  `_finite_json_number`、`_ensure_json_unicode`）的 `json.loads` 包装。
- `_json_candidates`：抢救候选，按序尝试——全文、所有围栏内容（含未闭合围栏）、
  去掉前缀解释文字的括号区；不从多处来源里挑。
- `_repair_json_text`：单遍字符串状态扫描，只做能唯一确定的修复——字符串内裸
  控制符转义、闭括号前尾逗号去除；顶层结构闭合即止（不收后面的解释文字）；停在
  半截就在最后一个闭合处收口、按栈补齐缺的括号；括号错配返回 None 不硬猜。
- `_rescued_json_payload`：逐候选先直接读、再修复读；全失败返回 None。
- `_salvage_chapter_rows`：整段修不好时按括号配平打捞完整的 `{...}` 对象（逐个
  先直接读再修复读），只保留带非空 `title`/`beat`/`hook` 的行，上限 60 行。

接线：

- `_payload_list(..., rescue=False)`：捕获 `unrecognized_format` 时若 rescue 开启
  则先 `_rescued_json_payload`，成功走同一套白名单解包与校验（全量通过→流水线
  直接继续；不足→既有 insufficient 链路，partial 进编辑器且 accepted 可接受）。
- `_parse_chapter_rows`（拆章+逐章大纲共用）传 `rescue=True`；对
  `unrecognized_format`、以及「`wrong_shape` 且完全无包装键」（模型按行连发章
  对象时修复扫描只会带回第一个）两种残留，用 `_salvage_chapter_rows` 打捞，
  找到行抛 `ContentIssue`：文案「{what}不是合法 JSON；已从原文找回 N 章放入下方
  编辑器，请检查补齐后再继续」，`category="unrecognized_format"`，partial=行列表，
  counts=`{"actual": N, "target": wanted}`。一点捞不到→维持原报错。

其余阶段（题材/书名/简介/角色/段落） rescue 保持 False，行为不变；
`extract_json_payload` 本身保持严格，原有解释文字/多围栏拒绝测试不受影响。

### 3.2 `naiba/writer/pipeline.py` — 截断但可解析时保留结果

`_parse_step_output`：finish_reason=length 但结构化解析成功时，原来
`partial=output if editor == "text" else None` 把拆出的章节丢掉；改为
`partial=output`，编辑器预填解析结果（`_pause_for_user` 已有大小防护）。

### 3.3 前端

零改动。`27-writer.js` 决策编辑器本就从 `pending_user.partial`（章节行数组）
预填；`available_actions` 由后端下发。

## 4. 测试

`tests/test_writer_prompts.py::ContentIssueTests::test_split_invalid_json_is_rescued_not_discarded`：

- 解释文字+围栏包裹的完整 10 章 → 修复后直接成功（正常返回）；
- 末章闭合后截断+尾逗号 → 修复出 7 章，insufficient，accepted 7 章可接受；
- 截断停在最后一章字符串中间 → 回退到上一个完整章收口，抢救 7 章
  （不完整的那章按设计丢弃）；
- 字符串值夹裸换行 → 转义修复后直接成功；
- 按行连发章对象（无数组括号）→ 打捞 10 章进编辑器，无 accepted、无 accept 动作；
- 纯文字 → 维持 unrecognized_format、partial None；
- 逐章大纲走同一套；严格合法 JSON 行为不变。

`tests/test_writer_pipeline.py::SplitChainTests`（新类，用假 Jobs 驱动真实链路）：

- `test_invalid_json_salvages_rows_into_pending_and_supplement_continues`：
  行连发 → needs_user，pending.editor=chapters、partial 三章、无 accept；
  用户补充提交（require_count=False）后流水线 done，章节 1–3 落索引。
- `test_truncated_split_keeps_parsed_rows_in_pending`：finish_reason=length
  但 JSON 完整 → needs_user/category=truncated，partial 保留三章，补充提交后 done。

## 5. 范围外（本轮不做）

- 角色/书名/简介/题材的同类抢救（`_rescued_json_payload`/`_salvage_chapter_rows`
  可复用，接线是每处几行的事，另行拍板）；
- 自动带错误反馈重试、跳过后补拆缺失批次的编排、提示词改动；
- 前端改动。
