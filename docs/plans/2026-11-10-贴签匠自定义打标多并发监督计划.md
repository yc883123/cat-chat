# 贴签匠自定义打标多并发与监督计划

日期：2026-11-10  
状态：仅计划，未实施；后续收到明确实施指令后再修改产品代码。

## 1. 目标与范围

只为「自定义打标」增加可选的多模型并发与监督流程。默认关闭时沿用当前单供应商、单模型、逐图打标路径；「预设打标」及其配置、提示词、并发行为均不变。

开启后，用户可配置最多 9 个打标员槽位，每个槽位独立选择一个 API 供应商和具体模型；槽位可重复选择同一供应商/模型。另选 1 个监督员供应商和模型。打标员共享当前自定义规则（手写系统提示词，或所选 Skill）并发处理批次图片；每张图片只分配给一个打标员，不对每张图重复调用全部 9 个模型。监督员并行审核已完成的不同图片，通过后落为正式标注；不通过时可退回原打标员有限次数重做，仍不通过则明确标为需人工检查，不静默采纳或覆盖。

本计划不是把聊天子 Agent 工具直接接到贴签匠。子 Agent 有独立 Job/事件/取消，但现有数量限制为父任务最多 4 个、要求会话归属且不自动断点恢复，不符合贴签匠 9 路图片 worker 与现有逐图账本。实现应保留贴签匠任务生命周期、SQLite 逐图事务和图片结果复用；在贴签匠域内编排受控 worker，并复用现有 provider / Skill 执行能力。

## 2. 用户交互

- 在「自定义打标」页增加「并发打标」开关，默认关闭；关闭时仅显示并提交现有模型选择，旧任务缺少并发配置仍按关闭处理。
- 开启后显示 1 个监督员模型选择，以及 1–9 个打标员模型槽位；每槽独立选择 API 供应商和该供应商下已检测到的具体模型。可增加/删除槽位，至少保留 1 个，最多 9 个；允许多个槽位重复选择同一供应商和模型。重复配置共用该供应商档案对应 API key 的并发额度。供应商额度不能一概自动识别，界面提供该档案的并发上限设置或明确采用的默认值；有效并行数可能因此低于槽位数，不擅自去重或假设每个槽位都有独立额度。
- 监督员配置 1 个模型身份，但审核队列必须支持多张不同图片同时送审；监督并发数由可用供应商额度与系统可配置上限共同限制。单张图片仍按“打标完成 → 监督 → 通过或退回”顺序推进。
- 普通模式原有模型选择仍是唯一执行模型。并发模式使用监督员与打标员列表，不把原有单模型控件误认为仍参与打标。
- 提交前显示图片数量、打标员数量、最多打标请求数及监督请求数；费用只说明按实际用量由各供应商计费，不虚构固定价格。Skill 可能多轮工具调用，需明确请求数不等于模型调用轮数。
- 进度按图片呈现：待分配、打标中（显示槽位/模型）、监督中、通过、退回重做、需人工检查、失败、取消及结果不确定。结果卡保留打标员、监督结论和重做次数；不展示内部 JSON 调试数据。
- 取消任务后不再派发新图；等待或取消在途供应商调用，逐图状态按实际结果收敛。重试/继续沿用任务时冻结的模型与提示词快照，不读取后来修改的 UI 选择。

## 3. 执行与监督规则

1. 任务创建时服务端重新校验每个供应商配置和模型名，冻结有序的 1–9 个 worker 模型、监督模型、自定义规则/Skill revision、输出约束和监督策略；客户端不传 API Key、任意端点或 profile 内容。
2. 图片由有界 worker pool 领取，每个 worker 槽固定使用其冻结模型配置；槽位数就是打标最大同时处理图片数，上限 9。队列调度不得超领或重复派发同一 item。监督阶段另设有界并发队列，允许不同图片同时审核；同一图片仍须等自己的监督结果后才能通过或进入返工。监督模型虽然只有一个配置，也不能因此把全批审核串行化。
3. 同一供应商/API key 下的多个槽位可能共享 RPM/并发配额。用户需为供应商档案设置可用并发上限；系统按档案维持请求闸门，打标和监督请求均遵守上限。额度未知时使用保守默认值并提示用户确认；不能因模型名不同推断额度独立。遇到 429/限流时按有界退避处理，避免重试风暴。
4. 每张图先执行打标，再把该图、冻结规则摘要、结构化候选结果和来源槽位提交给监督模型。监督模型返回受 schema 校验的结论：`approve` 或 `revise`，附简短理由和必要修订结果。监督模型不可改写规则、模型配置或其他图片结果。
5. `revise` 将该图退回原打标员重做，最多 2 次（总计最多 3 次打标尝试）；每次监督后必须重新检查。超过上限或监督输出不可解析/调用失败时，标为需人工检查或失败，不自动当作通过。实际重试次数可在后续 UI 配置，但首版固定，避免任务成本失控。
6. 监督通过的最终结构仍走贴签匠既有解析、标签过滤、触发词、TXT 回填/写入和逐图事务提交。只有监督通过结果能进入成功标注与结果复用；人工检查项保留候选证据，不能被误认为已审核成功。
7. 每次打标和监督调用的 usage、finish reason、模型标识必须在实际调用线程内即时捕获，禁止从共享或迟到的 runtime 状态推断归属。图片最终 usage 汇总其所有尝试，任务汇总覆盖打标、监督及失败请求。
8. 同图同配置的已通过结果允许复用；指纹包括全部 worker/监督模型及版本化监督策略，因为这些会改变正式输出。并发开关关闭时必须保留旧指纹口径，历史结果继续复用。并发数、重试次数、超时不作为内容身份字段，除非后续证明会改变结果。
8. 手写提示词与 Skill 两种自定义路径均支持并发。Skill 由每个打标员按现有 `engine=chat` 规则执行；监督员收到的是必要规则与候选结果，不自动继承聊天会话历史，也不通过通用子 Agent 工具访问工作区。现有贴签匠 TXT 工具仍限定每个 worker 只能写当前图片自己的 TXT；监督阶段不得写另一张图片或直接覆写已有候选 TXT。
9. 首版只对在线 API profile 开放多并发；本地 profile 不得并发挤占全局本地执行锁，需拒绝或要求切回关闭模式。若一组配置混入本地模型，提交时明确指出具体槽位并阻止任务启动，不静默降级。

## 4. 服务端与数据设计

- `naiba/labeler/jobs.py`：新增并发配置白名单和归一化；仅当自定义模式显式开启时接受 worker/监督模型集合，校验数量、必填字段、profile 有效性与在线限制；配置快照中只保存非秘密模型标识。
- `naiba/labeler/runner.py`：保留外层批次队列和 `_run_item` 的事务/恢复职责，将逐图串行循环替换为有界调度；打标槽位按冻结模型分配，监督使用独立有界并发队列；引擎按图片/调用隔离实例，协调线程负责任务级进度与终态，取消时等待已派发工作收敛。任何异常不得留下永久 `running`。
- 新增贴签匠并发额度管理：每个供应商档案提供“并发上限”设置，约束该档案使用的 API key 的在途请求数；所有重复使用该档案的打标槽和监督请求共享同一个限流闸门。默认值保守且可调整，达到上限时排队，不丢弃任务；429 按有限退避重试。
- 新增贴签匠监督模块或等价纯逻辑：定义监督提示词版本、严格 JSON schema、裁定解析、有限返工与人工检查归类；监督只消费结构化数据，不执行文件、工具或任意副作用。
- `naiba/labeler/db.py` 与任务事件：保存逐图阶段、worker 槽位、监督次数、结论类别、错误分类和用量；可通过现有 item/task 查询和事件轮询恢复 UI。必要的新字段先登记在对应领域契约，避免塞进通用 Job 协议。
- 任务中断时，已完成通过项保持成功；在途打标或监督项标记 `uncertain`（可能已计费）；未派发项保留待处理。继续任务跳过已通过项，对不确定项继续遵循显式确认，避免自动重复计费。
- 任务删除、TXT 输出清理、标注库行为沿用现有贴签匠边界。监督审查记录与候选输出随任务保留，不能因结果页分页而丢失。

## 5. 实施步骤

1. 先实现纯监督契约与模型结果归属：结构化候选、审核 schema、通过/退回/人工检查状态及相关单测，不开放真实并发。
2. 完成自定义模式开关、1 个监督配置和最多 9 个 worker 配置的前后端表单及服务端快照校验；关开关的旧请求/旧任务兼容。
3. 在 runner 实现有限 worker pool、逐图状态推进、监督/有限返工、线程内 usage 捕获、取消和恢复；预设模式继续固定并发 1。
4. 增加结果卡与任务事件展示、提交成本提示、人工检查项和继续/重试路径；TXT 仍由图片 worker 在其图片上下文中写入。
5. 先使用假模型和确定性屏障完成离线并发契约，再以明确的小样本真实供应商验证。线上调用会产生费用，真实探针必须先明确列出供应商/模型、图片数和最大调用轮数，并由用户另行确认后执行；本计划本身不授权付费探针。

## 6. 验收

- 关闭并发开关时，手写提示词与 Skill 两种流程都与现有串行行为一致；预设打标、旧任务读取、旧结果指纹复用无回归。
- 开启并发后最多 9 个可选打标员槽位；槽位允许重复选择供应商和模型，服务端按同一供应商/API key 的限额控制有效并发，不超发请求。用户若有多个 key，配置的供应商档案按各自 key 分别限流。
- 打标和监督分别以屏障测试多图同时运行，验证监督队列不会被单个监督模型配置变成串行；两个阶段的实际在途请求都不得超过各自供应商档案的并发上限。
- 1、2、9 个 worker 槽分别验证；超过 9、缺监督模型、无效模型、重复字段、客户端注入秘密/端点、混入本地 profile 均由服务端拒绝。运行峰值不超过所配槽数。
- 并发处理多图时，以事件屏障制造乱序返回；结果、模型归属、图片内容、usage、TXT 文件及 annotation 必须一一对应，无串写、无重复领取。
- 监督通过、首次退回后通过、两次返工后通过、超过次数需人工检查、结构错误、监督超时/鉴权失败、worker 失败等路径均有确定性测试。未经通过的结果不得进入成功标注与可复用缓存。
- 取消分别覆盖派发前、打标中、监督中、返工待派发和部分图片已通过；取消后不再开新请求，在途任务最终状态明确，没有僵尸 `running`。
- 进程中断时核实通过项、未派发项和 `uncertain` 项恢复语义；继续任务冻结旧模型与 Skill revision，不把迟到结果写入新任务。
- 用量覆盖多轮 Skill/TXT、监督、返工、失败及 runtime 内部重试；总量等于逐图各阶段可归属用量之和，不串线程或继承上次调用读数。
- 结果 UI 可区分打标员与监督员结论，人工检查项可见且不会被误导为完成；窄屏布局不溢出。
- 离线单测覆盖调度、账本和 UI 契约；真实供应商小样本验证通过后才将并发档位开放给用户。运行贴签匠专项与全量测试、静态检查、Playwright 桌面/窄屏冒烟，按项目维护说明执行。

## 7. 关键代码入口

- `public/index.html`：自定义打标区与共用单模型控件；`public/js/23-labeler.js::collectConfig/startTask`：配置快照与提交。
- `naiba/labeler/jobs.py::normalize_config/submit`：服务端配置校验与任务快照。
- `naiba/labeler/runner.py::LabelerRunner._run_task/_run_item`：批次调度、单图调用、逐图事务。
- `naiba/labeler/engines/provider.py`、`engines/chat.py`：手写规则与 Skill 的逐图模型执行。
- `naiba/labeler/db.py`：item 状态、标注和 usage；`naiba/labeler/store.py`：任务快照与事件。
- `tests/test_labeler.py`、`tests/test_labeler_custom_page.py`、`tests/test_labeler_skill_lifecycle.py`：领域与前端守门。

## 8. 尚需产品确认的默认解释

本计划将“9 个打标员”解释为最多 9 个可配置模型槽位，共同分摊图片队列；每张图只由一个槽位标注，再由独立监督模型审核。若用户原意是每张图片都要 9 个模型分别标注、由监督员综合投票，则需在实施前调整任务成本、结果证据与监督策略，本计划不按该更高成本语义实现。
