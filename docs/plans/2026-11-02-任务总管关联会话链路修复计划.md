## 一 目标与范围

修复任务总管关联已有会话后的启动、重试、步骤交接与结果查看问题，使用户能够明确知道任务向哪个会话执行、是否使用历史、结果在哪里，以及遇到冲突后如何安全恢复。

范围包括单次聊天任务、交给子助手、关联已有后台任务，以及包含上述类型的混合步骤链。保留普通聊天现有入口、工具确认与后台任务权限边界。

不包含重新设计整个任务总管、扩大工具权限、改变 Writer/Novel 生成规则、自动回写子助手正文、批量修复历史数据库或发布版本。自动续办属于独立计划；本次仅处理共享接口兼容和回归，不接管它的审查、预算与调度实现。

已有“回到关联会话”通过 `openConversation` 恢复会话及在途 Run 的路径，应保留。当前没有证据表明单纯跳转就是主要故障，不应重写整个会话导航。

## 三 产品行为约定

本计划建议采用以下边界，先把现有能力解释清楚，不顺手增加新的自动行为：

| 任务类型 | 关联的含义 | 历史和结果规则 |
|---|---|---|
| 单次聊天任务 | 向选中的主会话发送一条新消息 | 沿用普通历史回放；结果是本次 Run 对应的回复 |
| 交给子助手 | 使用所选会话的工作区、授权边界及任务配置运行独立子任务 | 当前默认不继承聊天历史；结果属于独立 Job |
| 关联已有后台任务 | 跟踪选中会话中的既有 Job | 关联、同步、查看不重新执行原任务 |
| 混合步骤链 | 按依赖顺序接续明确的步骤 | 前序结果由服务端核验后交接，不靠模型猜测编号 |

子助手界面必须提示“不继承聊天历史，请把任务要求写完整”。本次不默认开启 `fork`；以后若需要历史继承，应单独定义用户入口、历史边界与工具互斥规则。

“回到关联会话”负责会话导航，“查看本次结果”负责定位具体执行。默认不把子助手输出伪装成主会话的一条普通助手回复；自动回写正文需要另行确定产品行为和消息来源契约。

## 四 分项修复方案

### L01 区分明确未启动与启动结果未知

当前入口：`naiba/run/chat.py::ConversationRunMixin.submit_chat`、`naiba/super_agent/runtime.py::ExecutionCoordinator.command`、`RuntimeAdapter.start`、`naiba/super_agent/store.py::claim_command` 与 `settle_command`。

当前普通聊天检测到已有 active Run 会抛出 `ActiveRunError`，尚未创建新执行。但总管先持久化启动意图，再把异常统一按结果未知处理，留下待对账记录；没有执行句柄时，后续重试和取消又被该记录拦截。

修复步骤：

1. 为执行提交定义可判定的结果类别：明确未提交、已提交且有句柄、结果未知。使用可信的异常类型或结构化返回，不按错误文案猜测。
2. 仅在能证明尚未创建执行的路径上结算为“未启动”。不能把所有 `ValueError`、网络错误或任意异常都当成可安全重试。
3. 会话忙碌时显示“此会话正在执行，请结束后再开始”；任务保持可恢复、可取消，不冒称运行中。默认不隐式排队、不在后台无限重试。
4. 对同一请求重复提交返回同一拒绝结果；用户再次明确开始使用新的请求标识，可以重新检查并提交。保留旧记录供审计，不直接删除所有 claim。
5. 在实际提交的锁和事务边界内保留忙碌检查。前端禁用按钮或提交前预检查仅改善体验，不能代替服务端并发保护。
6. 对已成功提交但关联写回失败的情况，仍只能接回原执行；结果未知仍须保守冻结，不能用“找不到记录”作为安全重放证明。

验收要求：

- 原会话忙碌时新执行数为零；原会话结束后，用户再次开始只创建一次新执行。
- 明确未启动的任务可以取消；取消不会误伤原会话正在进行的 Run。
- 双击、请求重放、两个任务争用同一会话、服务重启都不导致重复提交。
- 成功提交后持久化失败的场景继续接回同一执行；真正未知结果不会自动重放。

### L02 拆分任务执行配置与会话授权校验

当前入口：`ExecutionCoordinator.prepare`、`RuntimeAdapter.start`、`ConversationRunMixin.submit_chat`、`naiba/run/session.py::bake_session_tool_ids`。

当前 `conversation_fingerprint` 同时包含模型和授权字段；普通聊天提交又会更新会话模型、固化工具集。任务自身的正常更新因此使原指纹失效。

修复步骤：

1. 将任务执行模型、会话授权基准、实际执行快照分开表达。任务所选模型用于该次执行，不能与“会话是否被外部修改”混为一个校验条件。
2. 优先为总管调用提供服务端受控的任务级模型覆盖，不默认改写原会话的模型选择；普通聊天手动切换模型行为保持不变。不得让任意客户端参数成为绕过授权检查的入口。
3. 抽取与普通聊天相同的有效工具集计算与固化入口，统一空工具集、互斥工具、单独授权和旧会话兼容口径，避免总管自行复制一套规则。
4. 首次执行确需固化会话工具时，记录当前执行导致的受控变化及最终基准，使重试和后继能够识别这次变化。更新应绑定执行关联、attempt 和版本，并采用条件写入，不能覆盖并发的人工设置变化。
5. 工作区、权限、Agent、工具授权等外部变化仍须阻止不符合原授权的继续执行，并提示重新确认或创建任务；不得简单删除指纹比较。
6. 同会话混合链的后继应使用合法的基准演进，不继续拿创建时的空工具集与已固化值直接比较。不同会话的基准不得互相传播。

验收要求：

- 任务模型不同于会话原模型时，首次执行、失败后重试、同会话第二步骤均可正常进行。
- 新会话首次固化工具后，不出现自身配置变化导致的误拦截。
- 人工修改权限、工作区或工具范围仍被检测；不能借重试恢复被撤销的能力。
- 普通聊天模型切换、历史回放、工具互斥及首次工具固化测试保持通过。

### L03 交接真实结果而非仅交接引用

当前入口：`RuntimeAdapter.sync`、`RuntimeAdapter.start`、`naiba/subagent.py::run_subagent_agent`。现有 `output_refs` 主要是 `run://` 或 `job://`，子助手默认无历史且禁止 Job 查询工具。

修复步骤：

1. 提供统一的服务端结果读取与交接逻辑，供步骤输入与只读结果展示复用；不新增第二套不一致的结果解析器。
2. 聊天结果按执行记录与消息关联读取本次最终回复，不读取“会话最后一条消息”。子助手读取该 Job 的 `result.response`；其他 Job 只提取声明可展示的结果、日志摘要和产物。
3. 从已经登记的依赖节点解析执行引用，校验 owner、所属会话、执行类型、当前 attempt 和真实终态。不能由用户文本中的任意 `run://`、`job://` 触发跨任务读取。
4. 向后继显式传递来源、执行标识、结果文本和可用产物引用；引用继续用于追溯，不能代替正文。前序内容按数据处理，不成为授权、系统规则或自动批准依据。
5. 为单项及总输入设置集中定义的大小上限；发生截断必须标明总量、保留量和省略情况。结果缺失、关键证据被截断或不支持解析时，明确阻断依赖该结果的自动推进，不把缺失描述成成功交接。
6. 记录实际消费的前序 attempt 与结果版本。同一后继重试不得静默换用别的执行结果；前序重试产生新版本后，由依赖有效性规则决定是否需要重新确认后继。
7. 保持子助手 Job 管理工具禁用，不通过开放这些工具绕开宿主交接责任；不得把完整 trace、snapshot 或敏感配置复制进输入。

验收要求：

- Chat→子助手、子助手→子助手、已有 Job→子助手都能收到前序真实结果中的唯一测试标记。
- 至少覆盖同会话与跨会话的显式混合依赖；无依赖或越权引用被拒绝。
- 覆盖超长、空结果、失败、已删除、旧 attempt、重复同步及重启，均有确定行为。
- 模型替身必须检查收到的实际输入，不能只返回固定成功文本掩盖缺失的交接。

### L04 明确关联说明并补齐指定结果入口

当前入口：`public/index.html`、`public/js/28-super-agent.js::renderCreateMode`、`renderDetail`、`naiba/app.py` 的总管 DTO、`public/js/08-conversations.js`、现有后台任务详情入口。

修复步骤：

1. 按第三节增加对应类型的关联说明；子助手不继承历史的提示应在填写目标时可见，不藏在帮助文档中。
2. 为每个有执行记录的节点提供“查看本次回复”或“查看任务结果”。结果区使用与 L03 同源的只读结果数据，必要时按需加载正文，避免轮询反复下载长文本。
3. 聊天结果定位到具体 Run 对应消息；子助手和已有 Job 定位到该任务详情、结果或日志。保留通用回到会话按钮，但不拿它替代指定执行结果入口。
4. `run://`、`job://` 作为内部引用，经服务端校验和前端受控事件处理，不能直接交给浏览器当作外部协议链接。
5. 对删除的会话、失效引用、未产出结果和读取失败提供明确提示与只读重试；不能因查看失败重新执行任务，也不能静默打开另一个结果。
6. 结果 DTO 只暴露展示所需字段，不返回原始模型请求、完整 trace、授权快照或密钥；输出内容使用安全文本或既有安全渲染管线。

验收要求：

- 同一会话里多个节点的结果按钮能分别定位各自执行，不全部跳到最新回复。
- 子助手正文在总管或任务详情可读；界面不声称已自动写入主聊天。
- 回到等待工具确认的会话后恢复原确认卡；导航和查看结果都不批准工具、不触发新模型调用。
- 两种视口下长标题、长正文、错误信息和结果弹窗均可阅读、滚动及关闭。

### L05 分离单项与整套任务的启动选项

当前入口：`public/js/28-super-agent.js::renderCreateMode`、`submitMixedDraft`、`createDomainThread`，以及后端 mixed 创建和推进逻辑。

修复步骤：

1. 单个任务的启动状态与混合清单的启动状态分别保存；切换当前编辑类型不得清除整套任务的用户选择。
2. 独立关联 Job 仍不提供“重新启动已有 Job”的隐式行为。混合清单是否可立即开始由整个清单决定，不取决于最后正在编辑哪种任务。
3. 把“创建后开始整套任务”与“完成后自动推进”分开表达，默认均保持关闭；前者只启动首个可执行步骤，后者控制后继推进。
4. 链中已有 Job 只绑定并同步：运行中的等待真实终态，已完成的按依赖规则推进，不重新创建或调用 retry。
5. 清单变空、创建失败、删除步骤、重新打开弹窗时采用明确的草稿规则；不得把旧勾选悄悄带到无关的新任务。

验收要求：

- Chat→Job、Job→Chat、子助手→Job 的编辑顺序都不改变整套选项。
- 切到 Job 再切回 Chat 后，整套原勾选保持；独立 Job 仍无重新启动行为。
- 开始、自动推进四种开关组合与服务端行为一致；双击创建不重复执行。

## 五 与自动续办并行开发的整合边界

当前工作树正在接入 `supervised.py`、`review.py`、`supervision_store.py` 及单次/监督创建分支。实施本计划前，核对相关改动的完成状态、提交接口与实际装配，不能把在途代码当成验收通过的能力。

- 普通节点与监督节点共享提交结果分类、授权基准及结果读取能力时，应共用明确接口，避免复制指纹判断或各自修一半。
- 不把监督轮次混入普通 Node 的 attempt；保留监督版本、人工输入失效、截止时间、轮数预算和独立审查 worker 的约束。
- 单次任务不携带监督参数；监督任务继续独立创建，不混进 mixed 节点。切换创建模式不能误删已有混合草稿。
- 查看结果、恢复确认卡和普通重试不隐式启动监督审查或自动补做。
- 涉及共享 `submit_chat` 签名或 Run 来源字段时，先登记契约并同时核查调用方；对接口尚未对齐的在途实现记为整合依赖，不在本计划中擅自重写整套监督逻辑。

### Playwright 前端与真实执行链

使用源码服务、独立临时数据目录、随机空闲端口和系统 Edge，覆盖桌面与 375px 手机。不操作正在运行的真实用户任务，不为了测试重启用户服务。

已有入口 `verify/browser_smoke.cjs`、`verify/super_agent_v1_ui_smoke.cjs`、`verify/super_agent_feedback_smoke.cjs` 应保留，并为本计划补关联执行专项。现有 V1 脚本中的 Chat/子助手创建检查不能替代执行验收；已有反馈脚本覆盖 Chat 工具确认，也不能替代本计划的重试、交接与子助手结果测试。

专项使用真实 App、HTTP、存储、Chat Run 与 Job 执行器，只将模型提供方替换为本地确定性服务。至少完成：

1. 只创建不执行，手动开始与双击防重。
2. 原会话忙碌时明确未启动，空闲后用户再次开始成功，取消不伤及原 Run。
3. 不同模型、新会话首次工具固化、失败重试和同会话第二步骤。
4. 前序纯文本经实际请求进入后继子助手；长结果、缺失结果及旧 attempt 有明确处理。
5. 单项及混合 Job 关联不产生新 Job；四种开始/推进组合符合配置。
6. 查看指定结果、返回会话、刷新与工具确认恢复，导航不触发执行。
7. 执行已提交但关联写回失败后，重启只接回原执行；未知结果保持不自动重提。
8. 单次与监督模式切换、混合草稿保留及共享接口兼容。

每个关键步骤后立即检查 `pageerror`、`console.error`、应用错误条和非预期业务 HTTP 错误；同时核对执行提交次数、实际输入与结果归属。预期的冲突响应必须精确断言，不能统一忽略所有错误。等待明确的接口或 DOM 状态，不靠固定长延迟判成功。

截图、日志、临时数据库只写忽略目录或系统临时目录，不进入提交。本地替身通过只能证明本地链路；外部供应商、真实费用和长时间运行另行授权验证，不混写为已通过。

## 八 历史数据与回退

- 读取旧 JSON null、缺字段、旧 claim 时保留现有兼容；普通旧任务不自动变为监督任务，也不自动开启执行或继承历史。
- 历史“无句柄且 claim 待定”不能仅凭查不到执行就批量解锁。只有存在可核验的明确未提交证据时，才提供显式恢复；否则保留人工对账。
- 需要修复真实存量数据时，另行给出 dry-run 清单、备份方案和用户确认；本计划不授权修改真实数据库。
- 出现回归时可先停止新增自动派发，保留已有运行和结果记录，按逻辑提交回退代码。涉及迁移时采用兼容回退，不删除新数据或历史执行。
