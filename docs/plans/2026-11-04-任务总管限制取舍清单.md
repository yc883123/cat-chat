## 零、归因修正：本地 ComfyUI 不产生费用

本稿初版把「防重复付费」当成多数护栏的理由，**这是错的**。本人 2026-11-04 23:08 指出跑的是本地 ComfyUI。复核后重新归因：

| 类别 | 事实 | 证据 |
|---|---|---|
| 全链路唯一真实付费点 | **反推提示词**调用 `model_key` 指定的云端 LLM，与模型供应商结算 | `recipes.py:1214` → `studio.prepare_generation`；A8 的模板 / 模型门槛只服务这一处 |
| 被误贴「可能产生费用」的 | **视频生成**走 `client.submit(target, workflow)` 到本机 / 局域网 ComfyUI；`naiba/super_agent/` 内无任何计费、余额、账单接口 | `runner.py:455`；`28-super-agent.js:1462, 1481, 1774` 三处文案 |
| 防御体系的真实来源 | super_agent 这套事务框架**本来就该**为付费 LLM 调用而建——那是写小说 / 自动对话 / 子助手线路，护栏有真实理由。问题不在框架本身，而在于**它同时管了两条成本结构相反的任务却没分流**，后接入的配方批次把整套「授权 → 冻结 → 双确认 → 幂等」仪式原样继承了下来 | `models.py:211`；`supervision_store.py:69`；`contracts.py:601-603`；`adapters.py:82-84` |

**所以不是「为了省钱才加防御」，而是「一套为付费 LLM 设计的事务仪式，被无差别套到了本地推理上」。** 对 B 类线路而言这些护栏完全正当，谈不上错；错的是 A 类没有走自己的路。「可能产生费用」这句话在本地生成文案里属误导，应去掉（反推文案保留）。

重新归因后的两点变化：

- **「钱」不再是「留」的理由**。C3 从「费用确认」降级为**范围确认**（跑哪几组 / 几条 / 哪个工作流 / 哪个目标）；本地跑坏了重来就是，成本是时间不是钱，那两次确认的仪式基本没有存在理由。
- **幂等、提交结果未知冻结、live graph 校验仍然要留**，但理由换成**时间、显存、结果正确性**：本地一条视频十几分钟，重复提交＝白等 + 占死显存 + 两个分不清哪个对的文件；图不对就跑＝整段时间白费。这些代价不以钱计，但一点也不比钱轻。

一句话（仅 A 类）：**遮羞布没了，「删」的理由反而更硬了**——原来还能拿「怕扣钱」解释的那几道门，现在只剩框架惯性。

## 一、裁决标准

| 裁决 | 含义 | 判据 |
|---|---|---|
| **留** | 用户必须看见、必须停一下 | 删掉它，用户可能白等十几分钟、占死显存、越权、或拿到错的结果且无法追溯 |
| **藏** | 内核照做，但从界面移走 | 系统本来就有这些信息，不需要人再确认一次就能算准；后台自动做，只在失败时说话 |
| **删** | 整条拿掉，不换等价门槛 | 只为让内部数据模型自洽（批级标量、不可变定义、revision 可复算）而要求人重复声明；或补丁叠加出来的重复门 |

一句话：**本地 ComfyUI 不产生费用，所以「钱」根本不是这里的护栏理由。真正该让人感知的只有「跑哪几组 / 跑什么」和「失败了、怎么办」两类，其余都属系统内部事务。**

## 二、前置发现：交接带值需要按字段类型分流

> **2026-11-04 23:33 本人澄清，本节结论已修订**：「造梦机调的参数有时候工作流自带素材路径，提示词文本，这种一定不要带过去」「真正定下来用什么素材一定是在任务总管」。**本节旧版「原样带当前值 / 全带当前值」的裁决作废**，以 `2026-11-04-任务总管统一实施计划-一个框架两种编排.md` §三 3.1 为准。

问题不只是「该带的没带」，还有「不该带的可能混进来」：

| 造梦机 / 工作流里有什么 | 现状 | 本人定下的口径 |
|---|---|---|
| `overrides: collectOverrides()`（`24-comfyui.js:1884-1903`，**不分字段类型，text 也收**） | 交接 body 不传（`28-super-agent.js:1944-1951`），纯参数全丢 | 纯参数按白名单带；**排除 text 与媒体类** |
| `shots`、当前选的 `media_inputs`（`:294`） | `shots` 不传回落 1；`media_inputs` 会进 body | `shots` 带；**`media_inputs` 一律不带** |
| 图内保存的提示词（`recipeSlotValue`，`:1936`） | 会被取来当草稿正文 | **一律不带**，组卡从空开始 |
| 工作流图内 LoadImage 默认文件名 / 文本默认值 | `24-comfyui.js:1907` 注释「其余按工作流原本的值执行」，执行端会沿用 | 建快照时清空或标「未采用」，不得静默生效 |
| 弹窗「✓ 工作流 ✓ 正文 ✓ 素材 ✓ 时长 ✓ 分辨率」`:1874` | 五个绿勾让人以为素材 / 正文已带入 | 改为「参数已带入；素材与提示词请在任务总管逐组填写」 |

**角色分工**：造梦机只定工作流与参数；任务总管逐组定素材与提示词。素材与提示词的最终决定权 100% 在总管。

> 裁决（修订）：交接按**字段类型分流**——纯参数带、素材路径与提示词正文一律不带、组卡初始为空；Q3 二选一保留但收窄为纯参数。仍是优先级最高的一条，但不再是「把用户做过的工作还给他」这么简单：**还给他的是参数，素材与提示词本来就归总管管。**

## 四、最该先动的三条（如果只做一件事）

### 1 · 删掉手工参数映射（A2 / A3）

后端 `recipes.py:366` **已经在调 `scan_params(graph)`**，只是拿它查 `field_type`，不拿来认用途；前端 `28-super-agent.js:1170-1180` **已经有自动预选**：唯一 `positive_prompt` 或唯一 `multiline` 槽直接选中，`1:144-1147` 还能按「时长 / duration」认时长槽。W1 恰好只有一个 multiline 文本入口，零歧义。

`recipes.py:194` 却写着「映射解释权在用户……不扫描猜测」，`contracts.py:606-608` 的契约注释反而写「服务端自动派生映射」——**注释与实现相反**，这也是这套东西显得一团糟的原因之一。

裁掉的不是「防止猜错」这个目标，而是「让用户从节点 ID 下拉里点一下」这个动作：唯一候选直接用，多候选才弹一次用途确认并按工作流指纹记住。防猜错的目标靠「歧义才问」保住，比现在更准。

### 2 · 把「请新建批次」换成一键「复制为新组」（C11）

`recipes.py:764-784` 的 `clone_draft` 已经把工作流、映射、素材、提示词、条数、模式**全部带出**，且注释明说「never clone authority or attempts」——不带授权、不带执行记录，天然安全。

也就是说：保留「已提交事实不可改写」这条正确内核，同时让用户一键得到一个可改的新组，全部输入不用重填。现在缺的不是能力，是把能力做成一个按钮，而不是甩一句「请新建批次」。C9 / C10 的全批锁同理，改成逐项判定即可，后端不需要新数据结构。

### 3 · 把「前紧后松」倒过来（C5 + D1）

当前预检只做 3 秒探活（`recipes.py:1068-1073`），真正会让生成失败的——节点类没装、必填缺失、LoRA 枚举不符、素材上传失败——全在批次已进入 `generation_running` 之后、`runner.py:444` 才报。前端自己承认（`28-super-agent.js:1821`）「预检不保证显存充足、模型已安装或付费余额足够」。

**正确取舍不是"删掉预检"，而是把 D1 的 live schema 只读校验前移一份到预检**：门变少了，但失败更早知道。这才是"限制少"还能"更安全"的唯一路径。前移只做只读 `object_info_node`，不提交、不上传、不启动推理。

## 七、架构选择：不新增框架（本人 23:13 追问）

问：「是不是需要增加一个框架，专门用来本地批量？」

**答：不需要。缺的是「编排减负」，不是「第二套框架」。**

### 为什么不用新框架

1. **A 类早就有自己的执行器**。`runner.py::_run_recipe_task` 独立把图提交到本地 ComfyUI，`recipes.py` / `recipe_store.py` 独立存批次，`24-comfyui.js` 独立扫参数。它**并没有复用** B 类的 `supervised.py` / `domain.py` 执行器——分家在执行层已经完成了。
2. **分流点也已存在**。`RECIPE_EXECUTOR_TYPE = "recipe_batch"`（`contracts.py:615`），`adapters.py:82-84` 按 `executor_type` 严格路由，前端 `28-super-agent.js` 已有 recipe 分支。再加一个框架等于把已有的分流重做一遍。
3. **真正混在一起的只是「编排仪式」**：授权 / 冻结 / 双确认 / 全批锁 / capabilities，是 recipe 分支自己照抄了 B 类的事务语义（见 §零）。这层就在 `recipes.py` 内部，改它即可，不必动框架边界。
4. **新框架的代价是实打实的**：第二套参数系统（母本 §5.1 明令「不另造参数扫描和类型系统」）、第二套状态机与 UI、旧批次兼容迁移、造梦机 → 总管交接重写、双份测试与回归；而 `comfyui/client.py`、`runner.py`、素材上传、工作流 store 仍得共用，等于只复制了编排层，收益极小、风险极大。实施切片计划 §2.3 也已写明「不另造生成通道」。

### 该做的是：一个框架、两种编排

| 层 | A 类 · 本地批量（改） | B 类 · 云端 LLM（不动） |
|---|---|---|
| 入口 / 分流 | `executor_type=recipe_batch`，按它渲染轻量确认 UI | 现有 `domain` / `supervised` 路由 |
| 编排 | **瘦身**：item 级快照 + 一次范围确认 + 静默预检 + 逐组独立；去掉授权仪式、全批锁、手工映射 | 保留预算 / 轮次上限 / 逐阶段审批 / 工具审批 / 人工边界 |
| 执行底座 | **共用不动**：`comfyui/client.py`、`runner.py` 提交与图校验、素材上传、`scan_params` / `enrich_slots`、工作流 store | 各自服务，不共用 |
| 正确性护栏 | 保留幂等、提交未知冻结、结果回收（理由见 §零） | 保留全部 |

一句话：**把 A 类从「付费事务」降级成「本地作业队列」，而不是给它另起一个框架。** 改动锁在 §零 表的 A 类代码边界内，B 类零改动。

> 若日后本地批量扩展到批量出图 / 批量音频 / 本地模型批量推理，仍应复用同一 `recipe_batch` 执行器与共用底座，按工作流类型扩展 item 输入，而不是新建框架。那是扩展点，不是分家理由。
