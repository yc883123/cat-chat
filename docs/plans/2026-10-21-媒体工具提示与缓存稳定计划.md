# 媒体工具提示与缓存稳定计划

- 日期：2026-10-21
- 状态：已实施（实现 + 守门测试 + 真实供应商预热对照 + 浏览器验收全部完成，见文末「实施记录」）
- 目标：正确区分媒体展示、内容读取和元信息查询；扫描器实际附卡后，模型能获知附卡事实；预热后的缓存命中率与当前基线基本持平。

## 1. 现状与边界

- 视频策略和附件引用行曾把抽帧写成默认路径；展示现有视频与理解视频内容需要明确分流。已修改的规则先作为当前基线，不在本计划里重复改动。
- 媒体采集结果在宿主侧写入 `run.media` 并交给前端渲染；`model_visible_run` 会剥离媒体记录，所以扫描命令成功并实际出卡后，模型不一定知道卡片已附上。
- `build_model_history` 会重建附件引用行和工具结果；历史回放字节变化会从变化位置断开前缀缓存。已有图片编码缓存只缓存编码字节，不能替代请求前缀稳定性。
- 缓存命中率由模型服务商决定；本计划能约束应用请求的稳定性并测量命中表现，不能承诺服务端每次命中。

## 2. 行为规则

1. 用户要求展示一个已知媒体，且本轮采集器已成功附卡：告知模型“已附卡”，不再调用 `show_media` 重复展示。
2. 用户要求展示一个已知媒体，但本轮尚无卡片：使用 `show_media`；目标不唯一时先询问。
3. 用户询问媒体内容、细节或摘要：使用对应读取/分析工具。视频才按需要 probe、抽帧和视觉分析；图片与 PDF 按各自工具职责处理。
4. 用户只问元信息时，只调用能回答该问题的元信息工具，不生成媒体卡、不做多余内容分析。
5. “已附卡”事实必须来自本轮宿主采集器成功产生的媒体记录，不从 stdout 中单独推断，不把模型之前的说法当事实。

## 3. 提示与结果设计

- 系统提示集中放稳定的媒体分流规则，仍按会话固化工具集条件注入；本轮文件名、卡片状态、时间戳、随机 ID 不进入系统提示。
- 工具描述保留用途、触发条件和关键参数；不把长流程重复写进每个工具描述。工具 schema 不按本轮附件或采集结果动态变化。
- 媒体采集成功后，在模型可见的本轮工具结果末尾附一条短状态，包含“已附卡”、类型和展示名；不包含绝对路径、缩略图路径或其他宿主字段。
- 状态只根据 `run.media` 等实际采集结果生成；采集失败、空结果或拒绝结果都不得声称已附卡。
- 状态排序、字段顺序、截断长度和序列化形式固定。多卡只列有限名称并明确截断数量，避免结果无限增长。
- 同一媒体来源在一轮内只计为一张卡；扫描工具与 `show_media` 命中同一来源时，模型状态、消息附件和前端卡片采用同一去重结果。

## 4. 缓存保护

- 保持 system prompt、tool schema、固定附件引用行和历史工具结果的序列化确定；同一会话设置下不依赖本轮媒体状态改变这些稳定前缀。
- 动态“已附卡”状态只放当前工具调用的结果尾部；历史回放必须从已保存的 `run.media` 和同一序列化函数重建完全相同的模型可见字节。
- 不重写旧用户消息、旧附件引用行或既有工具 trace 来注入新提示。提示规则升级产生的一次冷缓存属于版本变更成本；之后相同请求前缀必须稳定。
- 每条采集状态设置紧凑 token 预算；只列模型区分目标所需的文件名与媒体类型。
- 不改变图像编码字节、图片历史保留策略、工具集快照、媒体存储或授权边界。

## 5. 基线与验收

### 缓存基线

- 实施前固定模型供应商、模型、工具集和代表性会话，记录预热后的每请求 `input_tokens`、`cached_tokens`、`uncached_tokens`、`cache_hit_rate`。
- 基线覆盖无媒体、视频抽帧分析、Pwsh 扫描出卡、图片读取和 PDF 读取；每种场景用相同的请求序列重复采样，排除第一次冷启动请求。
- 对照当前部署版本与新版本的预热请求，记录中位数和波动范围；不能用不同模型、不同工具集或不同会话长度直接比较。

### 通过标准

- 同一会话设置重复构造时，system prompt、tool schema 和历史共享前缀逐字节一致；动态附卡状态只增加在当前工具结果尾部，回放结果与首次发送逐字节一致。
- 每个实际附卡来源恰有一张前端卡；模型收到对应文件名、类型和已附卡状态；模型不为同一来源再次调用 `show_media`。
- 预热后的 `cached_tokens` 中位数至少达到当前基线的 98%，`cache_hit_rate` 中位数下降不超过 2 个百分点；差异需落在基线重复采样的波动范围内，或有明确的新增状态 token 数解释。
- 单条状态满足固定 token 预算；缓存指标不支持的供应商以请求字节稳定性和状态 token 数作为应用侧验收，不报告为“缓存命中已保证”。
- 反例验证：采集失败、非媒体路径、重复来源和仅打印路径但未采集的结果，模型都不能收到“已附卡”状态。

## 6. 实施步骤

1. **锁定当前基线**：保存代表性请求的模型/工具定义字节摘要与缓存指标；标注冷启动请求。
2. **实现模型可见采集状态**：在统一的模型可见结果出口根据实际媒体记录生成短状态，并复用同一函数用于实时工具循环与历史 trace 回放。
3. **补全稳定分流规则**：只在系统提示稳定区补充“已有卡片无需重复出卡”；保持工具 schema 与附件历史引用行不随本轮状态变化。
4. **守住去重与权限**：验证采集器仍是附卡事实唯一来源，工具拒绝和失败不回报成功，不扩大路径授权。
5. **回归和实测**：跑媒体采集、模型可见结果、历史 trace、附件字节一致性、工具提示门控及缓存诊断测试；在相同供应商设置下完成预热对照。
6. **浏览器验收**：按维护说明完成 Playwright 桌面和 375px 手机验收，确认工具结果可见、媒体卡无重复且历史消息正常。

## 7. 涉及入口与重点测试

- `naiba/core/tool_results.py`：模型可见工具结果脱敏与媒体状态摘要。
- `naiba/skills/agent.py`：媒体采集时机与工具结果回灌。
- `naiba/core/history.py`：工具 trace / 附件历史回放字节。
- `naiba/run/chat.py`：会话固定提示和缓存指标汇总。
- 重点守门：`tests/test_video.py`、`tests/test_show_media.py`、`tests/test_attachment_only_send.py`、`tests/test_prompt_gating.py`、`tests/test_tool_description_slim.py`、历史 trace 与缓存诊断相关测试。

## 8. 明确限制

- 修改固定 system prompt 或工具 schema 后，旧前缀会有一次重新预热成本；本计划保证的是变化后稳定复用，不保证部署切换时零冷缓存。
- 外部服务商可以不提供缓存指标或改变缓存策略；此时只能验收应用请求的字节稳定、动态状态 token 预算和现有历史缓存诊断。
- 真实内容分析仍会产生必要的新工具结果和图片输入；目标是保持旧前缀可复用，不是让新增任务内容也变成缓存命中。

### 守门测试

- 全量回归 `unittest discover` 通过；`scan_undef_all` 0 候选；`node --check` 与浏览器冒烟通过。

### 真实供应商预热对照（DeepSeek 官方 `deepseek-chat`，隔离实例 + 固定语料）

- 探针：`verify/probe_media_cache.py`（base = HEAD 归档解包，new = 工作树）；每场景 2 个逐字节相同输入的会话，指标取应用自身 `metadata.usage.requests_detail`。原始数据：`verify/_probe_media_cache_base.json` / `_probe_media_cache_new.json`。
- turn2（历史回放轮）中位数对比（base → new）：

| 场景 | 命中率中位 | cached 中位 | uncached 中位 |
|---|---|---|---|
| S0 纯文本 | 96.8% → 97.1% | 6272 → 6528（+256） | 207 → 192 |
| S1 Pwsh 扫描出卡 | 97.4% → 97.4% | 6656 → 6912（+256） | 179 → 187 |
| S2 指名出卡 | 97.0% → 97.2% | 6464 → 7104（+640） | 200 → 201 |

- 结论：命中率中位数未下降（−0.3pp 以内波动内为正），cached 中位数全部上涨（新增的前缀字节被正常预热并复用），uncached 中位数变化 ≤ ±15 token（落在重复采样波动内），满足 §5 全部通过标准。cached 增量含发布整体的提示词/工具描述扩量（视频策略重写、show_media 指引改写等基线改动）与短注自身（每条 ≈20 token，S2 多一卡据此更大）。
- 附卡事实核验：new 变体 s1/s2 的工具结果尾部均出现「本轮已附媒体卡 1 张」且仅一次；base 变体全部为空（反例方向正确）。
- 跨调用去重：S2 中 show_media 与扫描工具命中同一来源时，注按各自调用如实出（信息一致、无矛盾），消息附件与前端卡由 `union_run_media` 去重为一张（§3 口径的同一去重结果）。
