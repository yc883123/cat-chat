# KVMem 在 Cat Chat 内独立启停模型：修复计划

日期：2026-11-17  
状态：仅计划，未实施。本文不构成执行授权。

## 1. 用户要实现的操作

配置一次后，直接在 Cat Chat 中启动 KVMem 推理模型，随时停止，再次启动。不需要先打开 KVMem 控制台或去控制台重新运行模型。

停止必须使 KVMem 托管的模型进程退出，释放该模型占用的显存和内存，让用户自行运行造梦机。后台控制程序可以保留少量普通内存，供下一次启动使用。

本次验收只覆盖启动、停止、再次启动和资源释放。**不调用 ComfyUI，不生图，不做自动显存调度。**

## 2. 已核实的问题

### 2.1 控制程序没开，Cat Chat 无法独立启动

`naiba/app.py::api_kvmem_start` 先调用 `client.status()`，没有后台启动控制程序的步骤。控制程序不可达时，启动请求在读取保存参数前就失败。

KVMem 有三个不同部分：控制台界面、后台控制程序、推理模型进程。模型启停仍由 KVMem 后台控制程序负责，Cat Chat 需要具备后台拉起控制程序的能力，不能把“先手动打开控制台”留作前提。

### 2.2 缓存读错了配置来源，保存范围也不完整

`naiba/kvmem.py::info()` 从 `info.draft.parameters` 提取 `Backend/Model/Worker/Gpu` 四项。`api_kvmem_status` 仅在就绪检查通过后保存这四项，`api_kvmem_stop` 停止前没有保存正在运行的完整配置。

本机安装的 KVMem 0.19.1 中：

- 实际运行配置在 `status.active_config`，结构为 `{schema_version: 1, parameters: {...}}`。
- 停止会清空 `active_config`。
- `info.draft` 来自后台保存文件，没有该文件时返回默认值，`Model` 可以为空。
- KVMem 网页编辑自动保存的是浏览器 localStorage，不能据此认定后台已有启动配置。
- `/api/launcher/start` 不会自动把本次参数保存成后台草稿。

因此，“模型曾经从控制台运行过”并不能保证 Cat Chat 记住了它。只补四项缓存，也不能保留上下文、显存分配等完整启动参数。

### 2.3 状态解析和操作后刷新不完整

`KVMemClient._status_payload()` 主要读取草稿顶层的 `backend/model/port` 等字段，真实配置却放在 `parameters` 中，也没有优先读取 `active_config`。

`public/js/07-models-agents.js::kvmemAction()` 操作后只立即刷新一次，没有持续确认启动完成、加载失败或停止完成。旧测试桩同时提供两套字段，掩盖了真实结构不匹配的问题。

### 2.4 Cat Chat 内缺少启动配置入口

现有供应商设置只提供 KVMem 管理开关和控制地址。通用“模型名称”是推理接口的模型标识，不能当成磁盘上的模型文件路径。

目前没有安装目录、实际模型路径、后端或完整启动配置的管理入口，首次配置仍会被迫依赖控制台。

## 3. 修复后的使用方式

1. 在 Cat Chat 的 KVMem 供应商设置里指定安装目录和实际模型；已经运行着模型时，可以点“读取当前运行配置”，带入现有完整参数。
2. 保存后点顶栏“启动”。后台控制程序没开时由 Cat Chat 拉起，不打开 KVMem 网页；随后使用已保存参数启动模型，状态持续更新到就绪或明确失败。
3. 点“停止”。停止前保存当前运行配置，通过 KVMem 正常停止其托管模型，确认模型进程退出后显示“已停止”。
4. 再点“启动”，使用已保存配置重新运行，全程留在 Cat Chat 内。

首次配置也能直接在 Cat Chat 内完成。没有可导入的运行配置时，允许填写模型路径、选择后端和 GPU，其余参数采用对应 KVMem 版本的默认值；已有完整配置可导入保留，不能要求用户先去控制台启动一次。

## 4. 实现方案

### 4.1 持久保存完整启动配置

涉及：`naiba/config.py`、`naiba/kvmem.py`、`naiba/core/contracts.py`。

- 为 KVMem 配置登记安装目录和版本化启动配置字段，实际模型路径与 API 模型标识分开。
- 完整参数保留数值、布尔等类型，不转换为四项字符串缓存。
- 设置中的启动配置按供应商保存；自动记录的最近运行配置按供应商和规范化控制地址隔离，避免共用地址或不同后端串用参数。
- 保存复用现有配置存储、原子替换和读改写锁；写入失败要明确提示，不能声称已记住。
- 临时控制令牌只放内存。启动配置中的 API Key 转入现有密钥处理，不在配置摘要、导入预览、公开供应商数据或日志中泄露。
- 兼容读取旧 `last-start.json`，四项旧缓存只能作为有限迁移来源，缺少的历史完整参数不能假称已恢复。
- 导入运行配置优先使用 `active_config`；没有运行配置时才考虑有效后台草稿。明确保存的配置是后续启动依据，不再依赖临时空草稿补值。

### 4.2 后台启动 KVMem 控制程序

涉及：`naiba/kvmem.py`、`naiba/app.py`。

- 由组合根持有后台控制程序管理对象和按控制地址隔离的操作锁。
- 启动操作先探测已配置控制地址。已有有效 KVMem 控制程序就复用；只有明确不可达时才尝试后台启动，协议错误或 HTTP 错误不能一概当成“没有启动”。
- 使用用户配置的安装目录验证自带 Python、`scripts/local-console.py` 和安装元数据，以参数数组拉起，不拼 shell 命令。
- 采用安装包支持的入口：自带 Python 的 `-X utf8 -I` 加控制程序脚本，明确本机回环地址、端口、后端根目录、受管状态目录和自带 worker 选项。
- 不传打开浏览器或交互选端口参数，不硬编码本机安装目录，不修改 KVMem 包文件。
- 有界等待控制程序可用，再提交模型启动配置。安装文件缺失、地址不匹配、端口冲突或启动退出分别报错。
- 核对控制程序协议和安装身份；占用端口的外部服务不能强杀或误接管。
- 记录自己拉起的进程句柄和日志，区分复用外部控制程序与本程序启动的控制程序。退出清理由明确所有权处理，不能扫 PID 杀进程。

### 4.3 启停与状态使用同一份实际配置

涉及：`naiba/kvmem.py`、`naiba/app.py`。

- 状态从真实 `active_config.parameters` 读取模型、后端和端口，停止态摘要可使用本供应商保存的配置。
- 启动使用完整保存配置，按所选后端与当前版本默认值合成，不能把另一后端的默认参数或旧参数混入。
- 对推理服务的就绪检查使用供应商已有鉴权，避免模型已经运行却因缺鉴权被误判失败。
- 停止前保存当前完整运行配置；保存不成功时明确提示，避免静默丢掉可恢复参数。
- 继续走 KVMem 的 `/api/launcher/start` 与 `/api/launcher/stop`，模型进程仍由 KVMem 管理。
- 同一控制地址的操作串行，正在加载时重复启动、不同供应商同时点启动等情况不得重复提交。
- 启动请求超时先查询受理与运行状态，不能盲目重试创建第二个模型进程。
- 保留已有使用中任务保护。停止应确认 KVMem 托管模型已退出，再展示停止完成；停止超时或失败不能报成功。

### 4.4 补齐配置界面和顶栏状态

涉及：`public/index.html`、`public/js/09-settings.js`、`public/js/07-models-agents.js`、必要的局部样式，以及 `naiba/http.py` 的配置读取路由。

- 现有 KVMem 设置区增加安装目录、实际模型路径、后端、GPU 和“读取当前运行配置”。完整配置导入和查看收在可折叠区，日常启停仍用现有顶栏按钮。
- 读取运行配置不启动模型；需要拉起后台控制程序以读取默认参数时，由用户明确点击对应动作。
- 供应商表单的加载、保存、取消、复制、预设和旧配置兼容一起处理。异步导入核对表单代次，不能覆盖用户已修改的输入或另一张卡。
- KVMem 未运行时也能保存本地启动配置，不能强制依赖 `/v1/models` 检测成功。
- 控制程序没开但配置完整时，“启动”仍可用；参数缺失时引导到 Cat Chat 内的配置入口。
- 操作后显示启动中／停止中，有界轮询直到就绪、停止或明确失败。保留已有供应商与请求代次校验，切会话后旧返回不能覆盖当前状态。
- 替换“先到 KVMem 控制台启动”的文案，不新增控制台窗口前置步骤。

## 5. 验证与验收

### 5.1 自动测试

扩展现有 `tests/test_kvmem.py`、`tests/test_kvmem_config.py`，使用与 0.19.1 相同的响应结构，至少覆盖：

- 草稿模型为空，但 `active_config` 有完整运行配置。
- 停止后后台清空配置，Cat Chat 仍可用原参数再次启动。
- 完整参数类型、后端隔离、供应商隔离、旧缓存迁移及密钥不外泄。
- 控制程序不存在时后台拉起，已有控制程序时复用。
- 模型加载失败、端口冲突、控制程序启动失败、重复点击和启动受理未知。
- 停止前保存失败、任务占用阻止停止、停止结果未确认不能报成功。

使用项目 `.venv`，按维护说明完成全量测试与静态检查。新增测试模块时同步 CI 分片清单。

### 5.2 浏览器验收

扩展现有隔离夹具 `verify/_serve_clear_kvmem.py` 和 `verify/clear_kvmem_smoke.cjs`，覆盖桌面和 375px 手机：配置保存、读取运行配置、离线保存、启动、停止、再次启动、状态持续确认、切会话迟到回包、错误可见且无脚本错误。

替身浏览器测试只证明界面与接口接通，不能作为真实模型释放显存的证据。

### 5.3 真机验收，仅 KVMem

实施后，在不打断正在进行的推理任务的前提下：

1. KVMem 控制台界面关闭，后台控制程序未运行时，从 Cat Chat 点启动，确认模型就绪。
2. 从 Cat Chat 停止，确认托管模型进程退出、该模型占用的显存及内存释放。
3. 再从 Cat Chat 启动，确认使用原模型和完整参数成功运行。
4. 检查 Cat Chat 或控制程序重启后，仍能使用已保存配置启动。

资源验收按模型进程退出和启停前后差值判断，不能要求整机显存归零。后台控制程序的小量普通内存不算模型未卸载。

**不调用造梦机，不运行生图工作流。**
