### 2.3 正确的区分（这是计划该写而没写的）

| | 内容 | 交接 |
|---|---|---|
| **值 · 填什么** | 具体素材文件（路径 / 受管引用）、提示词正文文本、工作流图内自带的默认文件名与默认文本 | **一律不带**；每组从空开始，由用户在总管逐组定 |
| **结构 · 往哪填** | 造梦机已识别并增强好的**完整槽位定义**：`node_id` / `field_name` / `field_type` / `role` / `label` / `control` / `media_optional` / 枚举候选 / 单位，以及由此确定的 `prompt_slot`、`duration_slot`、`media_slots` | **必须原样带过去**；总管直接用，**不再自己 `scan_params` 重扫、不再用正则猜时长** |

一句话：**用户要丢的是「素材文件和那段文字」，不是「素材该填进哪个节点、时长该写进哪个参数」。** 造梦机调好的那份「哪里填什么」正是最该交接的东西。

> 本人 23:33 说「真正定下来用什么素材一定是在任务总管」——指的是**选哪个文件**由总管定，不是「哪个节点是素材入口」也由总管重新猜。我把它读成了后者，这是本次事故的源头。

### 2.4 建议修法（仅方案，未实施）

1. 交接 body 增带 `params`（`enrich_slots` 后的增强槽位）与由其确定的三套映射 `prompt_slot` / `duration_slot` / `media_slots`；**值与结构分字段**，不要用「素材一律不传」这种会误伤结构的话。
2. 后端 `create_from_workflow` 优先采用递过来的映射；仅当缺失时才回退静态派生，且回退要在界面上明示「本次为自动识别」。
3. 交接弹窗把三类绑定都展示出来（提示词写进哪个节点、素材走哪几个槽、时长写进哪个参数），用户看得见才谈得上信任。
4. 组卡保留槽位定义、清空「值」；上传按递过来的 `role` 绑定，不再二次派生。
5. 写只读探针取真值：打印交接 body、`recipe.media_slots`、组卡 `data-recipe-media-upload` 的 role 三处，确认是否一致后再改代码（诊断纪律：真后端复现不出的 UI 形态不盲改）。

### 6.2 更正上一轮的推测

上一轮 §2.2 推测「role 对不上 ⇒ 保存绑不上」。**真值不支持**：最新草稿批次里素材已成功落库、生成 `effective_media_inputs` 并跑到 `pending`。因此本人说的「根本传不了素材」，**不是技术提交失败**，而是下面四点合起来造成的「不知道怎么填 / 不敢填」：

1. **语义全丢**：12 个槽只有节点号和连线串，没有 `<Picture N>` 对应关系、没有用途标签、没有可选性。用户面对 12 行 `載入圖片 · image → ref_images.ref_image_N`，不知道哪张图该放哪个槽、放几个算对。
2. **提示词槽必须手工挑**：自动派生为 null，交接弹窗那个下拉是**强制人工裁决**，恰恰违背「造梦机已设定好、递过去总管就知道」的预期。
3. **时长绑定不可见**：`259>value` 是正则猜中的，界面只写「15 秒 · 沿用工作流保存值」，从不说明写到哪个参数 → 「根本不知道哪个参数控制时间怎么就能填」。
4. **`media_optional` 缺失**：总管不知道哪些槽未选可安全跳过；12 个全 `required=false`，界面也没解释。

一句话：**递过去的是「没有语义的原始槽位清单」，不是造梦机里那份「哪里填什么」。** 这与本人 09:08 的判断一致，且比初稿定位更准。
