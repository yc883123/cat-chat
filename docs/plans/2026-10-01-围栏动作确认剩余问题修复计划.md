# 围栏动作确认剩余问题修复计划

## 目标

在现有围栏解析修复的基础上，补齐确认授权链路的边界安全，保证：

1. 任何来自整条代码围栏的工具调用都不能通过嵌套字段绕过强制确认。
2. Plan 只读模式在确认前后都保持只读约束。
3. “允许本轮继续执行”只接受明确的布尔值，并且授权范围可被用户看懂、可被测试证明。
4. 用户拒绝、超时、无确认入口时，本轮不会继续把动作失败回灌给模型形成重复调用。
5. 单工具、多工具、Plan、桌面和手机端都通过真实后端与 Playwright 验收。

## 当前审查结论

现有版本已经解决了正文中间代码围栏被当作裸工具协议、流式围栏正文被吞、显式拒绝后再次调用模型等主要问题。定向测试已覆盖围栏矩阵、流式护栏、Run 级授权和无确认 UI 收尾。

仍有以下缺口，按发布阻断级别排序：

| 优先级 | 缺口 | 影响 |
|---|---|---|
| P1 | 多工具 `fenced` 响应允许嵌套 `call.source` 覆盖顶层来源 | 可能绕过围栏强制确认，直接执行 `pwsh` 等工具 |
| P1 | Plan 的 `ReadOnlyToolExecutor` 在确认后被底层 `execute_unchecked` 绕过 | 只读计划可能执行 POST、写入或其它副作用 |
| P1 | API 对 `allow_run` 使用 `bool()` 强制转换 | 字符串 `"false"` 会被当成 `True`，错误扩大 Run 级授权 |
| P2 | 确认超时/失效没有统一走围栏终止收尾 | 可能把失败回灌模型并触发重复确认或额外模型调用 |
| P2 | 多工具围栏并行等待会生成多张确认卡 | 用户批准一张卡后，剩余调用仍可能悬挂等待 |
| P2 | Plan 确认详情丢失 `action_source`，前端没有 Run 级授权提示 | 用户无法判断这是代码围栏动作，也看不出批准范围 |
| P1 验收阻断 | Playwright 冒烟在终态要求 DOM 中仍有确认卡 | 实际动作成功，但验收脚本误报失败，无法形成发布证据 |

## 实施步骤

### 1. 封锁嵌套来源覆盖

涉及：

- `naiba/skills/agent.py`
- `tests/test_fence_actions.py`

规则：

- 顶层 action 来源为 `fenced` 时，所有 `tools.calls` 强制继承 `fenced`。
- 忽略或拒绝嵌套 call 的 `source` 字段，不允许 `final`、`native` 或其它值降级确认要求。
- 非 `fenced` 的 `native`、`bare_protocol_tail` 继续保持现有权限策略。

新增回归测试：

- 整条围栏包裹的多工具 JSON，其中一个 call 标记 `source=final`，仍必须产生 `fenced` 确认。
- `pwsh`、`write_file`、`http_request` 至少各覆盖一个绕过尝试。
- 确认被拒绝时，所有调用都不执行，模型调用次数保持为 1。

### 2. 保持确认后的执行代理

涉及：

- `naiba/tools/executor.py`
- `naiba/plans.py`
- `naiba/run/chat.py`
- `tests/test_fence_actions.py`
- 只读权限相关测试

规则：

- 待确认项必须保存实际执行代理或保存确认后的复核入口。
- `ReadOnlyToolExecutor` 的禁止工具、MCP、工作流和 HTTP method 检查，确认前后必须一致。
- 确认后的执行不能无条件落到底层 `execute_unchecked`；若仍需底层执行，先由外层代理重新校验。

新增回归测试：

- Plan + fenced `http_request POST`：确认后仍拒绝，底层实现不能被调用。
- Plan + fenced MCP `run_workflow`：确认后仍拒绝。
- Plan + fenced `GET`：确认后允许，证明只读能力没有被整体误伤。

### 3. 收紧 `allow_run` 协议

涉及：

- `naiba/app.py`
- `naiba/run/manager.py`
- `naiba/tools/executor.py`
- `public/js/12-chat-input.js`
- `tests/test_fence_actions.py`

规则：

- API 只接受 JSON `true` / `false`；字符串、数字、数组和对象返回 400。
- `allow_run=false` 只执行当前工具，不写入 Run 级授权。
- `allow_run=true` 才写入绑定当前 Run、工作区和工具集合的授权。
- 旧前端缺省字段的兼容策略必须明确写入测试；不能让任意缺省值无提示地扩大授权。

### 4. 统一拒绝、失效和超时收尾

涉及：

- `naiba/skills/agent.py`
- `naiba/tools/executor.py`
- `tests/test_fence_actions.py`

规则：

- 明确拒绝、确认 ID 失效、确认超时都走同一条围栏未执行收尾。
- 不把“用户拒绝/自动拒绝/确认失效”作为新的模型工具结果回灌。
- 原始围栏正文仍保留在最终消息中，并标注“未执行”。
- 终止后只允许产生一次终态消息，不得发起新的模型请求。

### 5. 收敛多工具确认行为

涉及：

- `naiba/skills/agent.py`
- `naiba/tools/executor.py`
- `public/js/12-chat-input.js`
- `tests/test_fence_actions.py`

规则：

- 一个 `fenced` 多工具 action 只产生一个可操作的确认回路。
- 用户选择“允许本轮继续执行”后，同一 Run 且工具集合、工作区不变的后续调用直接执行。
- 用户选择“仅允许这一次”时，其余调用必须按顺序重新确认，不能并行挂起多张卡。
- 用户拒绝时，整条 action 收尾，不执行其它同批调用。

### 6. 补齐 Plan 确认卡契约

涉及：

- `naiba/plans.py`
- `public/js/06-tasks-plans.js`
- `tests/` 中 Plan/事件契约测试

规则：

- Plan 的确认详情保留 `action_source`。
- `fenced` 来源显示与普通确认不同的说明，并明确授权范围。
- 确认请求显式传递 `allow_run`，不再靠缺省值隐式授予 Run 级授权。
- Plan、普通对话和历史回放使用同一来源字段和终态语义。

### 7. 修正 Playwright 验收脚本

涉及：

- `verify/fence_action_smoke.cjs`
- `verify/fence_action_smoke.py`

规则：

- “全程只确认一次”通过记录确认事件数量或确认卡出现次数验证。
- 不在终态重渲染后要求 `.tool-confirm` 仍留在 DOM 中。
- 保留桌面 1440×900、手机 375×720、按钮可点击、卡片不溢出、无横向滚动、零 pageerror 检查。
- 后端复核确认每个 Run 只有一个 `tool_confirm` 事件，两个工具均成功。

## 验收清单

### 单元与契约

使用项目虚拟环境运行：

```powershell
.venv\Scripts\python.exe -m unittest discover -s tests -p 'test_fence_actions.py' -v
.venv\Scripts\python.exe -m unittest discover -s tests -p 'test_llm_stream.py' -v
.venv\Scripts\python.exe -m unittest discover -s tests -p 'test_tool_permissions.py' -v
.venv\Scripts\python.exe -m unittest discover -s tests -p 'test_events_contract.py' -v
.venv\Scripts\python.exe -m unittest discover -s tests -p 'test_tool_registry_shape.py' -v
```

必须新增并通过：

- 嵌套来源覆盖回归。
- Plan 只读确认后复核回归。
- `allow_run` 类型校验回归。
- 超时/失效不回灌回归。
- 多工具只确认一次与拒绝全收尾回归。

### 真实链路与前端

```powershell
.venv\Scripts\python.exe verify\fence_action_smoke.py
```

脚本必须完成以下断言：

- 正文中的围栏示例不执行，正文完整。
- 整条围栏动作先确认，拒绝后不再请求模型。
- 批准后同一 Run 的后续围栏动作不重复确认。
- Plan 只读约束在批准后仍有效。
- 桌面和手机确认卡均可操作且不溢出。
- 浏览器无 `pageerror`、无横向滚动。

## 完成标准

只有当 P1 项全部修复、P2 回归测试补齐、真实 Playwright 冒烟通过，并且维护说明同步反映新增测试与契约时，才将本轮修复视为完成。

本计划不改变原生 function calling、尾部裸协议和已有 `auto/full/confirm` 权限模式的既定语义；只收紧围栏来源动作的来源继承、确认范围和只读执行边界。

### 补记中发现的两条现状（改代码前先看）

1. **Plan 模式当前已封存**：`run/chat.py` 里 `mode` 硬编码 `"craft"`，计划步骤执行器用
   `CraftToolExecutor` ⇒ `ReadOnlyToolExecutor` 目前**不可达**。§2 的加固属「复活时就已经是对的」
   的契约防线；冒烟无法直接验收「Plan 只读约束在批准后仍有效」，由
   `PlanReadOnlyConfirmTests` 单测承接。
2. **Plan 的前端 UI 是不可达代码**：`public/index.html` 没有 `#planBar` 等 Plan 容器，
   `06-tasks-plans.js` 的 Plan 段落从不渲染。实际给用户看的 Plan 确认卡就是普通对话的
   `.tool-confirm` 卡（已支持 `action_source`）。本轮只对齐契约，没有新建界面。
3. **确认卡上没有「仅允许这一次」按钮**：fenced 卡只有「拒绝 / 允许本轮继续执行后续操作」，
   `allow_run=false` 的语义由 API 与单测覆盖；若要给用户这个选项，属后续 UI 决策。
