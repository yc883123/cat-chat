# 自动压缩可靠性与缓存保护修复计划

日期：2026-10-29  
状态：计划稿，尚未实施  
依据：当前冻结版会话事件、Cat Chat 自动整理源码、`D:\rea\codex-上下文压缩拆解报告.md`、`D:\deepseek-harness` 只读源码检查及用户提供的 Codex 官方行为说明。

## 1. 目标

修复长对话自动整理连续失败、失败后仍沿用过长原历史继续请求，以及摘要内容校验过于脆弱的问题。同时把**缓存命中率作为硬性验收条件**：不触发整理时请求前缀不得变化；整理失败不得污染原请求历史；成功整理后要单独测量冷启动成本和后续缓存恢复。

## 2. 已确认事实

- 冻结版当前会话近期自动整理已触发多次，失败原因包括 `summary_not_structured`、`summary_missing_sections(1)` 和 `summary_failed:RuntimeError`。
- 当前失败路径不写摘要标记，但会继续沿用原历史。因而后续模型请求可能仍携带未整理、继续增长的上下文。
- 上次修复补齐了实时 usage 的窗口字段，并让循环整理检查参考最近一次实际输入 token。它改变触发判断，不把这些字段加入模型请求；目前证据不能证明它导致摘要请求异常，但更早发现阈值可能使摘要路径更常被触发。
- 用户提供的 Codex 拆解报告显示：压缩会整体替换中间历史，保留初始上下文、交接摘要和有限近期原话；压缩成功会改变后续请求前缀并导致一次缓存冷启动。报告也观察到窗口预留、压缩请求推理开销及超窗口兜底。
- `D:\deepseek-harness` 的压缩实现强调：摘要失败不能被视作已有压缩进展；只有先发生可验证的输入缩减/持久变化，才允许恢复性重试。该项目有多条机制与 Cat Chat 不同，不能直接照搬其全部窗口、token 计量或缓存实现。

## 3. 硬性缓存原则

1. **未触发整理时零请求差异**：system、工具定义、历史消息及其顺序必须和基线逐字节一致。触发估算、usage 事件、日志和 UI 状态不得进入模型请求。
2. **usage 只做旁路数据**：窗口、来源、缓存统计只写入 run event / 展示层，不写进聊天历史、摘要正文、工具参数或后续请求消息。
3. **失败不改前缀**：摘要请求失败、校验失败、取消或写标记失败时，不写压缩标记、不重建历史、不对原历史做裁剪。失败处理是否继续本轮另按窗口余量决定，但不得静默改变请求前缀。
4. **成功后承认一次冷启动**：成功替换历史必然建立新前缀。整理后的首个正常请求单独报告缓存冷启动，不把这一点误判为普通稳态缓存回归。
5. **检查恢复而非只看冷启动**：至少观察整理后首请求及后续两个相同稳定前缀请求，确认缓存重新建立；报告 cached/input/miss token、命中率和延迟。
6. **禁止为了提高样本量反复付费**：真实供应商探针先跑最小可判定样本，每个策略一组后先报告；只有用户确认后才扩样。

## 4. 计划实施内容

### 4.1 交接式摘要与稳健校验

将现有固定九标题摘要要求调整为面向接手工作的结构化交接文档。重点覆盖：

- 当前目标和用户约束；
- 重要背景、关键决定和事实；
- 已完成事项及实际验证结果；
- 尚未解决的问题、失败尝试和未完成状态；
- 关键路径、错误、命令或数据；
- 清晰的下一步。

不再用固定标题关键词命中数作为主要成功标准。保留必要的最短/最长长度、内容非空、非拒答、摘要确实比输入短等保护，避免把无效输出写入会话。校验只判断可用性，不强迫模型逐字输出某套标题。

### 4.2 摘要预算和有限恢复

- 为隐藏摘要请求明确设置独立输出预算，避免直接套用正常回复的小预算；同时保留运行时取消能力。
- 对摘要 `RuntimeError` 不进行同输入、同提示的盲目重试。
- 对明确的摘要输入超窗口错误，可考虑有限的降级：每次先实际缩小被总结区间，再重新计算 token 量并重试；输入没有变化不得重试。
- 恢复尝试设严格上限，并记录每次尝试的输入规模、输出 token、原因类别和是否实际减少了输入。
- 摘要只有通过校验且成功写入标记后，才算发生压缩进展；失败尝试不能消耗掉“已整理”状态或创建半成品标记。

### 4.3 失败后的安全收场

失败后根据有效窗口余量决定当前轮能否继续：

- 仍有足够预算时，可完成当前轮，但本轮不重复发送相同摘要请求；
- 接近或超过硬边界时，若没有成功摘要或其他可验证的输入缩减，就停止后续模型/工具调用，保留已经完成的工具结果，并给出明确状态；
- 不把“继续发送完整原历史”伪装成恢复成功；不因摘要失败清零上下文圆环或误报为压缩成功。

边界数值要复用 Cat Chat 自己的窗口、输出预算及工具 schema 预留口径，通过现有上下文拦截测试校准；不直接把 Codex 报告中观察到的 95% 当成 Cat Chat 固定窗口比例。

### 4.4 触发用量和圆环

保留上次已验证方向：实时 usage 带窗口元数据；循环触发同时参考本地估算和最近一次实际输入量，但不把多次请求输入量相加。明确区分“最近一次提示输入”“输出 token”“会话累计用量”和“窗口占用估计”，不能把累计账单 token 当作下一次 prompt 长度。

失败时保留最后一次真实聊天 usage 显示。隐藏摘要请求不应伪装成普通对话 usage；如需展示摘要尝试，应使用独立诊断字段或状态，不覆盖聊天圆环代表的最近一次对话请求数据。

## 5. 实施顺序

1. 为当前失败流程新增可确定性复现的假模型测试：结构标题变化、缺少某一固定词、运行时错误、摘要太短/太长、摘要未变短、标记写入失败、超窗口和取消。
2. 调整摘要提示与校验，验证交接信息可读且关键路径、失败状态、未完成工作和下一步可保留。
3. 实现有边界的摘要降级/恢复；只有发生实际输入缩减才允许重试，并保护取消与原始历史。
4. 实现失败后的窗口余量决策，确保无进展时不会继续发送已知超限的大历史，同时保留可继续完成的工具结果。
5. 检查 usage 事件、圆环及缓存数据隔离；不得把诊断元数据混入模型消息。
6. 完成所有本地测试和 wire 前缀对比后，才进行一组真实供应商缓存/摘要探针。

## 6. 测试与验收

### 单元与行为验收

- 摘要标题措辞变化但内容完整时可通过；缺少关键交接信息时仍拒绝写入。
- 运行时失败、校验失败、写标记失败都不改原消息、不产生半截标记。
- 相同输入不重复付费重试；只有先成功缩小摘要输入才允许一次有界恢复。
- 到达硬边界且无压缩进展时，不再发送原样超大历史；工具结果和运行轨迹仍保留。
- 窗口尚充足时，失败不会无故中断当前轮。
- 实时圆环在模型回复期间可计算百分比；摘要失败不清空圆环，不误报整理成功。
- 实时 usage、压缩原因和诊断字段不进入聊天消息、system、工具 schema 或请求历史。

### 缓存硬门槛

- 用 wire 测试对比修改前后的 system、tools、history 和完整请求 payload 哈希。未触发整理的路径必须完全相同。
- usage 元数据加入/移除不得改变模型收到的 payload 字节。
- 摘要请求的稳定前缀尽可能与会话原始 system、工具及历史对齐；摘要指令放在变化尾部，减少不必要的前缀差异。
- 真实请求报告至少包括整理前稳态、摘要请求、整理后首请求、后续稳定请求的 `input_tokens`、`cached_tokens`、`uncached_tokens`、命中率和耗时。
- 后续稳定态缓存应回到该供应商/模型基线同量级。判定使用稳定态数据，不以压缩后的首请求冷缓存单独判失败。
- 真实探针必须使用用户当前认可的 TE/摆烂档案；样本先做一组，不自动扩样。失败请求也计入成本和延迟报告。

### 性能验收

- 未触发整理时，模型请求次数不增加；除原有 usage 旁路事件外，不新增模型调用。
- 达到整理阈值后，只发生设计内的摘要请求；重试仅限输入确实缩小且有上限的恢复路径。
- 记录本地假模型循环耗时和真实供应商逐请求延迟，分开报告网络/供应商时间与本地处理耗时。

## 7. 范围边界

- 不重启或直接改动用户正在运行的冻结版实例；需要重新打包/更新时另按发布流程处理。
- 不修改正式配置、用户数据库或既有会话历史。
- 不把 Codex 的 95% 有效窗口、token 总量定义、摘要前缀或内部策略直接复制过来；必须按 Cat Chat 当前 provider 协议、窗口来源和缓存前缀行为重新验证。
- 本文档只定义计划，不代表代码已经修改、测试已经通过或真实供应商已经验证。
