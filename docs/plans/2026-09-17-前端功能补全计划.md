# 前端功能补全计划（2026-09-17）

本文是「前端功能缺口分析」的落地方案，覆盖七项：消息全文搜索、跨会话用量统计、会话导出、分支导航（含侧栏渲染）、删除单条消息、全局快捷键/命令面板、会话归档与批量管理。

**前置讨论（删除单条消息 vs 前缀缓存）见文末附录 A**，结论先记在这里：删除不破坏缓存机制，代价是删除点之后的内容一次性重缓存，比「编辑」便宜，与「分割线」同模式；位置越靠后越便宜，删尾部零成本。

每项计划均按项目惯例执行：先方案确认 → 再改代码；改代码同步改写维护说明对应章节；验证按 §六 分级（取最高级）；前端 UI 变更附 Playwright 截图证据。

## 一、消息全文搜索（建议最先做）

**现状依据**
- 侧栏搜索框（`workspaceSearchInput`）只匹配会话标题与工作区名：`public/js/08-conversations.js:248`、`:271`。
- 后端全文检索能力现成：`storage.search_history`（`naiba/storage/store.py:1078`，`instr(lower())` 子串匹配，支持全库/限定会话两种模式），目前只被 AI 工具 `recall_history`（`naiba/tools/providers/search.py:97`）使用，用户侧无入口。

**方案**
1. 后端新增 `GET /api/search/messages?q=...&conversation_id=...&limit=...`，薄包装复用 `search_history`，返回命中列表（会话 id/标题、消息 id、角色、片段、时间、命中总数、是否截断）。不做鉴权之外的额外限制（本地应用，与现有 API 同口径）。
2. 前端侧栏搜索框升级为双模式：输入框左侧加「标题 / 全文」切换（默认标题，保持现有行为不变）。全文模式调新接口，结果渲染为独立结果列表（替换会话树区域，Esc 或清空关键词退回会话树）。
3. 点击命中项 → 打开该会话并跳转到该消息：复用刻度轨跳转的「先扩懒加载窗口再定位」链路（`renderMessages` 窗口扩展 + 定位），跳转后高亮该消息 2 秒。
4. 会话内搜索（Ctrl+F）并入第六项命令面板/快捷键一起做，复用同一接口的限定会话模式。

**边界与性能**
- 现实现是全表子串扫描；消息总量十万级以内可接受（本地 SQLite，instr 扫描毫秒~百毫秒级）。接口设 `limit` 上限并显式返回截断标记。
- 升级路径（不在本期）：FTS5 虚表 + 触发器，数据量上去后再做。

**改动点**：`naiba/http.py`（新路由）、`naiba/storage/store.py`（如需补 limit 参数）、`public/js/08-conversations.js`（搜索 UI）、`public/index.html`（搜索框结构）、`public/styles.css`。
**验证**：storage 层单测（命中/截断/限定会话）+ 隔离实例 Playwright 冒烟（输入关键词 → 结果列表 → 点击跳转定位）。

## 二、跨会话用量 / 成本统计

**现状依据**
- 用量数据散落在运行事件流的 `usage` 事件里（`naiba/run/chat.py:498`、`_merge_usage_summary:169`），只有单条消息末尾的用量框和上下文圆环两处消费；事件流会被「历史数据管理」压缩，不适合做长期统计源。

**方案**
1. 新增 `usage_records` 表（DB 迁移，幂等）：`id, conversation_id, run_id, provider_id, model_name, input_tokens, output_tokens, cached_tokens, duration_ms, created_at`。每次模型请求终态时在写 usage 事件的同时落一行（单写入点，控制在 chat/plans/subagent 三处 run 完成的统一出口）。
2. 新增 `GET /api/usage/stats?granularity=day|week|month&days=N`：按时间聚合（总输入/输出/缓存命中 token、请求次数、平均速率），按模型与 API 分组两个维度。
3. 前端新「用量」页：设置页左侧导航加分组，或顶栏上下文圆环点击后的面板里加入口。内容：近 30 天趋势柱图（纯 SVG 自绘，项目无前端框架依赖）、按模型/API 的分组表、缓存命中率曲线。成本估算：不内置价格表（各家中转站价格差异大），只显示 token 量；价格表留作后续可配置项。

**改动点**：`naiba/storage/store.py`（表 + 写入 + 聚合查询）、`naiba/run/chat.py` 等三处写入口、`naiba/http.py`（路由）、`public/js/09-settings.js`（统计页）。
**验证**：写入点单测（三处出口都落行）+ 聚合查询单测 + 设置页截图冒烟。

## 四、分支导航（含侧栏渲染方案）

**现状依据**
- `branch_conversation`（`naiba/storage/store.py:1278`）复制消息与设置到新会话，**不记录任何来源信息**——源会话与分支互不相认，这是要补的核心。
- 侧栏约束：虚拟化列表、按工作区分组、组内按 `updated_at` 排序、另有「已收藏」横切分组。

**后端方案**
1. `conversations` 加两列（幂等迁移）：`branched_from_id TEXT`（源会话 id）、`branch_message_id TEXT`（分支点消息 id）。存量分支会话为 NULL（无法回溯，接受；按标题 `(N)` 弱推断不靠谱，不做）。
2. `branch_conversation` 写入这两列；会话列表/详情 API 返回分支字段 + 每个会话的分支数（`SELECT COUNT(*) ... WHERE branched_from_id = id`）。
3. 新增 `GET /api/conversations/{id}/branch_chain`：返回源会话（若有）+ 全部兄弟分支（按 created_at 正序），每项含标题、时间、是否当前会话。源会话已删除时返回 `source_deleted: true`。

**侧栏渲染方案（关键决策：平铺 + 徽标，不做树形缩进）**

不选树形缩进的理由：
- 树形与 `updated_at` 排序根本冲突——分支一有新消息就按时间顶到别处，视觉上「树枝乱飞」；强行让分支跟着源会话走又违背排序心智。
- 多级分支（分支的分支）会让虚拟化列表的行索引/行高计算复杂化，而虚拟化是侧栏性能基石，不能动。
- 用户真实诉求是「认得出这是分支、跳得过去」，不是看层级。

具体形态：
1. **分支徽标**：分支会话标题行左侧加小图标 `⑂`（SVG），悬停 tooltip「分支自《源标题》」；源会话标题行右侧加 `⑂N` 计数（N = 分支数）。
2. **点击徽标弹分支链小面板**（挂在 body，复用「⋯」菜单的 fixed 定位模式）：列出源会话 + 全部兄弟分支（当前会话高亮），点任意项跳转；源已删除显示「源会话已删除」。
3. **排序与分组不动**：分支仍按 `updated_at` 参与原工作区排序（工作区本就继承源会话，`store.py:1341` 复制 `workspace_group`）。
4. 删除源会话：分支保留，`branched_from_id` 悬空，徽标 tooltip 显示「源会话已删除」。

**改动点**：`naiba/storage/store.py`（迁移 + 写入 + 链查询）、`naiba/http.py`（路由 + 列表字段）、`public/js/08-conversations.js`（徽标 + 面板）、`public/js/04-messages.js`（branchMessage 后刷新侧栏徽标）。
**验证**：迁移幂等单测 + 链查询单测（源删除悬空）+ Playwright 冒烟（分支 → 源出现 ⑂1 → 点击面板互跳）+ 截图。

## 五、删除单条消息（先做附录 A 的缓存讨论确认）

**语义**：删除 = 从模型上下文剔除 + 界面移除（只隐藏不剔除等于没删，不做）。

**方案（推荐：硬删除 + 撤销窗口）**
1. `POST /api/messages/{id}/delete`：删除该行，返回被删消息完整快照（content/metadata/created_at/前后邻居 id）。
2. 前端操作区加「删除」：用户消息「编辑 · 分支 · 删除」，AI 回复「复制 · 重新生成 · 删除 · 新会话」。确认框按位置分级：
   - 删除的是尾部消息：直接说明「不影响后续缓存」。
   - 中间消息：写明「该消息之后还有 N 条，删除后下一轮对话会重建一次缓存（一次性成本）」；带图消息额外提示图片会重发。
   - user 消息提供两个选项：「仅删此条」/「连同其 AI 回复整轮删除」（默认整轮，避免孤儿回复）。
3. **撤销**：删除后 toast 10 秒内可撤销（快照暂存内存，撤销按原 created_at 插回）。撤销后消息序列逐字节复原 → 旧前缀缓存重新命中（撤销有缓存红利，见附录 A）。
4. 软删除方案（备选，不推荐）：messages 加 `deleted` 列、`build_model_history` 跳过、会话内「已删除 N 条 · 恢复」入口。长期挂着删除态会让 DB 与上下文多一个口径维度，违背快照式简洁风格；如用户对硬删除有顾虑再切换。

**边界情况（必须处理）**
- 删除带分割线标记的消息：分割线一并消失 = 上下文起点前移，确认框追加提示「此消息带有新会话分割线，删除后其之前的内容将重新进入上下文」。
- 删除发起后台任务的消息：任务面板归属锚点在 `background_tasks` 表、不依赖消息存在（OK）；但「任务产物挂回发起消息」逻辑需兜底——消息已删时产物改为挂会话末尾新消息或仅任务面板可见，二选一（推荐挂末尾，与「中止/取消轮次也展示产物」同心智）。
- 附件引用：删除后附件引用计数下降，自动缓存清理可能删文件——撤销窗口内暂存引用保护，确认后按现有引用逻辑自然生效。
- 被分支引用的消息：分支会话是复制体，不受影响。

**改动点**：`naiba/storage/store.py`（删除 + 邻居查询）、`naiba/http.py`（路由）、`naiba/core/history.py`（确认 build_model_history 无需感知——硬删除天然生效）、`public/js/04-messages.js`（按钮 + 确认框 + 撤销 toast）。
**验证**：删除/撤销/整轮删除单测 + 分割线联动单测 + 产物挂回兜底单测 + 冒烟（删除中间消息 → 重发命中新前缀的 cache 行为可用 mock 模型断言请求体序列）。

## 附录 A：删除单条消息与前缀缓存（前置讨论）

**机制回顾（项目既有事实）**
- DeepSeek 前缀缓存按「请求消息序列的最长公共前缀」命中，要求**逐字节一致**。
- 项目现有设计全部围绕它：「编辑」截断点恒为 user 消息（反复点不累积、前缀缓存命中）；「重新生成」截断点是提问本身；图片历史每条 user 消息独立携带完整图片稳定重发；Skill 引用首轮注入 system、后续轮追加会话末尾。

**删除单条消息的影响分析**
- 删除点**之前**的消息：序列逐字节不变 → 前缀缓存照常命中。
- 删除点**之后**的消息：整体前移一位，与缓存中的旧序列从删除点开始分叉 → 这部分作为新输入过一次 prefill 并重缓存（**一次性成本**，再下一轮即命中新前缀）。
- 删除**尾部**消息：前缀完全不变 → **零缓存成本**。

**与现有操作对比**
- 「编辑 / 重新生成」：截断点之后的消息**直接丢弃**——历史损失 + 同样的重缓存。删除单条比它便宜（tail 保留）。
- 「新会话分割线」：不删消息但上下文起点变化 → 同样是全新前缀、重缓存一次。**项目早已接受「换前缀 = 一次性重缓存」这个成本模式**。

**结论**
删除单条消息**不破坏缓存机制**，代价 = 删除点之后内容的一次性重缓存，成本随位置单调递减（越靠后越便宜，删尾部免费）。三个注意点：
1. 带图消息：图片块随 tail 重发，重缓存字节量大，确认框需提示。
2. 撤销红利：按原 created_at/内容逐字节插回后序列复原 → 旧前缀缓存重新命中，撤销几乎零成本。
3. 删除分割线所在消息 = 上下文起点前移，提示文案必须覆盖。
