## 二、能做什么

用户一句话，AI 直接干活：

> 「把 D:/books/某小说.txt 拆一下，看看有多少章」
> → 模型调 `novel_outline`，拿到章节索引（序号、标题、字数），**不含正文**

> 「把第 3 到第 5 章发我」
> → 模型调 `novel_chunks`，按索引取正文

> 「这是我刚写的一万字，帮我分一下章」
> → 模型调 `novel_split_text`，直接吃文本、不用先存文件

差异化在于第三条：竞品只能人手动导 TXT，Cat Chat 可以做到
**「AI 写长篇 → 自动拆章 → 继续干活」**的闭环。

---

## 三、两段式 API（最关键的设计）

这是能扛几十 MB 小说的全部秘密，照抄竞品：

```
novel_outline({path})            → {name, encoding, total, chapters:[{i,title,len}]}
novel_chunks({path, idx:[0,3,7]}) → {chapters:[{i,title,content}]}
```

**`novel_outline` 绝不带正文。** 索引长度只随章节数线性增长，与文件大小无关。
如果一次性把整本书回传，长会话的上下文会被瞬间撑爆——这一点比算法本身更关键，
有专门的守门测试（`test_outline_has_no_body`）。

## 四、拆章规则（四级降级，命中即停）

| 级 | 策略 | 触发条件 | 细节 |
| --- | --- | --- | --- |
| ① | 按标题切分 | 识别到 ≥2 个章节标题 | 主流路径 |
| ② | 符号分节 | 某类符号分隔行出现 ≥5 次 | 取其**后一行**当标题，或符号后同行内容当标题 |
| ③ | 单标题兜底 | 只识别到 1 个标题 | 仍按它切，好过乱切 |
| ④ | 等分兜底 | 一个标题都没有 | 按字数硬切，尽量在换行处收尾 |

### 能认的标题写法

- `第1章` / `第一章` / `第 12 章` / `第一百章`
- 全角数字 `第１２章`、汉字「两」`第两章` / `第两百章`
- 卷/篇/部/集/季：`卷三 风起`、`第三卷 云涌`
- 特殊词：`楔子`、`序章`、`序言`、`引子`、`尾声`、`后记`、`终章`、`番外`、`前言`、`附录`
- 英文：`Chapter 3 The Road`、`CHAPTER IV`（大小写都认）
- 数字序号：`12. 归途`

### 三个容易忽略的处理

**1. 剥头部**
网文 TXT 开头是版权声明/简介。用正文标记分隔线（`====正文====` 这类）定位起点，
**且只在全文前 20% 范围内找**——正文中间也可能有分隔线，越往后越可能是正文，
误判会把开头整段吃掉。找不到标记就原样保留（宁可多留，不要误删）。

**2. 卷不单独成章**
卷标题拼进所属章，变成 `第一卷 平庸少年 · 第一章 离乡`。否则会冒出一堆只有几个字的空章。

**3. 超长章再切**
单章 > 6000 字再切小块，标题加 ` (1/2)` 后缀。这是为喂模型服务，不是给人看的。

### 阈值

| 项 | 值 |
| --- | --- |
| 单章上限 `DEFAULT_MAX_LEN` | 6000 字符（可传 `max_len` 覆盖，范围 200–200000） |
| 单文件上限 `MAX_FILE_BYTES` | 60 MiB |
| 标题最多保留 | 60 字符 |
| 候选标题行最长 | 40 字符（超长行当正文） |
| 编码嗅探顺序 | `utf-8-sig → utf-8 → gb18030 → big5` |

## 五、输出预算（评审要求补齐的第 2 条）

| 限制 | 值 | 超限行为 |
| --- | --- | --- |
| outline 单页条数 | 默认 200，上限 1000 | 返回 `next_offset` 与「还有 N 章」说明 |
| chunks 单次章数 | 最多 40 章 | 直接拒绝，提示分批 |
| chunks 单次字符 | 40000 | 返回已取的章 + `remaining_idx` 续取，**不静默截断** |
| 单章超过单次上限 | — | 拒绝并说明「请调大 max_len 或分批」 |
| 文本入口输入 | 400000 字符 | 拒绝并提示分段 |

模型侧工具结果上限是 60000 字符，所以单次返回压到 40000，留出 JSON 结构余量。

## 六、索引参数校验（评审要求补齐的第 5 条）

`parse_indexes` 拒绝以下全部情况：

- 布尔值（Python 里 `True` 是 `int`，必须显式挡）
- 非整数（`"abc"`）
- 负值
- 超出章节总数
- 空数组 / `None` / 字符串

重复索引**去重保序**（`[2, 2, 0]` → `[2, 0]`）。

## 七、权限策略（评审要求补齐的第 1 条）

| 工具 | 策略 | 理由 |
| --- | --- | --- |
| `novel_outline` | `_make_read_policy`（与 `read_pdf` 同构） | 读工作区/Skill 根内免确认，越界必确认 |
| `novel_chunks` | 同上 | 同上 |
| `novel_split_text` | 免确认 | 只处理传入的字符串，不碰文件系统 |

判定与执行都基于**当前 Run 工作区**（`ctx_for_run`），不会出现「判定用 Run 工作区、
执行读旧工作区」的分叉。

## 八、缓存（评审要求补齐的第 5 条）

- 签名 = `(规范化绝对路径, mtime_ns, size, max_len)`，sha256 取前 32 位
- **max_len 进签名**：同一文件用不同切块上限会得到不同章节表，共用一个槽会串味
- 最多 4 个槽（LRU），避免长会话累积整本书占内存
- 文件被修改（mtime 变）后自动重读

有专门测试 `test_cache_does_not_cross_files` 验证不同文件不会拿到彼此的内容。

---

## 九、编码嗅探的一个诚实说明

`encoding` 字段是**实际选中的解码方式**，不是对源编码的确定性判定。

原因：`gb18030` 能解码大量其他编码的字节，所以「用 gb18030 读成功」不等于原文就是
gb18030。实测中一个纯 UTF-8 文件也可能被报成 `utf-8-sig`（因为 `utf-8-sig` 解码器
接受无 BOM 的 UTF-8 输入）。

这是评审 §1 明确点出的口径问题，文档与工具描述都按此如实说明，不宣称「精确识别源编码」。
