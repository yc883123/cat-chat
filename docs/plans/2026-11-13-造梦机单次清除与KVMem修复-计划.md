## 一、造梦机「单次」结果清除改勾选

### 现象

结果 → 单次 → `⋯` → `清除`，弹一次 `window.confirm("删除全部已结束的单次任务和它们的产物文件？…")`，确认后 `DELETE /api/comfyui/tasks`（body 只有 `exclude_batch: true`），**已结束的单次任务全删**。批量档有批次列表和逐条选择，单次档没有对应能力。

4.4.6（`da98f9b`）里没有这项改动：之前的方案批准后被叫停，只做了历史分页，没有写代码。

### 目标口径

- 点「清除」进入**清除模式**，不再直接删。
- 清除模式下逐条勾选，也支持全选 / 取消全选，确认后只删所选。
- 不保留「一键清除全部」独立入口。
- 批量档一行不改；批量条目不出现在单次列表里，也删不到。
- 分页/懒加载已经上线，原来「全选只勾可见 12 条」的口径已失效。现在全选 = **勾选当前已加载的全部已结束单次任务**，未加载的更早记录不勾。接手时请和用户确认这一条。

### 改动

**状态**（`public/js/24-comfyui.js` 顶部 `comfyui` 对象）：

```js
clearMode: false,
clearSelection: new Set(),
clearDeleting: false,
```

**结构与样式**

- `public/index.html`：`#comfyuiTasksSection` 的 head 与 `#comfyuiTaskList` 之间插入默认 `hidden` 的 `#comfyuiClearBar`，含已选计数、说明、`#comfyuiClearSelectAll`、`#comfyuiClearDelete`（默认 disabled）、`#comfyuiClearCancel`。
- `public/styles.css`：`.comfyui-clear-bar`、`.comfyui-clear-note`、`.comfyui-clear-count`、`.comfyui-task-select`（44px 命中区）、`.comfyui-task-card.is-selected`（`accent-soft` 底 + 左侧 3px 竖条）。注意 `#studioPageComfyui` 下任务卡是 `border: 0`，选中态不要只改 border。

**渲染与交互**（都在 `24-comfyui.js`）

- `clearableTaskRows()/clearableTaskIds()`：`comfyui.tasks` 里非批量、非 `queued/running` 的任务。
- `renderClearBar()`：显隐、计数、全选按钮文案（全勾满变「取消全选」）、删除按钮文案与 disabled；`clearDeleting` 期间三个按钮都禁用。
- `enterClearMode()`：没有可清除任务时 toast「没有可清除的任务；执行中的任务请先取消」；进入时清空勾选、收起 `⋯` 菜单（`details.comfyui-tasks-actions` 去掉 `open`）。
- `exitClearMode()`：清空模式与选择；取消按钮、切批量档、离开结果档、离开造梦机页都走它。
- `toggleClearSelectAll()`：已全选则清空，否则选中全部 `clearableTaskIds()`。
- `onTaskClearToggle(event)`：监听 `#comfyuiTaskList` 的 `change`，按 `[data-comfyui-task-check]` 更新选择集，只切当前卡的 `is-selected`，再 `renderClearBar()`（不整列重画）。
- `renderTaskCard(row)`：`clearMode && !isTaskActive(row)` 时在卡片最前面插 `label.comfyui-task-select` + `input[type=checkbox][data-comfyui-task-check]`；活动任务不出勾选框（要清先取消）。
- `taskFingerprint(row)`：追加清除态（`idle`/`clear`/`selected`），勾选变化时只重建变化的那张卡。
- `renderTasks()`：进入前按 `clearableTaskIds()` 收拢选择集（轮询、分页、删除都会换列表）。
- `deleteSelectedTasks()`：确认文案「删除所选的 N 条任务和它们的产物文件？批量产物不在这里删。」→ 请求

```js
DELETE /api/comfyui/tasks
{ task_ids: [...ids], cancel_active: false, exclude_batch: true }
```

按 `deleted/skipped/failed` 如实回报；失败和跳过的 id 留在选择集里，成功后 `forgetHistoryRows` + `refreshTasks()`；没有可清除任务就自动退出模式。

**退出时机**

- `setComfyuiPane(pane)`：`pane !== "tasks"` → `exitClearMode()`。
- `setComfyuiResultsSegment("batch")` → `exitClearMode()`。
- `onStudioPageChange` 的离开分支 → `exitClearMode()`。

**后端**

零改动。`naiba/comfyui/jobs.py::delete_tasks` 已支持 `task_ids` / `cancel_active` / `exclude_batch`；`exclude_batch` 只对「不传 id 清全部」生效，这里两个都传，批量条目本来就进不了单次列表。

### 测试与验收

- `tests/test_comfyui_frontend_assets.py` 新增守门：`#comfyuiClearBar`、`#comfyuiClearDelete`、`#comfyuiClearSelectAll`、`enterClearMode/exitClearMode/deleteSelectedTasks/clearableTaskIds`、`data-comfyui-task-check`、请求体三字段、`clearFinishedTasks` 已删、三条 CSS 选择器。
- 全量相关：`tests.test_comfyui_frontend_assets` 17 项通过；`tests.test_comfyui_module` 135 项通过。
- `verify/_serve_comfyui_history.py`（96 条单次、72 批真实分页 + 虚拟窗口 + 媒体懒读）桌面 1280×800、手机 375×812 均通过，产物在 `verify/comfyui_history_9khfiemo`。
- 没做的：清除模式本身没有专门的 Playwright 用例。要补的话在 `verify/comfyui_preview_delete_smoke.cjs` 的夹具里放两条已完成单次任务，断言进入模式、勾选、删除所选、取消退出。

## 二、KVMem 停止后不能从 Cat Chat 再启动

### 取证（2026-11-13 实测）

- 用户在顶栏 KVMem 弹层点「停止」，再点「启动」，报 `KVMem 尚未选择模型，请先在控制台选择模型后再启动`。
- 直接查控制台：`GET http://127.0.0.1:18199/api/launcher/info` 的 `draft.parameters.Model` 是空串 `""`；`/api/launcher/status` 是 `stopped`，`active_config` 为 `null`。
- 控制台把模型选择存在**它自己网页的 localStorage**（`kvmem-recent-models-<backend>`、`DRAFT_KEY`，见控制台 `monitor/launcher.js`），controller 不落盘；服务一停，draft 里的模型就没了。
- `POST /api/launcher/scan-models` 不带 `directory` 只扫安装目录，返回 `models: []`，找不到用户模型。

结论：启动不需要模型**列表**，只需要一个 `Model` 路径；Cat Chat 一直是把控制台自己的 draft 原样回传。卡住的是「没人记着上次用的路径」。

### 改法

**`naiba/kvmem.py`**

- 常量：`FALLBACK_PARAMETER_KEYS = ("Backend", "Model", "Worker", "Gpu")`、`LAST_START_FILENAME = "last-start.json"`。
- 缓存文件：`<data_dir>/kvmem/last-start.json`，按控制台 URL 分条，只存上面四个字段；没有 `Model` 不写；值没变不写。写入用临时文件 + `os.replace`，失败静默（不挡启动）。
- `read_last_start(path)`：坏文件/非 dict 一律当空缓存。
- `KVMemClient.info()`：读到 draft 时记录 `last_draft_parameters`。
- `KVMemClient.start(fallback=None)`：用 `fallback` 只补 draft 里的**空字段**，控制台已经选好的不覆盖；补完仍没有 `Model` 才报错，文案保留「尚未选择模型」，末尾加一句「成功启动一次后 Cat Chat 会记住它」。

**`naiba/app.py`**

- `api_kvmem_start`：读缓存（按 `client.manager_url`）→ `client.start(fallback=cached)` → 成功后写回 `last_draft_parameters`；启动摘要的 `model/backend` 在控制台 draft 为空时用缓存值兜底。
- `api_kvmem_status`：状态是 `ready/running` 时顺手把 `last_draft_parameters` 写进缓存。这样即便这次是从 KVMem 控制台启动的，Cat Chat 也能在下次状态刷新时记住参数。

### 限制（要跟用户说清）

缓存为空的那一次仍要在 KVMem 控制台选一次模型。用户现在就是这个状态：服务已停、draft 为空、`data/kvmem/last-start.json` 还不存在。选一次并启动后，新版本会把参数记下来，之后停止/启动都能在 Cat Chat 内完成。
如果用户愿意直接给出模型路径，可以手工预填 `D:\naibachatdata\kvmem\last-start.json`（用户的正式版 data_dir 是 `D:\naibachatdata`）：

```json
{"http://127.0.0.1:18199": {"Backend": "ninfer", "Model": "<模型路径>"}}
```

不要猜模型路径，扫盘匹配同名的做法不可靠。

### 测试与验收

- `tests/test_kvmem.py` 新增两项：draft 缺 Model 时用缓存补齐（且不覆盖已有 `Backend`）、缓存读写与坏文件降级。现有「未选模型必须报错」「start 原样回传 draft」保持通过。9 项全绿。
- 未做真机「停 → 启」：会实际拉起 12GB 模型，需要用户点头。要做的话在 8765 的接替版本上走一遍弹层：停止 → 启动 → 等 `ready` → 再停止。

## 三、KVMem 顶栏图标切会话/API 后消失

### 根因

`public/js/07-models-agents.js::applyConversationModel` 只改 `#modelSelect` 的值，没有重算 KVMem 控件。`renderKvmemControl()` 只认当前下拉值，切走时若被别处按旧状态隐藏，切回 KVMem 会话没人重绘，图标就停着不出来。

### 改法

`select.value = target`、`updateUnloadModelButton()` 之后补：

```js
renderKvmemControl();
void refreshKvmemStatus({ quiet: true });
void populateComposerModels(...);
```

`refreshKvmemStatus` 在非 KVMem 模型时直接返回，不会多发请求。

### 验收

- 切到普通在线 API 会话：图标隐藏。
- 切回 KVMem 会话：图标立即出现，状态在请求返回后更新。
- 切 API 下拉（`saveModelSelection`）原本就会重绘，本次不动。

## 五、风险与待定

1. **全选口径**：从「可见 12 条」改成「已加载的全部」。如果产品上要严格「只勾当前屏幕」，需要另做，别按现在这版交付。
2. **清除模式的指纹**：勾选状态进了 `taskFingerprint`，勾一条会重建那一张卡。列表大时没问题（虚拟窗口只挂视区），但如果你把指纹做得更细，注意别整列重建丢滚动位置。
3. **KVMem 缓存失效**：用户改 `data_dir`、换控制台地址，缓存对不上就退回「先在控制台选一次」的提示，不会拿错模型。
4. **缓存内容**：只有后端/模型/worker/GPU 路径，不含 token；token 每次从 `/api/launcher/info` 现取。
5. **8765 是冻结版**：三处改动都要新构建才生效。
