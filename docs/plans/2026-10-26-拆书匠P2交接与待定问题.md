## 一、一句话现状

拆书匠现在是**会话里的三个 AI 工具**（`novel_outline` / `novel_chunks` / `novel_split_text`），
算法层已完全脱钩、可被任何域复用；但**工作台上没有它**——不在页签名单、没有服务类、
没有数据域、没有前端文件。所以它目前**无法与造梦机、打标器并列**。

## 二、P1 已落地（提交 `306e2d8`）

| 文件 | 角色 |
| --- | --- |
| `naiba/core/novel_split.py` | 纯算法层。**只 `import re`**，零 IO、零业务依赖 |
| `naiba/tools/providers/novel.py` | IO 与工具层：读盘、编码嗅探、缓存、预算、路径解析 |
| `naiba/tools/registry.py:1172` | `build_novel_tool_specs()`，三个工具的 schema |
| `naiba/tools/registry.py:1400` | `registry.register_many(build_novel_tool_specs())` |
| `naiba/tools/registry.py:148-150` | `MEDIA_DECLARATIONS`：三件均 `policy=never / extract=none` |
| `tests/test_novel_split.py` | 算法层 24 项 |
| `tests/test_novel_tools.py` | 工具层 34 项 |

三个工具的能力边界：

- `novel_outline({path, offset, limit, max_len})` → 章节索引，**绝不带正文**，分页给 `next_offset`
- `novel_chunks({path, idx, max_len})` → 指定章正文；超预算给 `remaining_idx` 续取，不静默截断
- `novel_split_text({text, max_len, outline_only})` → 直接拆传入字符串，不碰文件系统

硬约束（照竞品两段式，比算法本身更关键）：**outline 不能回传正文**，否则长会话会被整本书撑爆。

预算与校验口径：

| 项 | 值 |
| --- | --- |
| outline 单页条数 | 默认 200，上限 1000 |
| chunks 单次章数 | 最多 40 章 |
| chunks 单次字符 | 40000（模型侧工具结果上限 60000，留 JSON 余量） |
| 文本入口输入上限 | 400000 字符 |
| 单文件上限 | 60 MiB |
| 单章上限 | 6000 字符（`max_len` 可覆盖，200–200000） |
| 缓存 | 签名含 `max_len`，4 槽 LRU |

## 五、拆书匠与会话的耦合点（只有两处，且都可摘掉）

`NovelProvider` 与聊天域的接触面：

1. `ctx_for_run()` —— 相对路径按当前 Run 工作区解析
2. `_make_read_policy()` —— 读工作区/Skill 根外的路径要确认

两者都只在「模型自主决定读哪个路径」时才需要。工作台里路径由用户在文件选择器里点选，
与打标器选文件夹、造梦机选图片同性质，不需要模型确认。

`NovelProvider.__init__(self, context: Any = None)` 的 `context` 是可选参数；
为 `None` 时 `_resolve` 退化成「必须给绝对路径」，不碰 Run 上下文。

**结论：工作台侧不需要、也不应该复用 `NovelProvider`。**

## 六、并列的正确范式：照造梦机

造梦机是唯一「工作台 + 会话工具」两边都有的模块，它两边**不共享服务层**：

| | 造梦机 | 打标器 | 拆书匠（现在） |
| --- | --- | --- | --- |
| 工作台服务 | `ComfyUIService` | `LabelerService` | **无** |
| 数据域 | `data/comfyui/` | `data/labeler/` | **无** |
| 会话工具 | `providers/comfyui.py` → 聊天域自己的 `JobSpec(kind="comfyui")` | 无 | `providers/novel.py` |
| 两边共享什么 | 只有「都能调 ComfyUI 的 HTTP API」 | — | `core/novel_split.py` |

造梦机的会话工具走 `app.jobs.start(JobSpec(...))`，与 `ComfyUIService` 的 runner
**一行代码都不共享**。工作流库、任务记录、串行执行全是工作台独有的。

所以拆书匠要并列，路径是**补工作台侧**，而不是让工作台去调会话工具：

1. 新建工作台服务（候选 `naiba/novel/service.py`），自己的数据域 `data/novel/`
2. `import naiba.core.novel_split` 复用算法——这是评审拆分换来的红利，直接可用
3. 权限换工作台口径：用户选的路径即允许，不接 `_make_read_policy`
4. 三处名单加 `"novel"`；新建 `public/js/25-novel.js`；`index.html` 加页签与 view

## 八、待拍板（3 个问题，未定前不要开工）

### 1. 工作台形态：任务队列 还是 文件处理工具

造梦机、打标器都是**任务队列**形状：提交一批 → 逐条执行 → 出产物 → 看进度。

拆书匠不同构：导入一个 TXT → 看章节列表 → 勾选 → 落盘成多个章节文件。
本质是**文件处理工具**，没有排队、没有逐条计费、没有重试。

- 套任务队列：多出用不上的进度轮询、并发控制、失败重试
- 按文件处理工具：与另两页交互范式不一致，「并列」只在视觉上成立

### 2. 落盘持久化口径

见 §七「评审 P2 备注」四项（崩溃恢复 / 版本字段 / 删除行为 / 容量上限）。

### 3. 是否需要独立的「作品」长期数据域

章节正文一旦长期保存，就不只是「一次拆分的产物」，而是一份书稿数据。
要不要为它建独立数据域（而不是塞在某个功能页目录下），影响后续「章节 → 生图 / 生视频」一条龙怎么接。
