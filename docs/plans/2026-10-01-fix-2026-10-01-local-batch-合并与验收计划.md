## 4. 审查发现与处理要求

### P0：围栏动作确认契约

master 后续加入 `action_source`、`confirmation_ui`、嵌套来源继承、批准后复核及多工具单卡确认。分支终态解析器与 master 返回契约不同；若直接选择分支实现，围栏动作可能失去 `fenced` 来源并绕过 master 确认流程。合并必须以 master 确认行为为约束，再移植分支对围栏示例、截断协议和正文尾锚定的改进。

### P0：围栏 API 与流式状态机

双方新增的 `core/text_fences.py` API 不兼容，`unwrap_whole_response_fence` 返回类型也不同。统一实现需同时满足 master 调用方和分支调用方，并保留 master 对 tabs/CRLF 的支持以及分支的跨 chunk 状态、半围栏标记、未闭合围栏和尾锚定语义。`llm/stream.py` 合并后还须保留 `_FenceGuard` / `_forward_guarded_text` 的 master 测试兼容入口，或提供等价适配。

### P1：异步 Job 媒体并发覆盖

`naiba/storage/job_media.py` 先读取消息快照，在内存中重算 `tool_runs`、`activity`、`attachments`，再把数组作为 metadata 键写回。两个 Job 并发完成时，后写者可能用旧快照覆盖先写者的媒体；按键更新只能隔离不同键，不能解决同一键的陈旧数组覆盖。应将读取、去重合并和写回放进同一事务，或采用等效的串行化/重读方案，并增加交错写回的回归测试，证明两个 Job 的媒体都保留且重试幂等。

### P1：图片缓存关闭语义

`naiba/core/history.py::_ImageEncodeCache.set_limit_mb(0)` 当前仍保留最新一项，`entries` 和 `bytes` 不归零；重新开启时也可能重用关闭前的值。这与“0 = 关闭记忆”不一致。实现应在运行时设为 0 时释放缓存，并测试正值 → 0 → 正值的 entries、bytes、重新编码和输出字节行为。

### P1：维护文档需重建

分支文档约 4044 行、749 KB，远超当前维护说明的 500 行 / 120 KB 限额，且包含事故时间线、真实盘符路径和过时验证计数。以 master 精简版为基础，仅提取当前有效的围栏、图片缓存、剪贴板、Job 和测试契约；不得整体采用分支文档。使用当前 master 的文档守门脚本复核 UTF-8 无 BOM、行数、字节数、路径和关键入口。

### P2：浏览器基础冒烟缺少有效输入区判据

分支 `verify/browser_smoke.cjs` 一次运行报告 `hasComposer: false`，脚本仍判通过。正式验收必须确认真实输入控件（例如 `#messageInput`）存在且可见，并把缺失列为失败；标题、消息区、侧栏及错误收集也需有效断言。
