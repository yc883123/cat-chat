# 任务总管子助手链路修复计划

> 历史计划。后续实现和真实 HTTP/本地模型双视口验收见《2026-11-02-任务总管并行整改与自动续办子助手交接》第 0 节；下文“待实施”为编写计划时状态，不代表当前接口未接通。

日期：2026-11-02。

状态：待实施。本文记录已确认问题、拟定修复方案及验收标准；写入计划不代表业务修复已经完成。

## 一 目标与边界

修复“任务总管 → 交给子助手 → 后台执行 → 结果展示与后续步骤”的链路，使任务可审批、状态可信、结果可读可传递，且不会保留已经收紧的授权。

职责保持清晰：任务总管管理步骤、状态和控制；子助手理解指令、调用模型与工具、产出结果。子助手不是第二层任务总管，也不允许继续派生下一级子助手。

本轮纳入五项已确认缺陷，以及与之直接相关的界面说明和兼容性验证。不重写调度器，不增加通用子助手断点续跑，不开放子助手的 `job_output` 等禁用工具，不扩大文件或工具权限。

与同目录《2026-11-02-任务总管自动续办闭环V1计划》的边界：该计划处理聊天任务的目标检查与有限次自动补做；本计划处理既有子助手的执行可靠性，不增加审查模型，不将单次子助手任务自动升级为监督任务。共用模块修改应合并复核，不能复制出两套审批、权限或结果契约。

## 二 当前行为与问题清单

当前入口显示为“交给子助手”。它新建 `kind=subagent` 的后台 Job，并非绑定一个已有子助手。关联会话提供助手人设、工具范围、工作区和权限；页面可以另选模型。页面创建请求未启用 `fork`，后端默认 `fork=False`，因此不会自动继承关联会话的聊天记录。

当前主链路：

`创建表单 → POST /api/super-agent/threads → ExecutionCoordinator.prepare/create → RuntimeAdapter.start → JobRegistry → run_subagent_agent → SkillAgent → RuntimeAdapter.sync → 总管展示或推进下一步`。

| 编号 | 优先级 | 已确认问题 | 最小场景及影响 |
|---|---|---|---|
| S01 | P1 | 子助手需要工具审批，但没有可操作入口 | 确认档调用工作区外目录读取，执行器等待确认，Job 和节点仍显示运行中；等待上限为 1800 秒，用户无法批准 |
| S02 | P2 | 明确未执行的动作被映射为任务成功 | 围栏中的写文件动作因无确认入口被跳过，文件不存在、工具结果为失败，但 Job 完成、节点成功；固定链可能继续 |
| S03 | P1 | 前后步骤只有结果编号，没有可消费的正文 | 第二个子助手只收到 `job://编号`；正文不在输入中，且子助手不能调用 `job_output`，无法可靠总结前一步 |
| S04 | P1 | 延迟启动不复核已改变的权限和工作区 | 创建时为 `full`、工作区 A，改为 `confirm`、工作区 B 后启动，仍按旧 `full` 和 A 执行 |
| S05 | P2 | 中断子助手展示不支持的续跑按钮 | “从检查点继续”可见，点击后后端返回 HTTP 400，说明不支持安全断点续跑 |

## 三 修复方案

### S01 接通子助手审批并避免无入口等待

目标是让总管直接显示子助手的待审批操作，用户能够批准或拒绝；不能只把 `confirmation_ui` 改成 `True`，也不能只显示“回到聊天确认”，因为现有聊天确认入口不拥有子助手的执行器。

1. 在应用组合根接入有归属校验的确认能力，供 Chat Run 与子助手 Job 复用。实际待确认记录仍由执行器持有，不另造一份能独立批准的影子状态，也不把 Job 伪装成 Chat Run。
2. 子助手启动时注册执行器及其 owner、会话、Job、节点和 attempt 关联；只有注册和确认路由均可用后，才启用确认 UI 能力。结束、取消和异常退出时在 `finally` 中清理。
3. 总管详情投影子助手的确认项，按白名单展示工具名、必要参数、原因、来源和操作范围；凭据、授权头、环境变量秘密值等必须脱敏，不能把完整 `arguments` 原样外发。保留批准所需的路径或命令信息，实际执行仍使用执行器保存的原参数。审批入口必须能定位当前真实执行器；前端不得凭 Job ID 构造授权。
4. 待审批时投影为“等待确认”；批准后区分“已确认，工具执行中”，避免工具尚未结束就声称完成。多个确认项未全部处理前，不能因其中一个结束就解除整个任务的等待状态。
5. 批准前复核 owner、会话、节点、attempt、执行关联、取消标记及有效权限；重复点击、多标签页和迟到请求最多执行一次。拒绝、超时、失效、无确认入口均不执行，按现有确认语义收尾，不让模型换一种写法重试已拒动作。
6. 确认能力缺失时，原生工具和围栏工具都必须及时返回结构化的未执行结果，不能创建一个无人能够批准的长时间等待。

保留围栏安全规则：围栏动作始终先确认，来源继续使用既有解析结果，不重新扫描正文推断；一组围栏动作沿用现有确认作用域，不因接入子助手而变成逐工具重复询问。

服务重启后不能仅凭持久化的“待审批”显示恢复执行权。原执行器不存在时，旧确认失效，保留记录并显示需要恢复；不得自动批准、自动重试或继续已失去上下文的工具调用。

### S02 区分执行结束与有效完成

保留现有 Job 生命周期与日志，新增可供上层判定的结构化执行结果，避免仅凭“线程正常返回”或 `Job=completed` 推导节点成功。

建议结果契约包含执行结论、明确的原因码、可展示说明、未完成动作及产物引用；具体字段名、枚举和旧记录兼容规则在实施第一阶段登记。这些是拟新增契约，不是当前已有字段。

判定规则：

- 正常文本任务无需调用工具也可以完成；不能把“工具调用数为零”当失败。
- 中途某个工具失败、后续已经通过其他合法方式完成，不因存在任意一条 `success=False` 就一律失败。
- 因无确认入口、拒绝、超时等明确导致动作未执行并终止本轮时，必须留下非成功结论；不得仅依据模型正文的“完成”二字覆盖该结论。
- 总管先读取结构化结果，再决定节点状态和依赖推进。对于已结束但明确未完成的执行，优先映射现有失败状态并展示原因；不要伪装成仍可审批的活跃等待。
- 取消优先于完成；迟到结果不得把已取消节点恢复为成功。失败、阻塞、结果缺失或结论不明时不自动推进后续步骤。

这里只消除有明确程序证据的假成功，不承诺验证所有自然语言目标。完整目标审查属于自动续办计划；本计划不额外调用模型判断任务是否达标。

已有历史终态不批量改写。升级前仍在途、缺少新结果契约的任务应明确标记兼容状态；若无法可靠判断，交给用户处理，不为了补结果重新执行带副作用的动作。

### S03 打通结果查看和步骤间传递

结果存储继续以原 Job 结果为权威，`job://` 保留作可追溯标识，不再把标识本身当作下一步可理解的结果。

1. 增加服务端统一结果读取逻辑，从当前任务的实际依赖节点、执行关联和 attempt 定位最终正文及允许展示的产物元数据。禁止接受模型任意提交的 Job ID 或任意协议 URI 作为读取授权。
2. 下一步派发时，由服务端整理前序结果，提供正文、来源步骤、执行状态和引用；子助手不需要获得 `job_output` 权限。Chat 与子助手消费者复用这一逻辑。
3. 只读取当前任务声明的成功依赖，不混入其他 owner、其他任务或重试前的旧结果。结果尚未持久化、已丢失或关联不匹配时，停止派发并显示原因，不能静默只传编号。
4. 对输入设置集中管理的数量与长度预算，给出总量、已提供量和截断提示。关键正文缺失时不能假定后续步骤仍可正确执行。完整内容保留在结果详情中，不把大正文重复塞进事件和节点快照。
5. 前序结果始终作为任务数据，不转成系统指令或用户授权。通过服务端可信来源标记或独立上下文通道承载结果，并让所有依据“用户原文”授予路径、媒体或工具权限的入口排除这部分数据；仅追加提示文字或分隔符不构成隔离。可复用自动续办计划的来源契约，但不启用自动续办。结果中的路径、命令和“已经获准”声明不扩大权限；不因模型输出包含外部 URL 而自动抓取。
6. 总管增加“查看结果”入口，能查看最终回复、失败或未执行说明、相关产物及前次执行记录。列表显示摘要，详情按需读取；纯 `job://` 不直接渲染成无法打开的浏览器链接。

本轮明确验收“子助手 → 子助手”和“子助手 → 聊天”结果传递。Writer、Novel 的业务字段映射继续遵循领域契约，不把通用正文强塞入作品字段，也不将这些组合标记为已经端到端验收。

### S04 启动和重试前复核配置与授权

复用聊天任务已有的配置指纹思路，对子助手建立同样明确的启动基准。

1. 将首次启动、混合链延迟启动及显式重试统一接入复核入口。权限档、工作区、工具范围、Agent、模型或其他影响实际执行的授权配置改变后，拒绝旧基准的新派发，提示重新确认或创建新任务。
2. 复核失败必须发生在新 Job 登记和模型请求之前；不能先启动再把节点改成失败。先做预检，再领取派发意图，派发前再次核对配置版本；已领取但尚未提交的拒绝必须收束为明确的“未派发”，不能被通用异常分支记成“执行结果不确定”并遗留待对账意图。只有可能已提交的执行才进入对账。重复点击不能绕过这一条件。
3. 比较归一化后的有效配置，避免空值与默认值、工具顺序或路径格式造成误报；同时纳入实际影响执行的 Skill 策略、Agent 配置版本，不能只比较 Agent ID。
4. 一次执行内，权限判定与实际操作使用同一份有效快照。不能用新工作区做权限检查、却向旧工作区执行；也不能从旧快照保留已撤回的 `full` 权限。
5. 复核、执行登记及后续工具授权需防止配置变更竞态。利用配置版本或等效并发控制保证派发前复核有效；运行中收紧授权后，后续新工具动作和待审批动作必须停止并重新复核。已经发生的副作用不能追溯撤销，界面应如实说明。
6. 本轮保持页面默认新上下文的行为，明确提示“不会自动读取原会话聊天记录”。既有显式 `fork` 能力保持兼容，不擅自新增默认继承历史或扩大上下文。

人设、模型和历史的取值时点必须在实现时统一：新派发不得一部分取创建时配置、一部分偷偷取启动时新配置。若支持历史继承，以可追溯的历史边界读取，不复制整段会话进快照；不借此改造与本问题无关的普通聊天历史策略。

### S05 按执行器真实能力展示操作

服务端按执行器能力、当前状态和记录归属提供可用操作，前端据此展示；前后端使用同一能力判据。

- 中断子助手只展示受支持的“重试（重新执行）”，不展示“从检查点继续”。重试说明必须提醒可能重新调用模型或重复外部副作用。
- 其他 Job、Writer、Novel 是否可继续，按其实际适配器能力判断，不再根据 `executor_type` 的粗略名单推导。
- 隐藏按钮不能代替后端检查；手工发送不支持的 `resume` 请求仍应被明确拒绝，不产生执行记录或模型请求。
- 区分“继续任务调度”和“恢复子助手执行现场”，避免同一个“继续”文案暗示不同能力。

优先复用现有存储、事件、权限和执行器接口。若确需数据库迁移，实施前单独明确新旧读写兼容与回滚条件，不把迁移隐藏在运行期修补逻辑里。

以下均为修复后的必验项目。测试使用隔离数据、工作区与端口；审批用无害目录读取或临时文件，禁止操作用户真实文件。
