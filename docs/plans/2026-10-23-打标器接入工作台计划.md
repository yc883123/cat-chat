## 1. 目标与依据

**目标**：在已经落地的工作台「打标器」基础上，按源码核对结果补齐 LoRA 训练包导出；不重复实施页面、上传、打标任务、断点续跑、标注库和已有导出能力。

**执行口径**：

- 已实现能力以当前代码、`tests/test_labeler.py` 和 §13.4 的验证结果为基线，计划中的“阶段”不再表示待重做工作。
- 只有标为“剩余缺口”或“尚未自动化验证”的项目才进入后续实施；其余条目保持现状，不改接口、不迁移数据、不重写任务链路。
- 本次源码差异的核心不是“再做一个打标器”，而是把现有标注记录可靠地导出为图片与 `.txt` 同主干的训练包。

**依据**：

1. 本人发来的 tutu v1.3.0 拆解报告（`图图超级智能标注工具` 静态拆解），其 §四「打标器是怎么实现的」与 §七「最小可行架构」是本计划的功能蓝本。
2. 本人定调：**不做应用内本地模型打标**。模型一律来自设置里的 provider：云端 API 与
   Ollama / LM Studio / llama.cpp 这类本地后端都算 provider（2026-10-23 明确：
   「有 provider 就行，不要用小模型打标」）。
3. 既有代码核查（下文 §2 全部为实测行号，非推测）。
4. 参考程序 `tutu-super-smart-marker` v1.3.0 的打包源码复核（REA 提取的 `app.asar` 清单、`BatchProcessing-*.js`、`tagGenerationApi-*.js`、`configPersistence-*.js`）。该程序只提供功能参考，不作为本项目的运行时依赖。

**核心判断**：不另起 Electron 壳。工作台已有「pywebview + WebView2 壳 / `naiba/http.py` 单进程 HTTP / 域模块 / Studio 任务持久化」结构，可复用界面、模型配置和任务基础设施；但打标器有批量逐图状态、幂等恢复和导出授权等新增契约，不能把 Studio 单任务生成器原样照抄。

### 1.1 参考源码核对结论

- 参考程序的入口是批处理步骤配置器：`tag` 与图片重命名、裁剪、抠图、导出等步骤共用批次，而非独立的工作台页。Cat Chat 将打标器做成功能页是本项目的产品选择，不应误写成参考程序原有结构。
- 打标任务以项目和图片 ID 提交到 `/tag-generation/start`，用 `/tag-generation/recent`、任务状态接口和取消接口恢复/管理；本项目输入是用户拖入的文件夹，经受管 uploads 形成引用，不引入参考程序的项目/图片库依赖。
- 参考程序保存上次打标/批处理配置，并支持关键词或描述输出、语言、焦点预设、过滤规则、参数及自定义提示；本项目只采纳与 provider 兼容的配置语义，不能照搬其 model tag、`provider_info` 或本地模型路由。
- 参考程序支持 default、Ollama、JoyCaption、WD14 与外部模型，且有模型专属选项；Cat Chat 只走已配置 provider（云端或现有本地服务），不加载 WD14/JoyCaption 等打标小模型。因此不复制参考程序的模型下载、模型专属参数或“清除既有标注”语义。
- 参考程序导出可选 `.txt` / `.json`、标签或描述、目标目录、同名覆盖/重命名及 ZIP；Cat Chat 采用受管导出目录和受控下载，保留 JSON/CSV/文本包，并增加 CSV 公式注入防护，不接受任意写入路径。
- LoRA 训练包必须同时包含图片与 caption；图片与 `.txt` 按**相同短文件名主干**配对，不能沿用 `naiba_chat_<时间>_<随机串>_<原名>` 这类上传缓存名。例如 `000001.png` 与 `000001.txt`。逐批导出生成短名，caption 内容写入对应 `.txt`，清单另存原始文件名/相对路径与导出名映射；不得仅导出 `.txt`，不得把 caption 冲突改成 `-2.txt`。
- 导出图片必须是用户选入批次的原始文件字节。现有 Cat Chat 上传会按图片设置处理/缩放后落盘，故导出前须有可验证的原图保留来源；原图缺失、配对数不一致、生成名碰撞或包内文件冲突时整包拒绝，不能静默退回上传缓存图、漏图、覆盖或拆开命名。
- 参考程序在创建任务请求超时或 500 时，会进入恢复模式并从 `/tag-generation/recent` 取最新任务；这不能证明该任务就是刚才那次提交。Cat Chat 的逐图 `uncertain` 只覆盖模型调用已发出而结果未落库，尚需单独定义「任务已创建但响应丢失」的幂等提交/关联键；不得按“最近一条”自动认领任务。
- 实装验收要覆盖上述被采纳行为的对应映射，并把未采纳项列为边界；不能仅以界面相似或接口名称相似判定接入完成。

### 1.2 Tutu 与 Cat Chat 的打包差异（Tutu v1.3.0 可执行文件静态复核）

| 链路 | Tutu 已观察到的行为 | Cat Chat 当前状态 / 差距 |
|---|---|---|
| 批次图片选择 | 批次任务执行导出步骤时，将项目图片 ID 传给 `ImageService.export_images_to_files()` | 文件夹选择把浏览器相对路径随受管上传引用保存；需沿这份任务映射回原始图片 |
| 普通 `.txt`/ZIP 导出 | 导出步骤格式仅 `.txt` / `.json`；TXT 导出对每张图复制图片，并把文本文件与最终图片共用文件名主干；ZIP 收集已写出的图片与文本文件 | `captions` 当前只把 `.txt` 写进 ZIP，未放入图片；文本名仍源自相对路径 |
| 重名处理 | `on_conflict=rename` 先选定可用图片文件名（如 `<stem>_1.png`），后续 `.txt` 沿用该图片主干；`overwrite` 显式为覆盖策略 | `_render_captions()` 只在 `.txt` 冲突时独立加 `-2`，无法和图片配对；训练包要求重构此行为为共同确定导出名或整批拒绝 |
| 图片来源 | 通过图片记录中的 `stored_path` 复制文件；具体代表用户导入原图还是已经处理的存储图，当前静态证据不能确定 | `store_uploaded_file()` 会先按 `image_upload_original` / `image_max_pixels` 处理，再保存处理后的 `main_bytes`；须保留传入上传的原始字节并明确其生命周期 |
| 映射 | PairedExport 专用工作流按结果图基名复制图片及描述到 `target/` 和 `target/<stem>.txt`；还会给控制图使用相同基名，描述标为可选 | Cat Chat LoRA 导出是标注任务图片到 caption 的训练集，不应复用 PairedExport 的控制图/生成结果语义；可借鉴配对写名机制 |

证据来自 Tutu 版本 `1.3.0` 的打包后端 EXE（Python 3.11 PYZ），而非仅 UI 字符串：已解析 `app.services.batch_service` 调用链、`app.services.image_service.ImageService.export_images_to_files`（源码行 8638 起、图片与文本配对路径在行 8940–9004、ZIP 写出在行 9188–9219）、`app.services.paired_export_service`（行 290–377）与 `app.schemas.batch.ExportStepConfig`（行 205）。静态拆解的关键限制：Tutu 的 `stored_path` 是否为未经变换的用户原图未证实；这里不将该点写成 Tutu 保证。

当前 Cat Chat 的差异清单：

1. `naiba/storage/media.py::store_uploaded_file()` 默认允许按 `image_max_pixels` 缩图，并按日、内容去重存储；`naiba/app.py::_upload_spooled()` 调用该入口，原始上传字节随 spool 清理，不保证仍可用于训练包。
2. `naiba/labeler/images.py::validate_image_refs()` 保留前端 `relative_path` 用于任务与标注映射；`public/js/23-labeler.js` 上传成功后把服务端返回的缓存名写回 `row.name`。当前已有相对名称映射，但没有独立的原始文件留存契约。
3. `naiba/labeler/export.py::_render_captions()` 仅向 ZIP 写 `.txt`，成员名来自相对路径；冲突会生成独立 `-2.txt`。该现状既缺图片，又破坏一一同名配对。
4. 修订目标：受管短名（批内唯一、跨平台安全；建议 6 位递增序号 + 原图片扩展名）同时用于图片与 `.txt`；清单记录原始相对路径、原始名称、导出名称、内容校验值及 caption 来源。排序规则固定，重复/歧义项整包拒绝；ZIP 不含重复图片；原图字节逐字节校验一致。导出次数变化不影响同一输入顺序下命名。

> **差异清单的范围**：上面 1–3 是现有代码与 Tutu 的事实差异，4 是唯一需要补的训练包目标。页签、上传、任务状态、provider 调用、逐图 checkpoint、恢复、标注查询、JSON/CSV/TXT 导出和句子库已经存在，不列为重新实施项。

### 2.3 一个更正：并发恐惧来自过时注释

`naiba/studio/runner.py:1-12` 顶部注释称「`ModelRuntime` 实例属性并发会互踩，同一时刻只跑一个生成任务」。
实测：`naiba/llm/runtime.py:632` 已是 `self._local = threading.local()`，`last_usage` / `last_reasoning` / `last_reasoning_id`（`:644-666`）与 `_FINISH_REASON`（`:107`）全部 thread-local。

⇒ `last_*` 读数是线程局部变量，但这只解决调用线程之间的诊断字段隔离，不证明多线程端到端安全、供应商限流可承受或结果与用量关联正确。`kind=local` 在 `complete()` 内有全局执行锁，实际串行。现有 runner 已按 §5 P0-a 结论在生产调用线程内立即捕获该调用结果及诊断信息；不得由管理线程读取 `last_*` 推断某一图片的用量。

### 3.2 本期不做

| 不做 | 原因 |
|---|---|
| WD14 / JoyCaption 本地模型打标 | 需 torch，包体积爆炸 |
| BiRefNet / SAM3 抠图 | 需 torch；SAM 受 License 商用限制 |
| 模型下载器 + sha256 校验、显存策略（懒加载/闲置卸载） | 无本地模型即无需求 |
| spaCy `zh_core_web_sm` 分句 | 规则分句兜底，后续可选 |
| 素材爬虫、视频处理、AI 生图、激活码、遥测上报 | 不在定位内 |

**留后路**：引擎按明确的 `engine` 标识扩展，本期只实现 `provider`（经 provider 调模型）。
模型 ID / tag 不承担安全或引擎路由职责；后续若要接应用内本地标注引擎，由独立适配层接入，
不改动前端页面结构。

**范围澄清**：允许所有已配置的 provider（`kind=online` 与 `kind=local`）。本地后端共用 runtime 的
全局执行锁，因此批次固定一次处理一张，并在每张开始前礼让进行中的对话 Run（聊天不被批量任务卡住）。
仍然**不接受**客户端提供的 `base_url` / `provider_info` / API Key：只认设置里已存在的 `model_key`。

## 4. 关键决策

| # | 决策 | 理由 |
|---|---|---|
| D1 | 打标器 = 工作台**功能页**，不是与「对话/工作台」平级的第三种模式 | 与模板同属生成域，共享任务/结果/交接基础设施；侧栏注释已预留此口子 |
| D2 | 唯一引擎 `provider`（云端与本地 provider 都走 `complete()`），不内置本地小模型 | 零新增依赖，exe 维持 81MB |
| D3 | 标注库用**独立 `data/labeler/labeler.db`**，不进 `chat.db` | 事务隔离，不污染消息库；清理策略独立 |
| D4 | 复用 Studio 的文件记录/事件流约定，但新增逐图事务化 checkpoint 存储；事件流仅用于通知和展示 | 现有 Studio 事件流与任务 JSON 不构成跨文件原子事务，不能单独保证计费安全恢复 |
| D5 | 并发数先由**探针**决定；初始默认 1，探针通过后才开放经验证的档位 | 供应商限流与逐图结果关联优先于吞吐；本地后端全局串行 |
| D6 | 图片编码复用现有视觉编码管线，经验证后再决定尺寸配置 | 避免重复实现；编码后的格式/MIME、尺寸和体积需有明确限制 |

### P0-a：并发探针（已完成；历史设计记录）

- 在隔离实例对在线 provider 用 N=1/2/4/6/10 调用 `app.models.complete()`；每次响应使用可区分的假模型用量/内容，验证调用线程内返回正文、usage、reasoning、finish reason 的归属，并覆盖超时、取消和异常。
- P0-a 只验证 `app.models.complete()` 在线调用线程中返回值/诊断数据的归属、取消/超时行为与运行时并发边界；Labeler worker 调度、事件顺序和 SQLite 并发写属于 P1/P2 实现后的自动化测试，不作为未实现代码的前置探针。
- 判据：每个结果都关联到提交项；无错配/丢结果/重复计数；探针不代表所有供应商限流安全。业务初始并发固定为 1，用户调高的档位仅开放已验证值。
- 产出：一个 `verify/_probe_labeler_concurrency.py` 只读探针 + 结论写回本节。探针不得默认联网或触发真实付费调用。

5. 文案前缀只拼一次（前端拼标签、后端给裸串）；storage 写路径包 `@_retry_transient_write`。
6. 协议常量永不可改；不手动打 tag。
7. 判结论用 Read 不用 tail；中文 stdout 写文件再读。

### 13.2 与早期方案的两处变更（本人拍板）

1. **改名**：早期稿的 `tagger` 容易被误解为本地标注模型；实施时包名/接口/数据目录/前端文件统一为
   `labeler`，页面中文仍是「打标器」。

   Ollama / LM Studio / llama.cpp 这类本地后端都可以选。应用内**仍不加载任何本地标注小模型**
   （没有 torch / WD14 / JoyCaption），引擎标识为 `provider`。

### 13.3 与聊天/其它功能并行的保证

- 打标在独立后台线程执行，HTTP 服务是 ThreadingHTTPServer：在线 provider 下与聊天并发互不阻塞。
- 本地 provider 共用 runtime 的全局执行锁：runner 在每张开始前查询 `runs.list_primary(active_only=True)`
  礼让进行中的对话，每张结束后再让出 200ms；聊天等待时看到的占用者标签是「打标器」。
- 打标页轮询只在「当前页 = 打标器且工作台打开」时运行；切页/退出工作台即停。
