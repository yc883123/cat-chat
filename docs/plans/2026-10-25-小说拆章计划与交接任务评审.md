## 1. qiyuan 实际代码核查

本次直接查看了 `D:\qiyuan_re` 中的打包代码与取证材料：

- `启元提示词助手.exe_extracted\PYZ.pyz_extracted\backend\txt_import.pyc`
- `启元提示词助手.exe_extracted\PYZ.pyz_extracted\backend\archive.pyc`
- `dumps\txt_import_consts.txt`
- `dumps\archive_outline_dis.txt`
- `dumps\nv_main.js`

从 `txt_import.pyc` 的常量、函数名和反汇编可确认：实现包含 `CHAPTER_RE`、`VOL_RE`、`SYMBOL_RE`、`BODY_MARK_RE`、`_strip_head`、`_split_by_sep`、`read_text_auto`、`_split_by_len`、`_cap_chunks`、`_by_heads`、`split_chapters` 和 `_load_chapters`。关键行为与计划基本一致：

- 编码依次尝试 `utf-8-sig`、`utf-8`、`gb18030`、`big5`，最终使用 UTF-8 替换错误；最大文件大小为 62,914,560 字节（60 MiB）。
- 常规标题至少识别到两条才优先按标题拆分；否则尝试重复符号分节，再处理单标题，最后按长度切分。
- 标题识别覆盖汉字数字、全角数字、卷/章/回等标题、序章类词语、英文 Chapter 和数字序号标题；单行候选长度不超过 40 字，标题最多保留 60 字。
- 正文标记只在文本前 20% 内生效；卷标题并入章节标题；超过 6000 字的内容会继续分块。
- `archive.pyc` 的 `file_outline` 返回文件名、编码、章节总长度与 `{i,title,len}` 列表，不返回正文；`file_chunks` 按指定索引返回 `{title,content}`。
- `nv_main.js` 中确实使用 `novel_screenplay_v1` 存储前端状态，支持计划对竞品存储方式的描述。

因此，计划的核心算法来源并非推测。但“按首次成功解码即可识别编码”只是竞品采用的启发式：GB18030 可解码大量其他编码字节，不能保证 Big5 等文本被正确识别。移植后应以真实样本验证，并把 `encoding` 解释为所选解码方式，而非确定的源编码。

## 2. 小说模块计划评审

### 可行部分

1. 先落无 UI 的算法与工具层、再做持久化工作台，是合适的分阶段路径。
2. outline 与 chunks 分离可以避免默认传输整本书正文；60 MiB 文件限制、缓存、标题候选长度和超长章节切块都有竞品实现依据。
3. 以 `documents` 工具 provider 和现有原子 JSON 写入模式为实现参考，整体符合当前项目结构。

### 开工前必须修订

1. **为文件工具补齐读取权限策略。**当前 `naiba/tools/providers/documents.py::DocumentToolProvider.tools()` 只给 `read_pdf` 配置 `_make_read_policy`，其他工具使用 `_no_confirm_policy`。如果 `novel_outline` / `novel_chunks` 只加入该 provider 而未调整策略，可能允许读取工作区外路径而不要求确认。新工具必须与 `read_pdf` 一样经过只读权限判定，并确保判定和执行都基于当前 Run 工作区。
2. **工具输出需有硬预算。**项目模型工具结果存在约 60,000 字符上限（`naiba/core/tool_results.py::MODEL_JSON_MAX_CHARS`）。章节很多时完整 outline 可能超限；所选章节正文也可能超限。应设计 outline 分页或章节数量上限，并给 chunks 增加最大章节数/字符数及明确的续取信息，避免 JSON 被截断后变成不可用结果。
3. **把 AI 生成文本入口纳入 P1 或调整目标表述。**计划将“AI 生成长文本 → 自动拆章”作为主要差异化，但 P1 工具只有基于文件路径的 outline/chunks；`novel_split_text` 被推迟到后续。若该差异化是本次目标，P1 应提供有大小限制的文本拆分工具，并让它复用同一纯算法。
4. **厘清纯算法与 IO 的边界。**计划将 `read_text_auto(path)` 放进“不做 IO”的模块，这两者冲突。建议拆成接受字符串的纯拆章层和受权限策略保护的文件读取/provider 层。读文件、嗅探编码和缓存都属于 IO/服务职责。
5. **补足索引参数和缓存边界。**`idx` 需要拒绝布尔值、非整数、负值及超范围值，并对重复索引采取明确口径。缓存签名建议使用规范化绝对路径、`mtime_ns` 和大小；若可用，应避免多文件共享的单一缓存槽造成错误复用，并给缓存设置条目/内存上限。
6. **补真实语料验收。**至少准备可分发的脱敏/合成样本覆盖 UTF-8 BOM、GB18030、Big5、全角数字、卷标题、序章/尾声、符号分节、乱码/替换字符、长章和正文中分隔线。计划要求几十个样本，当前没有随计划列出样本集或判定方法。

### 建议的 P1 验收补充

- 测试路径越界会进入确认流程，已确认路径按会话记录生效，Run 工作区变化时权限判定和实际读取保持一致。
- outline 响应不包含正文且分页完整；大量章节时不会超出单次结果预算。
- chunks 校验非法索引、空索引、重复索引和过多章节；超预算时给出可续取结果而不是静默截断。
- 文本拆分入口复用同一算法并有输入大小限制；算法对空文本、纯空白和单行输入有稳定且文档化的返回语义。
- 文件读取缓存不会因路径/文件元数据碰撞返回别的文件内容。

### P2 备注

P2 的持久化方向可行，但 `meta.json` 与 `chapters.json` 分开原子替换不能保证两文件作为一个整体事务更新。需要定义崩溃恢复/版本字段/删除行为，并限制章节总量和落盘空间。章节正文若作为长期作品数据保存，还应由作品数据域管理，不应依赖浏览器 `localStorage`。
