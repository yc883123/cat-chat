## 1. 本轮范围

按用户本轮口径，仅纳入下列七项：

| 编号 | 纳入问题 | 目标 |
| --- | --- | --- |
| A | 旧历史响应覆盖新会话 | 最后一次打开动作决定当前会话；迟到响应不得更新当前界面或恢复错误 Run；被作废的打开动作不再触发后续发送或预填 |
| B | 历史对话的 API / 模型保存、恢复与异步错写；全局默认缺少明确设置入口 | 会话选择独立保存；设置页明确配置新对话默认 API 和模型，并说明生效范围 |
| C | 织书台 / 拆书匠未保存正文在刷新、关闭时丢失；织书台切章也会丢 | 章节正文持续本地暂存，重新打开可恢复，冲突和暂存失败均可见 |
| D | 拆书匠并发保存稿件可能丢版本 | 读取索引、校验 revision、分配版本号和提交在同一临界区，成功稿件始终可查；`NovelStore` 其余清单写入同样在锁内读改写 |
| E | 织书台取消生成后仍可能提交任务 | 提交、取消、后台轮询三方有明确先后关系；流水线离开进行中状态后，在途提交返回的任务必须被取消或留下可追踪记录 |
| F | 拆书匠场次排序保存后回退 | 当前内容与最新剧本版本一致，重新读取、导出和后续生成保持新顺序，且不被并发的清单写入盖回 |
| G | 续写预检缺少原文却显示零差异 | 无法完成比较时明确显示未知，不冒充零差异 |

2026-11-11 用户确认的三项决定（已写入对应章节）：

1. 新建对话的模型：设置页配了新对话默认就用默认；没配就沿用当前输入区的选择（现状），不卡在「请选择模型」。见第 4 节。
2. 新对话默认单独存一对字段（API 档案加具体模型），不复用 `default_model_key`。见第 4 节。
3. `NovelStore` 其余清单写入方本轮一并收进锁。见第 6、8 节。

明确排除：HTML 同源附件、附件预检期间切会话串发、所有导入残本问题、要素/场次解析提示整改、造梦机、通用后台任务、任务总管、QQ、贴签匠和 MCP。本轮不借公共代码改动顺带修这些问题。

审核时看到、但属于排除范围或超出七项的同类问题，只登记不修：

- Agent 切换 `saveAgentSelection` 与思考强度 `setReasoningEffort` 保存返回后，同样按当前会话 ID 合并列表缓存。请求 URL 在发出时已固定，服务端数据不会错写，受影响的只有另一会话的前端缓存。
- Studio 任务开始执行时，`_run_task` 确认任务仍在排队之后、登记取消句柄之前有一个很短的空档；这时 `jobs.cancel` 返回成功，任务却照常跑完（`StudioRunner.cancel` 与 `_run_task`；只读了代码，没有复现）。属通用后台任务，本轮不修；E 只按任务终态判断是否停下，见第 7 节。
- 织书台删除作品不检查是否有进行中的流水线。本轮只要求 E 的在途提交在作品被删时仍能取消返回的任务，不改删除入口。

本轮不包含版本号调整、提交、推送、打包或发版，也不修改真实用户数据库、作品和配置。不根据旧审查的“22 项 / 12 高 10 中”扩充范围。

## 2. 已核实的模型行为

历史对话仍保存 `model_key`（API 档案标识）和 `model_name`（该档案下的具体模型名），并非已经取消按会话记忆模型。

现有入口：

- `public/js/07-models-agents.js::saveModelSelection`：先等待全局设置保存，之后才读取 `state.conversationId` 保存会话；切会话会造成错写，并把目标会话的具体模型名清空。
- `persistConversationModelName`：请求 URL 在发出时已固定，但响应后合并列表仍读取当前会话 ID，可能污染其他会话的前端缓存。
- `applyConversationModel`：显式传入历史 `model_name`；空模型名正常应显示“请选择模型”，不会必然继承上一会话具体模型。已有模型不在目录中时保留原值并要求重新检查。
- 缺失或已删除的 `model_key` 会静默使用全局默认；旧 `provider_id` 的兼容恢复也需要核对。
- 设置页 API 卡片的“当前”来自 `provider.is_default`，实际表示全局默认 API，不代表当前会话。现有默认可由旧 `provider_id` 迁移、首次保存档案或删除默认后的首个剩余档案自动产生；聊天区切 API 又会隐式改变它，用户没有独立明确的默认设置入口。
- `default_model_key` 是全应用共用的兜底值，不只管新对话（2026-11-11 核实）：
  - 后端：`ConfigStore.profile("")` 与 `generation_options("")` 回落到它；QQ 会话绑定在没有渠道默认时用它（`channels/service.py`）；提词库生成请求没带 `model_key` 时用它（`studio/service.py::prepare_generation`）。
  - 前端：辅助对话、贴签匠、任务总管新建、拆书匠、织书台、提词库的供应商下拉都拿它做预选。
  - 启动时 `_migrate_model_profiles` 会把空值或失效值补成第一个档案；`upsert_model_profile` 在它为空时自动填入；删除默认档案时改指向剩余第一个。
  - 结论：这个字段不能改成「可为空、待设置」，否则上述调用方会报错或换用别的档案。
- 设置页档案内 `provider.model`（表单标签「模型名称」）与普通会话的具体模型选择不同，但它在运行时有多处用途，不只用于连接测试（2026-11-11 核实）：
  - QQ 渠道没配渠道默认模型时，用它做会话模型名（`channels/service.py`）。
  - 视觉识别没单独指定模型时用它（`vision/runtime.py`）。
  - 档案没有显式设置图片能力时，`_infer_supports_images` 按它推断；对话侧是否沿用这份推断尚未核对。
  - KVMem 就绪检查、任务总管新建时的模型预选也读它。
  - QQ 的渠道默认是独立设置，本轮不改 QQ。
- `openConversation` 两次等待没有完整的过期校验，可能把旧会话消息与模型控件重新填回当前界面。它有 18 处调用，其中编辑重发、分支预填、搜索跳转在它返回后继续执行后续动作，见第 3 节。
- 具体模型保存目前只提交 `model_name`，可能留下“有具体模型名、没有 API 绑定”的旧会话。发送时空 `model_key` 虽可解析到全局默认，解析后的实际档案标识却未必固化到会话和 Run 快照，存在 API 随默认值漂移的条件。
- 新建对话目前发送输入区当时的 API 与具体模型（`createConversation` 传 `$('#modelSelect').value` 与 `composerModelChoice()`），所以在会话 A 里点「新对话」沿用 A 的选择。请求里 `model_key` 为空时，`api_create_conversation` 与 `ChatStorage.create_conversation` 会把它补成 `online:<全局旧 provider_id>`；默认档案是本地模型时前缀就是错的。
- 模型目录加载已有 API 档案和会话 ID 检查，应保留这些保护并补齐“同一会话内连续切换”的代次校验。

以上足以解释“切到历史对话仍看到新 API / 模型”的代码风险，但尚未读取真实历史数据确认用户遇到的具体一条记录。实施和验证使用隔离夹具，不擅自修写历史绑定。

## 3. A：会话加载只接受最后一次打开动作

### 修改方式

1. 为 `openConversation` 增加独立请求代次和目标会话 ID。用户直接点开的打开动作、新建会话、删除当前会话或进入空白新对话时，统一使更早的打开请求失效。
2. 在会话详情 GET、首轮上下文 GET，以及会改变当前界面的异步恢复步骤之后检查代次。旧成功响应、旧失败响应都不更新当前状态、消息、模型、Agent、工作区、首轮信息或 toast。
3. 会话详情与首轮上下文两个 GET 并行发出，都回来后在一个同步块里一次提交 `state.conversationId`、列表缓存、消息、模型、Agent、工作区、联网与思考开关、首轮信息和会话切换广播，避免 `state.conversationId` 已指向 B、消息仍显示 A 的半完成状态。首轮信息失败不阻止当前会话打开，但只清理本次目标的首轮信息。
4. Run 订阅和恢复同时核对会话与打开代次；迟到的 A 不能恢复订阅或关闭 B 的侧栏/连接。已发出的只读请求可取消以省请求，但正确性必须依靠代次检查。
5. 区分打开动作的来源（`openConversation` 共 18 处调用）：
   - 用户直接点开：侧栏点击、任务面板回跳、托盘通知回跳、分支链跳转、辅助对话的跟随标题、任务总管里的会话链接、搜索命中 `openSearchHit`。点下去就取新代次，作废一切更早的打开。
   - 先等一个接口、再打开会话：分支 `branchMessage`、工作台交接 `confirmStudioHandoff`、删除当前会话后打开下一个、编辑重发 `resendFromUserMessage`（截断后重载本会话）。代次在用户点下去时就记下；等接口期间用户又点开了别的会话，就不再打开。
   - 程序自动重载：运行结束 `finishRunSubscription`、取消后 `cancelCurrentRun`、发送被 409 拒绝与断流兜底（`sendChatMessage`）、取消编辑 `cancelActiveEdit`、编辑重发失败后的重载、启动或列表刷新时打开第一个会话。同样在动作开始时记下代次，要打开时代次已变就放弃；它们不能把用户刚点开的会话顶掉。
6. `openConversation` 返回本次打开是否生效：提交到界面返回真；被作废或被放弃返回假，不抛错也不弹提示；只有仍然有效的打开失败才抛出。返回假之后调用方停止后续动作：
   - 编辑重发：不自动发送，也不丢内容。原会话已被截断，改好的文字与恢复出来的附件留在输入区（输入区不随会话切换清空），并提示已切到别的会话、内容未发送。
   - 分支：不把分支内容预填到别的会话的输入区；分支会话已建好，提示到列表里打开。
   - 搜索命中：不在别的会话里定位消息。
   - 工作台交接：不提示已打开；新会话在列表里。
7. `08-conversations.js` 与 `11-run-stream.js`、`04-messages.js`、`12-chat-input.js` 互相 import，代次状态放在 `08` 内部或 `state` 上，由 `08` 导出读取函数，不新增反向依赖。
8. 保留已有切会话清理行为，不改附件发送链路。

### 验收

用可控延迟夹具覆盖：

- A 慢/B 快；详情完成顺序相同但 first_turn 顺序相反；A 失败/B 成功；连续打开同一会话；新建会话令旧请求失效；当前会话有活跃 Run。
- 编辑重发途中切到 B：没有任何内容自动发到 B，B 的消息不变；改好的文字没有丢，页面提示未发送。
- 分支、交接途中切到 B：停在 B，B 的输入区不被预填。
- A 的 Run 刚结束、终态重载在途时用户点 B：最终停在 B，A 的重载不生效。
- 被作废的打开请求失败：不弹错误提示。

最终消息、会话 ID、API、模型、Agent 和 Run 订阅必须全部属于最后一次有效打开动作。

## 4. B：历史对话保留自己的 API 与具体模型；新对话默认有独立入口

### 用户行为口径

- 历史会话保存并恢复自己的 API 档案和具体模型名。打开历史对话本身只读，不把全局默认写入它。
- 用户在会话 A 主动切 API 或具体模型，只修改 A。取消会话底部切 API 隐式修改全局默认的行为；全局默认由设置页单独配置。没有当前会话时只修改待创建会话的选择，不自动保存为全局默认。
- 设置页增加「新对话默认模型」设置：选择 API 档案和该档案下的具体模型，显式保存后生效。两项要么同时保存，要么都为空。文案说明它只用于新建对话，不改变已有对话；未设置时显示未设置，不悄悄选目录第一项。
- 新建对话的取值顺序：
  1. 调用方显式传了完整组合（分支、工作台交接、QQ 绑定），用它；
  2. 否则新对话默认已配置且仍然有效，用它，并把两项写入新会话；
  3. 否则沿用当前输入区当时的选择（现状），不卡在「请选择模型」。
- 新对话默认指向的档案被删除，或具体模型不在最新目录里：设置页提示默认已失效；新建时按「没配」处理，回落到输入区的选择，不改绑其他档案，也不阻止新建。
- API 档案编辑里的「模型名称」（`provider.model`）是档案自身的默认模型，服务于 QQ、视觉识别、KVMem 和任务总管等没有单独指定模型的调用，不是新对话默认。新对话默认是独立的一对设置，职责写清。
- A 的保存请求进行中切到 B，A 的请求仍归 A；返回结果不改 B 的列表项或控件。
- 旧会话确实没有绑定时显示「未设置 API / 模型」；可显示默认候选，但必须与已保存值区分，不能让用户误认为这是历史选择。发送前仍需满足现有模型选择和目录校验。
- 已保存 API 被删除时保留可识别的旧绑定提示，要求重新选择；不静默替换成全局默认。旧 `provider_id` 仅在能唯一映射到有效 API 档案时兼容恢复。
- 已保存具体模型不在最新检测目录中时，继续展示已保存模型并标注需要检查，禁止静默选目录第一项。
- 不为缺记录的历史会话猜测或批量回填过去用过的模型。
- `default_model_key` 保持现状，继续作为全应用共用兜底：`_migrate_model_profiles`、`upsert_model_profile`、删除默认档案时的自动改指向都不改。它不能变成可空，否则 QQ 绑定、提词库生成和各工作台预选会报错或换用别的档案。

### 修改方式

1. 新增一对设置字段，存新对话默认的 API 档案标识和具体模型名（字段名实施时定），两项要么都有、要么都空。登记到 `naiba/config.py` 的默认值、`update_settings` 白名单和校验，以及设置读写接口与契约测试。不做数据库迁移，升级后为空即「未设置」。
2. 设置页显式保存新对话默认时，同时把 `default_model_key` 设成同一个档案，让其他模块的预选跟着走。读取、保存、有效性检查和新建初始化使用同一套解析规则。
3. 新建对话初始化按「用户行为口径」的取值顺序落在 `createConversation` 及其调用方：分支 `branchMessage`、工作台交接、QQ 绑定等显式路径保持原参数；其余走新对话默认或输入区选择。默认失效时按「没配」处理。正常路径前端不再发空 `model_key`，后端现有的 `online:<旧 provider_id>` 补值可以不动。
4. `saveModelSelection` 在第一处 await 前固定会话 ID、API 选择和操作代次；移除会话切 API 对全局 `/api/settings` 的隐式写入，只写当前会话。没有当前会话时只改待创建的选择。返回后按原 ID 合并缓存，只有当前页面仍属于该会话且代次有效才更新控件。
5. 具体模型保存采用相同的目标快照规则；用户明确选模型时，把当前有效 `model_key` 和 `model_name` 一次写入同一会话设置，避免只有模型名的半绑定。正常发送时先解析并固定实际 API 档案标识，再按既有边界持久化并建立 Run 快照；打开历史页不触发这项补写。
6. 同一会话的选择变更按会话串行提交，迟到的「清空具体模型」不得覆盖更新的选择；一个会话的队列不阻塞另一个会话。`applyConversationModel` 补齐缺失/失效绑定分支；模型目录响应保留现有归属检查，并增加同目标重复请求的过期保护。
7. 设置页 API 卡片的角标「当前」改成「默认」（或等义说法），提示里写清它是各功能页的默认预选，不代表当前会话。「模型名称」表单标签不改名，旁边补一句说明它的用途。全局默认与会话选择的保存反馈分开处理：失败不回滚另一会话的控件，不显示成功却只完成一半。
8. 拆成两批实施。B1 是竞态修复：第 4 至 6 条，加发送时固化实际档案。B2 是新对话默认入口：第 1 至 3 条和第 7 条里的角标与说明。第 4 条里「会话切 API 不再写全局设置」必须和 B2 同批上线，否则用户没地方改默认。两批都完成才算 B 完成。同步纠正「空模型名会跟随供应商默认」的过时注释，保留普通对话发送必须有明确具体模型的现行规则。

### 事实

- `default_model_key` 的读取方：`ConfigStore.profile("")`、`generation_options("")`；QQ 绑定（`naiba/channels/service.py`，空了直接报错）；提词库 `prepare_generation`（`naiba/studio/service.py`）；前端的辅助对话、贴签匠、任务总管新建、拆书匠、织书台、提词库都拿它预选。
- 它的自动维护：启动时 `_migrate_model_profiles` 把空值或失效值补成第一个档案；`upsert_model_profile` 在它为空时填入；删除默认档案时改指向剩余第一个。

## 5. C：两处正文草稿暂存与恢复

### 问题与现状

- 织书台和拆书匠的章节正文只在保存时落服务端；未保存正文在刷新、关闭时丢失。
- 织书台切章没有任何保护：`openChapter` 成功后直接 `writer.draftDirty = false` 并重填编辑区，不确认。拆书匠的 `beginEdit` 在编辑中点另一份稿件的「编辑」时同样直接覆盖。两处都要验收。
- 现有设定/大纲草稿在 localStorage，`applyWriterDraft` 遇到版本对不上直接丢弃。正文草稿是用户唯一副本，不能照搬「过期即丢」。

### 存储与隔离

- 新增章节正文草稿专用存储，浏览器端用 IndexedDB 承载长正文。织书台现有设定/大纲 localStorage 草稿继续沿用，不搬迁、不因保存设定删除正文草稿。
- 草稿按模块、作品、章号及来源稿件/版本区分。记录正文、基础 revision（或来源标识）、更新时间、编辑代次；同章不同改编稿互不覆盖。
- `input` 后短延时增量暂存，并在切章、切书、切工作台、页面隐藏前尽早提交待写草稿。不能依赖 `pagehide` 中才开始的异步写入完成。
- 草稿是本地恢复副本，不自动新增服务端版本、不触发生成、不回写只读导入章节。
- 草稿存储做成可替换后端的独立模块：确定性前端测试跑在 Node 的 `vm` 里（`verify/writer_draft_offline_test.cjs`，由 `tests/test_writer_ui.py` 调起），那里没有 IndexedDB；测试注入内存后端，浏览器里用 IndexedDB。

### 恢复与冲突

1. 打开章节时先等待对应草稿读取，再决定初始编辑内容，避免服务端响应覆盖已恢复正文。
2. 冲突判定分模块：
   - 织书台按章节 revision 判。revision 只在保存正文、切版本、删版本时变；正文草稿不要挂在作品 revision 上——保存正文会同时推进作品 revision，现有设定草稿正是在这之后被判过期。
   - 拆书匠按「来源稿件是否还在、内容是否没变」判。拆书匠的稿件不可变，章节 revision 每新增一份稿件就涨、AI 改编写回也涨；照初稿按 revision 判，没受影响的草稿会全被标成冲突。
3. 基础一致时恢复到编辑区，保留「未保存」状态并提示已恢复本地草稿。
4. 基础变化、原稿被删除或基础信息不完整时，不直接覆盖服务端内容，也不按过期自动删除。提供「查看/复制草稿、基于当前版本继续编辑、丢弃此草稿」；丢弃必须由用户操作。
5. 成功保存后只清除本次提交对应、且编辑代次仍相同的草稿。保存等待期间的输入继续暂存；保存失败、409 和刷新失败都保留草稿。
6. 清理作品/章/稿时限定对应草稿键；缓存清理不能无提示删除未保存草稿。
7. IndexedDB 禁用、配额不足或事务失败时，显示「正文尚未暂存，请先保存或复制」，保留编辑区内容；仍有未暂存修改时加离页提醒。不得静默吞错。

### 入口与提示

- 页面重载后，织书台回到设定页且不打开任何章节，拆书匠打开第一章且不在编辑态。草稿不能只靠「打开那一章」才发现：打开作品时要列出这本书有草稿的章并提示，可从提示直接进入。
- 切章、切书、切工作台前按「恢复与冲突」第 4 条处理；织书台切章和拆书匠 `beginEdit` 这两处现在没有确认，验收必须覆盖。

### 能力边界

- 浏览器按地址隔离本地存储：桌面版换端口，或者手机用另一个地址访问，看不到原来的草稿。验收和用户说明都要写清。
- 验收目标是正常刷新、关闭和重新进入可恢复已经写入本地存储的草稿。进程突然崩溃或断电可能落在最新一次事务提交前，不承诺恢复尚未落盘的最后输入。通过持续短延时暂存缩小窗口，界面不能把「正在暂存」显示成「已暂存」。
- 桌面版点关闭只是藏到托盘，页面不卸载；从托盘退出再启动后才算重新进入，验收要覆盖这条。

### 验收

织书台与拆书匠分别覆盖：输入后刷新、输入后立即切章/切书、编辑中切到另一份稿件、关闭重开、桌面版托盘退出再启动、保存成功/失败/409、保存中继续输入、基础版本变化、来源删除、多章多稿隔离、旧设定/大纲草稿共存、大段正文、存储失败。恢复后的正文逐字比对；版本数不因本地暂存增加。

### 事实

- 全项目目前没有使用 IndexedDB。
- `tests/test_writer_ui.py` 钉了 `27-writer.js` 的 import 关系（不 import `25-novel.js`）和离线用例数（「27 cases passed」「writer export offline: 8 cases passed」），加用例要同步改这两处。
- 新增 `public/js/` 模块不用登记：打包整目录带走，`esm_graph_check.py` 和 `tdz_check.py` 扫整个目录，入口只有 `main.js`。
- 桌面版 WebView 是持久 profile，本地存储退出后还在。

## 6. D：拆书匠并发稿件保存与清单写入

### 修改方式

1. 将 `NovelStore.save_manuscript` 从读取清单/章节索引、revision 检查、来源校验、重复判断、版本号分配，到稿件与索引提交的整个过程纳入同一把现有 `threading.RLock`。可采用公开加锁方法与内部 locked 实现，避免外部调用漏锁。
2. 带正文的 `update_chapter` 同样整段进锁，避免拿调用前的旧索引回写、把并发新增的稿件索引盖掉。
3. `NovelStore` 其余「读清单或章节索引、改、写回」的方法本轮一并收进锁内读改写：`update_chapter`、`save_manuscript`、`delete_chapter`、`apply_elements`、`apply_outline`、`apply_script`、`update_scene`、`delete_scene`、`reorder_script`、`update_summaries`。`apply_*` 经 `_check_apply_revision` 读清单，`update_scene` 同样调用它，必须在锁内读；`update_summaries` 和 `delete_chapter` 的清单修改也要在同一临界区完成。
   已经整段在锁内、不用改：`delete_manuscript`、`delete_records`、`_upgrade_book`、`preflight_chapters`。
4. 有 expected_revision 的同基线并发保存只能一项成功，另一项明确 409；前端保留冲突方编辑。
5. 未提供 expected_revision 的合法调用在锁内依次读取最新索引，两个成功结果必须都能从章节列表找到，版本号不重复。
6. 保留完全相同内容的去重语义。校验失败不新增可见稿件；写入失败不宣称保存成功。

### 验收

用线程事件控制交错，不靠 sleep 碰概率：同 revision 双保存、无 revision 双保存、人工保存与 AI 写回交错、保存与删除交错、重复内容、写盘失败。重新创建 store 读取落盘结果，核对稿件文件、章节索引、revision 和版本号；所有成功响应对应的记录都可查询。

### 事实

- 锁是 `threading.RLock`，同线程可重入，嵌套调用不会死锁。
- `delete_records` 在锁内不调任务系统，没有跨模块拿锁的路径。

## 7. E：织书台提交、取消与轮询的三方竞态

### 修改方式

1. 协调三方：提交、取消、后台轮询。轮询每 0.5 秒扫一次，不能只按「任务号是否为空」判断。
2. 提交在途时，轮询不能因为任务号为空就判失败。做法是让「正在提交」可被识别；标记放内存还是落盘实施时定，落盘要先登记契约。服务重启后的收敛沿用现有「进行中的流水线标为已中断」。
3. 提交返回后只做一个判断：流水线还是不是本次尝试、还在不在进行中。不是，就取消刚返回的任务，并记录处理结果。这一条同时盖住流水线被替换、attempt 改变、被轮询判失败、作品已被删。
4. `cancel_pipeline` 的读任务号和写取消放进同一次加锁；写取消前在锁内复查状态，已经不在进行中就报「已结束」，不改写。
5. 取消后以任务到终态为准报告结果。任务还在跑就如实说「停止尚未确认」，保留任务号；不伪装已停止。
6. 不在作品 store 的锁里调 `jobs.submit` 或 `jobs.cancel`，避免取消请求排不进来。
7. 取消作用域限定织书台流水线，不改通用后台任务和其他工作台。

### 验收

用线程屏障卡位，不靠 sleep。至少覆盖四种交错：

- 点生成后、任务号回填前，轮询先扫到；
- 同一空档里用户点取消；
- 取消读到任务号之后、写取消之前，轮询写回任务并提交下一步；
- 取消读到「进行中」之后，最后一步刚好完成。

另加提交前、`jobs.submit` 内部、返回后写回前三个时间窗，验证取消先发生时提交次数为零；提交已在途时返回的任务号收到取消且无后续步骤；写回失败不遗留无归属任务；旧 attempt/旧 pipeline 不污染新一轮。检查取消失败提示和句柄记录。此处不声称能撤销取消前已发生的模型调用或费用。

### 事实

探针用真实 `WriterPipelineManager` 加假任务队列、临时目录，四种交错全部复现：

| 交错 | 结果 |
| --- | --- |
| 点生成后、任务号回填前，轮询先扫到 | 流水线被判失败「流水线缺少当前任务，无法推进」；任务号照样回填，任务照样跑，没人取消 |
| 同一空档里用户点取消 | 显示已取消；任务照样跑 |
| 取消读到任务 1 之后、写取消之前，轮询写回任务 1 并提交了任务 2 | 取消打在已完成的任务 1 上，任务 2 继续跑 |
| 取消读到「进行中」之后，最后一步刚好完成 | 已完成的流水线被改成「已取消」 |

- 第一种不需要用户点取消，点生成或重试就可能撞上。窗口是 `start_pipeline` / `retry_pipeline` 落下「进行中、任务号为空」到 `_submit_step` 回填之间，轮询每 0.5 秒一次。
- 后两种的原因是 `cancel_pipeline` 在锁外读清单，`_cancel` 没在锁内复查状态。
- `store.update_pipeline` 只校验流水线 ID 和 attempt，不校验状态；所以第一种情况里回填照样成功。
- 另一处只读了代码、没复现：Studio 任务开始执行时，`_run_task` 确认任务仍在排队之后、登记取消句柄之前有个很短的空档，这时 `jobs.cancel` 返回成功，任务却照常跑完。属通用后台任务，本轮不修，所以才有上面第 5 条。
- Studio 不反向调用织书台 store，没有反向拿锁的路径。
- 任务总管通过 `api_start_pipeline` / `api_cancel_pipeline` 调同一套逻辑，读流水线的 `status` 和 `current_task_id`。改状态语义时要看它。
- 现有 `tests/test_writer_pipeline.py` 的假任务队列 `_Jobs` 没有卡位能力，要加。

## 9. G：原文缺失时差异显示未知

### 修改方式

- 指定改编稿预检逐章核对是否存在唯一且可读取的原文。原文记录缺失、存在多个候选或读取失败，均不能计为相同。
- 只要所选范围内有不可比较章节，整体 `comparison` 为 unknown，`divergent_chapters` 为 null；沿用现有前端未知提示（`27a-writer-continuation.js` 按 `divergent_chapters == null` 显示「与原文的差异尚无法完整核对」），不添加误导性的零计数。
- 可在现有覆盖说明中列出不可比较的原因或章号，避免把未知与真正比较完成后的零差异混淆。若增加接口字段，先更新契约及测试。
- 原文不可比较不替换用户已选的有效改编稿，不扩展为导入恢复功能；正文完整性仍走现有预检。

### 验收

所有原文完整且相同为 0；完整且有差异为真实数量；缺原文、原文损坏、原文候选不唯一、部分章节不可比较均为未知；所选改编稿不变，原文路径正常预检不受影响。

损坏原文的夹具要真把磁盘上的稿件文件改坏。`_chapter_manuscripts` 已经把损坏稿件标成 `kind: "broken"`，匹配不上「原文」这个类别，所以 `preview_source` 里「读取失败算未知」的分支实际走不到；只改记录状态或只删文件都复现不出这条。
