## 2. 批次二：三栏按阶段分离 + 自由大纲/分部 + 拆章

### 2.1 阶段从三个变四个 + 左栏按阶段分离（反馈 #2 #3 + 截图批注）

> 依据是反馈文档里那 5 张截图上的手写批注（纯文本提取拿不到，必须拆 docx 看 `word/media/`）：
> 「设定界面、应该全是设定内容」／「大纲设定、几万字、分几部作品」「单部作品大纲、多部作品大纲、几万字的文字展示即可」
> 「设定汇总」「大纲汇总」／「**左侧的正文改成章节，右侧红框增加正文**」「单章节编写」「设定好的章节数量及章节字数限制」
> 「正文章节拆分及章节简述，可以选择整部作品要拆分成多少章，单章作品字数限制，章节结尾选择留有悬念。」

**结论（已按用户口头纠正定稿）：阶段标签从 3 个变 4 个——设定 → 大纲 → 章节 → 正文。**
不是「正文页里并排四列」。原「正文」标签**改名「章节」**（只放拆章与生成参数），**右侧新增第四个标签「正文」**（写作区）。

| 阶段 | 左栏 | 中栏 | 右栏 |
|---|---|---|---|
| 设定 | 作品摘要 + **设定版本**（**不挂目录**） | 设定表单（批次三细化那套） | 说明（预检） |
| 大纲 | **设定汇总**（创意/题材/角色/雷区只读）+ 大纲版本 | 部标签 + **几万字大纲文字** + 「去章节页拆章」 | 大纲概览（部数/字数/预计章数） |
| **章节**（新） | **大纲汇总**（当前部大纲原文，可切换部） | **正文章节拆分 + 章节简述**（拆多少章 / 单章字数限制 / 结尾留悬念；下面是逐章简述列表） | 拆分进度 / 本次会带上什么 |
| **正文**（新） | **设定好的章节数量 + 章节字数限制**，下面接目录（按部分组 + 分页） | **单章编写**（整屏宽，只放正文与版本） | 说明 |

- 「写这一章」（章节页）提交后生成，完成自动跳「正文」页看结果；正文页只做「单章编写」，参数一律回章节页改；
- 单章字数限制与结尾策略是**章节级参数**（跟着章走，不是全局设定），落库在章节索引里；
- 手机（≤760px）：四阶段仍收成 `作品 / 编辑 / 说明` 三档，阶段按钮横向可滚；不新增第四档。

改动点：

- `public/index.html`：`#writerStages` 增 `data-writer-stage="chapter"`；`.writer-book` 内拆三个 `[data-writer-side="setup|outline|chapter|draft"]` 容器（chapter 与 draft 共用目录结构，只差「大纲汇总」折叠块）。
- `public/js/27-writer.js`：
  - `writer.stage` 取值扩成 `setup|outline|chapter|draft`；`setStage()` 的白名单同步；
  - 新增 `renderSide()` 按阶段切 `hidden`（复用 `applyPaneAccessibility` 的 inert 口径）；
  - `renderChapters()` 只在章节/正文两侧渲染，并**按部插入分组标题**；
  - 新增 `renderSetupSummary()`、`renderParts()`、`renderSetupVersions()`、`renderSplitCard()`；
  - 目录分页 `writer.tocPage` + `#writerTocPager`；搜索按章号/标题过滤；
  - 「写这一章」→ `submitPipeline('chapter', {...})`，pipeline 终态 `setStage('draft')`。
- `naiba/writer/prompts.py`：`build_draft_context` 增 `target_chars`、`ending`；`split` 步新增（见 2.2）。
- `public/styles.css`：`#writerStages` 四个按钮的窄屏横向滚动；`.writer-columns` 四阶段共用三栏，不加第四列。
- 守门：`test_writer_ui.py` 增「四个阶段按钮都在」「目录不得出现在设定/大纲侧」「章节页有拆章卡」「正文页没有参数表单」；冒烟逐阶段断言。

**风险**：`renderAll()` 里所有 `renderXxx` 现在假设「目录总在 DOM 里」；分离后每个函数都要明确自己属于哪一栏，否则会出现「大纲阶段把目录渲染进隐藏容器」这类静默错。落法是先抽 `renderSide()`、再逐函数改归属，最后跑冒烟。

**另**：`writer.stage` 的旧值 `draft` 现在语义变了（= 第四个阶段「正文」），章节页要新值 `chapter`；已发布的 3.9.12 客户端不做兼容（前端整包随版本走），但**存进 localStorage 的 `stage`/草稿里若有旧值，需按白名单回落**，未知值一律当 `setup`。

### 2.2 大纲模型：文字大纲 + 分部（反馈 #49）

新 outline 版本内容（`schema: 2`）：

```jsonc
{
  "schema": 2,
  "parts": [ { "no": 1, "title": "第一部 · 雾港", "text": "【主线】…（几千到几万字）", "chapter_from": 1, "chapter_to": 96 } ],
  // 单部作品的 parts 只有一个元素；不再要求「章」这一级
}
```

- `naiba/writer/store.py`
  - 新增 `normalize_outline_parts(raw)`：部数 1–20，每部 `text` 不设硬上限（落盘上限 200,000 字符），部标题可空（自动「第 N 部」）。
  - `save_outline(..., parts=...)` 与既有 `chapters=...` 并存：**两者互斥**，`parts` 模式不再同步章节索引（同步移交给拆章）。
  - `load_outline` 归一：老文件 `{chapters:[...]}` → `{schema:1, chapters:[...]}` 原样返回，前端识别为「逐章大纲（旧版）」。
  - manifest 增 `parts: [{no,title,chapter_from,chapter_to}]`（由拆章结果回写）。
- `naiba/writer/prompts.py`
  - 删 `OUTLINE_MAX=30`；新增 `SPLIT_MIN, SPLIT_MAX = 1, 9999`、`SPLIT_BATCH = 200`。
  - `outline` 步改造：输出**纯文本大纲**（按部），不再出 JSON 章节数组；`parse_outline_text()` 取正文（容忍模型带 ``` 围栏）。
  - 新增 `split` 步 + `parse_split()`：输入当前部大纲文字 + 设定摘要 + `chapter_from` + 本批目标数，输出 `[{no,title,beat,hook}]`，**只允许追加/覆盖未成稿章**。
- `naiba/writer/pipeline.py`
  - 新增 kind `outline_text`（生成大纲文字）与 `split`（拆章，单批 ≤200，可重入）；
  - 旧 kind `outline` 保留 = 老客户端/老任务兼容（文字+拆章两步合并），新 UI 不再用。
- `naiba/writer/service.py` + `naiba/http.py`：`PATCH book` 接受 `parts`；新增 `POST /books/<id>/split`（目标章数、part_no、chapter_from），返回本批结果与 `remaining`。
- 前端：大纲面板 = 部 tabs + 大文本编辑（自动存草稿）+ 拆章卡（目标章数 + 预设 30/100/300/1000/3000/9999 + 「只拆当前部 / 全书一起拆 / 按现有章节补拆」）。

**老作品怎么办（需拍板，见 §5-1）**：建议旧数据只读展示 + 「升级为文字大纲」按钮（把每章 `beat` 拼成文本，用户可改），不自动迁移——自动迁移会把 30 章的梗概糊成一段不可用的文字。

**9999 章的现实口径**：不是一次生成。拆章按批（默认 200/批），前端循环提交、可中断续拆；右栏显示「第 1–200 / 201–400 …」进度。一次让模型吐 9999 章必然是流水账，分批才有质量可言。

### 2.3 生成设定后自动跳大纲（反馈 #51）

`submitPipeline('setup_all')` 的流水线终态回调里：`if (kind === 'setup_all' && status === 'done') setStage('outline')` + toast「设定已保存，接着生成大纲」。守门：冒烟断言完成后 `.active` 阶段是 `outline`。

## 5. 需要你拍板的 6 件事（括号里是我的建议）

1. **正文四栏的顺序**：目录 | 章节 | 正文 | 说明（推荐，正文拿整屏宽、说明本来最窄）／目录 | 章节 | 说明 | 正文。
2. **老作品的逐章大纲**：保留只读 + 手动「升级为文字大纲」（推荐）／自动迁移成一段文字（不推荐，梗概会糊成一团）。
3. **9999 章的拆章粒度**：每批 200 章、可中断续拆（推荐）／一次拆完（不推荐，质量必崩）。
4. **30 种风格的约束文案**：统一模板 + 每风格 2–3 句差异（推荐，本轮可交付）／逐条精写长约束（拖 2–3 天）。
5. **标签上限**：20（推荐）／30／不限。
6. **99 个配角怎么来**：主角色一次生成、配角分批 10 个/批（推荐）／一次全给（不推荐，token 与质量都撑不住）。

## 6. 验收（逐条写进冒烟）

- 设定/大纲/正文三阶段左栏内容各不相同，且切换不残留上一阶段的内容（含手机三档）；**设定页看不到章节目录**。
- 大纲：新增第二部 → 切部 → 两部的文字互不覆盖；保存后版本列表出现新版本；大纲页**没有**逐章梗概表。
- 正文：四栏都在（目录/章节/正文/说明）；`章节` 栏能拆章；`正文` 栏能编辑并保存版本。
- 拆章（正文页）：目标 100 章 → 章节数变 100、目录分页正确、已有正文的章未被覆盖；目标 9999 时按批推进、可取消。
- 单章字数限制 / 结尾策略：选题后 `POST /pipelines` body 带上，`generate/preview` 里能看到对应提示词段落。
- 老作品（批次一之前创建的）：大纲显示为「逐章大纲（旧版）」只读，点升级后变成可编辑文本。
- 设定：题材树选「男生类 › 都市 › 悬疑」后，请求体 `genre.cat/sub_cat/channel` 正确；标签选 8 个能提交、选 21 个被拒并提示。
- 角色：加 10 个主角被拒（提示上限 9）；配角 20 个可保存；卡片 12 字段往返一致。
- 参考作品：加两条、勾 3 个维度，提示词里出现对应文本（用 `/api/writer/generate/preview` 断言）。

第一次读文档只提取了纯文本，漏掉了图上的批注（我第一次自己转录还认错了几处字：把「章节大纲」读成「大纲」、

| 图 | 页面 | 图讲什么 / 红字原文 |
|---|---|---|
| 图1 | 设定（深色主题，玫瑰灰烬 · 0 章） | **没有红字**。说的是「**切换页面丢状态**」——切走再回来填的内容没了（批次一已修） |

| 图4 | **章节页** | 左侧栏 = **大纲汇总**；中栏 = **正文章节拆分以及简述，可以选择正式作品要拆分多少章作品，单章作品有字数限制，章节结尾选择留有悬念** |

结论（已落进 §2.1 / §2.2）：
- 设定页左栏**不要目录**，整页只放设定；

- 正文页左栏 = 设定好的章节数量与章节字数限制（下面接目录）；中栏 = 单章编写。

## 7. 实施记录（2026-10-30 已落地，3.9.13-beta）

按本计划全部实现并发布，落地时与本计划的两处差异：

1. **拆章位置**：按图4 批注，拆章卡落在「章节」页（不是正文页），正文页只做单章编写。
2. **正文页仍是三栏**：图5 的「右侧红框增加正文」被理解为**第四个阶段标签**，而不是正文页里的第四列；正文页仍是「目录 | 单章编写 | 说明」。
