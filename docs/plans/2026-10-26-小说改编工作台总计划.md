### 阶段一：导入与拆章（零 AI）

任意小说 TXT 丢进去 → 自动识别编码 → 自动拆章 → 勾选 → 存成作品 → 章节可编辑/导出。

## 五、跨阶段统一契约（最重要的一节）

### 5.1 两条铁律

| 铁律 | 说明 |
|---|---|
| **两段式** | 索引接口（章节列表 / 作品详情）**绝不带正文**，正文只按需取单章。整本回传会撑爆上下文，这是拆书匠 P1 就定下的规矩，有 `test_outline_has_no_body` 守门传统 |
| **零 AI 边界** | 脚本与算法层不 import `app` / `llm` / `run` / `jobs` / 任何会话 Run 模块；用 AST 守门钉死 |

### 5.2 数据模型与持久化契约

```
data_dir/studio/novel/<book-id>/
├── book.json    # {schema_version:1, revision, id, title, source:{name, encoding, bytes, split_level, max_len}, chapter_ids[], created_at, updated_at}
└── chapters/0001.json    # {schema_version:1, revision, i, title, len, content}
```

阶段二、三在 `book.json` 增字段：`characters[] / scenes[] / props[] / outline / summaries{} / script[]`。单章一文件：改一章不重写整本，坏文件不拖累其它章。所有 JSON 写入沿用 `naiba/studio/custom.py:69-76` 的 `_safe_path` 越界校验和 `:109-120` 的同目录临时文件 + `os.replace` 原子替换。

持久化规则固定如下：

- `schema_version` 当前为 `1`；未来字段升级必须显式迁移，不按缺字段静默猜测。`revision` 为单调递增版本，用于编辑和 AI 结果写回的乐观并发校验。
- `book.json` 是作品清单的权威来源，`chapter_ids` 决定哪些章节属于作品。保存章节时先原子写章节文件，再原子更新 `book.json`；两者之间进程崩溃时，未登记的孤儿章节忽略并可清理，已登记但缺失或损坏的章节使作品进入“数据异常”状态，禁止静默补空正文。
- 新作品导入先写入临时作品目录，清单和全部章节均成功后才提交为正式目录；失败或中断的临时目录不出现在作品列表中，可由清理逻辑删除。
- 删除只接受已校验的 `book-id`，作用范围严格限定为对应作品目录；删除中断不得波及其它作品，遗留目录保持可重试清理。删除作品不删除 Studio 历史任务记录，但历史任务打开时应提示作品已删除。
- 单个源文件继续沿用 `MAX_FILE_BYTES = 60 MiB`；作品目录总量上限暂定为 `256 MiB`，任何导入、编辑或 AI 写回超过上限都整项拒绝，不自动截断、不删除历史章节。该上限集中定义，不散落在接口和前端。

注意：`tests/test_sqlite_write_retry.py` 的 AST 守门只扫 `ChatStorage`，Studio 下新写路径不在守门内，需自觉沿用上述原子写范式。

### 5.3 任务字段（阶段二、三）

阶段一是文件处理工具：导入 TXT、识别编码、拆章、勾选、保存和编辑均在一次请求或本地页面交互中完成，不创建 Studio 任务，不进入任务队列，也不提供任务进度、重试或取消。

阶段二、三的 AI 生成才进入 Studio 任务队列，沿用 `service.py:197-212` 的 `input_data` 契约，小说侧固定：

| 字段 | 取值 |
|---|---|
| `module` | `"novel"` |
| `origin_label` | `"创作场"`（**必填**，否则历史来源显示不出来） |
| `title` | `《书名》· 阶段名` |
| `novel` | `{book_id, stage, chapter_ids}`（input 是自由 dict，retry 原样带回） |

**不往 `MODULE_TABS`（`22-studio.js:15`）加 `novel`**：那是分类导航数据源，加进去会在模块库多一个空分类。

### 5.4 长文策略（阶段二、三）

| 做法 | 取证 | 本侧取值 |
|---|---|---|
| 章节级调用，全书不进 prompt | `nv_main.js:1548-1568` | 一次只带勾选章节，默认 1 章 |

### 5.6 前端信息架构与响应式契约

前端以 `_novel_workbench_mockup.html` 为评审基准。该文件是独立预览，不是生产页面；生产实现必须接入现有 Studio 壳层、主题变量和事件绑定，不复制 mockup 的临时导航或演示数据。

#### 5.6.1 统一页面结构

- 「创作场」是 Studio 的独立分页，不混入聊天顶栏、模型/Agent 选择或会话输入区；沿用现有 Studio 的深色侧栏、浅色工作区、模块级阶段导航。
- 顶部阶段导航固定为「拆章 / 要素 / 大纲 / 剧本」。当前阶段使用轻强调色，切换阶段不丢失当前作品、章节选择和任务状态。
- 阶段一至三共享同一个三栏工作区：左栏「作品与章节」、中栏「当前阶段编辑区」、右栏「作品预览 / 任务结果 / 下一步」。不为每个阶段另造一套页面壳。
- 左栏承担作品摘要、章节筛选、章节勾选和当前章节定位；中栏承担当前操作和正文/结构编辑；右栏承担保存状态、生成状态、结果摘要和下一步入口。正文和章节列表遵守两段式，列表区域不一次性渲染整本正文。
- 面板内部独立滚动，页面本身不产生横向滚动；标题、状态和操作按钮不得依赖 hover 才可发现。

#### 5.6.2 手机横屏优先

- `844×390`、`812×375` 是横屏首要验收尺寸。横屏保留三栏同时可见：章节栏约 `170px`，中间编辑区占剩余主宽度，右侧预览栏约 `198px`；可压缩次要说明文字，但不能隐藏章节、编辑和结果三个核心区域。
- 横屏窄宽度下保留独立的深色窄导航和紧凑阶段栏；按钮、状态点、章节标题和芯片允许换行或省略，不得互相覆盖。
- 桌面宽度使用弹性列，不写死整页像素宽度；三栏最小宽度不足时先压缩留白和辅助文案，不能把正文区域压到不可编辑。

#### 5.6.3 手机竖屏降级

- `390×844`、`375×812` 竖屏不强行保留三栏，改为「章节 / 编辑 / 预览」三档分段控件，同一时间只显示一个面板，避免横向滚动。
- 默认打开「编辑」档；切换到「章节」或「预览」后保持当前作品和选中状态，返回不会重新加载或清空内容。
- 每个分档必须有明确的当前态和可聚焦控件；隐藏面板不可被键盘或辅助技术访问。

#### 5.6.4 视觉和控件约束

- 复用 `public/styles.css` 的语义变量、主题覆盖、边框、阴影、圆角和状态色；浅色/深色都必须可读，不新增一套小说专用色板。
- 采用紧凑的工作工具风格：细边框、小圆角、短按钮、信息卡和状态点；不使用大英雄区、营销式说明、渐变背景或卡片套卡片。
- 章节列表项标题最多两行，第二行放字数/处理状态；长书名和长章节名使用省略或换行，不能挤压复选框和操作入口。
- 破坏性操作（删除作品、删除章节、覆盖已有改编结果）必须有明确确认；保存、排队、完成、失败、已过期等状态必须有文字，不只用颜色或图标表达。
- 阶段二、三的任务状态在右栏和移动端「预览」档均可达；取消、重试、查看结果不依赖回到桌面布局。

#### 5.6.5 前端视觉验收

除功能 smoke 外，每阶段都要检查：桌面 `1440×900` / `1280×900`、横屏 `844×390` / `812×375`、竖屏 `390×844` / `375×812`，浅色和深色各一遍。验收重点是三栏或分档状态是否清晰、文本是否溢出、面板滚动是否独立、按钮是否可达、隐藏区域是否不可聚焦。

### 5.7 编码

顺序 `utf-8-sig → utf-8 → gb18030 → big5`（复用 `CONV_FILE_ENCODINGS`，`naiba/core/conv_files.py:32-34`）。
**口径要诚实**：`encoding` 是「实际选中的解码方式」，不是对源编码的确定性判定——gb18030 能解大量其它编码的字节。文档与 UI 都不宣称「精确识别」。
