# 甲、输入框「展开/折叠」失效与空框残留

> 诊断手段：静态 `public/` 服务 + 真后端隔离实例（8801）+ Playwright 只读探针 + 截图像素级取证。

## 1. 报障与已确认的事实

本人两次报障：

1. **手机端**（360 宽，草稿「你好」）：点双箭头 → 弹出输入法，输入框一点没变大。
2. **桌面端**（截图 1584×1067）：点双箭头 → **完全无反应**。
3. **追加**：展开后输入框**变得很大但里面是空的**，且双箭头已不高亮。

### 1.1 实测数据（真后端隔离实例，桌面 1584×1067，DPR1）

`verify/_probe_box_height.cjs` 逐帧读数：

| 步骤 | textarea 高 | is-expanded | aria-pressed |
|---|---|---|---|
| 初始空 | 39 | false | false |
| 折叠 + 「你好」 | 39 | false | false |
| **展开 + 「你好」** | **39** | **true** | **true** |
| 展开 + 20 行 | 480 | true | true |
| 展开 + 清空 | 39 | true | true |
| 收起 + 清空 | 39 | false | false |

手机视口（360×780 DPR3）读数同形：展开 + 「你好」= **39px**，上限从 180px 抬到 561.6px 而实际高度不变。

**结论：状态切了，上限抬了，实际高度一动不动。桌面手机同一个 bug。**

### 1.2 截图像素取证（本人第二张截图）

| 观测项 | 像素读数 | 含义 |
|---|---|---|
| 输入框蓝框 | y=775 → 1016，**241 物理 px** | 框高 241 |
| 框内 y=778~954逐行扫描 | **每行 0 个非背景像素** | 177px 纯空白，无文字无卡片 |
| 双箭头键底色（x=1380~1420） | `(23,26,36)` = 背景色 | **未高亮 ⇒ 非展开态** |

| 发送键尺寸 | 55×52 物理 px | ~~CSS 38×38 ⇒ 缩放比 ≈ 1.447（Windows 150%）~~ **订正（2026-10-05 晚）：这是把截图物理像素当 CSS 尺寸算出来的伪比例。** 两张截图同窗口同布局（双箭头键 x=1380~1420、发送键 x=1440~1480 完全一致），真实 DPR = **1.25** |

**订正后的换算式（DPR 1.25）**：241 ÷ 1.25 = **192.8 CSS px**；减去 `.composer` 的 padding+border（6×2+1×2=14）⇒ textarea ≈ **178.8 CSS px**，对应 **7 行**内容高（7 × 23.2 + 16 = 178.4；真机实测 178px，逐位吻合）。

### 1.3 已排除的假设（都做了实测，不是推理）

| 假设 | 实测结果 |
|---|---|
| 清空后高度残留是通用问题 | **否**。发送（`11-run-stream.js:553`）、插话入队（`18-interjections.js:341`）、种子填入（`04-messages.js:71`）、分支预填（`:658`）、编辑回填（`:246`）**全部调了 `resizeTextarea()`**，真后端实测清空后一律回落 39px |

| 某个 hidden 元素仍占位（`pending-files` / `run-guidance-list` / `input-mirror` / 各弹层） | **否**。`verify/_probe_tall_empty.cjs` 逐一强制 `display:none` 每个候选元素，`#composerForm` 高度**全部 Δ=0** |

## 2. 根因（问题一：展开无效 —— 已完全确定）

### 2.1 展开只放宽「上限」，不放宽「实际高度」

```js
// public/js/13-skill-refs.js:412-413
const cap = composerExpanded ? expandedCap() : MAX_COMPOSER_H;
input.style.height = `${Math.min(input.scrollHeight, cap)}px`;
```

```css
/* public/styles.css:2820 */
.composer-wrap.is-expanded textarea { max-height: 72dvh; }
```

高度**永远由内容决定**。草稿只有「你好」时 `scrollHeight = 39px`，把上限从 180px 抬到 768px **完全用不上**。

灌 20 行草稿后再点：桌面 480px（内容高）、手机 562px（触 561.6 上限）—— **只有长草稿才看得出展开**。这就是为什么这个功能从上线起从未被察觉。

### 2.2 手机端强制弹键盘，把 bug 放大成反向体验

```js
// public/js/13-skill-refs.js:393, 396-398
if (composerExpanded && focus) $('#messageInput')?.focus();
export function toggleComposerExpanded() {
  setComposerExpanded(!composerExpanded, { focus: true });   // 恒传 true
}
```

手机上 `focus()` 必弹键盘 ⇒ 观感变成「点了双箭头就弹输入法」。桌面 focus 无害，所以桌面是纯粹「零反应」。

### 2.3 参照系错+ 监听源漏（键盘态下上限永不重算）

- `MAX_COMPOSER_H_EXPANDED_RATIO` 用 `window.innerHeight`（`:368`），CSS 用 `dvh`。
- **Android软键盘弹起时两者都不缩小**，只有 `visualViewport.height` 缩。
- 重算只监听 `window.resize`（`:388`），而键盘开合**只走 `visualViewport.resize`**。

项目里 `09-settings.js:2507`、`15-bind-events.js:1350` 早就用 `visualViewport` 修过同类问题，**展开态是漏网的**。

## 3. 改动方案

### S1 — 展开态给真实的最小高度（核心）

`public/js/13-skill-refs.js`：

```js
// 展开态下限：与 CSS 的 min-height 兜底同源，改一处必改另一处。
const MIN_COMPOSER_H_EXPANDED_RATIO = 0.40;   // 占可视视口 40%

// 统一的可视视口高度：键盘弹起时 window.innerHeight / dvh 都不缩，只有它缩。
function visibleHeight() {
  const vv = window.visualViewport;
  return vv && vv.height ? Math.min(vv.height, window.innerHeight) : window.innerHeight;
}

function expandedMin() {
  return Math.max(200, Math.round(visibleHeight() * MIN_COMPOSER_H_EXPANDED_RATIO));
}

function expandedCap() {
  return Math.max(expandedMin(), Math.round(visibleHeight() * MAX_COMPOSER_H_EXPANDED_RATIO));
}
```

`resizeTextarea()` 的量高行改为三段（**折叠态分支逐字不动**，守住 §九.128 的 placeholder 契约与 `test_composer_height.py` 的负向断言）：

```js
const cap = composerExpanded ? expandedCap() : MAX_COMPOSER_H;
const content = Math.min(input.scrollHeight, cap);
const height = composerExpanded ? Math.max(content, expandedMin()) : content;
input.style.height = `${height}px`;
```

效果（1067 高桌面 / 780 高手机）：

| | 折叠 | 展开 |
|---|---|---|
| 空/两字草稿 | 39 | **427/ 312**（真变大） |
| 20 行草稿 | 180（封顶） | 480 / 562（触上限） |

`setComposerExpanded()` 里把重算监听补上 `visualViewport`：

```js
const vv = window.visualViewport;
vv?.addEventListener('resize', onViewportChange);
vv?.addEventListener('scroll', onViewportChange);   // 键盘推挤时 offsetTop 变
window.addEventListener('resize', onViewportChange);
```

`onViewportChange` 内只在 `composerExpanded` 时 `resizeTextarea()`（折叠态不受键盘影响，保持现状）。**绑定只做一次**，沿用现有 `composerResizeBound` 标志位。

### S2 — 焦点策略：手机端展开不自动弹键盘

`toggleComposerExpanded()` 改为按指针判定（复用现成 helper `isCoarsePointer()`，`01-core.js:1051`）：

```js
export function toggleComposerExpanded() {
  // 粗指针（手机/平板）：focus 必弹键盘，会把刚展开的区域又压掉一半 ⇒ 不抢焦点。
  // 细指针（桌面）：保持原行为，点完直接能打字。
  setComposerExpanded(!composerExpanded, { focus: !isCoarsePointer() });
}
```

用户在展开态点输入框后键盘正常弹，此时 `visibleHeight()` 已经变小、S1 的重算会把框收缩到键盘上方并保持「大」——这正是想要的效果。

### S3 — 空框残留 241px：**已收口（误诊，无代码改动）**

原计划：先拿本人机器上的真值再修。已按此执行——**只读**探针 `verify/_probe_user_box.cjs`（不进产品包）配一键启动器 `verify/_probe_user_box_start.cmd`（自动带调试端口启动 + 自动挂探针），在本人真机上完成取数：

| 真机读数 | 值 | 判读 |
|---|---|---|
| 内联高度（有内容态） | 有值，**178px** | 与 `sdafa` + 6 个手动回车（7 行）逐位吻合（7×23.2+16≈178.4） |
| 全选删除后 | 立刻回落 **39px**（一行） | 清空路径健康，无残留 |
| 空框展开 → 再收起 | 仍 **39px** | 展开往返也不残留 |
| 原始截图 241px 复核 | 241 ÷ 1.25（DPR 实测）= 192.8 CSS − 14 = **178.8px** | = 7 行，与真机同值；原「1.447 缩放」是算错的伪比例 |

**结论：241px 是纯换行内容撑高的正确高度**（换行不渲染像素，截图扫行「看不见」才被误判为空白；发送键灰掉则因 trim 判空，`03-media.js:1264`）。**无代码改动，无守门新增。** 探针留在 `verify/` 作自动捕手；已知盲区：其自动落盘触发条件是 `valueLength===0`，纯空白值（本次这种）不触发，复现时靠人工交互即可。

原「三种可能」定位表（内联有值⇒漏 resize / 无值 computed 高⇒CSS 层 / 无值 computed 低⇒外层元素）不再需要，实测走的是第四种此前没列出的可能：**高度正确，内容本身是换行**。

### S4 — CSS 兜底与清理

`public/styles.css:2817-2824`：

```css
/* 展开态下限兜底：仅防 JS 未跑/首帧塌陷。
 * ⚠️ 不能用 vh/dvh 比例值：键盘弹起时 vh/dvh 都不缩，min-height 会优先于
 * 内联 style.height，把 S1 的「收到键盘上方」又顶回去。只能用与
 * expandedMin() 绝对下限同源的固定值。 */
.composer-wrap.is-expanded textarea { min-height: 200px; }
```

同时删掉 `expandedCap()` 里对 `window.innerHeight` 的依赖（已由 S1 替换），并把注释里「与 styles.css 同值，改一处必改另一处」的两处交叉引用更新到新的三个常量。

### S5 — 展开键换位置换形态（本人 2026-10-05 交互预览定稿）

形态：**18×18px 迷你按钮**（现为 38px 标准 icon-button），图标换成 **45° 斜向双箭头**（现有双山形 SVG 外套 `<g transform="rotate(45 12 12)">`，svg 显示尺寸 11px）。

位置：从发送键旁的按钮列**挪进 `.composer-input` 内部**，绝对定位于 textarea 右上角。

关键实现点（全部来自交互预览实测，不是推理）：

1. `#expandComposer` 节点从按钮列移入 `.composer-input`（`index.html:188-193` 内、textarea 之后）；`.composer-input` 需补 `position: relative`。
2. 防遮文本 + 防滚动条挡按钮：给 `#messageInput` 加 **`margin-right: 26px` 排水沟**。**必须用 margin 不能用 padding**——padding 只推得开文字，滚动条仍贴元素右缘，会压住按钮（预览实测暴露，滚动条 15px 宽）。按钮放在沟里，滚动条永远够不到。
3. `#inputMirror` 与 textarea 同盒覆盖，**必须吃同样的 margin-right**，否则镜像与文本错位。
4. 编辑态：`.composer-input` 随整个 composer 搬进气泡，按钮在父容器内天然跟随，无需额外处理；skill/file 弹层同样锚在 `.composer-input` 内，确认弹层 z-index 高于按钮（按钮只给 `z-index:2`，不挡弹层）。
5. 更新 `index.html:229-231` 的旧注释（记录的是「放按钮列不遮文本」的理由，已过时，改写为新位置的理由 + margin 排水沟的坑）。
6. `styles.css:2824` 的 `.expand-button[aria-pressed="true"]` 高亮规则保留（class 名不变）。

- **报障**：冻结版 exe（`D:\naiba-chatexe\cat-chat.exe`，3.1.1-beta = `7671180`）里 `claude-opus-5.5`（provider `codecraftapi`）「说话很奇怪」，每轮只吐几个字。

## 一、现象与证据

### 1.1 账对不上

会话 `7116d4141cf14f6ca994f7d59fcbdd81`（工作区 `D:\naiba-chat`，`reasoning_effort=high`，provider `f8ef3053318d` / `claude-opus-5.5` / `openai_chat`）。

`run_events` 里**每轮只 1 个 delta**，而同轮 usage 的 `last_output_tokens`：

| 轮 | 界面看到的字 | 该轮 output tokens |
|---|---|---|
| 1 | 「收到，手机上双」(7字) | 143 |
| 3 | 「收到，」(3字) | 130 |
| 6 | 「收到，先不急着改——我来定位下」 | 276 |
| 12 | 「先定位」(3字) | 513 |
| 14 | 「已定位双箭头逻辑，先不改代码——把」 | 1120 |

> 取证注意：产品在跑时**不要读活库**（`chat.db-wal`/`-shm` 有锁），先复制 `chat.db`/`-wal`/`-shm` 三件再开只读连接。
> **工具轮的助手消息不落库**（扫最近 400 条 assistant 无一带 tool action），所以中间那几段正文只能从 `run_events` 取。

### 1.2 原始 SSE（决定性）

直连同一端点抓三个用例（必须带浏览器 UA，否则 Cloudflare `403 error 1010`）。带工具那个用例：

```
content    ← "手机点双箭头却弹起键盘，这个交"        正文前半句
tool_calls ← list_directory（name 先到）
arguments  ← {"path":"/"}
content    ← "互确实反直觉 — 先帮你把问题理清楚再定修复方案。"   后半句在 tool_call 之后
finish_reason = "tool_calls"
```

边界是 **「这个交」+「互确实…」= 交互**，正文被从词中间劈开。这是 Anthropic 的原生顺序（`tool_use` block 可排在 `text` block **之前**）被 OpenAI 桥照搬的结果。

附带发现：三例 delta 字段只有 `role/content/tool_calls`，**该中转完全不回 `reasoning_content`**（CASE1：296 completion_tokens 对 40 字正文）⇒ 看不见的思考也在账单里。本计划**不处理**这一项，另议。

## 二、根因

`naiba/llm/stream.py`：

```python
if tool_calls:
    guard.finish(status)
    guard.detected = True        # ← 720-734，问题在这一行
    for call in tool_calls:
        ...
    continue
```

`_ProtocolStreamGuard.feed()` 开头是 `if self.detected: return` ⇒ 一旦来了 native tool_calls，**守卫永久闭嘴**：

1. tool_call **之后**到达的正文不再作为 delta 外发（界面只剩前半句）；
2. 末尾 `if native_tool_calls: content = _build_action_from_native_tool_calls(...)` 又把 `full_content_parts`（含后半句）整块顶掉 ⇒ 后半句永久丢失。

### 影响面（不是 Claude 专属）

触发条件是**顺序**，不是模型名：

| 上游顺序 | 现象 |
|---|---|
| 正文全部在 tool_call **之前** | 正常（DeepSeek 等，所以一直没暴露） |
| 正文被 tool_call **劈成两段** | 只显示前半截（本次） |
| 正文全部在 tool_call **之后** | **一个字都不显示**，只剩工具卡片 |

受影响路径只有 SSE 流读取器（`_read_sse_response`，覆盖 `openai_chat` / `codex_responses` / `claude` / `lm_studio` 全部在线中转）；本地 Ollama 那条（`_read_ollama_stream`）没有该分支，不受影响。

---

## 三、修复方案（最小改动）

**只改 `naiba/llm/stream.py` 的 native tool_calls 分支**：

- 去掉 `guard.detected = True`；
- 保留 `guard.finish(status)`（把前半句立刻放出去，不要压在缓冲里）；
- tool_call 载荷本身仍走 `delta.tool_calls` → `native_tool_calls` 累加器，**不经过 guard**，因此不可能泄漏成正文；
- 后续正文继续走 `guard.feed(...)` ⇒ 正常外发；`full_content_parts` 的拼接顺序天然正确（先到的在前）。

安全性核对（已验证）：

| 依赖点 | 结论 |
|---|---|
| `has_content`（`stream.py:736`）里的 `guard.detected` | 同一行已 OR 了 `bool(native_tool_calls)` ⇒ 等价替代，不断熔断判定 |
| codex 聚合回填分支（`stream.py:756`） | 前置条件含 `not native_tool_calls` ⇒ 不受影响 |
| `tests/test_protocol_fence_guard.py` | 钉的是 **guard 类内部**对文本协议（JSON/XML/Harmony）的语义，本改动不碰 guard 类 ⇒ 保持绿 |

### 明确不做（边界）

- **不动 `_ProtocolStreamGuard` 内部逻辑**（「判定为协议后剩余正文不再外发」对**文本协议**是对的，有测试钉死）。
- **不把丢掉的正文塞回 assistant 历史**（见 §五缓存：这是唯一会改请求字节的选项）。若将来要做，单独开计划。
- **不动 reasoning 缺失问题**（中转不回 `reasoning_content`），只在报告里留档。

### ⚠️ 评审待决（2026-10-05 复审发现）：同一 chunk 内 text 与 tool_calls 并存

`_stream_delta_full`（`protocols.py:479-542`）对 `openai_chat` / `lm_studio` 会从**同一个 delta** 同时取出 `content` 和 `tool_calls`（OpenAI 规范允许，部分中转会合批）。而循环里 `if tool_calls: ... continue`——该 chunk 的 text 已在 `:715` 被 `inline_parser.feed(text)` 吞掉，既不进 `full_content_parts` 也不进 guard，**本方案的修复对这种情形不生效，那半句仍丢**（codecraftapi 实测是分事件的，所以本次报障能被治好；其余中不保证）。

两个选项，执行前由本人定：

- **A（顺手修掉）**：tool_calls 分支里在 `guard.finish(status)` 之前先 `if text: full_content_parts.append(text); guard.feed(text, status)`（同一 delta 内 content 语义上先于 tool_calls），并在 T 系列里加一条「同 chunk 共存」用例；
- **B（明确不做）**：把该情形写进本节「明确不做」，加一条测试钉死当前丢弃行为，并把 §二影响面表格第 2 行加注「仅覆盖 text 与 tool_calls 分属不同 SSE 事件的情形」。

## 五、缓存命中影响：**判定为「不变」，并给出可验证的证明**

### 5.1 结论

**不影响，且可逐字节证明。** 缓存命中率只取决于**出站请求字节**；本修复改的是**入站响应 → 界面**这一段。

| 环节 | 修前/修后 | 依据 |
|---|---|---|
| 进下一轮请求的 assistant 消息 | **完全一致** | `naiba/skills/agent.py:1318` 与 `:1537`（**两处 call site，执行时都要核**）`assistant_message(content)`，`content` 即模型返回的 action（`_build_action_from_native_tool_calls`，只吃 `native_tool_calls` 累加器） |
| tool 结果 / system / 工具表 / 历史顺序 | 未动 | — |
| 被删的那行 `guard.detected = True` | 只影响 `status({"type":"delta"})` 是否发出 | 属 UI 事件，不进请求体 |
| 流式 delta 与落库消息 | 工具轮助手消息本就**不落库** | 扫库实测 |

附带说明：**现存的 bug 本身也不伤缓存**（丢的是响应侧），因此修前修后缓存表现应当一致。

### 5.2 证明方法（零成本，不发请求）

新增探针 `verify/_probe_toolcall_prose_bytes.py`：

1. 拦截产品自己的出站入口（`naiba.net.open` 打桩，抛非网络类异常以避开重试），把每个请求体截下来；
2. 跑同一段「多轮工具调用」对话，修前 / 修后各跑一次；
3. 对每轮请求体算 SHA-256 并列比 ⇒ **逐字节一致**即结案。

> 注意：`verify/` 有**三份名单必须同步** —— `.gitignore` 放行 ↔ `cleanup_verify.py` 的 KEEP ↔ 实际文件。新增该探针时三处都要加。

运行时佐证（可选，花少量 token）：真机跑一轮多轮工具调用，看 `usage_records.cached_tokens` / 界面缓存命中率是否与修前同量级。
