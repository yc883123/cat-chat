# 自动压缩上下文（自动整理对话上下文）计划

日期：2026-10-26
背景：用户要求落地「自动压缩上下文的新工具」。产品方案见
`D:\deepseek-harness\cat-chat-auto-compaction-proposal.md`（讨论稿），实现参考 DSH
`packages/compaction/compaction-basic`（阈值公式、保留尾部、摘要指令、KV cache 语义）。

## 1. 目标与非目标

目标：上下文接近模型窗口时，把**较早历史自动替换为一份摘要**，让用户留在当前对话继续；
完整聊天记录一条不删，界面在整理位置放一张可展开的整理卡。

**方案（2026-10-26 修订）：阈值触发、同一模型隐藏总结、摘要定稿后稳定复用。**

- **不加入摘要模型**：总结请求用当前对话这一轮实际选中的同一 profile（同 provider、
  同 model、同配置），只多发一次请求，不请求另一个模型、不需要额外 Key。
- 隐藏请求：不走 agent 循环、`options` 里没有 `tools` 键、不流式；只喂「将被压缩的历史 +
  旧摘要」，要求输出结构化交接信息（九个分区）。
- 摘要定稿后冻结：只在触发时生成一次并写进标记，之后每轮原样重放，不每轮重写。
- 保留最近 N 个**完整轮次**原文，不按消息行数切。
- 校验通过才写标记；失败或不合格就不整理，本轮按原历史继续。
- **旧摘要不丢**：再次整理时，区间模型视图天然以旧摘要开场，交给模型的是
  「旧摘要 + 新进入区间的历史」。
- 触发点提前（默认 70%）：总结请求与本轮回复都要留空间。

> 早期版本曾用「本地确定性抽取」实现（零模型调用）；因用户要求改为
> 「同一模型隐藏总结」，本地抽取已移除。

非目标（P2 及以后）：单对话覆盖全局模式的 UI（后端字段先留）；整理标记里直接搜索原文；
图片历史参与整理（只整理文本区域，历史图片按现有链路处理）。

## 2. 与现有机制的关系

- **窗口容量**：沿用 `profile["context_window"]`（供应商值/本地探测/kind 回退），与
  `usage["context_limit"]`、现有轮首闸门同源。
- **估算器**：复用 `SkillAgent._context_fits / _estimate_content_tokens /
  _estimate_serialized_tokens`（同一启发式家族，触发口径与拦截口径一致）。
- **边界语义**：沿用「新会话」标记行的思路——标记写在**被整理区间最后一条消息**的
  metadata 上（`messages` 排序键是 `(created_at, rowid)`，不插行）。重放时
  `build_model_history` 遇到 `compaction` 标记：清空此前历史，改为一条固定的摘要消息，
  后续消息照常追加。多个标记最后生效；新摘要由模型把旧摘要合并（摘要指令含该规则）。
- **轮首闸门不变**：`SkillAgent.run` 的「不截断、超限拦截」保持。自动整理发生在它
  之前；整理后仍超限的极端情况照旧拦截（`context_full`）。

## 3. 行为设计

三模式（全局设置 `auto_compaction.mode`，默认 **auto**，阈值默认 80%）：

| 模式 | 行为 |
| --- | --- |
| auto 自动整理 | 每轮发请求前估算上下文用量（固定成本 + 全部历史 + 本轮输入），≥ 窗口×阈值 → 整理后继续本轮 |
| remind 整理前提醒 | 同口径估算，超阈值只推 `compaction` 提示事件（前端 toast），本轮照常 |
| off 关闭 | 与现状完全一致（估算也不做，零字节差异） |

- 整理区间 = 除最近 `retain_turns`（默认 3）个**完整轮次**外的全部。一轮 = 一条 user
  消息及其后的全部内容，到下一条 user 消息为止（按轮次切，避免劈开提问与答复）。
- 总结请求：`models.complete(profile, messages, {stream: False, max_tokens})`，不挂工具；
  消息 = 区间模型视图（含旧摘要、工具调用记录；图片降级为 `[图片]`）+ 固定指令。
- 指令要求九个分区：当前目标 / 用户约束 / 已确认事实 / 已作决定 / 完成进度 /
  待办事项 / 关键工具结果与文件路径 / 尚不确定的事项 / 下一步。
- 校验：长度 120–20000 字符、分区关键词至少命中 4 个、至少 2 个 Markdown 标题、
  摘要必须比原文短。任一不过就不写标记。
- 摘要回放为一条 user 消息：固定前导 + `<compacted-summary>…</compacted-summary>`，
  落标记时一次定格，后续逐字节重放（前缀缓存从摘要之后继续有效）。
- 失败处理：请求异常 / 输出不合格 / 写库失败 / 被取消 → 不写任何标记，本轮按原样继续。
- 撤销：整理卡上「撤销整理」→ 删除该标记（`json_remove`，原子），旧消息全部回到
  上下文（代价：下轮前缀缓存重预热一次）。

## 4. KV cache 口径（本次验收硬约束）

- off / 未触达阈值的会话：请求组装路径与旧版**逐字节一致**（估算不改变任何请求内容；
  `build_model_history` 只在出现新 metadata 键时才改变行为）。用 wire 探针 A/B 验证。
- 整理本身发一次总结请求（同一模型，无法复用旧前缀，属一次性成本）；整理后的下一轮从
  摘要消息起建立新前缀，之后每轮照常复用。整理只发生在逼近窗口的长会话，稳态会话不受
  影响。实测（2026-10-26，tedschat / deepseek-v4.1-flash）：稳态命中率
  候选 86.02% vs 基线 85.91%，cached token 相同（1280）；无标记会话历史 sha256 逐字节一致。

## 5. 改动清单

- `naiba/core/messages.py`：登记 `compaction` metadata 键。
- `naiba/core/history.py`：`COMPACTION_REPLAY_*` 模板 + `compaction_replay_message()`；
  `build_model_history` 的 compaction 分支。
- `naiba/core/compaction.py`（新）：设置解析/校验、估算、按轮次切分、总结请求构造、
  格式校验、标记 payload、`compact_conversation()` 编排（含隐藏模型调用）。
- `naiba/run/chat.py`：`build_model_history` 之后、vision 处理之前的
  `_maybe_compact_context` 钩子（aux 对话不整理）。
- `naiba/storage/store.py`：`clear_compaction_marker`（撤销，json_remove 原子删键）；
  写入直接用既有 `merge_message_metadata`。
- `naiba/config.py`：`auto_compaction` 默认值 + `update_settings` 白名单与校验。
- `naiba/http.py`：`POST /api/conversations/<id>/compact`（手动整理，同口径）、
  `DELETE /api/compaction/<message_id>`（撤销）。
- 前端：`04-messages.js` 整理卡（含展开/撤销）、`09-settings.js` + `index.html`
  三模式设置、`12-chat-input.js` `compaction` 事件 toast、`styles.css` 卡片样式。
- 测试：`tests/test_compaction.py`（估算/切分/重放/标记/撤销/设置校验/chat 钩子
  fail-open/无标记零差异回归）。

## 6. 验收

- 全量单测通过；wire 缓存探针 A/B 前缀字节一致；live 探针命中率近乎不变。
- 浏览器手验（隔离实例）：设置三模式可改可存；超阈值会话（小窗口 provider 模拟）
  自动出整理卡且下一轮上下文从摘要开始；撤销后旧消息回到上下文。
