# 任务总管批量执行助手：产品修复计划

日期：2026-11-03  
状态：待用户审阅；只形成计划，未据此修改业务代码、启动任务或验证实际生成。  
定位：造梦机负责调通工作流，任务总管负责批量准备、逐组审核、执行与结果处理。

## 一、用户已经明确的要求

1. 产品选择为 **A＋③：造梦机的批量执行助手，小批量完整闭环**，不是独立短剧平台；建单成功、单条成功都不能代替批量验收。
2. **工作流原来暴露什么参数，总管就复用什么参数、控件与保存值**。已有能力不应再通过“新建／编辑方案”重复注册才允许使用。
3. 总管仍要提醒制作输入是否齐备：提示词、图片／视频／音频、分辨率、时长或总帧数等。依据工作流真实能力提醒，不统一强制图片、时长，不伪造没有暴露的参数。
4. 逐组添加内容与素材。分组、批量是基本能力，不再作为可砍掉的增强项讨论。
5. 支持整批默认设置、逐组参数覆盖、逐组不同工作流；总管内直接选择、更换造梦机已保存的工作流。
6. 现成提示词直接生成、反推后生成，两条路径都必须跑通。直接模式不要求反推模型或规则。
7. **逐组审核、逐组确认生成**：哪组准备好即可先生成，不必等待其他组的反推或审核完成。
8. **单组失败继续其他组**，失败项单独处理，成功项不重跑。
9. 提供可选的“每次工作流执行后卸载模型”，复用造梦机已有释放能力，主要服务视频任务的内存／显存累积风险。

### 本文不擅自扩大或替用户决定的事项

- 不新增作品／剧集管理，不接小说创作主线，不做自动剪辑成片。
- 不把“第一版”缩成仅同工作流、仅单条、仅一种提示词模式。
- “方案”是否最终删除尚未拍板；本轮明确取消它作为运行前的强制重复配置门槛，既有方案先兼容。
- 后文标为“实施建议”的默认值、调度与技术结构属于可审阅方案，不冒称用户已逐项批准。

## 三、现状与根因：只保留本次有源码支持的判断

### 3.1 交接变成二次配置，产品角色错位

造梦机交接目前进入方案编辑／映射流程，而不是直接准备批量任务。用户已经调好的图和参数，没有自然变成总管的可用任务草稿。

本次读取入口：`public/js/24-comfyui.js::handoffToSuperAgent` 附近、`public/js/28-super-agent.js` 的交接与自定义方案函数、`public/index.html` 的制作和方案弹窗。

方案实际包含冻结工作流、提示词／媒体绑定、规则及覆盖；“编辑”保存为新的不可变定义。当前编辑入口没有直接更换工作流的控件，不等于服务端必须禁止换图。

**修复方向：复用工作流配置，把必要的批处理输入识别与高级管理分开；不能只把按钮改名。**

### 3.2 当前按整批固定配置组织，难以承载各组不同工作流

`naiba/super_agent/recipes.py` 的批次围绕单个 `recipe`、统一时长及模型配置组织；单项主要保存正文、素材、提示词和覆盖。支持逐组工作流不仅是增加下拉框，还涉及快照、授权、反推、恢复及结果归属。

**修复方向：每组必须能形成独立的有效执行快照，整批默认值只是新组的起点。**

### 3.3 已有就绪检查，但没有生成前的目标端在线检查

- `public/js/28-super-agent.js::recipeReadinessList` 当前核对素材、文本与生成快照，不实际探测 ComfyUI 在线状态。
- `naiba/super_agent/recipes.py::_assert_baseline/_authorize` 校验配置、目标与素材快照，没有在授权前完成目标端可达性检查。
- `naiba/comfyui/runner.py::_run_recipe_task` 会在执行阶段上传素材、检查图，再提交；所以不是后端完全不检查，而是故障发现太晚。
- `naiba/comfyui/service.py::api_health` 已有短超时健康检查能力，可复用底层逻辑。

**修复方向：准备时可显示连接状态，确认生成前必须检查本组实际目标，执行器仍保留最后校验。**

### 3.4 反推已有可保留价值，不应推倒重写

当前反推会组合用户要求、时长、冻结规则和媒体编号；图片交给视觉模型，音视频主要使用用户文字描述，并明确模型没有观看／收听原件。见 `naiba/super_agent/recipes.py::_reverse_payload`。

保留现有提示词质量和人工编辑能力；本轮优先解决逐组调用、不同工作流的适配、输入变化提醒及失败隔离，不为“优化”自动增加模型调用。

### 证据边界

以上来自本次源码和既有文档读取；工作树正在变化，行号和中间实现可能变化。没有读取用户具体失败任务的完整记录，不能断言所有失败均由一个根因引起；也未在本轮运行真实 ComfyUI 或付费模型。

## 四、目标用户链路

### 4.1 起点

两条入口到同一种批量草稿：

- 造梦机选择／调好工作流 → 交给任务总管，带入当前工作流与明确的当前参数。
- 总管新建批量任务 → 选择造梦机已保存的工作流。

交接须说明使用“已保存值”还是“当前未保存调整”；可保留当前调整为本次任务覆盖，但不得静默丢弃、改写原工作流或伪称已保存。

不先弹“新建方案”要求用户重新配置整套图。

### 4.2 同一个准备界面完成日常操作

- 顶部：批次名称、默认工作流、默认生成设置。
- 中部：逐组内容卡，每组显示工作流、提示词状态、素材与必要设置；允许改为其他工作流、调整参数、使用现成提示词或反推。
- 配置控件复用造梦机元数据与渲染能力；适配布局不另造参数扫描和类型系统。
- 专业绑定、规则管理、工作流原始结构不挤进日常首屏。
- 仅突出当前缺项与下一步，不重复堆叠多层状态和说明。

**实施建议：**默认值为新组初始化；修改整批默认时，明确询问是否应用到现有未执行组，不静默覆盖逐组修改，更不能改已确认／执行中的组。

### 4.3 逐组审核与运行

- 现成提示词：核对该组 → 连接／输入检查 → 确认生成。
- 需要反推：反推该组 → 修改／核对提示词 → 连接／输入检查 → 确认生成。
- 可提供批量触发反推，但不能迫使用户等待整批反推完才生成已准备好的组。
- 已确认组可以执行，其他组仍可准备和审核；不能沿用整批“任何一组活动就锁所有组”的行为。
- 每次确认明确范围、工作流、生成条数与可能费用；确认反推不等于确认视频生成。

## 五、核心修复设计

### 5.1 工作流能力复用与制作输入提醒

复用造梦机已保存的槽位、控件类型、标签、默认值、枚举和媒体语义；对总管增加的是“随组变化的输入用途”，不是第二套图配置。

| 输入 | 总管行为 | 必须避免 |
|---|---|---|
| 提示词 | 复用已知目标；现成文本或反推结果进入对应字段 | 直接模式强迫配置反推模型 |
| 图片／视频／音频 | 按实际入口展示、指出必填与可选、复用上传 | 因为有入口就要求全部填满；所有图套同一媒体上限 |
| 分辨率 | 原图暴露宽高就用宽高，暴露比例／档位就用原控件 | 把比例参数误当像素尺寸；静默改原图 |
| 时长／帧数 | 使用工作流真实单位与约束；没有可调入口则说明沿用工作流 | 秒数直接写入帧数字段；通用工作流统一套 H3 限制 |
| 其他参数 | 保留已暴露控件和值，可按原分组／折叠组织 | 只保留少数数字导致原有枚举／布尔丢失 |

能从已有元数据明确识别时直接复用；不明确时只请求确认有歧义的用途。例如多段文本不可猜哪段是正向／负向提示词，多媒体入口不可乱配首尾帧。首次用途确认可记住在对应工作流版本，不要求反复填写。

多段提示词本轮不扩展复杂编排，但必须保留其他文本字段原值，不能错误覆盖；数据结构避免把“整图只有一个文本输入”写死。后续支持多段反推单独设计。

H3 参考容量沿用其已确认能力，9 图／3 视频／3 音频是上限而非必填组合；自定义图按其真实入口处理，不能因内置适配器支持可选裁剪，就声称任意图都支持。

### 5.2 逐组快照、更换工作流和默认继承

每组至少固化：工作流 ID／指纹／图、有效参数、媒体绑定及文件快照、提示词、反推配置（仅需要时）、生成目标、次数、执行选项、版本与授权依据。

- 有效配置只计算一遍，表单、预览和执行共用，历史结果保留当时快照。
- 未执行组更换工作流：保留正文与原素材，读取新图参数，重新匹配输入；不能凭相同节点号自动套旧覆盖。
- 不兼容的旧绑定撤出执行配置，给出缺项，不静默删素材或把旧首帧当新尾帧。
- 提示词保留可编辑；若用途、素材引用或反推条件变化，标记需复核，不直接销毁人工文本。
- 已提交／在途组不原地换图；通过复制为新组调整，保留旧执行事实。
- 改某组配置只影响该组授权；已审核的其他组不应被无关批次修改整体作废。
- 既有单方案批次按旧协议读写或通过兼容适配投影，禁止迁移时改写历史输入、补授权或自动执行。

### 5.3 生成前预检：尽早发现，不制造新的注册门槛

1. 准备界面展示实际目标的连接状态与检查时间，不把一次“在线”当长期保证。
2. 打开该组生成确认时检查：实际冻结目标可达、工作流与输入就绪、媒体有效、提示词引用存在；支持的图声明检查应批量／缓存合理复用，不重复折腾用户。
3. 最终确认由服务端复核版本与目标；预检失败不进入已运行状态，不留下错误的生成提交意图。
4. 预检通过后仍可能掉线，执行器保留上传／图校验／提交最后防线，正确区分“确定没提交”与“可能提交成功”。
5. ComfyUI 离线：保留草稿，提示启动或检查地址，提供重新检测；不要求重建任务。
6. 目标发生变化：重新核对后才能授权，不静默把任务转到新地址；检查冻结目标，而非只查全局当前设置。
7. 预检不声称保证显存足够、所有模型均已安装、付费余额充足或视频必定成功；无法确证的项给出边界，不伪造全绿。

只准备正文、编辑或反推时不因 ComfyUI 离线全面禁用；视频生成前才是硬门槛。远端服务也按目标地址检查，不只检查本机进程。

### 5.4 调度、进度与失败处理

**实施建议：**同一 ComfyUI 目标默认串行提交需要生成的工作流执行；逐组确认后进入就绪队列，其他组可继续反推／编辑。确认多组、每组多次仍是批量执行，不依赖同时占满显存。

状态直接告诉用户：待补输入／待反推／待审核／排队／生成中／结果下载中／完成／失败／提交待核对。没有可靠进度就展示阶段和已完成数，不伪造百分比。

- 单组确定失败：保留错误与输入，继续其他已确认组。
- 同一组含多次生成时，一次确定失败不覆盖成功结果；其余明确未提交的执行可继续，失败执行留待用户明确重试。
- ComfyUI 整体离线等目标级故障：暂停该目标后续提交，保留队列，其他目标可继续；恢复后继续明确未提交的项，不让所有组逐个撞错。
- 提交结果未知：该项待对账，不自动重提；只有目标本身异常才暂停该目标其他项，不能一律扩大成整批锁定。
- 下载失败：仅补收集已有结果，不重新生成。
- 支持逐组查看输入、播放／下载结果、明确重试及复制为新组；正常操作不用看 JSON、指纹或后台路径。

### 5.5 可选：每次执行后卸载模型

用户要求纳入本轮，不是以后再加的附属项。

- 选项文案：**每次工作流执行后卸载模型**。
- 解释：适合视频任务，尝试释放模型占用与执行缓存；下一次可能重新加载，速度会变慢，不能保证解决所有内存累积或显存不足。
- 复用 `naiba/comfyui/client.py::free_models`，底层是 `POST /free`，载荷为 `unload_models=true`、`free_memory=true`。不是模拟点击前端按钮。
- 目标使用本次执行冻结的 ComfyUI 地址；不能简单调用只读全局地址的现有 HTTP 门面后就认定作用于正确目标。
- “每次”以一个原生工作流执行为单位，而不是整个批次结束；每组生成三次就有三个执行边界。
- 时点为远端该次执行已明确结束、必要产物信息可追踪之后，下一次同目标执行提交之前。不能刚建单／刚提交就释放，也不能以本地线程退出等同远端结束。
- 执行失败但远端已确定停止时可请求释放；执行仍在途、取消尚未确认、提交结果未知时不按“已结束”触发。
- 仅下载重试不算一次新的工作流执行，不触发额外卸载。
- 释放是目标级全局操作：同目标调度须协调造梦机和总管；遇外部队列／在途执行，遵循 ComfyUI 实际语义，标注延后／仅已请求，不承诺当前立刻清空。
- `/free` 受理不等于已测得释放完成。请求状态、失败原因单独记录，不把已成功的视频改判失败，不因此重新生成。
- 释放请求失败的默认恢复建议：按目标级维护异常暂缓下一次提交，允许重试释放或本次跳过后继续；不静默绕过用户启用的策略。
- 不自动杀进程、重启 ComfyUI、卸载第三方插件或影响其他目标。

**待审阅的默认建议：**开关默认关闭，按批次设置并冻结到各次执行；复制／复用任务时可继承偏好，生成确认展示是否开启。避免对图片任务默认增加重载成本。开启后的速度与内存收益必须实测，不能事先保证“状态最佳”。

### 5.6 反推只做服务于闭环的增量优化

- 保留当前规则与输出质量，逐组可反推、修改、确认；其他组不因一组反推失败锁死。
- 反推读取本组实际工作流上下文、时长单位、素材编号与要求，不沿用其他组配置。
- 模型不具备音视频理解时继续如实使用文字描述，不包装为已观看／收听。
- 素材、工作流或要求变化后标记需复核，保留旧文本／人工修改；明确重反推才调用模型。
- 检查空输出、格式混入、无效媒体引用等客观问题；不偷偷追加一次“优化模型”调用。
- 多段提示词自动分配、自动质量打分等延伸不挡住本轮真实批量运行。

## 六、如何借鉴辉映／启元，而不是再换皮

既有对照来源：`docs/plans/2026-11-03-漫剧前端对照与制作入口整改建议.md`。其竞品依据为静态代码材料，不是本轮实机验证。

只吸收与本定位相关的部分：

- 辉映的“使用处处理制作配置”：选工作流、更换、补配置后回当前组，不让用户跨模块重填。
- 启元的“内容上下文与下一步承接”：每组内容、素材、提示词、结果一直关联；反推完成后直接审核，生成完成后直接审看／补做。
- 套用配置、反推、人工编辑、视频生成分别表达清楚；默认配置能用，但不会因套用偷偷调用模型。
- 不借本次机会新增作品级平台；先证明上述交互能让一个小批次跑通。

## 七、实施顺序与门禁

阶段只是实现顺序，不是删减已确定需求。

### 阶段 0：重新盘点工作树与最小实际样本

- 核对暂缓旧计划的现有改动，不覆盖其他修改。
- 选定造梦机已跑通的实际工作流，记录它实际暴露的参数、必要媒体与输出；具体任务失败用记录取证，不凭旧报告认定。
- 明确本轮真实执行样本／费用授权；此阶段不自动跑付费探针。

## 八、验收矩阵：用户能完成，而非代码里有按钮

### 主验收批次

逐组添加至少三组：

1. 工作流 W1，现成提示词，使用默认参数与所需素材。
2. 工作流 W1，反推后人工修改，使用不同参数与素材。
3. 工作流 W2，不同输入要求；验证同批不同工作流与独立设置。

组 1 可先确认运行，组 2／3 仍能准备。安排一个确定的单项失败，确认其他已确认组照常完成；成功项不重复提交。失败修复后明确重试；播放／下载结果，与对应组输入一致。

真实失败注入优先用本地替身；未经许可不消耗真实付费生成来制造故障。

### 必须补测的分支

| 场景 | 通过标准 |
|---|---|
| 从造梦机交接 | 已保存值和当前调整来源明确；不重复配置，不丢正文／素材 |
| 总管直接选换工作流 | 读取正确控件与值；旧覆盖不串入新图；素材不静默丢失 |
| 参数与制作提醒 | 原有已暴露控件可用；必填／可选准确；秒／帧及比例语义正确 |
| 直接提示词 | 无反推模型也能走完生成；不发生提词请求 |
| 反推 | 本组上下文正确，人工修改保留；未确认不生成视频 |
| 部分组在执行 | 其他组仍可编辑、反推、审核；授权不因无关组修改失效 |
| ComfyUI 未启动 | 确认前发现，保留草稿，重新检测后继续，不制造运行失败 |
| 检查后断连 | 不误报预检保证成功；确定未提交与提交未知正确区分 |
| 单组失败 | 其他就绪组继续，成功项不重跑 |
| 仅下载失败 | 仅下载已有结果，生成提交计数不增加 |
| 目标级离线 | 后续同目标提交暂停而非逐个报错；恢复不盲目重提未知项 |
| 开启逐次卸载 | 正确目标、正确结束边界、下次提交前请求；多次生成不只批末释放 |
| 关闭逐次卸载 | 无额外 `/free` 调用，不改变普通图像运行节奏 |
| 卸载异常 | 成功产物仍成功，维护问题可见，可重试／跳过，无隐式重生成 |
| 重启／刷新／旧数据 | 不丢快照与结果，不复制授权，不自动复活旧任务 |

### 证据要求

- 替身：核对最终执行图、媒体配对、目标、执行次数、授权／幂等和 `/free` 顺序。
- 真实环境：确认造梦机已成功的工作流在总管中也能生成并取回产物；小批量、混合工作流和两种提示词路径要有对应证据。
- 付费调用先获授权、先最小样本，不为“全覆盖”自动扩大采样。
- `/free` 受理、显存下降、系统内存变化分别记录，不能互相冒充；不以重启后恢复代替正常卸载验收。
- 若只有替身通过而真实链未过，结论必须写“批量机制通过，实际生成未验收”，不能写“已修好”。
