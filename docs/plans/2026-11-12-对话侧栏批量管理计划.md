## 1. 范围

对话模块左侧边栏加一个「批量管理」入口。进去后能勾选多个对话，一次归档（或取消归档），一次删除。

这次不做：

- 回收站和撤销。批量删除和现在的单条删除一样，删了就没了。
- Shift 连选、按分组整组勾选。
- 批量收藏、批量移动工作区、批量重命名。
- 改单条删除接口，原因见第 10 节。
- 版本号、提交、推送、发版。

## 2. 已核实的现状

下面每条都读过源码。

### 2.1 侧栏

- `public/index.html` 的 `#sidebarWorkspaceHeader` 里现在有三个图标按钮：`#workspaceSearch`、`#workspaceSort`、`#addWorkspace`。
- 列表是虚拟滚动。`renderSidebar` 每次重建行模型 `sidebarRowCache`，`renderSidebarWindow` 只画可视的那一段，滚动时整段重写 `innerHTML`。勾选状态不能存在 DOM 上。
- 行高在 `sidebarMetricsNow` 里量一次后缓存。行高一变，窗口和滚动位置会错位。
- 同一个对话会同时出现在工作区分组和「已收藏」分组里。
- 折叠的分组、「展开其余 N 个会话」后面的对话不在行模型里。
- 全文搜索时，`renderSearchResults` 用消息命中列表替换整棵会话树。
- 侧栏宽度默认 272px，最窄 170px（`sidebarClampWidth`）。手机上是抽屉，宽 `min(86vw, 310px)`。
- 切到工作台、任务总管都经过 `01-core.js` 的 `setAppView`，它会把 `#sidebarWorkspaceHeader` 和 `#sidebarWorkspaceTree` 设成 `hidden`。

### 2.2 归档

- 前端 `toggleConversationArchive` 调 `POST /api/conversations/<id>/settings`，带 `{archived: true|false}`。
- 后端 `set_conversation_archived` 只改标记，不动 `updated_at`。归档只是从侧栏和全文搜索里藏起来，数据都在。

### 2.3 删除

- 前端 `deleteConversation` 先弹系统确认框，再调 `DELETE /api/conversations/<id>`。
- 后端路由直接调 `storage.delete_conversation`，里面是一条 `DELETE FROM conversations`。`messages`、`background_tasks`、`plans` 三张表靠外键级联删掉，`run_events` 跟着 `background_tasks` 级联。磁盘上的附件文件不动。没有回收站。
- 这个路由不检查对话有没有任务在跑。前端只拦一种情况：要删的是当前对话，而且它正在回复。
- 同一个路由还被 `21-aux-chat.js` 的 `closeAuxChat`（关辅助对话标签）用着。
- 清空消息的路由 `DELETE /api/conversations/<id>/messages` 会先查 `list_background_tasks(conversation_id, active_only=True)`，有任务在跑就回 409。
- `create_chat_run` 在 `BEGIN IMMEDIATE` 事务里先查对话在不在，不在就报「对话不存在」。新建的运行记录初始状态是 `queued`，属于 `ACTIVE_TASK_STATUSES`。
- 侧栏行上的转圈图标只看顶层回复：`syncActiveConversationRuns` 过滤掉了子任务和分离式任务。

### 2.4 测试和验证

- 侧栏现有两份单测 `test_sidebar_favorites`、`test_sidebar_view_prefs`，登记在 `.github/test-shards.json` 的第 4 片。新测试模块不登记就不会在 CI 里跑。
- `verify/seed_favorites.py` 写的是仓库 `data/chat.db`，也就是真实开发库。新冒烟不用它。
- `verify/_serve_tmp.py` 能起一个隔离实例，数据目录、配置、端口都独立。全新实例会弹首启引导，脚本里要先关掉（维护说明 6.1）。


- 入口放在「分组与排序」和「新建工作区」之间，只有图标，悬停提示和读屏名称是「批量管理」。再点一次等于「完成」。
- 状态行在搜索行下面、列表上面。
- 操作栏在列表下面、底栏上面。

分两处放是因为宽度：最窄 170px 时标题行可用宽度 142px，放不下五个控件。删除离全选远一点，也不容易连着点错。

### 3.2 进入后列表的变化

- 每行左边的星标换成勾选框，同样 26×26，行高不变。
- 点一行的任何位置都是勾选或取消，不打开对话。
- 「⋯」、分支徽标和分支计数、拖拽排序、「＋ 新会话」、分组上删工作区的 × 都不显示。
- 分组标题照常能展开和收起，「展开其余 N 个」「收起」照常能用。
- 正在回复的转圈图标保留，方便看出哪些删不了。
- 搜索、分组与排序、筛选照常能用。
- 全文搜索停用。进入时如果正处在全文模式，切回标题模式并保留关键词。「全文」按钮置灰，提示「批量管理时只能按标题搜」。
- 打开着的「⋯」菜单、分组与排序面板、分支链面板，进入时先收起。

### 3.3 勾选规则

- 勾选只对列表里列出来的行有效。「列出来」指在行模型里，滚出屏幕的也算。折叠分组里的、没展开的不算。
- 每次重建行模型后，把已选集合收到「还列着的对话」范围内。换搜索词、收起分组、切筛选之后，不在列表里的对话自动取消勾选。所以删不到看不见的对话。
- 同一个对话出现两行（工作区分组和已收藏）按一个算。勾一处两处都亮，计数不重复。
- 「全选」勾上当前列出来的全部对话。已经全选时再点是全部取消。只选了一部分时显示成半选。
- 当前打开的对话可以勾。

### 3.4 归档

- 选中的全是已归档：按钮显示「取消归档」，对全部选中项取消归档。
- 其他情况：按钮显示「归档」，把选中项都设成已归档，本来就已归档的不变。
- 不弹确认，归档能撤回。
- 等服务端回包后再改界面，不做乐观更新。
- 成功的取消勾选。筛选是「隐藏已归档」时它们从列表消失。
- 回包说某个对话已经不存在，就把它从列表移除。

### 3.5 删除

- 弹系统确认框，和单删、拆书匠批量删除用的是同一种。列出前 5 个标题，超过 5 个时最后一行写还有几个：

```
删除选中的 8 个对话？里面的消息会一起删掉，删了找不回来。

· 贴签匠并发方案
· 发版核对
· 造梦机取消重试
· 提词库排版
· 新对话
还有 3 个
```

- 确认后提交。还在回复或有后台任务在跑的对话，服务端跳过不删。
- 成功的从列表移除。没删掉的保持勾选，停掉回复后再点一次就行。
- 删的是别的对话时只刷新侧栏，不重载当前对话视图。这和单删是同一个约束：重载会把正在流式输出的消息挤出页面。
- 当前打开的对话被删掉后，按这个顺序找下一个：
  1. 当前筛选下还列得出来的第一个对话。
  2. 没有，就切到剩下的第一个。
  3. 一个都不剩，显示空白页。
- 切换沿用 `deleteConversation` 里的打开代次校验：`beginConversationNavigation`、`isConversationOpenCurrent`、`openConversation(..., { expectedGeneration })`。

第 1 步是比单删多出来的。单删固定切到 `state.conversations[0]`，它可能是被筛选藏起来的已归档对话。批量全选删除后，剩下的很容易全是已归档的。

### 3.6 执行中

- 从请求发出到收完结果，两个操作按钮、「全选」、「完成」和行勾选都不响应。
- 归档每批最多 100 个，删除每批 20 个，一批一批顺序发。删除要级联清消息和事件，分小批是为了进度能动。状态行显示 `正在删除 20/87`。
- 某一批请求失败（断网、500）：这一批全部算没完成，保持勾选，后面的批次不再发。可以直接再点一次。删除对已经不存在的对话算成功，重发不会报一堆错。
- 执行中切去别的视图：已发出的批次照常收结果并更新列表，没发出的不再发。

### 3.7 退出

- 点「完成」，或再点一次入口图标。
- 按 Esc。条件有三个：没有弹窗和菜单开着；这次按键没被别处处理过（搜索框里按 Esc 是清关键词，不退出）；不在执行中。
- 切到工作台或任务总管。
- 关手机抽屉不退出，勾选保留。
- 退出时清空勾选。刷新页面等于退出，批量模式不保存。

## 4. 后端

### 4.1 接口

`POST /api/conversations/batch`

请求：

```json
{"action": "delete", "ids": ["对话 id", "对话 id"]}
```

`action` 取 `archive`、`unarchive`、`delete`。

回包，HTTP 200：

```json
{
  "action": "delete",
  "succeeded": ["id1", "id2"],
  "failed": [{"id": "id3", "code": "busy", "error": "还在回复或有任务在跑"}]
}
```

- `ids` 必须是字符串数组，去重后 1 到 100 个，否则回 400。`action` 不认识也回 400。
- 只处理主对话。辅助对话的 id 记入 `failed`，`code` 是 `not_main`。
- 归档、取消归档：id 不存在，记 `missing`。
- 删除：id 不存在算成功。有活跃任务，记 `busy`。
- 部分失败仍回 200，逐项说明。回包形状和拆书匠批量删除一致（`succeeded`、`failed`）。

路由加在 `naiba/http.py` 的 POST 分支里，紧挨 `/api/conversations/reorder`，用精确匹配。鉴权和其他接口相同。

不让前端循环调现有单条接口，原因两个：选 200 个就是 200 次请求；单条删除接口在服务端不查任务。

### 4.2 存储

`naiba/storage/store.py` 新增两个方法，都带 `@_retry_transient_write`。

`set_conversations_archived(ids, archived)`

- 一个 `BEGIN IMMEDIATE` 事务。先查出这批 id 里存在的主对话，再用一条 `UPDATE` 改 `archived`。
- 不动 `updated_at`，和单条归档同一个约束。
- 返回实际改到的 id。

`delete_conversation_if_idle(conversation_id)`

- 一个 `BEGIN IMMEDIATE` 事务，按顺序判断并返回结果：
  1. 对话不存在，返回 `missing`。
  2. 不是主对话，返回 `not_main`。
  3. `background_tasks` 里这个对话有状态属于 `ACTIVE_TASK_STATUSES` 的任务，返回 `busy`。子任务和分离式任务都算。
  4. 否则执行和 `delete_conversation` 相同的 `DELETE`，返回 `deleted`。
- 一个对话一个事务。中途某个失败，不连累已经删掉的。

检查和删除放进同一个写事务，是因为 `create_chat_run` 也用 `BEGIN IMMEDIATE`，两边会排队。要么新回复先建好，删除看到有任务就跳过。要么删除先完成，新回复报「对话不存在」。不会删掉一个刚开始回复的对话。

「有任务」的口径和清空消息一致，任何活跃任务都算，比侧栏转圈图标宽。删除会级联清掉这个对话的全部任务记录，所以不能只看顶层回复。

现有的 `delete_conversation` 和 `set_conversation_archived` 不改。数据库结构不变，`CURRENT_SCHEMA_VERSION` 不动。

### 4.3 业务方法与契约

- `naiba/app.py` 新增 `api_batch_conversations(body)`：校验参数，归档走批量方法，删除逐个调 `delete_conversation_if_idle`，汇总成回包。
