## 三、剩下各节要怎么改

每节先写「要改成什么」，再列支撑它的事实。事实都在 `7c22c3c` 上读代码核过；标「探针」的另外用真实代码跑过。

### 第 3 节 A：会话切换

新稿在附录，可以直接替换第 3 节。相对初稿多了三点：

- `openConversation` 有 18 处调用，按来源分三类处理（用户直接点开；先等一个接口再打开；程序自动重载）。后两类在动作开始时记下代次，要打开时代次变了就放弃。
- `openConversation` 返回本次是否生效，调用方据此停止后续动作。最要紧的是编辑重发 `resendFromUserMessage`：它先截断原消息，再打开会话、填输入框、发送。被作废后如果继续走，改好的内容会发进用户刚切过去的会话。
- 两个 GET 并行，回来后在一个同步块里一次提交全部界面状态。

### 第 4 节 B：默认模型（改动最大）

要改成：

1. 新增一对设置字段存「新对话默认」（档案标识加具体模型名），两项要么都有、要么都空。字段名实施时定，先登记到 `naiba/config.py` 的默认值、`update_settings` 白名单和校验。不做数据库迁移，升级后为空即「未设置」。
2. `default_model_key` 的自动回退原样保留。它是共用兜底，不能变成可空。
3. 设置页显式保存新对话默认时，同时把 `default_model_key` 设成同一个档案，这样其他模块的预选跟着走。
4. 新建对话的取值顺序：
   - 调用方显式传了完整组合（分支、工作台交接、QQ 绑定）用它；
   - 否则新对话默认配了且有效，用默认；
   - 否则沿用当前输入区的选择（现状）。
   - 默认指向的档案被删了，或模型不在最新目录里：设置页提示默认已失效，新建时按「没配」处理，不改绑别的档案，也不卡住。
5. 聊天区切 API 不再写全局设置，只改当前会话；没有当前会话时只改待创建的选择。
6. 设置页 API 卡片的角标「当前」改成「默认」之类不会和当前会话混淆的说法，提示里写清它是各功能页的默认预选。「模型名称」这个表单标签不改名，旁边补一句说明它的用途。
7. 拆成两批：B1 是竞态修复（保存请求固定目标会话、按会话串行、迟到响应不回填别的会话、选模型时一并写 API 绑定、发送时固化实际档案）；B2 是默认入口加上第 5 条。第 5 条必须和 B2 同批上，不然用户没地方改默认。

事实：

- `default_model_key` 的读取方：`ConfigStore.profile("")`、`generation_options("")`；QQ 绑定（`naiba/channels/service.py`，空了直接报错）；提词库 `prepare_generation`（`naiba/studio/service.py`）；前端的辅助对话、贴签匠、任务总管新建、拆书匠、织书台、提词库都拿它预选。
- 它的自动维护：启动时 `_migrate_model_profiles` 把空值或失效值补成第一个档案；`upsert_model_profile` 在它为空时填入；删除默认档案时改指向剩余第一个。
- `provider.model` 的运行时用途：QQ 渠道没配渠道默认时拿它当会话模型名；视觉识别没单独指定模型时用它；`_infer_supports_images` 在档案没显式设置图片能力时按它推断；KVMem 就绪检查；任务总管新建预选。
- 新建对话现状：`createConversation` 发的是输入区当时的 API 和具体模型，所以在会话 A 里点「新对话」跟 A。`model_key` 为空时，`api_create_conversation` 和 `ChatStorage.create_conversation` 会补成 `online:<旧 provider_id>`，默认是本地档案时前缀是错的。按上面第 4 条的取值顺序，前端不会再发空值，这个后端补值可以不动。
- 分支 `branch_conversation` 直接复制源会话的绑定；工作台交接带任务自己的模型。
- 设置页保存单项设置的现成样板：`saveInterjectDirectSend`（`public/js/09-settings.js`），单项 POST `/api/settings`，失败回滚控件。
- 会跟着断的现有资产：
  - `tests/test_provider_cards.py` 钉了表单标签「模型名称」和角标类名；
  - `tests/test_composer_model_follow.py` 钉了源码行 `persistConversationModelName(composerModelChoice())`；
  - `verify/composer_model_smoke.cjs` 靠「API 已切换」这条提示判断切换完成。

### 第 5 节 C：正文草稿

要改成：

1. 冲突规则分模块写：
   - 织书台按章节 revision 判（它只在保存正文、切版本、删版本时变）。
   - 拆书匠按「来源稿件是否还在、内容是否没变」判。拆书匠的稿件不可变，章节 revision 每新增一份稿件就涨，AI 改编写回也涨；照初稿按 revision 判，没受影响的草稿会全被标成冲突。
2. 问题描述补一条：织书台切章现在没有任何保护。`openChapter` 成功后直接把未保存标记清掉、重填编辑区；拆书匠有确认框。拆书匠在编辑中点另一份稿件的「编辑」（`beginEdit`）同样直接覆盖。验收要覆盖这两处。
3. 「打开章节时等待草稿读取」要落到入口上：页面重载后，织书台回到设定页且不打开任何章节，拆书匠打开第一章且不在编辑态。草稿不能只靠「打开那一章」才发现，打开作品时要列出这本书有草稿的章并提示。
4. 草稿存储做成可替换后端的独立模块。现有确定性前端测试跑在 Node 的 `vm` 里（`verify/writer_draft_offline_test.cjs`，由 `tests/test_writer_ui.py` 调起），那里没有 IndexedDB。
5. 能力边界补一条：浏览器按地址隔离本地存储。桌面版换端口，或者手机用另一个地址访问，看不到原来的草稿。
6. 验收补「桌面版从托盘退出再启动后恢复」。点关闭只是藏到托盘，页面不卸载。

### 第 7 节 E：织书台取消（改动第二大）

要改成：

1. 协调的是三方：提交、取消、后台轮询。初稿只写了前两方。
2. 提交在途时，轮询不能因为任务号为空就判失败。做法是让「正在提交」可被识别；标记放内存还是落盘，实施时定，落盘要先登记契约。服务重启后的收敛沿用现有「进行中的流水线标为已中断」。
3. 提交返回后只做一个判断：流水线还是不是本次尝试、还在不在进行中。不是，就取消刚返回的任务。这一条盖住初稿第 3、4 条列的情况，还盖住「被轮询判失败」和「作品已被删」。
4. `cancel_pipeline` 的读任务号和写取消放进同一次加锁；写取消前在锁内复查状态，已经不在进行中就报「已结束」，不改写。
5. 取消后以任务到终态为准报告结果。任务还在跑就如实说「停止尚未确认」，保留任务号。
6. 不在作品 store 的锁里调 `jobs.submit` 或 `jobs.cancel`。
7. 验收补下面四种交错，用线程屏障卡位，不靠 sleep。

事实（探针：真实 `WriterPipelineManager` 加假任务队列，临时目录，四种交错全部复现）：

| 交错 | 结果 |
| --- | --- |
| 点生成后、任务号回填前，轮询先扫到 | 流水线被判失败「流水线缺少当前任务，无法推进」；任务号照样回填，任务照样跑，没人取消 |
| 同一空档里用户点取消 | 显示已取消；任务照样跑 |
| 取消读到任务 1 之后、写取消之前，轮询写回任务 1 并提交了任务 2 | 取消打在已完成的任务 1 上，任务 2 继续跑 |
| 取消读到「进行中」之后，最后一步刚好完成 | 已完成的流水线被改成「已取消」 |

- 第一种不需要用户点取消，点生成或重试就可能撞上。窗口是 `start_pipeline` / `retry_pipeline` 落下「进行中、任务号为空」到 `_submit_step` 回填之间，轮询每 0.5 秒一次。
- 后两种的原因是 `cancel_pipeline` 在锁外读清单，`_cancel` 没在锁内复查状态。
- `store.update_pipeline` 只校验流水线 ID 和 attempt，不校验状态；所以第一种情况里回填照样成功。
- 另一处只读了代码、没复现：Studio 任务开始执行时，`_run_task` 确认任务仍在排队之后、登记取消句柄之前有个很短的空档，这时 `jobs.cancel` 返回成功，任务却照常跑完。属通用后台任务，本轮不修，所以才有上面第 5 条。
- Studio 不反向调用织书台 store，没有反向拿锁的路径。
- 任务总管通过 `api_start_pipeline` / `api_cancel_pipeline` 调同一套逻辑，读流水线的 `status` 和 `current_task_id`。改状态语义时要看它。
- 现有 `tests/test_writer_pipeline.py` 的假任务队列 `_Jobs` 没有卡位能力，要加。

## 附录：第 3 节 A 新稿（未贴入计划）

### 修改方式

1. 为 `openConversation` 增加独立请求代次和目标会话 ID。用户直接点开的打开动作、新建会话、删除当前会话或进入空白新对话时，统一使更早的打开请求失效。
2. 在会话详情 GET、首轮上下文 GET，以及会改变当前界面的异步恢复步骤之后检查代次。旧成功响应、旧失败响应都不更新当前状态、消息、模型、Agent、工作区、首轮信息或 toast。
3. 会话详情与首轮上下文两个 GET 并行发出，都回来后在一个同步块里一次提交 `state.conversationId`、列表缓存、消息、模型、Agent、工作区、联网与思考开关、首轮信息和会话切换广播，避免 `state.conversationId` 已指向 B、消息仍显示 A 的半完成状态。首轮信息失败不阻止当前会话打开，但只清理本次目标的首轮信息。
4. Run 订阅和恢复同时核对会话与打开代次；迟到的 A 不能恢复订阅或关闭 B 的侧栏/连接。已发出的只读请求可取消以省请求，但正确性必须依靠代次检查。
5. 区分打开动作的来源（`openConversation` 共 18 处调用）：
   - 用户直接点开：侧栏点击、任务面板回跳、托盘通知回跳、分支链跳转、辅助对话的跟随标题、任务总管里的会话链接、搜索命中 `openSearchHit`。点下去就取新代次，作废一切更早的打开。
   - 先等一个接口、再打开会话：分支 `branchMessage`、工作台交接 `confirmStudioHandoff`、删除当前会话后打开下一个、编辑重发 `resendFromUserMessage`（截断后重载本会话）。代次在用户点下去时就记下；等接口期间用户又点开了别的会话，就不再打开。
   - 程序自动重载：运行结束 `finishRunSubscription`、取消后 `cancelCurrentRun`、发送被 409 拒绝与断流兜底（`sendChatMessage`）、取消编辑 `cancelActiveEdit`、编辑重发失败后的重载、启动或列表刷新时打开第一个会话。同样在动作开始时记下代次，要打开时代次已变就放弃；它们不能把用户刚点开的会话顶掉。
6. `openConversation` 返回本次打开是否生效：提交到界面返回真；被作废或被放弃返回假，不抛错也不弹提示；只有仍然有效的打开失败才抛出。返回假之后调用方停止后续动作：
   - 编辑重发：不自动发送，也不丢内容。原会话已被截断，改好的文字与恢复出来的附件留在输入区（输入区不随会话切换清空），并提示已切到别的会话、内容未发送。
   - 分支：不把分支内容预填到别的会话的输入区；分支会话已建好，提示到列表里打开。
   - 搜索命中：不在别的会话里定位消息。
   - 工作台交接：不提示已打开；新会话在列表里。
7. `08-conversations.js` 与 `11-run-stream.js`、`04-messages.js`、`12-chat-input.js` 互相 import，代次状态放在 `08` 内部或 `state` 上，由 `08` 导出读取函数，不新增反向依赖。
8. 保留已有切会话清理行为，不改附件发送链路。

### 验收

用可控延迟夹具覆盖：

- A 慢/B 快；详情完成顺序相同但 first_turn 顺序相反；A 失败/B 成功；连续打开同一会话；新建会话令旧请求失效；当前会话有活跃 Run。
- 编辑重发途中切到 B：没有任何内容自动发到 B，B 的消息不变；改好的文字没有丢，页面提示未发送。
- 分支、交接途中切到 B：停在 B，B 的输入区不被预填。
- A 的 Run 刚结束、终态重载在途时用户点 B：最终停在 B，A 的重载不生效。
- 被作废的打开请求失败：不弹错误提示。

最终消息、会话 ID、API、模型、Agent 和 Run 订阅必须全部属于最后一次有效打开动作。
