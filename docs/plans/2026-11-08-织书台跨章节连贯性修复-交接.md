## 一、各切片做了什么

### 切片 1：角色字段修复（角色卡背景与关系进入正文提示词）

- `naiba/writer/prompts.py`
  - 角色生成系统提示（`STEP_SYSTEM["chars"]`）的 JSON 模板明确要求 `relations`（与谁、什么关系），并声明不许留空。
  - `parse_characters()` 解析时保留 `relations`（上限 1000 字，与 store 归一化 `CHAR_LONG_MAX` 一致）。
  - 重写正文人物摘要：新增 `_character_line()`（字段顺序固定：身份→出身→背景→关系→性格→说话→目标；单字段独立限长、超长保留开头加省略号，不再整条中段乱砍）、`select_context_characters()`（主角优先 + 被章节梗概/上一章节选/段落要点/补充要求点名的配角必带）、`_fit_characters_text()`（按预算装填；相关人物压缩次要字段也要带上，无关配角放不下就排除并如实报告）。
  - 删除正文上下文「固定最多 6 人 + 总长 500」一刀切：正文人物槽预算 `DRAFT_CHARS_SLOT_CHARS = 2400`；设定链（chars/outline/大纲步）沿用紧凑摘要（最小字段集 + 预算装填），不盲扩到整张角色表。
  - `_characters_text()` 输出补上 `intro`/`background` 与 `relations`（此前正文摘要漏掉背景字段，正是角色背景丢失的根因）。
- `naiba/writer/store.py`：`_normalize_characters()` 的 `intro↔background` 双向映射与 `relations`/`origin` 保留本就正确，补往返回归测试钉住，不改旧行为。

### 切片 2：章节状态存储与生成接入

- `naiba/core/contracts.py`：新增快照键常量 `WRITER_CHAPTER_STATES_KEY = "chapter_states"`（先登记契约再接线）。
- `naiba/writer/store.py`
  - 状态文件 `studio/writer/<book>/chapter-states/0001.json`，一章一文件；`normalize_chapter_state()` 收敛结构（人物出场/位置/身体与身份状态、关系变化、已知/未知、事件、未决线索、下章待办），未知键丢弃、超长截断、全空拒绝。
  - `save_chapter_state()`：锁内固化 `source_version_id` + 内容指纹（sha256 前 16 位）；状态是派生数据——写状态不推进作品 revision、不改正文；`status="failed"` 时 `state` 强制为空，失败提取绝不落成可被误读的有效状态。
  - 有效性判定 `effective_status`：`ready`（状态来源 = 章节当前指针且提取成功）/ `stale` / `failed` / `missing`（缺失）。
  - 失效传播 `_invalidate_states_from_locked()`：重写/换版本/删版本导致第 N 章当前正文变化时，第 N 章及之后各章的旧状态立即标记失效（挂进 `save_chapter_version` / `select_chapter_version` / `delete_chapter_versions` 三个内容变更入口）；换回「被提取的那一版」时本章状态保持有效，下游章节不豁免。只改状态记录 status，不动正文、不清空已提取事实。
  - `chapter_context_states()`：新章生成读取前序最近 4 章（`CHAPTER_STATE_WINDOW`）的有效状态，stale/failed/缺失一律跳过。
  - `chapter_state_overview()` / 报告存取（见切片 3）；删章节/清空章节连带清理状态文件。
- `naiba/writer/prompts.py`
  - 新步骤 `state`：`STEP_SYSTEM["state"]`（章末状态记录员，严格 JSON，只记正文明确写出的事实）、`build_state_user()`（本章全文，超 16000 字按头 12000 + 尾 4000 截取并标注省略；附角色名单统一人名）、`parse_chapter_state()`（严格 JSON、全空按失败处理）。
  - `build_draft_context()` 新增 `chapter_states` 参数与「前情状态」槽（位于出场角色与本章梗概之间）：逐章渲染（人物在何处/何状态、关系变化、X 不知道……、事件、未决、下章），带续写要求（位置/关系不得无故回退、「不知道」不得写成已知）；预算 `CHAPTER_STATES_SLOT_CHARS = 2400`，超预算丢最旧的章；槽位如实在 slots 里报告带入的章号。
- `naiba/writer/pipeline.py`
  - 正文类 kind 的步骤统一改为 draft 后跟 state：`chapter`/`chapter_continue`/`chapter_rewrite` = `["draft","state"]`，`chapter_segs` = `["segs","draft","state"]`，`chapter_all` = `["draft","state"] × N` 交错（第 N+1 章开写前必须能读到第 N 章刚落盘的状态）；`_chapter_for_step()` 按 kind 解析每步对应章号（批量按下标折半）。
  - **状态提取是尽力而为的派生步**：state 任务失败（模型错误）或解析失败只落 failed 状态记录 + `state_errors`（流水线记录里最多留 10 条），正文早已保存、链继续走完；唯独「用户取消」仍停链，取消后不提交下一步。存储层写失败同样降级为 failed 记录，不阻断链。
  - state 步提交时读取的版本号固化进流水线记录（`state_source_version_id`），写回时原样盖章——提交与写回之间章节被改也不会把状态错挂到新版本上。
  - 单章 kind 的前序状态随快照冻结（与章节基线同口径），rebase 时随基线一起刷新；`chapter_all` 不冻结、每步现读（验收要求：批量下一章读刚保存的有效状态，不复用批次开始时的旧快照）。
  - 新 kind `state_rebuild`（重建章末状态）：用户触发的补建入口，按 from_no/want_count 对范围内**已写正文**的章逐章重新提取（没正文的章跳过；范围内无正文如实拒绝）；每类入口（单章/续写/重写/分段/批量/重建）与既有重试、取消、冲突、幂等语义全部沿用。
- `naiba/writer/service.py`：`api_preview` 与正式提交共用同一 `build_draft_context`（含前情状态槽），预检即实际发送；`state_rebuild` 走既有 `/pipelines` 接口，无新端点。

### 切片 3：只读连贯性检查

- 新模块 `naiba/writer/coherence.py`（不调用模型、不改正文、不动版本）：
  - 四类确定性规则，对已保存的章末状态做跨章交叉比对：`character_unintroduced`（无铺垫出现）、`character_vanished`（主角最后一次出场后直到全书末条状态再未出现）、`knowledge_conflict`（第 k 章「不知道 S」、第 j 章已知道而中间无事件交代）、`relation_conflict`（先结盟后又「互不相识」= confirmed；后又「初次见面」= tentative）。
  - 每条发现带：章节号、涉及人名、`confirmed/tentative` 分级、摘要、证据（状态条目 + 在正文中按关键字定位的原文引文，找不到原文时只留状态条目）；规则命中不冒充事实判断。
  - 报告 schema 1：`checked_chapters`、`chapter_versions`（版本绑定）、`findings`、`notes`（无有效状态的章如实说明覆盖范围并提示重建）；`report_is_stale()` 按章节当前指针判定旧报告过期。
- `naiba/writer/store.py`：`save_continuity_report()` / `load_continuity_report()`（`continuity-report.json`，坏文件按没有处理）。
- `naiba/writer/service.py` + `naiba/http.py`：`POST /api/writer/books/<id>/continuity/run`（运行并保存）、`GET /api/writer/books/<id>/continuity`（读取 + stale 标记）。
- 前端最小呈现（`public/index.html`、`public/js/27-writer.js`）：
  - 正文页新增「跨章连贯性检查」组：`运行检查` 按钮 + 报告容器；`renderContinuity()` 渲染发现清单（类型 · 矛盾/存疑 · 章节 · 摘要 · 证据引文），过期报告显著提示重跑；进入正文阶段自动拉取最近报告；文案明确「不会改动正文」。
  - 正文操作栏新增「重建状态」按钮（对当前章触发 `state_rebuild`，旧作品补状态/重写后补建用）；`STEP_LABELS`/`KIND_LABELS` 补 `state`/`state_rebuild` 中文名。

## 四、计划中未覆盖或降级处理的点

1. **状态提取走独立流水线步，而不是合并进正文任务**：计划未指定形态；选择独立 `state` 步是为了严格 JSON、失败可单步重试、不污染写作提示词。代价是每章多一次模型调用（真实成本待真实模型验证）。
2. **真实模型行为未验证**（计划 §六允许）：提取质量（漏事实/编关系）、前情状态槽对各类模型窗口的实际影响、`build_state_user` 的 16000 字截取策略对超长章的效果，全部只用确定性假模型验证过请求上下文与状态流转；未做任何真实供应商探针。
3. **连贯性检查是确定性规则引擎，不是模型评审**：计划 §三.C 未强制模型判断；本轮对结构化状态做交叉比对（无模型调用、零成本、可重放）。关键词规则（结盟/互不相识等）必然漏判语义级回退——这是「可能缺少交代」分级 + 证据可回溯设计下接受的降级；后续可加模型评审步而不改报告 schema。
4. **顺手修正一条预存冒烟断言**（非本计划引入）：`verify/writer_ui_smoke.cjs` 的「空正文不假装导出成功」检查期望「没有正文」，而 2be9710（2026-11-03）已把含附录导出的空态文案改为「没有内容可导出」，冒烟脚本当时未同步——本轮跑冒烟时必然失败，按「改产品要同步脚本预期」口径更新为当前文案；另有 continuity 两路由 mock 属于新接口的冒烟配套。
5. **状态提取失败的中途语义**：批量（chapter_all）某章 state 失败会继续写后续章（计划「不得阻止正文保存」），该章状态落 failed 且后续章读不到它（跳过而非误读空状态）；整链最终 done 并在 `state_errors` 里如实报告。未做「失败自动阻塞批量」的保守分支。
6. **未做 UI 的范围**：连贯性检查只有正文页一处入口与清单呈现，无逐条「去处理」跳转、无按章筛选；`state_rebuild` 只有当前章按钮，无范围选择框（API 支持 from_no/want_count，前端未暴露范围 UI）。
