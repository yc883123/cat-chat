# 任务总管自动续办闭环 V1 实施计划

> 历史计划。本轮实现与隔离验收见《2026-11-02-任务总管并行整改与自动续办子助手交接》第 0 节；外部模型 A15 仍未验收，不能把计划勾选或本地替身当供应商通过证据。

日期：2026-11-02。

状态：待实施。本计划定义第一版的产品行为、技术边界与验收要求，不代表功能已经实现或通过验收。

## 一 目标与范围

让任务总管在一个已有会话内，围绕用户明确给出的目标，检查 Agent 每轮执行结果；未达标时组织具体的补做指令，有限次自动继续，达标或需要用户处理时停止。

第一版的核心是“替用户盯着任务完成”，不是无条件反复发送“继续”，也不是另建一个聊天机器人。

纳入范围：

- 一个任务绑定一个已有主会话，沿用该会话的执行 Agent、工具范围与工作区。
- 用户明确目标、完成标准和运行限制后，主动开启自动续办。
- 每轮执行结束后检查结果，决定完成、补做或等待用户。
- 用户可以查看每轮依据、自动指令与结果，并随时暂停、接管或取消。
- 调度由服务端负责；关闭任务页面不影响执行。

暂不纳入范围：

- 跨会话调度、动态更换 Agent、多监督者互审。
- 将监督闭环嵌入 Writer、Novel 或混合阶段链。
- 无限续聊、自动增加预算、自动授予新权限。
- 自动回答涉及用户偏好、账号、授权或重要取舍的问题。
- 独立的通用代码测试平台、任意文件扫描器、精确金额封顶系统。

普通聊天、单次聊天任务和原有固定步骤链保持原行为，旧任务不自动升级为监督任务。

## 二 现有基础与实现缺口

现有聊天任务已能把用户目标发送到关联会话，复用普通 Chat Run；任务总管负责状态、控制和结果回链。预设步骤可以按配置自动推进，但没有依据回复内容动态组织下一轮指令的闭环。

当前实现入口：

- `public/js/28-super-agent.js`：创建聊天任务、提交目标、展示任务和关联会话。
- `naiba/run/chat.py::ConversationRunMixin.submit_chat`：提交普通聊天执行。
- `naiba/super_agent/runtime.py::RuntimeAdapter.sync`：同步底层执行结果。
- `naiba/super_agent/store.py::append_event_and_apply`：将完成事件映射为节点成功，并可能结束整个任务。
- `naiba/run/manager.py`：插话、引导、取消和工具确认。

必须解决的三个结构问题：

1. **一轮结束不等于目标完成。** 监督任务收到底层 Run 完成后，应进入待检查状态，不能先把整个任务标为完成再追加下一轮。
2. **检查结果不能阻塞控制。** 现有任务对账持有协调锁；审查模型必须在独立、有界的 worker 中运行，不能占着锁等待网络响应。
3. **自动消息不能冒充人工授权。** 现有聊天提交会创建用户角色消息；自动续办需要可信来源标记，并在权限与历史消费路径中保留来源区别，而不只是改变气泡颜色。

## 三 用户入口与默认设置

在“任务总管 → 新建任务 → 聊天任务”中增加执行方式：

- 单次执行：保持现有行为，默认选中。
- 自动检查并继续：启用本计划的监督闭环。

自动模式显示以下设置：

| 设置 | 第一版规则 |
|---|---|
| 关联会话 | 选择一个已有主会话；同一会话只允许一个未结束的监督任务，暂停和等待中的任务也占用关联 |
| 任务目标 | 继续使用“你想完成什么”，不再增加一份重复的任务指令 |
| 完成标准 | 必填，可逐条填写；没有标准时不允许启动自动模式 |
| 最大自动续办次数 | 默认 3 次，可选 1–5 次；默认即“首次执行 1 轮，加最多 3 轮补做，共最多 4 轮” |
| 运行窗口 | 默认启动后 30 分钟，可在启动前调整；暂停和等待不自动延长截止时间 |
| 审查模型 | 第一版使用任务所选的同一模型，但使用独立审查上下文，不加载执行 Agent 的角色和工具 |
| 创建后立即执行 | 保持默认关闭；勾选或手动开始后才产生执行和审查请求 |

上述数值是本计划的第一版默认方案，实施时集中定义并由服务端校验，前端不能绕过。

启动前明确提示：自动补做会产生新的模型调用；一次执行可能包含多次工具推理，执行轮数不等于模型请求次数。不得宣称“最多 4 轮就只调用 4 次模型”。

示例目标：“修复导出按钮无响应的问题。”

示例完成标准：“按钮点击能触发导出；导出文件内容正确；相关测试通过；完成桌面与手机 Playwright 验证。”

## 四 执行与检查流程

1. 冻结本次目标、完成标准、模型、Agent、工具范围、工作区和运行限制，记录版本。
2. 发起第一轮普通 Chat Run，同时提供目标和完成标准。
3. 等待该 Run 的真实终态及结果消息落盘，读取与此 Run 对应的结果，不使用“会话最后一条消息”代替。
4. 先执行程序检查：是否取消、是否有人工新输入、是否待审批、是否到达限制、结果是否完整。
5. 在允许检查的条件下，提交一次独立模型审查。
6. 校验审查结果；只有合法决定才能改变监督状态。
7. 需要补做时，再次核对用户输入版本、权限、预算和取消状态，原子登记下一轮派发意图，然后提交一次续办。

| 审查决定 | 含义 | 后续动作 |
|---|---|---|
| `done` | 完成标准已满足，且对应依据足够 | 标记目标完成，给出逐项结果及产物入口，不再发送消息 |
| `continue` | 存在明确缺项，能在原授权内继续处理 | 生成一条具体补做指令，进入下一轮执行 |
| `needs_user` | 缺少资料、需要用户选择或新的授权 | 显示问题并等待用户，不代答、不自动批准 |
| `blocked` | 当前无法可靠继续，或已经无有效进展 | 保留结果，显示未完成原因，等待人工处理 |

轮数耗尽、截止时间到达、取消、服务异常是程序控制结果，不能被模型改写成成功。工具审批已经存在时，优先进入等待，不额外调用审查模型替用户作决定。

执行状态建议使用“等待开始、执行第 N 轮、待检查、正在检查、等待你处理、暂停自动续办、正在停止、已取消、目标完成”。具体检查阶段保存在监督任务自己的 `phase` 中，不必把全部细分状态加入全局任务枚举。

## 五 审查输入与结果契约

### 审查输入

每次输入只包含判断当前目标所必需的信息：

- 原始目标、完成标准、允许的范围与禁止事项。
- 当前目标版本、执行轮次和剩余续办次数。
- 当前 Run 的最终回复，以 `detail.message_id` 和 `run_id` 定位。
- 当前轮的真实工具结果摘要、错误、相关产物引用和可核实的检查记录。
- 上一轮未达标项、已经补做的内容，以及必要的用户补充。

不默认灌入整段聊天、完整推理轨迹、凭据或无关日志。超长输入按固定预算裁剪，明确说明哪些内容未提供；关键依据缺失时不能假定其已通过。

会话中的文本、工具返回和产物内容均作为待检查的数据，不能借此更改审查规则、授权范围或运行限制。

### 审查输出

模型只返回结构化结果，至少包含：

- `decision`：四种决定之一。
- `summary`：给用户看的简短判断摘要，不是内部思维过程。
- `criteria_results`：逐条标准的通过、未通过或无法判断，以及依据引用。
- `missing_items`：仍缺少什么。
- `next_instruction`：仅在继续时提供的一条具体指令。
- `user_question`：仅在需要用户处理时提供的问题。
- `progress_summary`：相对上一轮新增了什么有效结果。

服务端校验字段类型、枚举、长度、条件必填项和引用归属。未知决定、空输出、非法结构或越界引用均不能触发新执行；显示检查失败，保留原始执行结果，等待用户处理。

### 证据强度

- Agent 写“已经修改、测试通过”只是陈述，不能代替实际修改记录和测试结果。
- 程序可核对记录是否属于当前任务、工具是否成功、产物是否存在；这些事实也不能单独证明所有业务要求都正确。
- 文案表达、风格等主观标准可由模型评价，界面标为模型判断，不冒充确定性测试。
- 缺少可获得的证据时，要求执行 Agent 在原权限内补做检查；第一版的审查模型不带工具，也不自行执行 shell。
- 必需的后台工作尚未完成时，“已提交后台任务”不能算目标达成。可关联的任务等待真实终态；无法可靠关联时交给用户处理，不盲目重提。
- 对仍为“无法判断”的必需标准，不自动标记达标。用户可以单独确认接受，并明确记录为“用户确认完成”。

## 六 自动续办与人工接管

自动补做指令应包含具体缺项、需要交付的结果、验收方法和原任务边界，避免只说“继续”“再想想”。

例如：“目前只有原因分析，尚未提交修复。请在原工作区修改导出按钮事件绑定，执行相关验证，反馈修改位置和真实验证结果；不要处理其他功能。”

普通聊天里显示“任务总管 · 自动续办 · 第 N 轮”，保留它对应的任务、审查记录及前一轮执行引用。所有自动消息和 Agent 回复都保留，不覆盖历史结果。

人工优先规则：

1. 用户在关联会话发送新消息、提交插话或进行引导时，先持久化暂停自动续办，并使旧审查结论失效。
2. 插话仍走现有机制；不得自动点击“引导”，不得把本轮剩余插话悄悄作为下一轮输入。
3. 审查期间用户已经发话，旧结果可以留作记录，但不能再据此发送旧指令。
4. 用户明确点击“继续自动续办”后，按最新有效输入和剩余预算重新确定执行位置，不重发已完成轮次。
5. 修改目标、完成标准、Agent、模型、工作区或权限后，需要重新确认执行基准；旧版本的审查结果不能复用。

暂停、继续和取消保持不同语义：

- 暂停自动续办：阻止新检查和新轮次派发，在途执行仍可能完成；提示不得声称供应商已经停止计费。
- 继续自动续办：先对账并核对当前权限、截止时间和剩余次数，不自动重置预算。
- 取消任务：请求取消在途 Run 和审查调用，显示“正在停止”；收到执行器确认后才显示已取消。已经产生的外部副作用不会因此自动撤销。

## 七 安全与运行限制

### 权限和来源

自动消息来源由服务端内部入口写入，前端不能自行伪造。即使模型协议使用 `user` 角色，后端也必须知道它来自总管，不是用户新增授权。

凡是依据用户原文授予路径、工具或执行权限的入口，都必须识别自动来源。自动生成的路径、同意语句或“请直接执行”不能扩大原授权；新增范围或需要确认的操作交回用户，审查模型不能批准工具确认。

执行继续复用现有权限检查。授权收窄立即生效；授权或配置改变后先暂停并复核，不能靠创建时的快照保留已经撤回的权限。

### 防止空转

- 达到续办次数上限后，不再创建第 N+1 轮；最后一轮仍可进行一次已预留预算的检查。
- 连续两次检查发现相同未解决缺项，且没有新增有效依据，转入等待处理。
- 相同补做指令、相同结果或同一失败重复出现时，纳入无进展判断；不能仅通过换一种措辞绕过限制。
- 执行失败不自动重跑可能带副作用的操作；保留失败状态，用户显式重试后仍计入运行限制。
- 审查失败不启动模型修复模型的无限循环，不在原结果后直接拼接并执行未知文本。

### 时间与费用

运行窗口从用户开始任务时计算，暂停和等待不自动延长。到期后停止新派发，并请求取消在途可取消调用；需要继续时由用户显式确认新的窗口。已在外部执行的工作可能无法立即停止。

审查调用设置独立超时、输入预算和输出上限；执行 Agent 沿用其单轮步数及超时限制。应用内部的模型重试也要记录，不能隐藏其调用和费用影响。

界面分别展示执行轮数、审查次数及可获得的 token 用量。供应商不返回用量时标记未知，不能记成零。本版以轮数、时间窗口和单次调用限制控制运行，不承诺精确金额硬上限。

## 八 后端实现方案

### 独立监督执行器

新增 `supervised_chat` 执行器，用一个稳定的任务节点承载整个监督闭环，每轮具体执行继续使用普通 Chat Run。

底层 Run 完成只推进监督节点到“待检查”；只有目标检查通过或用户明确确认接受，才发布上层节点完成事件。普通 `chat_run` 和原有固定链不改变完成语义。

执行轮次与失败重试 `attempt` 分开记录，不能把一次正常补做当成重试旧节点。

### 持久化与幂等

新增监督配置与轮次记录，至少保存任务 ID、目标版本、轮次号、Run ID、输入及输出消息 ID、人工输入版本、审查状态、决定、依据引用、下一条指令、运行限制和取消代际。

每次审查与续发都有持久唯一键。先保存审查决定和派发意图，再执行；重复事件、重复轮询和重复点击不能多发一条消息或多创建一个 Run。

自动提交必须在同一事务边界复核人工输入版本、取消状态、配置版本、预算及会话占用，再登记消息和 Run。仅在调用前做一次检查不足以避免用户与管家同时发消息。

如果提交已发生但回执或绑定尚未保存，重启后通过关联键找回既有 Run；结果不明时进入需要恢复，不重新提交可能付费或有副作用的请求。已保存的审查决定可以复用，不能无故再调用一次模型。

### 执行线程与恢复

调度线程只负责领取工作、记录状态、发起有界 worker 和对账。模型请求不在全局协调锁内等待，暂停和取消始终可以提交。

关闭或刷新前端页面时，服务端继续运行。服务进程重启后先恢复关联、状态与运行计数；第一版要求用户确认继续，才恢复新的自动派发。旧审查的迟到结果不得覆盖新的用户输入、取消状态或目标版本。

### 拟改动入口

| 入口 | 改动职责 |
|---|---|
| `naiba/core/contracts.py` 与 `naiba/core/messages.py` | 先登记监督事件、字段和自动消息来源契约 |
| `naiba/super_agent/models.py` 与 `store.py` | 监督配置、轮次持久化、合法转换、幂等与恢复 |
| `naiba/super_agent/` 下新增监督执行与审查模块 | 状态推进、证据整理、审查提示及严格解析 |
| `naiba/super_agent/runtime.py` 与 `domain.py` | 注册监督执行器，接入有界调度、控制与对账 |
| `naiba/run/chat.py`、`manager.py` 与 `naiba/storage/store.py` | 可信内部提交、人工优先、原子提交条件及消息来源落库 |
| `naiba/core/history.py` 与相关权限入口 | 在历史重放、用户意图与授权判断中保留自动来源边界 |
| `naiba/app.py` 与 `naiba/http.py` | 任务创建、控制、监督详情与审查摘要接口 |
| `public/index.html`、`public/js/28-super-agent.js` 与消息渲染入口 | 自动模式设置、进度、控制、来源标签和结果回链 |
| `tests/` 与 `verify/` | 确定性回归、故障场景、真实服务和 Playwright 验收 |

数据库按实施时的最新迁移顺序追加，不复用历史迁移编号。共享消息 metadata 继续按键原子合并；日志和对外响应不暴露凭据及完整推理轨迹。

## 九 前端展示

不增加第二套聊天窗口。任务总管负责进度、检查和控制，详细对话仍在关联会话中。

任务详情展示：

- 目标与完成标准。
- 当前阶段，例如“执行第 2/4 轮”“正在检查结果”“等待你补充信息”。
- 已用与剩余续办次数、截止时间、已知用量和最近进展时间。
- 每轮判断摘要、未达标项、依据引用和自动发送的下一条指令。
- 暂停、继续、取消及回到关联会话的入口。
- 完成后的逐项验收结果、产物和仍需注意的问题。

达到限制时明确写“未完成，已达到自动续办上限”；没有证据时写“无法确认”；运行失败时写明失败环节。不要把这些结果统一显示为完成。

正在检查时显示开始时间与已等待时长，避免页面像卡住。只有获得真实流式或用量数据时才显示相应计数和速度，不显示虚构百分比。

## 十 实施顺序与阶段交付

### P0 契约与状态设计

确定监督任务字段、来源契约、轮次定义、状态转换和完成门槛。建立迁移与旧任务兼容测试，明确权限和人工优先的拦截点。

交付条件：使用测试替身即可覆盖开始、单轮结束、待检查、继续、等待、取消和完成，且普通任务行为不变。

### P1 单会话监督后端

### P2 人工接管与异常恢复

接齐插话、普通消息、待审批、暂停取消、无进展停止、非法审查输出以及服务重启对账。

### P3 前端接线

增加自动模式、完成标准、限制设置、轮次详情、检查状态、来源标签和人工接管提示，保持桌面与手机均可操作。

交付条件：用真实后端完成 Playwright 创建、检查、补做、控制、回链与刷新恢复，不用纯页面 mock 代替接线验收。

### P4 综合验证与交付

先完成确定性测试与前端回归，再使用用户确认的模型和请求预算进行小样本真实验证。修改维护说明中的当前行为入口，保留独立验收证据。

交付条件：下表所有必需项具备实际证据，才宣布功能完成；发布、推送和版本升级不包含在本计划的自动授权中。

## 十二 完成判据

用户只需要给出目标和完成标准。Agent 首轮未达标时，总管能依据结果提出具体补做要求，并在限制内自动继续；达标后停止，需要用户或无法推进时及时交还控制。

整个过程中，用户能看见为什么继续、为什么停止、已经执行了什么，以及还缺少什么；不会被冒充授权，不会因刷新、重启或重复事件多执行一轮。
