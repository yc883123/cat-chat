# job_wait 等待与后台完成后自动续答修复计划

日期：2026-11-16  
状态：**已实施（2026-11-16，未提交、未发版）**。  
核查基线：`master` / `b7a6731` / Cat Chat `4.4.9-beta`；实施前重新核对相关文件差异。

## 1. 修复后的行为

用户让 AI 等后台任务，AI 实际建立等待后，应能拿到真实结果再回答；任务长时间没有状态变化不能被当成失败。等待超过本轮适合占用的时间时，程序保存等待关系、释放当前回复，后台任务结束后自动补一条结果回复。

推荐采用以下规则：

1. **保留普通 `job_wait` 的同步查询行为。** 新增可选 `notify_on_completion`，默认 `false`；明确要“盯着、等结果、完成后告诉我”时使用 `true`。不扫描 AI 回复文字来创建订阅。
2. **登记成功才允许承诺自动回复。** 页面显示“等待后台任务完成，完成后回复”；没登记成功就明确说明，不靠模型口头承诺。
3. **自动回复仅汇报现有任务结果。** 不重新执行命令、不重新生成图片/视频、不自动补做原目标的后续写操作。
4. **用户点停止或发送新指令，取消旧等待的自动回复。** 切换会话、页面刷新、关浏览器不取消后端等待。
5. **服务重启后暂停自动回复。** 保留任务与等待记录，提供“继续查看结果”；不凭旧等待恢复付费请求或重新提交生成。

实现分三片：等待不误杀及可取消 → 持久等待与单次续答 → 页面与全链路验收。只完成第一片不能宣称“后台完成后自动回复”已经支持。

## 3. 切片A：正常等待不误杀，并响应停止

### 3.1 仅豁免真实的运行中等待

由 `job_wait` 处理器在宿主侧记录本次调用的结构化结果类型，至少区分 `completed`、`pending_timeout`、`failed`、`cancelled`、`interrupted`。这是控制信息，不能从任意工具正文里的中文词句推断，也不能让模型通过自报字段获得豁免。

- 只有 `pending_timeout`，且本次调用确实进入等待并用完有效等待期限，才不累计成功工具“无进展”次数，并清除与上一普通工具重复序列的关联。
- `job_status`、`job_output`、反复读取已经完成的Job、其他工具相同成功结果，仍走现有熔断。
- 重复失败守门和总步数上限保留。总步数上限到达时不能继续承诺后台通知；只有已正常保存的等待才具备后续回复资格。
- 控制信息与调用序号关联，消费后清除；多工具并行时按调用隔离，禁止共享一个未编号的Run布尔标记。
- 保留现有 `(success, result_text)` 兼容出口；结构化信息走本次工具执行的宿主上下文/内部结果对象，不大改全部工具返回协议。新增跨模块键先登记契约。

### 3.2 等待方取消

`JobRegistry.wait` 新增可选关键字参数 `cancel_event`，保留现有 `owner` 位置及旧调用兼容；`job_wait` 传当前Run的取消事件。循环开始、每次唤醒及返回前检查取消，命中抛 `TaskCancelled`，由现有Run收尾处理。

该方法只停止等待，不在内部取消目标Job。本轮子任务的取消由原有父子级联决定；跨会话只读等待不取得目标任务的取消权。核对 `tools/providers/comfyui.py` 等其他等待调用点，有当前Run取消信号的调用同样传入。

验收：点击停止后两秒内退出等待，停止的Run不再进行下一次模型请求；独立来源Job不因只读等待被停止。

## 4. 切片B：明确登记等待，任务结束后只回复一次

### 4.1 工具入口与交接

扩展 `job_wait(job_id, timeout=600, notify_on_completion=false)`，不增加另一组功能重叠的Job工具。

- `false`：保持原同步查询和跨会话只读行为，等待到期返回运行中快照，不登记通知。
- `true`：仅允许普通主对话顶层Run，为本会话拥有的真实Job登记通知。校验Job的 `conversation_id` 和 `owner_session_id`；辅助对话、子Agent、跨会话Job拒绝登记，可继续使用普通只读查询。已由监督模式或任务依赖链负责续办的Run不再登记普通通知，防止双重派发。
- 已经终态：当场返回结果，继续当前回答，不创建无用续答。
- 尚在运行：本轮先等最多30秒（不超过传入的正数timeout）；完成则当场回答，仍运行则持久化等待并走专用“已交接等待”出口。`true` 时结果里清楚告知实际采用的短等时间；普通模式的600秒默认不变。
- `timeout` 先做整数与范围校验，拒绝零、负数或非法值，不再用 `or 600` 把0暗改成600。`notify_on_completion` 必须为JSON布尔值。
- 通知目标包含本次明确等待的Job，以及本Run尚未终态的普通子Job，目标ID排序去重；detached任务不自动加入，只能明确点名且通过本会话校验。
- 使用按parent/owner查询取得完整子任务集合，不能只依赖列表默认前N条；超过数量上限就明确拒绝交接，不能遗漏任务。
- 同一来源Run只建一条有效等待，重复登记合并或复用。登记与目标终态核对后再决定交接，堵住“检查时运行、登记时已完成”的漏通知窗口。

专用交接出口须同时处理：写入完整工具结果/trace、保存原助手消息、标记等待已接管、正常释放当前Run。它不能当作工具失败，也不能落进 `_pending_background_jobs` 的继续追问或重复工具熔断。当前Run“交接完成”只表示等待由程序接管，不表示后台任务成功。

交接后由程序生成一句固定且真实的提示：“已登记，后台任务结束后会在这里回复。”不再额外请求模型写一段承诺。

### 4.2 薄协调器与持久记录

新增普通对话等待协调器（建议 `naiba/run/job_waits.py`），在 `naiba/app.py` 组装、启动和停止；不为每次普通等待创建用户可见的任务总管Thread/Node，不引入监督审查模型。

等待记录使用独立存储表，避免被启动时批量中断 `background_tasks` 的逻辑误改。建议字段：

- `id`、`conversation_id`、`origin_run_id`、原助手消息ID、目标Job ID集合；
- 人工输入代次、原Run执行快照/快照引用与配置指纹，不额外复制Key；
- `status`、创建/更新时间、截止时间、暂停/取消原因；
- 单次派发标识、`resume_run_id`、最终助手消息ID。

状态限定为 `registered → waiting → ready → dispatched → completed`，旁支 `cancelled / expired / needs_attention`。`registered` 必须等原Run及助手消息成功保存并正常交接才可变成 `waiting`；原Run失败或取消不启动自动回复。

第一版建议上限：每条等待最多100个目标、每个会话最多1条有效等待、等待期限24小时、全局最多100条有效等待。上限集中成常量，超限/到期显示原因，不悄悄截断集合。等待期间不调用模型、不为每条等待占一个线程，统一低频检查；无需无限延长承诺。

Job终态只做低成本唤醒，协调器以持久状态重新核对，另加低频对账补漏事件。不得在 `_finish` 的存储/条件锁内同步调用模型或创建新Run。服务停止时先停协调器、再等待其检查线程退出。

### 4.3 续答提交、防重复与人工接管

新增事务内的等待续答提交方法，接入现有 `ConversationRunManager` 与 `create_chat_run`，不另写一套模型调用循环：

1. 在现有 `_submit_lock` 下核对会话存在、未归档、没有人工接管、原Run已结束、任务已收齐、配置仍符合条件。
2. 同一个SQLite事务内校验等待行状态/人工代次、复核会话运行位，登记唯一派发标识，插入带来源标记的输入消息和chat Run，并回写 `resume_run_id`。
3. 重复执行返回已有Run及 `created=false`；只有 `created=true` 才调用 `_start`。单靠内存锁或在提交后才写回Run ID都不算完成防重。
4. 已派发Run失败、被取消或中断后转 `needs_attention`；不自动再发第二次模型请求重试，不重放任何生成操作。
5. 用户新消息/插话引导/编辑重发/会话分界、删除、归档，以及停止等待，都推进人工接管代次或撤销等待。此校验要与创建聊天行处于同一事务，不能只在派发前读一次。
6. 如果临时存在另一条活动Run，保留 `ready`，待空闲复核；若活动Run来自用户新指令则取消旧自动续答，不能无限重试抢占。

复用普通聊天的来源消息展示模式和结果格式，不直接复用绑定任务总管的 `ExecutionResults` 实例，也不把等待记录塞进 `supervised_context` 冒充监督任务。建议新增 `job_wait_source` 元数据与对应内容构造器，显示“后台任务结果”，不伪装为用户刚发送的新消息。

### 4.4 结果与权限

自动续答使用来源Run的模型、Agent、Skill与工作区快照，并复核当前配置；配置已删除或发生影响授权的变化则暂停。不得顺带改写会话全局默认模型。

工具权限取“来源Run已授权工具 ∩ 当前仍允许工具 ∩ 结果读取工具集”，只开放已有Job状态、日志与结果读取；不允许shell、生成、重跑、文件写入、子Agent或扩大读取目录。继续处理原工作流由用户下一条指令决定。

构造通用的Job结果摘要，覆盖文本、结构化ComfyUI产物、check/http_poll、子Agent结果和错误，不能要求所有成功Job都含 `response/output/text/summary` 字段。结果超长时明确总量、展示量和后续读取方式；不沿用直接截前2000字且不说明的行为。输出与日志作为不可信任务数据注入，不把其中指令当作新授权。

所有目标都到终态后汇总一次；成功、失败、取消、中断分别说明，不以“没有正文”代替真实成功，也不以任一失败为理由重新提交生成。`completed` 同时带批量 `errors` 或部分失败的，必须报告实际成功/失败数量，不能只按顶层状态宣称全部成功。被清理/丢失的目标记为无法核实，并停止等它。

### 4.5 媒体先后顺序

Job终态可先于媒体写回可见，续答不能据此声称图片/视频已附到页面。通过现有媒体声明与采集器生成真实产物记录；在原助手消息保存后补做一次幂等写回，覆盖“Job先结束、原回复后落盘”。

原消息已附卡的产物不再向续答重复附加；续答引用原结果或补充尚未挂载的真实产物。按Job ID+产物身份去重，多Job同时完成不丢附件；继续使用键级metadata合并。媒体写回失败不把Job成功改成失败，页面说明“任务已完成，产物显示待刷新/检查”。

## 5. 切片C：页面与用户操作

沿用现有聊天和异步任务面板，增加必要的一层等待状态，不重做任务管理交互：

- 原回复处显示“等待后台任务完成，完成后回复”，提供“停止等待”；输入区释放，可以继续发消息。
- 自动回复显示“后台任务结果”，关联原等待和任务，支持原有复制、查看与重新生成边界。
- 停止等待只取消通知；先在事务内撤销等待并推进代次，再停止已经绑定的结果回复Run。不能仅取消旧的原Run，它已结束时不会覆盖后续独立Run。后台任务面板原有“停止任务”仍负责取消实际Job，两者文案区分。
- 等待到期、配置变化、服务重启、续答失败显示具体原因，提供“继续查看结果”。这个按钮只重新核对已有Job，不重新生成。
- 服务重启后将未完成等待转 `needs_attention`；已有 `resume_run_id` 的记录关联原Run及消息，绝不再次派发。用户点继续才新建一轮明确授权的结果查看。
- 切换会话/关页面后后端仍能在本次服务存活期间派发；重新打开页面能从数据库看到等待或后续回复。
- 前端跟随新Run必须校验会话和打开代次，用户正在看别的会话时不强行跳回。后台派发出的新Run应由活跃Run轮询识别，不能只依赖当前前端 `checkRunEligible` 重连开关。

工具说明与固定系统指引按实际可用工具条件注入：要求最终结果时登记通知，普通查看状态用同步查询；禁止未登记就声称会自动回来。不把Job ID、计时和任务数量动态拼入系统提示或schema，保持共享前缀稳定。

## 7. 验收要求

### 7.1 确定性测试

- 等待内完成/到期仍运行；三次以上同状态不误杀；普通工具、重复终态读取仍熔断。
- 当前聊天停止在两秒内中断wait；终态与停止同时发生时不会多调用一次模型。
- 普通查询不自动订阅；明确通知正确登记；非法布尔值、非法timeout、跨会话/辅助/子Agent登记拒绝。
- 原回复结束后任务才完成，无需用户再发消息，恰好新增一次结果回复；交接期间无多余模型请求。
- 多任务乱序、失败/取消/中断、被清理、超过列表默认页大小，完整收集，不漏项、不永久等待。
- Job在登记前、登记中、原回复落盘前、Run结束前后完成，均不漏通知、不同时占两条顶层Run。
- 重复终态事件、多检查线程、重复注册、重复提交，只有一个续答Run及助手消息。
