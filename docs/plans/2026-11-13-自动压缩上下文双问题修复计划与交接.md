## 4. 修复必须保持的约束

1. 原始用户消息、工具结果和完整执行轨迹保留，压缩只改变发给模型的视图，不能删除审计原文。
2. 摘要来源仍是当前选中的模型，不能无提示切换供应商；摘要专用参数不得修改模型卡、会话设置或普通回复的 profile。
3. 摘要只有完整、校验通过、有效历史实际变短并成功提交后才算成功。半截摘要、取消后迟到结果、存储失败都不能污染原历史。
4. 未触发整理的正常请求，system、tools、history 和顺序保持逐字节不变；失败保持旧视图。成功换前缀会产生一次缓存冷启动，不承诺零影响。
5. 用量诊断不进入模型历史；真实聊天计费和占用圆环不被隐藏摘要覆盖。摘要调用如记账，单独归属且只计一次。
6. 工具执行与历史重放分离，整理、恢复、撤销或重启都不能再次执行已经完成的工具。
7. 当前权限、最新用户指令、有效技能约束和会话分界不能因摘要被丢弃或变成更高权限指令。摘要中的工具输出继续作为不可信资料。
8. 辅助对话、关闭模式、仅提醒模式保持既有范围；普通聊天与计划执行的共享路径须一起验证。

## 5. 第一阶段：补诊断和可理解的失败提示

先登记契约，再修改生产方、持久化与 UI。优先扩展现有 `attempts`，必要的新顶层字段须在 `contracts.py` 登记，所有新增字段向后兼容。

每次隐藏请求应能区分：

- 输入估算与接口实际输入；旧 `attempts.input_tokens` 保持“估算”的既有含义，不能悄悄改口径。
- 请求输出上限、接口报告的输出量、接口明确提供时的 reasoning_tokens；缺失值保持未知，不能填 0 冒充实测。
- `finish_reason` 原值、截断来源（输出终止原因 / 正文形态）、摘要字符数，不持久化失败摘要原文或思考全文。
- 摘要目标长度、请求的思考档、实际映射出的参数类型、是否能够明确控制思考、尝试编号、耗时及失败类别。
- 整理范围是旧历史还是当前轮、成功前后完整有效请求的估算收益；限制记录数量与错误长度并脱敏。

界面须至少区分“摘要达到输出上限”“当前没有可整理的完整片段”“模型服务连接失败”“摘要没有缩短”“保存整理结果失败”。尚无实际摘要请求的 `region_too_small` 应作为跳过原因处理，不先显示完整整理成功式流程；只有确实开始请求才显示 started。

失败保留原圆环；成功立即显示估算占用，下一次真实 usage 再替换。恢复尝试期间只显示一段连续的整理进度，最终失败才显示失败，不连续弹多个相同提示。

## 6. 第二阶段：摘要长度、思考和输出预算

### 6.1 给摘要一个可实现的目标

建议第一版将正文目标设为约 2000–3500 中文字符，并按输入规模缩小目标；数字是待本地模型验证的初值，不是模型能精确遵守的硬承诺。路径、约束、已执行操作、失败状态与下一步优先，避免要求逐项复制所有历史命令输出。

目标正文长度与 API 的“思考加正文输出额度”分开表达；超过建议目标但完整且有效的摘要不能仅因超目标就拒绝。继续保留内容非空、拒答、截断、最大字符数和有效收益校验，不恢复固定九标题命中测试，不通过截取半份摘要强行过校验。

### 6.2 摘要使用独立的思考策略

复制当前 profile 后，仅对隐藏摘要调整，通过现有 `resolve_thinking` / `thinking_payload` 能力映射选择明确可控的低开销档位。正常对话仍沿用用户设置。

**不能直接把 `reasoning_effort='off'` 当作关闭思考。** 当前 llama_cpp 会归入 OpenAI Chat 映射，某些预设的 off 只是“不发字段”，后端可能继续默认思考；`options.reasoning_enabled=False` 也不等于关闭模型推理。若 off 没有有效控制字段，可用明确有协议效果的最低档；若仍无法控制，记录为未知并依靠长度与预算策略，不能对 UI 宣称已关思考。

不凭模型名臆造 `enable_thinking`、`think:false` 等字段。若 Basalt 需要特定模板参数，先核实该测试服务的版本和实际请求协议，再在能力声明与 wire 测试中支持；不在通用压缩函数里硬编码某家方言。

### 6.3 计算真正可用的输出空间

将摘要输入（含旧摘要、提示词、协议开销）、模型窗口和输出上限纳入同一个预算。建议计算关系：

```text
可用输出 = min(摘要策略额度,
               模型声明的输出上限〔已知时〕,
               上下文窗口 - 本次摘要输入 - 估算安全余量〔窗口已知时〕)
```

没有正的有效空间时，先缩小可总结区间或返回明确不足，不发必然超限的请求。小窗口不能被 `max(8192, ...)` 强行压过。未知窗口保持未知并使用有界策略，不能当成无限窗口。

预算限制必须标明来源：当前 `profile.max_output_tokens` 可能是用户输出偏好，不能称为后端实测硬上限；`thinking.max_output_ceiling` 是另一类声明能力。实现默认保留既有明确正数限制，并区分配置限制、声明能力与后端实测值，不能为提高额度悄悄越过用户限制。0/空值表示未设置或未知，不代表零可用额度。

初次请求可保留最高 8192 的默认策略额度，配合短正文和独立思考策略；确有空间且模型支持时，恢复请求最多可以提高至 16384，仍受声明上限与窗口限制。不直接修改用户全局配置，不统一给所有摘要升到最大值。

### 6.4 有界恢复

保留每次整理最多 3 次外层摘要调用的总上限，输入超窗口缩区间与输出截断恢复共用此上限，不能层层相乘。

| 失败类型 | 处理 |
|---|---|
| 明确的输入上下文溢出 | 沿完整边界缩小输入，实际 token 估算减少后才重试；不越过会话分界/已有摘要保护边界 |
| 输出上限截断 | 最多一次有变化的恢复：缩短正文目标，必要时使用有效的更低思考档或在有空间时提高输出额度；记录实际变化 |
| 仅由正文形态怀疑截断 | 单独记录来源；加强完整收尾要求后最多一次有变化恢复，不直接认定输出额度耗尽 |
| 拒答、无收益、写入失败 | 不通过反复相同请求碰运气；保留原视图并报告具体原因 |
| 取消、停止、会话失效 | 立即结束，迟到摘要不得提交 |

截断恢复重新生成完整交接稿，不直接拼接两段摘要、不把残稿当作事实来源。输入仍相同的情况下，必须确有长度/思考/预算策略变化才能恢复；这与“输入溢出必须先缩输入”是两种不同机制。

底层运行时已经会对部分网络异常、429/5xx 重试，方案应统计真实请求次数并核对上限，不能再套一层无界循环。若 API 在输出流或工具调用之后才失败，也不能盲目重放正式请求。

## 7. 第三阶段：支持当前轮较早工具轨迹的压缩

这是本次最容易破坏数据的部分，必须先落设计与测试，再改列表切片。

### 7.1 分离“完整执行轨迹”和“模型工作视图”

当前 `messages[trace_start:]` 同时承担发给模型与收尾保存 trace 的职责。直接删掉这里的工具消息，会让取消、错误、正常收尾和下一轮重放永久丢数据。

实施应维护两份有明确职责的数据，覆盖 `reset_context`、围栏拒绝等特殊返回路径：

- 完整执行轨迹：按真实执行顺序追加，工具结果和最终答复各保存一次；所有终态出口读取这一份。
- 模型工作视图：初始历史、当前任务、已接受的交接摘要、保留的近期完整工具组，以及后续新增内容；摘要成功只替换这一份。

没有整理时，两份数据构造出的模型请求必须与现实现完全一致。整理一次或多次后，完整轨迹不得混入旧轮完整历史，不得重复追加最终答复；所有 `trace_messages` 写入出口都要检查，不能只修正常返回路径。

### 7.2 整理边界必须是完整工具组

以 assistant 的一次完整工具调用消息及其全部对应 tool 结果为一个最小闭合单元。并行多工具的一组结果全部到齐，才可以作为切点；原生工具和兼容文本工具路径都要覆盖。

当前用户目标、最新有效插话、动态 Skill 约束、尚待确认或执行中的调用，以及最近完整工具组不得被随意抽走。建议先保留最近 2 个完整工具组作为默认，再按实际窗口和摘要收益验证；不能把 user 行数当作本轮的切分依据。

消息组过大且无法留下安全尾部时，应明确提示已保留结果但不能继续；不得留下孤立 tool 结果、悬空 tool_call_id，或以重新执行工具代替读取既有结果。

### 7.3 允许同轮多次整理，避免每步重复尝试

把 `_compaction_attempted` 的“整轮只许一次”改为基于范围和状态的尝试记录。至少区分：未具备可整理边界、真实请求失败、成功提交、新增内容形成新的可整理范围。

- 无可整理区间不消耗真实请求次数；新工具组完成后可重新判断。
- 同一历史版本、相同闭合终点、相同策略的失败请求不能原样再发。
- 成功后重新估算完整请求，不使用压缩前 usage 直接再次触发；新 usage 返回前，以已接受视图的估算加后续增长为准。
- 新范围显著增长或策略确有变化才允许新的尝试，不能只拿“列表又多一条”作为重试条件。
- 设置单次整理、单 Run 的调用上限和增长间隔；建议初始单 Run 最多 12 次外层摘要调用，具体常量在实现中集中定义并测试。达到上限后有明确状态，不能继续发送已知超限请求。
- 用户停止、窗口硬边界和无进展保护优先于尝试次数。真实请求耗时和底层重试也应受取消控制。

### 7.4 持久化与下一轮不能留到以后补

只压本轮内存不够：若收尾仍让下一轮完整回放巨大 trace，问题立刻复现。推荐保留原始 trace，并新增一个独立的、版本化的模型重放描述；旧 `compaction` 标记继续表示旧历史前缀整理，不强行复用成含糊的“半条 assistant 消息已整理”。

实现前在 `core/messages.py` / `core/contracts.py` 定义新描述的契约：来源 Run 与用户输入 ID、原始 trace 指纹、覆盖的闭合范围、摘要、保留尾部的定位信息、版本/代次，以及前缀依赖。范围绑定稳定消息 ID 和 trace 序号，不能只保存可变数组下标。字段名由实现提交统一确定，文档里的名称不能当成已经存在的字段。

`build_model_history` 应从有效的描述构造模型视图，校验来源和范围；描述缺失时按旧格式兼容。存在摘要时，不能同时再拼出同一段原始 trace。完整轨迹和视图描述必须在同一可恢复提交中关联，防止摘要成功但原始轨迹尚未保存就崩溃。

必须定义并验收：正常完成、取消、步数耗尽、工具解析失败、窗口停止、`reset_context`、进程中断后的读取、下一轮继续、会话分支/编辑重发、撤销整理和删除清理。当前 Chat 重启按中断恢复，不自动重新执行；本次继续保持这个边界。若采用恢复检查点，恢复只读取已经完成的工具结果，不自动重做外部副作用。

投影依赖的原始轨迹前缀应以追加段或等价方案保存，避免每步重写整份长 trace。主对话、计划执行及子代理读取既有摘要时应遵循同一重放口径，但这不扩大辅助对话的自动整理权限。工具执行游标、确认状态、外部 Job 句柄与摘要视图独立，不以“相同工具名和参数”做全局去重。

撤销通过原始数据重建视图。运行中若不能安全切换，则阻止这次撤销并说明原因，不能只删数据库标记而让活 Run 继续使用另一份上下文。若有多个依赖摘要，应明确撤销某一摘要时哪些后续描述同时失效。

新增引用必须进入 `message_traces` 及媒体清理保护逻辑；共享 metadata 按键原子合并。不能出现 UI 还看得到原始工具记录，但清理器已经删掉其依赖的轨迹或附件。

## 8. 第四阶段：失败后的停止与正式请求补救

摘要失败不自动等于本轮失败。仍有空间时保留当前行为，可以继续；但下一次正式请求必须按真实将要发送的 system、schema、历史、当前任务、工具轨迹、插话、附件和输出预留重新检查。

估算应与最近真实输入互相校准，不能把多次输入累计当成窗口占用，也不能仅用偏小字符估算忽略已观察到的真实增长。压缩成功后须切换到新视图的估算基线，避免旧真实 usage 反复触发。

已知超过有效窗口且无可验证压缩进展时，保留结果并停止新的模型/工具请求，明确告诉用户停止原因。禁止一边说“正在恢复”一边原样重发已知超限输入。

若本地估算放行、服务端才明确拒绝输入超窗口，可做一次“成功缩短有效视图后的正式请求补救”。只适用于确认请求未产生输出/工具副作用的窗口拒绝；连接中断、一般 400、未知受理状态不能按此重发。单条用户输入自身过大时，明确反馈输入限制。

## 12. 证据查询方式

只读打开私下交接的数据库，不直接用 `ChatStorage` 初始化它，避免迁移或启动恢复写入。以下 SQL 的 `:conversation_id` 用第 2 节目标 ID 绑定：

```sql
SELECT r.run_id, r.sequence, r.created_at, r.payload
FROM run_events AS r
JOIN background_tasks AS b ON b.id = r.run_id
WHERE b.conversation_id = :conversation_id
  AND r.event_type IN ('compaction', 'context_full', 'error')
ORDER BY r.created_at, r.sequence;
```

`created_at` 为毫秒时间戳，统一按 UTC+8 展示。普通回复的 `metadata.performance.chat` 不等于隐藏摘要诊断；usage 的累计 requests 与最后一次 input/context 字段也不能混用。原始正文、工具输出、配置密钥及接口凭据不复制进公开报告。
