## 2. 发布前优先问题

以下编号用于整改追踪；P1为阻断/信任问题，P2为明显误导与可用性问题。

### A01 · P1 · 未启用的LoRA仍阻止官方方案

官方I2V的开关默认false：`naiba/super_agent/recipe_assets/h3_i2v.api.json:124`；R2V同样默认false：`naiba/super_agent/recipe_assets/h3_r2v.api.json:292`。`naiba/comfyui/runner.py:580` 全图遍历并在`:617`枚举检查，不处理失活分支。

用户结果：没有用这个LoRA也过不了预检；将强度设0仍不能解决。此项为静态确认，并非本轮在真实ComfyUI上复跑用户失败任务。

### A02 · P1 · 保存本机可用方案的路径断开

更改模型/LoRA文本后，配方保存会拒绝，并要求先在造梦机保存到工作流（`naiba/super_agent/recipes.py:303`）。但造梦机现有“保存参数”只保存显示项和顺序（`public/js/24-comfyui.js:730`、`naiba/comfyui/service.py:295`），不固化这些实际值。

整改：新增保存当前配置为用户方案版本的能力，不原地覆写官方原件或已执行任务。

### A03 · P1 · 自定义方案时长可能没有真正绑定

后端有duration_slot（`recipes.py:219`），制作表单/保存请求没有（`public/index.html:1746`、`public/js/28-super-agent.js:1295`），所有方案却给4–15秒输入（`index.html:1736`）。执行只在绑定存在时覆盖（`recipes.py:802`）。

整改：方案作者一次性完成业务字段映射；未绑定就不展示伪可调字段。需要补离线契约测试和GUI验证，此轮是静态发现。

### A04 · P1 · 审核展示和实际执行不是同一份最终参数

所谓完整生效工作流只裁剪图片节点，提示词/时长/数值仍在独立覆盖数据中（`recipes.py:460,795,802`），真正合并在`runner.py:437`。不能把基础图称为实际执行图。

整改：同一个执行计划驱动审核摘要与提交；把不确定的随机值明确标注，而不是展示互相冲突的JSON。

### A05 · P1 · 未准备好也能走到最后一次确认

**GUI复现**：多图草稿没有提示词→点击“核对并确认生成”→审核页显示空提示词→“确认本次操作”→最后才拒绝。后端确实拦截，没有空提示词生成或越权执行。

代码：`recipes.py:468`、`28-super-agent.js:1183`；最终守卫`recipes.py:731`。

### A12 · P2 · 总管没有播放器，造梦机却可以播放同一视频

**GUI与代码共同确认**：总管只有“打开/保存”链接。`recipeOutputMarkup`要求`output.type=video`（`28-super-agent.js:963`），原生产物为路径字符串（`runner.py:841`），配方转换只补path/exists（`recipes.py:914`），未补媒体类型；造梦机从扩展名识别（`24-comfyui.js:2109`）。图片和音频有同类缺口。

点击链接后的外部打开/下载不在受控浏览器中出现，不能宣称成功；播放器缺失本身已有代码与截图支撑。

### A13 · P2 · 下一步、状态和可用动作口径不一致

配方反推/生成运行时、成功后都保留等待确认卡；普通任务存在保存即显示进行中、下一步指向被阻断后继的问题。通用按钮还可能允许stopping状态点继续、达上限自动续办仍给继续（`28-super-agent.js:275`、`runtime.py:671`、`supervised.py:699`）。

整改：后端统一返回当前可做动作及原因，前端只给当前有效的主操作。状态说明必须和用户下一步一致。

### A14 · P2 · 缺少方案管理、修复回跳和任务直接回链

使用入口存在，不等于管理入口。原生提词/造梦任务主要展示ID文本，无法直接打开；普通作品回链只到书、不定位阶段/章节；自动续办的逐轮引用也不能直接定位。

整改：我的方案＋打开原生任务/具体章节/本轮对话；缺依赖修复后返回原任务。底层标识留内部诊断。

### A15 · P2 · 预设、错误与时间线文案技术化

GUI可见“有界配方批次”“派发”“精确槽位”“执行指纹”“按阶段处理”“原生任务”“三字段/六字段”“R2V”；普通任务还有英文阶段、审批标识。用户不能据此判断发生了什么。

文案必须短且准确，不改语义、不隐藏费用、权限和执行范围。例：

| 当前 | 建议 |
|---|---|
| 图片→提示词→视频配方 | 用图片批量制作视频 |
| 有界配方批次 | 按图片分组生成视频 |
| 核对并确认反推 | 预览并生成提示词 |
| 确认本次操作 | 确认生成N组提示词 / 确认生成N条视频 |
| 暂停后续派发 | 暂停后续任务 |
| 仅补收此项产物 | 重新下载已有结果（不会重新生成） |
| 官方I2V单首帧、英文三字段 | 每张图片生成一条视频。先生成提示词，确认后制作视频 |
| R2V连续1–6图、英文六字段 | 每组选择1–6张参考图，共同生成一条视频 |
| 不能改稿后隐式重建 | 这条视频已经提交过。要修改内容，请复制为新任务 |

### A17 · P2 · 少数状态一致性缺口仍需补验证

- 已完成任务文件遗失后，batch可变partial而线程保留completed（`recipes.py:499,1134`）。应显示“曾完成，文件需重新下载”，不能简单留已完成。

### A18 · P1 · 输入方式不明确：剧本被当成补充说明，直接用提示词也没有独立路径

**用户追加确认（2026-11-03，新增整改要求，尚未实施）**：H3提词需要图片和剧本共同作为主要输入，不能仅给“补充说明”式表单；同时必须支持不调用反推、直接使用现成提示词。

在素材与正文输入区之前提供明确切换：**“图片＋剧本生成提示词” / “直接使用提示词”**。这两项是互斥的输入方式，不再要求用户同时填剧本和现成提示词，也不能靠“提示词有没有填”暗中推断模式。

| 输入方式 | 默认表单 | 执行流程 |
|---|---|---|
| 图片＋剧本生成提示词 | 方案所需图片；剧本正文（包含动作、对白等）；额外要求可选并收起 | 图片与完整剧本一起交给对应H3提词模板→生成可编辑提示词→用户检查→另行确认生成视频 |
| 直接使用提示词 | 方案所需图片；完整视频提示词 | 不选择、不校验、不调用反推模型，不要求剧本→检查素材、提示词和视频设置→确认生成视频 |

约束：

- “剧本”是正文主输入，不再被“内容要求/补充说明”替代；额外要求与剧本分开。按已选单图或参考图方案传入正确素材，不悄悄改变图片用途和顺序。
- 已有提示词路径原样保留用户提示词；不自动润色、翻译或重写。只做方案必要的兼容性检查，有问题先提示，不偷偷修词。
- 批量任务每项明确对应本组图片与剧本/提示词；不自动把整部长剧本拆段，也不把一份剧本暗分给多组。跨模式混合批次不是本次默认增加的功能。
- 切换时分别保留两种模式的草稿，不互相覆盖；只保存当前模式需要的执行输入。生成结果不自动覆盖另一模式已有的提示词草稿。
- 修改素材、剧本、提示词或切换模式后，旧审核确认失效，必须重新查看当前清单；切换本身不发模型请求、不启动视频、不恢复任务。已有执行记录的任务仍遵守不可改稿边界，使用复制新任务入口。
- 生成提示词路径只在确有待生成提示词时要求对应模型；直接使用路径前后端都不再强制反推模型，不能只把字段藏掉。
- 确认按钮区分“生成提示词”与“确认生成N条视频”，保留必要的调用/费用与执行范围说明。

追加验收：两种模式可从创建走到确认；图片＋剧本均出现在提词输入且剧本对白不被截断；直接使用时反推请求数为0、提示词不改写；空剧本/空提示词按当前模式就近校验；切换保留草稿且旧确认作废；两种模式深浅主题和窄屏可读。

## 3. 职责与最小表单

### 造梦机配置一次

选工作流、模型、LoRA、尺寸/采样等生成参数；明确素材与提示词用途；检查本机可用性；保存为可重复使用的方案版本。

### 任务总管每次只填写当前任务需要的信息

1. 选一个可用方案（最近使用优先）。
2. 选择“图片＋剧本生成提示词”或“直接使用提示词”。
3. 添加图片或分组，只填写所选模式对应的剧本或提示词。
4. 确认每组几条、必要时调整时长。

模型和参数默认继承方案，只有明确需要时才展开修改；没有必要重新挑供应商、理解种子或节点ID。生成提示词模式按需沿用提词模型；直接使用提示词模式不要求反推模型。两种模式替换正文表单，不增加一组必须同时填写的字段。

### 可视化审核不增加一轮填表

默认只读：素材缩略图/用途→提示词→视频数量；附模型、LoRA状态、时长/尺寸、运行位置、可能费用及就绪检查。主按钮明确具体动作与数量。

缺少依赖时只列阻断项和下一步，允许去造梦机修复并返回；素材/提示词不丢失。运行中只提供真正支持的暂停/取消；已完成以播放/下载/复制新任务为主。

## 5. 明确没有验证的内容

- 浏览器运行环境不支持系统文件上传，原图/目录选择和完整分组导入未通过真实GUI；预置草稿不替代这些行为。
- 真实H3推理、显卡内存、实际Comfy节点/模型安装；未进行付费或真实生成。
- 真实断电/进程重启恢复、提交响应丢失、远端取消失败等异常。
- 原生confirm弹窗出现时浏览器DOM/截图受阻；用官方对话框接口处理后可继续，但弹窗视觉本身不判通过。
- 无可用console/pageerror监听能力，未注入事件收集，不能声称控制台完全无错误。
- 自定义方案保存、字段映射和模型替换的全部有效/无效组合，目前只有入口GUI和静态审查，不是整套端到端通过。
- 普通单次聊天实际执行、子助手允许/重试、自动续办需要人工处理/预算耗尽/人工确认完成、独立后台Job关联执行、混合任务完整执行及Writer/Novel整链成稿没有全部动态验收。相应入口/逻辑已纳入静态矩阵，不能以其他成功路径替代。
- 配方暂停时首项完成后的后续派发阻断未验；取消后的未开始项目文案只有DOM提示，局部视觉待补。

## 6. 建议整改顺序

1. **先修可信度**：失活LoRA依赖、方案实际保存、时长/审核同源、审批状态守卫、字段可编辑性、对比度。
2. **再修用户路径**：方案管理/配置回跳、最少输入、可视化审核、按状态主操作、准确下一步与错误清理。
3. **最后收口结果体验**：播放/下载、原生任务与章节回链、状态筛选、移动布局、全量通俗文案。
4. 补齐缺失验收场景后重新跑，不把单测数量或一次成功生成当作全功能可用证据；审核通过前不重新发布。
